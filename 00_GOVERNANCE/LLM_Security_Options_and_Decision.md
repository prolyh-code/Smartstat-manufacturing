# LLM Security Options and Decision

- 처리 일시: 2026-09-12
- 범위: LLM_extention 설계의 데이터 기밀성 문제와 구현 전 제약 조건 정리
- 상태: 검토용 초안, Ian 결정 대기

## 1. 문제 정의

기존 PRISM Add-on의 핵심 설계 원칙은 "런타임에 AI/LLM이 없다"는 것이다. 이 원칙은 단지 UX 편의성 때문에 제정된 것이 아니라, 제조 현장 데이터의 기밀성을 보장하기 위한 구조적 장치로 이해하는 것이 타당하다.

LLM 확장 기획에서는 데이터가 다음 정보들을 포함할 수 있다.

- 설비명 / 라인명 / 모델명
- 품질 불량률
- 생산량 및 불량 수치
- 공정 조건
- 작업자/교대/시점
- 고객·영업·품질 관련 민감 정보

이러한 데이터가 외부 LLM Provider로 전송되면 데이터 통제권과 보안 책임이 외부로 넘어간다.

## 2. 옵션 비교

### 옵션 A: 외부 LLM API 직접 사용

장점:
- 구현 속도가 빠름
- Agent 기능을 빠르게 검증 가능
- 데이터/초기 프로토타입 실험이 용이

단점:
- 제조 데이터 유출 위험
- 회사 정보처리 규정 충돌 가능
- 민감 정보 노출에 대한 책임이 불명확
- 현장 데이터 통제권 상실

결론:
- 본 프로젝트의 기본 원칙과 충돌
- 초기 MVP로는 부적절

### 옵션 B: 온프레미스 또는 VPC 격리형 LLM

장점:
- 데이터가 사내 네트워크 내에서 유지됨
- 외부 전송 최소화
- 규정 준수 가능성 높음
- LLM Provider 교체 대비 구조적 유연성 확보

단점:
- 운영 비용 증가
- GPU/서버/모델 운영 부담
- 모델 성능과 속도 제약 가능

결론:
- 가장 현실적이고 안전한 경로
- 구현 범위와 비용을 감안해 사내 인프라 수준을 확인해야 함

### 옵션 C: 데이터 마스킹/익명화 후 외부 호출

장점:
- 외부 실험은 가능
- 데이터 유출 위험을 일부 줄임
- 프로토타입 검증은 가능

단점:
- 마스킹 실패 시 민감 정보 노출 가능
- 제조 맥락을 유지하는 데 어려움
- 실제 현장 판단을 위한 의미 손실 가능

결론:
- 실험용/비민감 데이터 검증용으로는 유용하지만, 운영용 솔루션으로는 보완이 필요함

## 3. 권장 결론

권장 방향은 옵션 B를 기본으로 하고, 옵션 C를 보조적으로 사용하는 구조이다.

즉,

1. 민감 정보는 LLM context에서 분리
2. 설비명, 라인명, 제품명, 작업자 정보를 pseudonymized identifier로 변환
3. 사내 온프레미스 혹은 VPC 내 배포형 모델을 우선 활용
4. 외부 LLM은 비민감 샘플 데이터 또는 시뮬레이션 데이터에만 제한

## 4. 최소 설계 규칙

- Raw data와 LLM context는 분리한다.
- 민감 필드는 사전 마스킹 후 전달한다.
- 외부 API 사용 여부는 제품 보안 정책에 의해 승인되어야 한다.
- 사용자가 데이터 업로드를 선택할 때, "민감 데이터 포함 여부"를 명시적으로 확인한다.
- 현장 데이터는 저장소/로그/모델 추론 로그에 남기지 않는 정책을 둔다.

## 5. 다음 액션

1. Ian에게 외부 LLM 허용 여부를 확인한다.
2. 허용 불가 시, 온프레미스 또는 VPC 내부 LLM 구조를 기본 설계로 확정한다.
3. 허용 가능 시, 데이터 분류 기준(공개/내부/민감)을 정의한다.
4. Agent의 Knowledge Base와 Company Knowledge의 민감 필드를 분리하는 방안을 문서화한다.

## 6. 요약

보안 문제는 LLM 확장 설계에서 가장 우선순위가 높은 제약 사항이다. 기존 PRISM의 결정론적 비-AI 설계가 의미를 가지는 이유는 바로 이 문제를 차단하기 위한 것이며, LLM을 도입하더라도 이 원칙을 무시하면 제품의 신뢰성을 훼손할 수 있다.

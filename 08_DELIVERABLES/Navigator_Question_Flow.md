# Analysis Navigator — 스무고개 방식 질문 흐름

> **[2026-09-10 v2 재설계 — DEC-011]** Ian이 v1(2026-09-10 초안)의 두 가지 문제를 지적했습니다: (1) 데이터에서 자동으로 파악한 내용을 질문 없이 그냥 넘겨버리면 안 되며, "이 내용으로 분석할까요?"라고 반드시 확인해야 한다. (2) "어떤 분석을 원하시나요?"의 선택지가 여전히 기술적(원인분석/핵심요인분석 등 통계 카테고리 이름)이라 통계 지식이 없는 사람에게는 부담스럽다 — 질문은 일상적인 말투로 하고, 어떤 분석을 할지는 **앱이 답변을 종합해 판단**해야 한다. 마치 "스무고개"처럼, 쉬운 질문을 순서대로 던져 점점 좁혀가는 방식으로 다시 설계했습니다.

## 1. 설계 원칙 (v2)

1. **스무고개 방식.** 사용자가 통계 카테고리를 메뉴에서 직접 고르지 않습니다. 쉬운 상황 질문을 순서대로 던지고, 답변이 쌓일수록 후보가 좁혀지며, 마지막에 어떤 분석(패키지)을 실행할지는 **항상 앱이 결정**합니다.
2. **통계 용어·패키지 이름을 사용자에게 절대 보이지 않습니다.** "원인분석", "핵심요인분석", "MSA", "결과검증" 같은 이름은 이 문서와 개발자(Claude Code)를 위한 내부 라우팅 표에서만 쓰고, 사용자가 보는 화면에는 등장하지 않습니다.
3. **자동으로 파악한 내용도 반드시 확인질문으로 되묻습니다 — 침묵 스킵 금지.** 데이터에서 무언가를 자동으로 알아냈다면, 그 내용을 **기본 선택지로 미리 표시한 가벼운 확인 질문**으로 바꿔 보여줍니다("이렇게 이해했는데 맞나요? — 맞아요(추천) / 아니에요"). 사용자는 대부분 한 번 누르기만 하면 되지만, 앱이 잘못 짚었을 때 바로 고칠 수 있습니다. 이는 AI가 없는 환경에서 자동판별 오류를 사용자가 직접 잡아낼 수 있는 유일한 안전장치이므로 생략하지 않습니다.
4. **질문 하나당 선택지는 2~4개, 쉬운 일상어로.** 통계 용어 없이 "무엇을 했는지", "무엇이 궁금한지"를 상황 중심으로 묻습니다.

## 2. 상황 파악 질문 트리 (사용자에게 보여지는 화면)

```
Q1. "요즘 상황에 가장 가까운 것을 골라주세요."
    A. 최근에 뭔가를 바꾸거나 조치를 했다
    B. 딱히 바꾼 건 없는데, 문제가 있다
    C. 특별한 문제는 없지만, 그냥 지금 상태가 괜찮은지 확인하고 싶다
    D. 잘 모르겠다 — 데이터부터 보여줬으면 좋겠다

[Q1-A: 조치를 했다]
Q2. "그 조치에 대해 지금 알고 싶은 건 어느 쪽에 가깝나요?"
    A. 그 조치가 효과가 있었는지 아직 확인을 못 했다 — 지금 확인하고 싶다      → (내부) ResultVerification
    B. 효과가 있었던 건 이미 확인했고, 그게 지금도 잘 유지되고 있는지 보고 싶다  → (내부) Maintenance

[Q1-B: 문제가 있다]
Q3. "그 문제의 원인으로 짐작 가는 게 있나요?"
    A. 네, 짐작 가는 게 있다
    B. 아니요, 전혀 감이 안 잡힌다 — 관련될 만한 조건들을 폭넓게 봐야 한다

  [Q3-A: 짐작 가는 원인이 있다]
  Q4. "그 원인 후보들을 어떻게 확인하고 싶으세요?"
      A. 후보를 하나씩 짚어서, 진짜 그것 때문인지 확인하고 싶다         → (내부) RootCause
      B. 여러 조건을 한꺼번에 놓고, 그중 뭐가 제일 크게 작용하는지 비교하고 싶다  → (내부) KeyFactor

  [Q3-B: 감이 안 잡힌다] → (내부) KeyFactor (폭넓게 비교/탐색)

[Q1-C: 문제는 없지만 확인만]
Q5. "확인하고 싶은 게 어느 쪽에 더 가까우세요?"
    A. 우리가 쓰는 측정 도구(저울, 게이지 등)가 정확한지 궁금하다     → (내부) MSA
    B. 요즘 나오는 결과/수치가 평소와 다른지 궁금하다               → (내부) ProactiveComparison

[Q1-D: 잘 모르겠다] → §5 폴백 처리
```

각 질문은 2~4개 선택지뿐이며, 어느 질문에도 통계 용어가 등장하지 않습니다. 최대 3번의 클릭(Q1→Q2 또는 Q1→Q3→Q4)으로 분석 방향이 정해집니다.

## 3. 데이터 확인 질문 (자동판별 → 항상 "맞나요?" 확인질문으로 전환)

상황 트리로 어떤 분석인지 정해지고 나면, 그 분석에 필요한 세부사항을 데이터에서 자동으로 파악합니다. **자동으로 파악했다고 그냥 넘어가지 않고, 아래처럼 기본값이 미리 선택된 확인 질문을 반드시 보여줍니다.**

| 확인 항목 | 데이터에서 단서를 찾았을 때(확인질문, 기본값 표시) | 단서를 못 찾았을 때(일반 질문, 기본값 없음) | 내부적으로 쓰이는 모듈 |
|---|---|---|---|
| 대응 여부 | "같은 대상(부품·설비 등)을 조치 전/후로 측정하신 것 같아요. 맞나요?" [맞아요(추천) / 아니에요, 서로 다른 대상이에요] | "이 두 그룹, 같은 대상을 전후로 측정하신 건가요, 아니면 서로 다른 대상을 비교하시는 건가요?" [같은 대상 / 다른 대상] | M-TESTSELECT-COMPARE(paired 분기) |
| 측정 순서 | "데이터가 시간 순서대로 정리되어 있는 것 같아요. 맞나요?" [맞아요(추천) / 아니에요, 순서가 섞여 있어요] | "이 데이터를 측정한 순서(시간순)를 알고 계세요?" [알아요 / 몰라요] | M-ASSUMP-AUTOCORR, M-VIZ-CONTROLCHART |
| 원인 후보의 종류 | "'{열이름}'은 A라인/B라인처럼 몇 가지로 나뉘는 종류 같아요. 맞나요?" [맞아요(추천) / 아니에요, 온도처럼 계속 바뀌는 숫자예요] | "'{열이름}'은 몇 가지로 나뉘는 종류인가요, 아니면 계속 바뀌는 숫자인가요?" [몇 가지 종류 / 계속 바뀌는 숫자] | M-DATA-PROFILE(변수타입) |

이 확인질문들은 상황 트리(§2)가 끝난 뒤, 해당 분석에 실제로 필요한 항목만 골라 순서대로 보여줍니다(모든 분석에 모든 질문이 나오는 것은 아닙니다 — §4 참조).

## 4. 라우팅 결정표 (내부용 — 개발자·Claude Code 참조, 사용자에게는 노출 안 됨)

```
Q1-A→Q2-A(방금 한 조치 확인) → 대응여부 확인 → 측정순서 확인 → RECIPE ResultVerification
Q1-A→Q2-B(예전 조치 유지 확인) → 측정순서 확인(필수) → RECIPE Maintenance
Q1-B→Q3-A→Q4-A(원인 하나씩) → 원인후보 종류 확인 → RECIPE RootCause
Q1-B→Q3-A→Q4-B(원인 한꺼번에 비교) → RECIPE KeyFactor
Q1-B→Q3-B(감이 안 잡힘) → RECIPE KeyFactor(탐색적)
Q1-C→Q5-A(측정도구 확인) → RECIPE MSA
Q1-C→Q5-B(요즘 결과 확인) → 대응여부 확인 → 측정순서 확인 → RECIPE ProactiveComparison
Q1-D(잘 모르겠음) → §5 폴백
```

## 5. "잘 모르겠음" 폴백 처리

Q1에서 "잘 모르겠다"를 고르면, AI로 추측하지 않고 데이터부터 보여줍니다: M-DATA-PROFILE(데이터 구조 파악, 사용자에게는 노출 안 됨) → M-VIZ-HISTBOX(그래프 먼저 제시) → "이 데이터를 보니 아래 상황들이 가능해 보입니다"라며 Q1의 관련 선택지만 추려서(전부가 아니라) 쉬운 말로 다시 제시합니다. 이것도 어디까지나 추천이며, 최종 선택은 항상 사용자가 합니다.

**[2026-09-10 추가, §8 드라이런에서 발견]** 데이터가 너무 빈약해(예: 비교할 그룹이 하나뿐이고 시간정보도 없는 단일 열) 위 방식으로도 추천할 선택지를 좁히지 못하는 경우, "이 데이터만으로는 어떤 분석이 맞을지 추천하기 어렵습니다. 비교할 대상(예: 전후 데이터, 다른 그룹)이나 측정 시점 정보가 더 있으면 다시 시도해 주세요"라고 솔직하게 안내하고 억지로 추천하지 않습니다 — 무리한 추천이 오히려 잘못된 분석으로 이어질 위험이 더 크기 때문입니다.

## 6. 왜 이렇게 바꿨는가

v1은 "무엇을 확인하고 싶으신가요?"라는 질문 하나에 6~7개 선택지를 한꺼번에 보여주는 메뉴식이었고, 선택지 문구도 은연중에 통계적 분류(원인 vs 핵심요인 구분 등)를 사용자가 스스로 판단하게 했습니다. v2는 그 판단을 여러 개의 아주 쉬운 질문으로 잘게 쪼개 앱이 대신 판단하도록 바꿨고("스무고개"), 데이터 자동판별 결과도 침묵 처리하지 않고 매번 확인받도록 했습니다. 이 변경은 DEC-011로 기록했습니다.

## 8. 검증: 시나리오 드라이런 (2026-09-10)

Ian이 직접 클릭해볼 수 있는 프로토타입이 아직 없으므로, Claude가 대표 시나리오 9건(Case Library 기반 6건 + 경계사례 3건)을 손으로 짚어가며 이 트리를 미리 걸어보고(dry-run) 결과를 점검했습니다. 통계 전문가 독립검증이 아닌 self-review이며(GAP-07과 동일한 한계), Ian이 실제로 한 번 더 훑어보고 확정하는 것을 권장합니다.

| # | 시나리오 | 경로 | 도착 레시피 | 결과 |
|---|---|---|---|---|
| S1 | 냉매충전 툴을 바꾼 뒤, 서로 다른 부품들의 전/후 토크값을 비교하고 싶다(CASE-001) | Q1-A → Q2-A → 대응여부(단서없음→확인질문→"다른 대상") → 측정순서(단서없음→"몰라요") | ResultVerification | 정상 |
| S2 | 3개월 전 파라미터를 조정했고, 이후 매주 데이터를 계속 쌓고 있다. 지금도 괜찮은지 궁금하다 | Q1-A → Q2-B → 측정순서(타임스탬프 열 있음→확인질문 기본값"맞아요") | Maintenance | 정상 — 자동감지도 확인질문으로 전환되는지 검증됨 |
| S3 | 불량률 상승, A라인/B라인 중 어디가 문제인지 의심됨 | Q1-B → Q3-A → Q4-A → 원인후보 종류(열값이 문자열→확인질문 기본값"몇 가지 종류") | RootCause | 정상 |
| S4 | 온도·압력·속도 중 뭐가 불량에 가장 큰 영향을 주는지, 특별히 의심되는 건 없음 | Q1-B → Q3-B | KeyFactor(탐색적) | 정상 |
| S5 | 우리가 쓰는 저울이 정확한지 확인하고 싶다 | Q1-C → Q5-A | MSA | 정상 |
| S6 | 최근 로트가 평소와 다른지 그냥 점검, 특별한 문제는 없음 | Q1-C → Q5-B | ProactiveComparison | 정상 |
| S7 | 3개 시점(전/중간/후) 데이터로 개선 여부를 보고 싶다 | Q1-A → Q2-A → (M-DATA-PROFILE이 3그룹 자동감지, 별도 질문 없이 내부 분기) | ResultVerification(3그룹 분기: Welch's ANOVA/Kruskal-Wallis) | 정상 — 그룹 수는 사용자에게 묻지 않고 자동 처리되는 것이 맞는지 확인, 문제없음 |
| S8 | 조치를 예전에 했지만 효과를 확인한 적이 한 번도 없다 | Q1-A → Q2(?) | — | **문제 발견**: v2 초안의 Q2 문구("방금 한 조치"/"예전 조치 유지")가 "예전에 했지만 아직 확인 안 함"을 어디에도 명확히 담지 못함 → **Q2 문구를 "확인 여부" 기준으로 수정**(위 §2 반영 완료: A="아직 확인을 못 했다", B="이미 확인했고 유지되는지") |
| S9 | 데이터가 딱 한 그룹, 시간정보도 없는 단일 열뿐 | Q1-D(잘 모르겠음) → 폴백 | — | **문제 발견**: 기존 폴백 로직이 "그래도 뭔가 추천"하는 것을 전제로 설계되어 있었음 → **"추천할 수 없다"는 솔직한 안내 분기를 §5에 추가**(위 반영 완료) |

**추가로 점검했으나 문제 없음으로 확인된 것들**: (1) MSA·Maintenance 패키지의 자체 내부 경고(설계미달·데이터부족)는 §3 확인질문과 별도로 패키지 내부(M-ASSUMP-DESIGNADEQUACY)에서 처리되므로 중복 질문이 생기지 않음. (2) KeyFactor는 연속형 변수만 입력받는 패키지라 §3의 "원인후보 종류" 확인질문이 필요 없음 — 라우팅 결정표(§4)에도 해당 질문이 없어 정합함.

**발견된 문제 2건은 이 문서에 즉시 반영했습니다.** 이 드라이런은 Claude 혼자 수행한 self-review이므로, Ian이 실제 현장 시나리오 1~2건으로 다시 한번 확인해 주시는 것을 권장합니다.

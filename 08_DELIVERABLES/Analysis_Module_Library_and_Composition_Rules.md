# 분석 모듈 라이브러리 및 조합 규칙

> **왜 이 문서가 필요한가**: 이전에 작성한 패키지 명세 5건(결과검증·원인분석·핵심요인분석·MSA·유지관리)은 각각 독립된 프로즈 문서로, 정규성검정·효과크기·해석조립 같은 동일한 로직을 매번 새로 설명했습니다. Ian의 지적대로, 실제 통계분석은 하나의 기법이 아니라 여러 기법이 연속으로 이어지는 것이 일반적이며, 이 "이어짐"을 매번 처음부터 글로 쓰는 방식은 지속가능하지 않습니다. 이 문서는 그 5개 패키지에서 반복 사용된 하위요소를 **재사용 가능한 원자 모듈(Atomic Module)**로 추출해 카탈로그화하고, 모듈을 연결하는 **조합 규칙(Composition Rule)**을 정의합니다. 목표는 앞으로 새로운 분석 목적이 생겼을 때 Claude(연구 단계)와 Claude Code(개발 단계) 모두가 처음부터 글을 쓰는 대신 **카탈로그에서 모듈을 골라 연결(조합)**하는 방식으로 작업할 수 있게 하는 것입니다. **런타임(배포된 Add-on)에서든 이 조합 작업 자체든 AI를 사용하지 않습니다** — 모듈 선택과 연결은 결정론적 규칙(아래 §4)을 따릅니다.

## 1. 설계 근거

실배포 분석 플랫폼(KNIME·Alteryx)은 재사용 가능한 개별 노드를 시각적으로 연결(체이닝)해 전체 워크플로우를 구성하는 아키텍처를 이미 상용화하고 있으며, 이 조합 과정 자체에는 AI가 필요하지 않습니다(SRC-138, CLM-37). 독립적으로 개발·최적화된 원자적 블록을 필요에 따라 재조합하는 조립형(composable) 아키텍처는 민첩성(빠른 변경)·속도(신속한 조립)·확장성(점진적 확장)의 이점을 제공한다고 보고됩니다(SRC-139, CLM-38). 본 카탈로그는 이 원리를 제조 통계분석 패키지 설계에 적용한 것입니다 — 다만 KNIME/Alteryx는 범용 데이터 플랫폼이고 본 카탈로그는 제조 통계분석에 특화되어 있다는 점, 그리고 두 벤더 자료 모두 마케팅 성격이 있어 독립검증은 아니라는 점(CLM-37 limitation)을 유의해야 합니다.

## 2. 모듈 카탈로그

각 모듈은 **입력 → 처리(결정로직) → 출력** 구조를 가지며, 여러 패키지에서 동일하게 재사용됩니다. "사용 패키지" 열이 2개 이상이면 실제로 재사용이 입증된 모듈이고, 1개면 현재는 특정 패키지 전용이지만 향후 재사용 후보입니다.

### 2.8 신뢰성(Reliability) 모듈 [2026-09-10 신규, G10/DEC-012]

**[2026-09-10 추가, GAP-09 전수화 작업 중 도출] M-INTERP-ASSEMBLE의 조립 알고리즘 일반 규칙(2가지 슬롯 유형)**: 해석 슬롯을 조립할 때는 슬롯의 성격에 따라 두 가지 방식 중 하나를 택해야 하며, 이를 혼동하면(예: 원래 동시발생 가능한 것을 배타적 단일분류로 잘못 설계) 실제로 발생 가능한 조합을 놓치는 템플릿 누락이 생깁니다(Maintenance 패키지 Rule1~4가 실사례였음, RUN-019 드라이런에서 발견).

1. **배타적 핵심분류(exclusive core classification)**: 결과가 논리적으로 동시에 두 가지일 수 없는 슬롯(예: 유의/비유의는 하나만 참일 수 있음, 효과크기등급도 하나만 해당). 이런 슬롯은 "차원의 곱 - 논리적으로 불가능한 조합"만큼의 템플릿이 필요하며, 표 형태(분류규칙→템플릿)로 전수 설계합니다. ResultVerification/ProactiveComparison/RootCause의 유의여부×효과크기등급이 이 방식.
2. **접두 경고(prefix warning)**: 핵심분류와 논리적으로 독립적이며, 있음/없음 중 하나이고 핵심분류 결과와 무관하게 항상 최우선으로 붙는 슬롯(예: 자기상관경고·다중비교경고·데이터부족경고·설계미달경고). 핵심분류 템플릿 1세트 + 경고문구 1개만 있으면 "경고 있음×핵심분류 N가지" 전부를 커버하므로, 경고별로 핵심분류 조합을 다시 쓸 필요가 없습니다.
3. **목록형 조립(composable list)**: 같은 종류의 이상신호가 여러 개 동시에 발생할 수 있는 슬롯(예: Western Electric Rules 4종은 논리적으로 동시에 여러 개가 위반될 수 있음). 이런 경우 "각 항목별 개별 템플릿 + 동시발생 시 안내문 1줄"만 준비하면, 항목 수를 n개라 할 때 2ⁿ가지 조합을 전부 커버할 수 있어 표 형태보다 훨씬 적은 템플릿으로 전수 커버가 가능합니다. Maintenance 패키지가 2026-09-10에 이 방식으로 재설계됨(기존에는 배타적 단일분류로 잘못 설계되어 있었음 — 오류 사례로 기록).
슬롯을 설계할 때 이 3가지 중 어디에 해당하는지 먼저 판단하는 것이 새 패키지의 §4 작성 순서에 추가됩니다(§5 절차 갱신 참조).

## 3. 조합 표기법 (Composition Notation)

패키지는 다음 형식의 "레시피"로 표현합니다. 이 표기법은 그대로 Claude Code의 선언적 설정(YAML/JSON 등)으로 옮길 수 있도록 의도적으로 단순하게 설계했습니다.

```text
RECIPE <패키지ID>
TRIGGER: <사용자가 이 패키지를 트리거하는 조건>
INPUT: <필수/선택 입력 필드>
FLOW:
  <모듈ID>
  → <모듈ID>
  → BRANCH(<분기조건>)
      <조건A> → <모듈ID 또는 skip>
      <조건B> → <모듈ID 또는 skip>
  → <모듈ID>
  → M-INTERP-ASSEMBLE
  → M-SAFETY-FALLBACK   ※ 모든 레시피의 마지막 단계는 항상 이것
```

규칙: (1) 모든 레시피는 M-DATA-PROFILE로 시작한다. (2) 모든 레시피는 M-SAFETY-FALLBACK으로 끝난다(예외 없음). (3) 경고성 모듈(M-ASSUMP-AUTOCORR 등)의 출력은 M-INTERP-ASSEMBLE 단계에서 다른 해석 템플릿보다 항상 먼저 표시되도록 우선순위 태그를 붙인다. (4) 카탈로그에 없는 기능이 필요하면 §5의 절차를 따라 신규 모듈을 추가한 뒤에 레시피를 작성한다 — 레시피 안에 카탈로그 밖의 즉석 로직을 넣지 않는다.

**확장 — 패키지 체이닝(NEXT)**: 레시피는 선택적으로 마지막 줄에 `NEXT: <조건> → <다른 레시피ID>(추천만)`을 추가할 수 있다. 이는 한 패키지의 결과가 다른 패키지 실행을 자동으로 추천하는 것으로, **자동 실행은 아니며 항상 사용자 확인을 거친다**(연쇄적으로 자동 실행하면 AI 없는 환경에서 사용자가 무슨 일이 일어났는지 통제·추적하기 어려워지므로 금지). 첫 적용 사례는 예방적 비교 패키지(DELIV-PKG-SPEC-006) §3 참조.

## 5. 신규 패키지를 "조합"으로 만드는 절차

향후 새로운 현장 목적(예: 공정능력 분석, 수율 분석 등 — PRISM 범위 밖인 것에 한함)이 생겼을 때, Claude(연구 단계) 또는 Claude Code(개발 단계)는 다음 순서를 따릅니다:

1. **목적·트리거 정의**: 어떤 현장 목적이고, 어떤 입력 데이터가 있을 때 트리거되는가.
2. **표준 골격 적용**: M-DATA-PROFILE로 시작, M-SAFETY-FALLBACK으로 종료하는 기본 골격을 먼저 놓는다.
3. **필요 기능을 카탈로그에서 매칭**: "시각화가 필요한가? 가정확인이 필요한가? 어떤 검정/통계기법이 필요한가?"를 §2의 카탈로그와 대조해 기존 모듈로 채울 수 있는 부분을 먼저 채운다.
4. **빈 구멍(카탈로그에 없는 기능) 식별**: 기존 모듈로 채울 수 없는 단계가 있으면, 그 단계만 신규 모듈로 정의한다(모듈 ID 부여, 입력/출력/결정로직 문서화 — §2와 동일한 형식으로 카탈로그에 추가). **패키지 전체를 새로 쓰지 않고, 빠진 조각만 새로 만든다.**
5. **경고 우선순위 배치**: 새 패키지에 경고성 모듈이 있으면 M-INTERP-ASSEMBLE 단계에서 판정 템플릿보다 먼저 표시되도록 명시한다.
5-1. **[2026-09-10 추가] 해석 슬롯 유형 판정(GAP-09 대응)**: §4 템플릿을 쓰기 전에 각 슬롯이 (a) 배타적 핵심분류, (b) 접두 경고, (c) 목록형 조립 중 어디에 해당하는지 먼저 판정한다(§2.7의 3가지 유형 설명 참조). 이 판정을 건너뛰고 바로 표를 쓰면, 실제로는 동시발생 가능한 항목을 배타적 분류로 잘못 설계해 조합을 놓치는 위험이 있다(Maintenance 패키지의 Rule1~4가 실제로 이 실수를 저질렀던 사례 — RUN-019에서 발견·수정).

네. 이번 **Step 20은 지금까지 설계한 제조 통계분석 Agent의 "판단 체계"를 완성하는 단계**라고 보는 것이 맞습니다.

Step 19까지는 Agent가 **분석을 실행할 수 있는 구조**를 만들었습니다.

이제는 그 결과를 단순한 숫자가 아니라,

> **통계 결과 → 발견(Finding) → 증거(Evidence) → 가설(Hypothesis) → 교란요인(Confounder) → 다음 분석(Next Best Analysis) → 제조 판단(Engineering Decision)**

으로 연결해야 합니다.

이 부분을 성급하게 LLM에게 맡기면 Agent가 결국 "그럴듯한 설명을 하는 챗봇"이 됩니다. 따라서 이번 단계에서는 **LLM의 추론과 Rule 기반 판단을 명확하게 분리**하겠습니다.

---

# Step 20. Finding / Evidence / Hypothesis / Next Best Analysis Engine

## 20-1. Step 20의 핵심 목표

최종적으로 Agent가 다음과 같은 질문에 답할 수 있어야 합니다.

> "A라인과 B라인의 토크 차이가 있는가?"

단순한 답:

> p-value = 0.0016입니다.

가 아니라,

> **통계적으로 차이가 있는가?**  
> → 그렇다.
> 
> **얼마나 차이가 나는가?**  
> → 평균 2.9 N·m.
> 
> **제조적으로 중요한 차이인가?**  
> → 제조 허용 기준과 비교해야 한다.
> 
> **Line 자체가 원인인가?**  
> → 아직 알 수 없다.
> 
> **다른 요인이 섞여 있는가?**  
> → Model 구성 차이가 의심된다.
> 
> **다음에는 무엇을 해야 하는가?**  
> → 동일 Model 기준 A/B 비교가 적절하다.

까지 연결하는 것입니다.

---

# 20-2. 가장 중요한 개념적 분리

이번 단계에서 다음 5개를 반드시 분리하겠습니다.

|개념|의미|
|---|---|
|**Result**|통계 도구가 계산한 숫자|
|**Finding**|데이터에서 관찰된 사실|
|**Evidence**|그 Finding을 뒷받침하는 근거|
|**Hypothesis**|아직 검증되지 않은 원인/설명 후보|
|**Decision**|제조적으로 취할 판단/행동|

예를 들어:

### Result

```
Welch t-test
p = 0.0016
mean difference = -2.9 N·m
95% CI = [-4.69, -1.11]
```

### Finding

> A라인의 평균 Torque가 B라인보다 낮다.

### Evidence

> Welch t-test에서 통계적으로 유의한 차이가 확인됨.

### Hypothesis

> Line별 Torque 차이가 공정 조건 또는 Model 구성 차이와 관련되어 있을 가능성이 있다.

### Decision

> 동일 Model 조건에서 A/B 비교를 추가 수행한다.

이 구조를 반드시 시스템 데이터 모델에 반영합니다.

---

# 20-3. Result와 Finding을 분리해야 하는 이유

이것은 아주 중요한 설계입니다.

예를 들어 Tool Result가:

```
{
  "mean_a": 163.2,
  "mean_b": 166.1,
  "p_value": 0.0016
}
```

라고 하겠습니다.

이 숫자만으로 LLM이:

> B라인이 문제다.

라고 말하면 안 됩니다.

왜냐하면 **통계적 차이와 원인은 다른 개념**이기 때문입니다.

따라서:

```
ToolResult
    ↓
Finding Generator
    ↓
Finding
```

이라는 별도 단계를 둡니다.

---

# 20-4. Finding의 유형

Finding을 하나의 문자열로만 저장하지 않는 것을 권장합니다.

제조 통계 Agent에서는 최소 다음 유형이 필요합니다.

```
FindingType

OBSERVED_PATTERN
GROUP_DIFFERENCE
MEAN_SHIFT
VARIATION_DIFFERENCE
DISTRIBUTION_DIFFERENCE
TREND
CORRELATION
REGRESSION_EFFECT
OUTLIER_PATTERN
DEFECT_DIFFERENCE
SPECIFICATION_RISK
CAPABILITY_RISK
PROCESS_CHANGE_EFFECT
CONFOUNDING_PATTERN
```

예를 들어:

```
{
  "finding_id": "F-001",
  "type": "GROUP_DIFFERENCE",
  "statement": "Line A has a lower mean Torque than Line B.",
  "direction": "A_LOWER_THAN_B"
}
```

이렇게 저장합니다.

---

# 20-5. Finding에는 반드시 Source가 있어야 한다

모든 Finding은 어디서 나왔는지 추적 가능해야 합니다.

```
{
  "finding_id": "F-001",
  "source_analysis": [
    "TC-0006"
  ],
  "source_dataset": "DS-UC03-001"
}
```

즉:

> **모든 Finding은 근거가 없는 독립적인 LLM 문장이 될 수 없습니다.**

이것은 향후 Agent의 **Traceability**를 확보하는 핵심입니다.

---

# 20-6. Evidence의 개념

Evidence는 단순히 "p-value가 작다"가 아닙니다.

Evidence는:

> **특정 Finding이 어느 정도의 신뢰성을 가지고 있는지를 판단하기 위한 구조화된 근거**

입니다.

우리가 앞서 정의한 증거 수준을 그대로 사용합니다.

```
E0 → Evidence 없음
E1 → 관찰된 패턴
E2 → 통계적 차이/연관성
E3 → 반복 검증된 후보
E4 → 실험/개선 검증
```

이것을 이번 단계에서 실제 판단 체계로 만듭니다.

---

# 20-7. E0 — Evidence 없음

예:

> M4에서 토크 불량이 증가한 것 같다.

데이터를 아직 분석하지 않았다면:

```
{
  "level": "E0",
  "status": "UNVERIFIED"
}
```

이 상태에서는 Agent가:

> "M4가 원인입니다."

라고 말할 수 없습니다.

허용되는 표현:

> "M4가 관련 요인일 가능성이 있어 추가 확인이 필요합니다."

---

# 20-8. E1 — Observed Pattern

실제 데이터에서 패턴이 관찰된 경우입니다.

예:

```
M4 defect rate = 2.92%
Other machines = 0.8~1.2%
```

그러면:

```
{
  "level": "E1",
  "type": "OBSERVED_PATTERN"
}
```

입니다.

허용:

> "M4에서 상대적으로 높은 불량률이 관찰되었습니다."

아직:

> "M4 때문에 불량이 증가했습니다."

는 허용하지 않습니다.

---

# 20-9. E2 — Statistical Evidence

통계적 검정을 통해 차이 또는 관계가 확인된 경우입니다.

예:

```
Chi-square
p < 0.001
```

또는:

```
Welch t-test
p = 0.0016
```

이면:

```
{
  "level": "E2",
  "type": "STATISTICAL_DIFFERENCE"
}
```

가 됩니다.

허용:

> "M4와 다른 설비 간 불량률 차이가 통계적으로 유의합니다."

하지만 여전히:

> "M4가 불량의 원인이다."

는 허용하지 않습니다.

---

# 20-10. E3 — Candidate Strengthened

E3가 이번 Agent에서 상당히 중요합니다.

하나의 분석 결과만으로 결론을 내리는 것이 아니라 **다른 조건에서도 동일한 패턴이 반복되는지**를 확인합니다.

예를 들어:

```
전체 데이터
M4 높음

        ↓

Model C
M4 높음

        ↓

Shift별
M4 높음

        ↓

Time별
반복적으로 높음
```

이렇게 되면:

```
E2
 ↓
E3
```

으로 Evidence Strength가 올라갈 수 있습니다.

그러나 여전히 **관찰 데이터라면 인과관계가 확인된 것은 아닙니다.**

---

# 20-11. E4 — Improvement / Experimental Evidence

E4는 가장 강한 수준입니다.

예:

```
원인 후보
   ↓
공정 조건 변경
   ↓
변경 전/후 비교
   ↓
반복 검증
   ↓
불량률 개선
```

또는:

```
DOE
 ↓
Factor effect
 ↓
interaction
 ↓
optimal condition
 ↓
confirmation run
```

이런 경우입니다.

즉:

> **E4는 단순 관찰 분석이 아니라 실제 개선 또는 실험으로 검증된 증거**입니다.

---

# 20-12. Evidence Level은 단순 점수가 아니다

여기서 중요한 점입니다.

다음과 같은 오해를 방지해야 합니다.

```
p-value가 매우 작음
        ↓
E4
```

이렇게 하면 안 됩니다.

Evidence level은:

> **통계적 유의성의 크기가 아니라 검증의 단계**

를 의미합니다.

따라서:

```
p = 0.000001
```

이라도 관찰 연구라면 E2일 수 있습니다.

반대로 적절한 실험과 반복 검증을 수행했다면 E4가 될 수 있습니다.

---

# 20-13. Evidence와 Causal Strength를 별도로 둔다

이것도 매우 중요합니다.

예:

```
{
  "evidence_level": "E2",
  "causal_strength": "NONE"
}
```

E2라고 해서 causal strength가 높은 것이 아닙니다.

권장 구조:

```
Evidence Level
E0~E4

+

Causal Strength
NONE
ASSOCIATION
CANDIDATE
SUPPORTED
EXPERIMENTALLY_SUPPORTED
```

이렇게 분리합니다.

---

# 20-14. Hypothesis의 역할

Finding과 Hypothesis를 섞으면 Agent가 매우 위험해집니다.

### Finding

> M4의 불량률이 높다.

### Hypothesis

> M4의 설비 조건이 불량 증가에 영향을 줄 가능성이 있다.

즉:

```
Finding = What we observed
Hypothesis = Why it may be happening
```

입니다.

---

# 20-15. Hypothesis 상태

앞서 정의한 상태를 그대로 사용하되 의미를 더 명확히 합니다.

```
UNTESTED
SUPPORTED
STRENGTHENED
WEAKENED
REJECTED
CONFIRMED
```

그러나 여기서 **CONFIRMED는 매우 엄격하게 제한**합니다.

예:

```
Machine M4
p < 0.001
```

만으로:

```
CONFIRMED
```

를 생성하면 안 됩니다.

---

# 20-16. Hypothesis Lifecycle

예를 들어:

```
H-001
"M4가 토크 불량 증가와 관련된다."
```

처음:

```
UNTESTED
```

Machine 분석:

```
M4 defect rate ↑
p < 0.001
```

↓

```
SUPPORTED
```

그런데 Model 구성 차이를 발견:

```
M4 → Model C 생산 집중
```

↓

```
WEAKENED
```

동일 Model 분석 후:

```
M4 effect remains
```

↓

```
STRENGTHENED
```

이후 공정 조건을 변경하고 반복 검증:

```
defect ↓
```

↓

조건에 따라:

```
CONFIRMED
```

까지 갈 수 있습니다.

---

# 20-17. Confounder가 중요한 이유

제조 데이터에서는 이것이 매우 흔합니다.

예:

```
M4
 ↓
Model C 생산 집중
 ↓
Model C 자체가 Torque 불량률 높음
```

그러면:

```
Machine → Defect
```

라는 관계가 사실은:

```
Machine → Model Mix → Defect
```

일 수 있습니다.

따라서 Agent가 단순히:

> M4가 원인이다.

라고 하면 안 됩니다.

---

# 20-18. Confounder 구조

```
{
  "confounder_id": "C-001",
  "factor": "Model",
  "affected_factor": "Machine",
  "risk": "HIGH",
  "reason": "M4에서 Model C 생산 비율이 높음",
  "status": "UNRESOLVED",
  "recommended_analysis": "SAME_MODEL_GROUP_COMPARISON"
}
```

여기서 `affected_factor`의 명칭은 실제 구현에서는 조금 더 명확하게:

```
exposure_factor = Machine
confounder_factor = Model
outcome = Torque defect
```

형태로 바꾸는 것도 권장합니다.

그러면 인과추론 개념과 더 잘 맞습니다.

---

# 20-19. Confounding Risk 계산

MVP에서는 복잡한 causal graph를 바로 구현할 필요는 없습니다.

먼저 Rule 기반으로 시작합니다.

예:

```
Machine별 defect 차이 존재
+
Machine별 Model composition 차이 큼
+
Model별 defect 차이 존재
```

이면:

```
Confounding Risk = HIGH
```

로 판단합니다.

즉:

\[ ConfoundingRisk = Association_{Factor-Outcome} \times Imbalance_{Factor-Confounder} \times Association_{Confounder-Outcome} \]

같은 개념적 구조를 사용할 수 있습니다.

MVP에서는 실제 수학식보다 **명시적인 규칙 기반 판정**을 권장합니다.

---

# 20-20. Next Best Analysis

이제 핵심 기능입니다.

Agent는 분석을 한 번 하고 끝나는 것이 아니라:

> **"현재 상태에서 무엇을 추가로 분석하면 가장 많은 불확실성을 줄일 수 있는가?"**

를 판단해야 합니다.

이것이 **Next Best Analysis(NBA)**입니다.

---

# 20-21. NBA의 기본 입력

NBA Engine은 다음을 봅니다.

```
Problem
+
Current Findings
+
Evidence
+
Hypotheses
+
Confounders
+
Completed Analyses
+
Available Data
```

그리고 후보 분석을 생성합니다.

예:

```
Same Model Comparison
Shift Comparison
Operator Comparison
Machine Comparison
Correlation
Regression
Trend Analysis
```

---

# 20-22. NBA 후보 생성과 선택을 분리

여기에서도 LLM과 Rule을 분리합니다.

### LLM

후보를 생성합니다.

```
Candidate 1
Same Model comparison

Candidate 2
Shift comparison

Candidate 3
Operator comparison

Candidate 4
Regression
```

### Rule Engine

실행 불가능한 것을 제거합니다.

```
Operator data 없음
→ REMOVE

Pair ID 없음
→ paired analysis REMOVE
```

### NBA Scoring Engine

남은 후보를 평가합니다.

---

# 20-23. NBA Score

앞서 정의한 식을 실제 구조로 발전시키겠습니다.

\[ NBA = R \times I \times D \times V \times M \]

### R — Relevance

현재 질문과 얼마나 관련 있는가?

### I — Information Gain

현재 불확실성을 얼마나 줄이는가?

### D — Data Availability

필요한 데이터가 존재하는가?

### V — Statistical Validity

현재 데이터 구조에서 적절하게 수행할 수 있는가?

### M — Manufacturing Impact

결과가 실제 제조 의사결정에 얼마나 중요한가?

---

# 20-24. 예시

현재 상태:

```
Finding:
M4 defect rate high

Evidence:
E2

Confounder:
Model = HIGH

Hypothesis:
M4 may cause defect
```

후보:

|분석|Relevance|Info Gain|Data|Validity|Impact|
|---|---|---|---|---|---|
|동일 Model A/B/M 비교|5|5|5|5|5|
|Shift 비교|3|2|5|5|3|
|Operator 비교|2|2|4|5|2|
|Trend|2|2|5|5|2|

그러면 동일 Model 비교가 가장 높은 NBA가 됩니다.

# 20-25. "추가 분석을 많이 하는 Agent"가 좋은 Agent가 아니다

이것도 반드시 설계에 넣어야 합니다.

Agent가:

```
t-test
↓
ANOVA
↓
correlation
↓
regression
↓
another regression
↓
PCA
↓
...
```

를 계속 수행하면 좋은 Agent가 아닙니다.

**정보가치가 낮아지는 순간 멈춰야 합니다.**

---

# 20-26. Stop Engine

Agent에는 반드시 Stop Engine이 있어야 합니다.

Stop 조건은 최소 5개입니다.

### STOP-01

질문이 충분히 답변됨.

### STOP-02

추가 분석의 정보가치가 낮음.

### STOP-03

데이터가 부족함.

### STOP-04

통계분석으로 더 이상 인과관계를 확인할 수 없음.

### STOP-05

DOE 또는 현장 실험이 필요함.

---

# 20-27. Stop과 "분석 실패"를 구분

이것도 중요합니다.

```
STOP
```

은 실패가 아닙니다.

예:

> 현재 확보된 관찰 데이터로는 Line 간 차이는 확인되었으나 원인까지 확정할 수 없습니다. 추가적인 통계분석보다 동일 Model 조건의 확인 또는 관리된 실험이 필요합니다.

이것은 **정상적인 Agent 종료**입니다.

오히려 이런 판단을 할 수 있어야 좋은 Agent입니다.

---

# 20-28. Statistical Significance vs Manufacturing Significance

이번 단계에서 반드시 시스템화해야 합니다.

예:

```
Mean Difference = 0.2 N·m
p < 0.001
```

통계적으로는 유의할 수 있습니다.

하지만 제조적으로:

```
허용 가능한 공정 편차 = ±2 N·m
```

라면 실제 개선 우선순위는 낮을 수 있습니다.

반대로:

```
Mean Difference = 2.5 N·m
p = 0.08
```

따라서:

```

```

을 별도로 생성합니다.

# 20-40. 최종적으로 사용자에게는 복잡성을 숨긴다

내부는 복잡해도 사용자 화면은 복잡할 필요가 없습니다.

예:

### 분석 결과

**A라인과 B라인의 평균 토크에는 통계적으로 유의한 차이가 있습니다.**

- A라인: 163.2 N·m
- B라인: 166.1 N·m
- 차이: −2.9 N·m
- Welch t-test: p = 0.0016

### 현재 판단

**통계적 차이: 확인**

### 주의사항

**Line 자체의 영향이라고 아직 판단할 수 없습니다.**

Model 구성 차이가 존재할 가능성이 있습니다.

### 다음 분석

**동일 Model 기준으로 A/B라인을 비교하는 것이 적절합니다.**

이 정도면 현장 사용자가 이해할 수 있습니다.

필요한 사용자는:

> "왜 그렇게 판단했나요?"

를 눌러:

```
Evidence E2
↓
Welch t-test
↓
p = 0.0016
↓
Model confounding risk = HIGH
```

까지 내려갈 수 있게 합니다.

즉, 우리가 기존 기획에서 정의했던 **3단계 설명 수준**도 그대로 활용할 수 있습니다.

# 다음 단계: Step 21 — Golden Case 자동 평가 시스템

이제 **반드시 평가 시스템을 만들어야 합니다.**

왜냐하면 지금부터 Agent가 실제로 작동하기 시작하면 다음 문제가 발생하기 때문입니다.

> "LLM이 이번에는 잘했는데, Prompt를 수정했더니 지난번에 잘하던 분석이 망가졌다."

또는:

> "Welch t-test는 정확하지만, Agent가 paired t-test를 잘못 선택한다."

또는:

> "통계 결과는 정확하지만 제조적 원인이라고 과도하게 해석한다."

이런 문제를 사람이 매번 수작업으로 확인하면 개발 속도가 급격히 떨어집니다.

따라서 Step 21에서는 우리가 앞서 설계한 **Golden Case를 실제 자동 Regression Test 시스템으로 발전**시켜야 합니다.

핵심은:

```
Golden Case
    ↓
Agent 실행
    ↓
Tool Calls
    ↓
Statistical Results
    ↓
Finding
    ↓
Evidence
    ↓
Hypothesis
    ↓
Next Analysis
    ↓
Final Answer
    ↓
자동 평가
    ↓
PASS / FAIL
```

그리고 평가를 단순히 "답변이 비슷한가?"로 하지 않고,

**① 통계 정확성 → ② 분석 방법 선택 → ③ 가정 검증 → ④ Finding → ⑤ Evidence Level → ⑥ 인과관계 과잉 해석 → ⑦ Next Best Analysis → ⑧ 최종 제조 판단**

으로 분해할 것입니다.

특히 **Critical Error를 하나라도 발생시키면 전체 Case를 FAIL시키는 기준**을 실제 자동화 규칙으로 만드는 것이 중요합니다.

그 단계까지 가면 드디어 이 프로젝트를 **Claude Code로 실제 개발하면서도 Agent 성능이 회귀하지 않도록 관리할 수 있는 개발 체계**가 만들어집니다.

# Step 16. UC-03 Golden Dataset & Data Contract

## 16-1. 기준 Use Case

### 사용자 질문

> **A라인과 B라인의 토크 차이가 있는지 확인해줘.**

이 질문 하나를 Agent가 다음과 같이 해석해야 합니다.

```
Problem Type
= GROUP_COMPARISON

Response Variable
= Torque

Factor
= Line

Groups
= A, B

Objective
= Difference Detection

Data Type
= Continuous

Relationship
= Initially Unknown
```

여기서 중요한 것은 **사용자는 통계 용어를 말하지 않았다는 것**입니다.

사용자는 "t-test를 해줘"라고 하지 않았습니다.

Agent가 제조 질문을 통계적 문제로 변환해야 합니다.

---

# 16-2. Golden Dataset 설계

실제 제조 데이터와 유사하게 다음 구조를 사용합니다.

|컬럼|유형|의미|
|---|---|---|
|Timestamp|DateTime|측정 시각|
|Model|Categorical|제품 Model|
|Line|Categorical|생산 Line|
|Machine|Categorical|설비|
|Shift|Categorical|근무조|
|Operator|Categorical|작업자|
|Torque|Numeric|측정 토크|
|Defect_Flag|Binary|불량 여부|
|Target|Numeric|목표값|
|LSL|Numeric|하한 규격|
|USL|Numeric|상한 규격|

다만 **UC-03의 핵심 분석에는 모든 변수가 필요한 것은 아닙니다.**

최소 분석에는:

```
Line
Torque
```

가 필요합니다.

다른 변수들은 **Confounding Check와 향후 분석을 위한 Context**로 보존합니다.

예를 들어:

|---|---|---|---|---|---|
|2026-08-01 08:01|M1|A|A01|1|163.2|
|2026-08-01 08:02|M1|A|A01|1|164.1|
|2026-08-01 08:03|M1|A|A02|1|162.8|
|...|...|...|...|...|...|
|2026-08-01 08:01|M1|B|B01|1|166.4|
|2026-08-01 08:02|M1|B|B01|1|165.8|
|2026-08-01 08:03|M1|B|B02|1|167.1|

Golden Dataset에서는 실제 제조 데이터와 마찬가지로 **A/B 간 평균 차이가 존재하도록 설계**하되, 단순 비교만으로 끝나지 않도록 일부 Model/Machine 구성을 다르게 설정할 수 있습니다.

이것이 중요한 이유는 나중에 Agent가

> "B라인의 토크가 높으므로 B라인이 원인이다."

라는 잘못된 인과 판단을 하지 않는지 검증할 수 있기 때문입니다.

# 16-7. ToolCall

Agent가 실제 분석 Tool을 호출할 때는 다음과 같은 계약을 사용합니다.

```
{
  "tool_call_id": "TC-0006",

  "tool_name": "welch_t_test",

  "tool_version": "1.0",

  "analysis_node_id": "N06",

  "arguments": {
    "dataset_id": "DS-UC03-001",
    "response": "Torque",
    "group": "Line",
    "group_a": "A",
    "group_b": "B"
  },

  "reason": "Two independent groups with unequal variance",

  "expected_output": [
    "mean_a",
    "mean_b",
    "mean_difference",
    "statistic",
    "p_value",
    "confidence_interval",
    "effect_size"
  ]
}
```

여기서 **`reason`을 저장하는 것**이 중요합니다.

나중에:

> 왜 Welch t-test를 사용했는가?

라는 질문에 답할 수 있기 때문입니다.

# 16-8. Rule Engine 검증

ToolCall이 실행되기 전에 Rule Engine이 검사합니다.

```
Line
 ├─ categorical?       YES
 ├─ groups = 2?        YES
 ├─ Torque numeric?    YES
 ├─ independent?       YES
 ├─ missing acceptable? YES
 └─ variance equal?    NO

→ Welch t-test
```

따라서 LLM이 실수로

```
ANOVA
```

를 선택하더라도 Rule Engine에서 교정할 수 있습니다.

# 16-10. Result와 Finding의 분리

여기서 중요한 설계 포인트가 다시 등장합니다.

### ToolResult

> 평균 차이 = -2.9 N·m, p = 0.0016

### Finding

> A라인의 평균 토크가 B라인보다 낮은 것으로 나타났다.

### Evidence

> 두 라인의 평균 차이에 대한 통계적 근거가 존재한다. → E2

이 세 가지를 분리합니다.

과

> Line이 그 차이의 원인임

을 시스템 차원에서 구분합니다.

# 16-13. Confounder

예를 들어 분석 결과가 다음과 같다고 가정합니다.

```
A Line
Model M1 80%
Model M2 20%

B Line
Model M1 20%
Model M2 80%
```

그리고 M2 자체가 토크가 높은 Model이라면,

```
Line → Torque
```

차이가 실제 Line 효과인지

```
Line → Model → Torque
```

때문인지 알 수 없습니다.

따라서 Agent는:

```
{
  "confounder_id": "C-001",
  "factor": "Model",
  "affected_factor": "Line",
  "risk": "HIGH",
  "reason": "Model composition differs substantially between lines",
  "status": "UNRESOLVED",
  "recommended_analysis": "same_model_comparison"
}
```

처럼 기록합니다.

이것이 일반 통계 프로그램과 **제조 통계 Agent의 중요한 차별점**이 됩니다.

---

# 16-14. NextAction

분석이 끝났다고 바로 종료하지 않습니다.

Agent가 다음을 판단합니다.

```
현재 질문:
A/B 차이가 있는가?

→ YES, 통계적으로 차이가 있음.

하지만:
Model 구성 차이 존재

→ Line 효과인지 불명확

따라서:

Next Action
= 동일 Model 기준 A/B 비교
```

구조는:

```
{
  "action_type": "CONTINUE_ANALYSIS",

  "analysis_type": "SAME_MODEL_GROUP_COMPARISON",

  "priority": "HIGH",

  "reason": "Model composition may confound the observed Line difference",

  "expected_information_gain": "HIGH"
}
```

# 16-15. 최종 Agent 답변 구조

사용자에게는 내부 JSON을 그대로 보여주지 않습니다.

최종 결과는 다음과 같이 표현합니다.

### 결론

**A라인과 B라인의 평균 토크에는 통계적으로 유의한 차이가 있습니다.**

### 통계적 근거

- A라인 평균: 163.2 N·m
- B라인 평균: 166.1 N·m
- 평균 차이: -2.9 N·m
- Welch t-test: p = 0.0016
- 95% CI: -4.69 ~ -1.11 N·m

### 제조 관점

A라인의 토크가 B라인보다 낮은 경향이 통계적으로 확인되었습니다.

다만 **이 결과만으로 Line 자체가 토크 차이의 원인이라고 판단할 수는 없습니다.**

### 추가 확인 필요

라인별 Model 구성에 차이가 있다면 Model 효과가 Line 효과와 혼재할 수 있습니다.

따라서 **동일 Model을 대상으로 A/B라인을 다시 비교하는 것**을 권장합니다.

# 16-16. Golden Case의 핵심

이제 이 전체 과정을 하나의 테스트 케이스로 고정합니다.

```
GC-UC03-001
│
├── User Question
│
├── Dataset
│
├── Expected Problem Model
│
├── Expected Data Assessment
│
├── Expected Analysis Plan
│
├── Expected Tool Calls
│
├── Expected Statistical Results
│
├── Expected Findings
│
├── Expected Evidence
│
├── Expected Confounders
│
├── Expected Next Action
│
├── Expected Final Interpretation
│
└── Forbidden Conclusions
```

### Forbidden Conclusions

다음 표현은 **FAIL**로 처리합니다.

> "B라인이 토크 불량의 원인이다."

> "B라인 때문에 토크가 높아졌다."

> "p-value가 0.0016이므로 B라인이 더 좋은 공정이다."

> "통계적으로 유의하므로 제조적으로도 문제가 있다."

이것은 단순한 문장 품질 문제가 아니라 **Agent Safety Rule**입니다.

# 16-17. 여기서 매우 중요한 설계 결론

이제 Agent의 내부 구조가 상당히 명확해졌습니다.

```
User Question
       ↓
Problem Model
       ↓
Analysis Plan
       ↓
Tool Call
       ↓
Tool Result
       ↓
Finding
       ↓
Evidence
       ↓
Hypothesis
       ↓
Confounder
       ↓
Next Action
       ↓
Final Decision
```

이 구조가 앞으로 **UC-05, UC-07, UC-11**에도 거의 그대로 적용됩니다.

차이는 Tool과 Analysis Plan의 내용입니다.

즉, 지금 만든 UC-03 구조는 단순한 테스트 사례가 아니라 **전체 Manufacturing Statistical Agent의 공통 데이터 모델을 검증하는 기준 사례**입니다.

# Step 17로 넘어갑니다

다음 단계는 이제 상당히 구체적입니다.

## **Step 17 — Statistical Engine 실제 구현 명세**

첫 번째로 다음 세 가지를 실제 소프트웨어 함수 수준으로 정의하는 것이 좋습니다.

```
descriptive_statistics()
two_sample_t_test()
welch_t_test()
```

특히 `welch_t_test()`를 중심으로

**입력 → 전처리 → 계산 → 진단 → Effect Size → CI → 결과 Schema → 오류 처리 → Unit Test → Golden Case 검증**

까지 내려가겠습니다.

그리고 여기서 한 가지 중요한 원칙을 적용하겠습니다.

> **통계 Engine의 함수 설계는 "LLM이 사용하기 편한 함수"가 아니라 "통계적으로 정확하고 독립적으로 검증 가능한 함수"를 먼저 만든다.**

그 위에 Tool Layer를 씌우는 방식으로 진행하겠습니다.

이렇게 하면 이후 Claude Code에게도 **"이 함수와 테스트를 구현하라"**는 수준의 작업 지시가 가능해집니다.

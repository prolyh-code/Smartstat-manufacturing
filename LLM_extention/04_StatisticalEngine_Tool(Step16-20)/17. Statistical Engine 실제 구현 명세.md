좋습니다. 지금까지 설계한 **제조 통계분석 Agent**를 실제 소프트웨어 구현 단계로 전환하겠습니다.

## Step 17. Statistical Engine 실제 구현 명세

이번 단계의 목표는 **LLM보다 먼저 통계 계산 자체를 완전히 신뢰할 수 있는 상태로 만드는 것**입니다.

전체 개발 순서는 다음과 같이 유지합니다.

> **Statistical Engine → Tool Layer → Rule Engine → Agent → Evaluation → UI**

즉, 이번 단계에서는 LLM이나 화면을 만들지 않습니다.

---

# 1. Statistical Engine의 역할

Statistical Engine은 Agent의 가장 아래쪽에 위치합니다.

```
사용자 질문
    ↓
LLM Agent
    ↓
Analysis Planner
    ↓
Rule Engine
    ↓
Tool
    ↓
┌─────────────────────────────┐
│     Statistical Engine      │
│                             │
│  descriptive_statistics()   │
│  two_sample_t_test()        │
│  welch_t_test()             │
│  paired_t_test()             │
│  anova()                    │
│  correlation()              │
│  regression()                │
└─────────────────────────────┘
    ↓
검증된 Statistical Result
    ↓
Finding / Evidence
```

여기서 중요한 원칙은 다음입니다.

> **LLM은 통계를 계산하지 않는다.  
> Statistical Engine이 계산하고, LLM은 그 결과를 해석한다.**

따라서 Statistical Engine은 **LLM이 없어도 독립적으로 실행되고 검증되어야 합니다.**

---

# 2. 첫 번째 구현 대상

Step 17에서는 우선 다음 3개부터 구현합니다.

|Function|목적|우선순위|
|---|---|---|
|`descriptive_statistics()`|기본 통계량|★★★★★|
|`two_sample_t_test()`|두 집단 평균 비교|★★★★★|
|`welch_t_test()`|등분산 가정이 없는 두 집단 비교|★★★★★|

특히 **`welch_t_test()`를 기준 구현 모델**로 삼는 것이 좋습니다.

이유는 이후 모든 통계 함수의 공통 구조를 정의하기 좋기 때문입니다.

# 3. Statistical Engine 공통 처리 구조

모든 분석 함수는 다음 구조를 따릅니다.

```
Input
  ↓
Input Validation
  ↓
Data Preprocessing
  ↓
Statistical Calculation
  ↓
Assumption / Diagnostic
  ↓
Effect Size
  ↓
Confidence Interval
  ↓
Result Validation
  ↓
Standard Result Schema
  ↓
Return
```

이를 코드 관점으로 표현하면:

```
def welch_t_test(data, response, group, group_a, group_b):

    validate_input(...)

    prepared_data = preprocess(...)

    diagnostics = diagnose(...)

    result = calculate(...)

    effect_size = calculate_effect_size(...)

    confidence_interval = calculate_ci(...)

    validated_result = validate_result(...)

    return validated_result
```

여기서 중요한 점은 **계산과 해석을 분리하는 것**입니다.

Statistical Engine은:

> "A가 B보다 낮다. 그러므로 A라인이 문제다."

라고 말하지 않습니다.

대신:

> A mean = 163.2  
> B mean = 166.1  
> difference = -2.9  
> p = 0.0016  
> CI = [-4.69, -1.11]

처럼 **통계적 사실을 반환**합니다.

# 4. `descriptive_statistics()`

가장 먼저 구현할 기본 함수입니다.

### Input

```
descriptive_statistics(
    data,
    variable="Torque",
    group=None
)
```

그룹을 지정하면:

```
descriptive_statistics(
    data,
    variable="Torque",
    group="Line"
)
```

### 기본 출력

```
{
  "variable": "Torque",
  "n": 1840,
  "mean": 164.65,
  "median": 164.20,
  "std": 8.21,
  "variance": 67.40,
  "min": 141.2,
  "q1": 159.1,
  "q3": 170.4,
  "max": 189.5,
  "iqr": 11.3
}
```

그룹 분석이면:

```
{
  "groups": {
    "A": {
      "n": 920,
      "mean": 163.2,
      "median": 163.0,
      "std": 7.8
    },
    "B": {
      "n": 920,
      "mean": 166.1,
      "median": 165.8,
      "std": 8.5
    }
  }
}
```

### 반드시 명시할 것

표본분산은 기본적으로:

\[ s^2=\frac{\sum(x_i-\bar{x})^2}{n-1} \]

즉 **`ddof=1`**을 사용합니다.

이 부분은 Excel, Minitab, Python 간 결과 차이를 방지하기 위해 명시적으로 고정하는 것이 좋습니다.

# 5. `two_sample_t_test()`

두 독립 집단의 평균 차이를 검정합니다.

예:

> A라인과 B라인의 토크 차이가 있는가?

### 가설

\[ H_0:\mu_A=\mu_B \]\[ H_1:\mu_A\neq\mu_B \]

### 기본 계산

Student's two-sample t-test는 등분산을 가정합니다.

\[ t= \frac{\bar X_A-\bar X_B} {S_p\sqrt{\frac{1}{n_A}+\frac{1}{n_B}}} \]

여기서 pooled variance:

\[ S_p^2= \frac{(n_A-1)S_A^2+(n_B-1)S_B^2} {n_A+n_B-2} \]

입니다.

---

# 6. `welch_t_test()`

이번 단계에서 **가장 중요한 함수**입니다.

Welch t-test는 두 집단의 분산이 동일하다는 가정을 하지 않습니다.

### 가설

\[ H_0:\mu_A=\mu_B \]\[ H_1:\mu_A\neq\mu_B \]

### 통계량

\[ t= \frac{\bar X_A-\bar X_B} {\sqrt{\frac{s_A^2}{n_A}+\frac{s_B^2}{n_B}}} \]

자유도는 Welch–Satterthwaite 근사식을 사용합니다.

\[ \nu = \frac{ \left(\frac{s_A^2}{n_A}+\frac{s_B^2}{n_B}\right)^2 }{ \frac{(s_A^2/n_A)^2}{n_A-1} + \frac{(s_B^2/n_B)^2}{n_B-1} } \]

---

# 7. Welch t-test의 출력 계약

Tool Layer에서 사용할 수 있도록 결과를 표준화합니다.

```
{
  "tool_name": "welch_t_test",
  "tool_version": "1.0",

  "input": {
    "response": "Torque",
    "group": "Line",
    "group_a": "A",
    "group_b": "B"
  },

  "sample": {
    "n_a": 920,
    "n_b": 920
  },

  "descriptive": {
    "mean_a": 163.2,
    "mean_b": 166.1,
    "std_a": 7.8,
    "std_b": 8.5
  },

  "result": {
    "mean_difference": -2.9,
    "statistic": -3.18,
    "degrees_of_freedom": 1821.4,
    "p_value": 0.0016
  },

  "confidence_interval": {
    "level": 0.95,
    "lower": -4.69,
    "upper": -1.11
  },

  "effect_size": {
    "name": "cohens_d",
    "value": 0.15
  },

  "diagnostics": {
    "variance_equal": false
  },

  "status": "SUCCESS",
  "warnings": []
}
```

여기서 **통계량과 해석을 분리**합니다.

예를 들어 다음과 같은 필드는 Statistical Engine에 넣지 않는 것이 좋습니다.

```
"interpretation": "B라인의 토크가 높다"
```

이것은 상위 **Interpretation Layer**의 역할입니다.

# 8. Effect Size

p-value만 반환해서는 안 됩니다.

예를 들어:

> p = 0.001

이라고 해도 실제 차이가 제조적으로 중요한지는 별개의 문제입니다.

따라서 최소한 Cohen's d를 제공합니다.

\[ d=\frac{\bar X_A-\bar X_B}{S_p} \]

다만 Welch test 자체는 등분산을 가정하지 않으므로 **effect size 계산 방식은 별도의 명세로 고정**해야 합니다.

MVP에서는 다음처럼 명확하게 정의하는 것을 권장합니다.

```
Test statistic
    ↓
Welch t-test

Effect size
    ↓
Cohen's d
    ↓
pooled SD 기반
```

추후에는 Hedges' g 등을 추가할 수 있습니다.

---

# 9. Confidence Interval

두 평균의 차이에 대해 95% CI를 제공합니다.

개념적으로:

\[ (\bar X_A-\bar X_B) \pm t_{\alpha/2,\nu} \sqrt{ \frac{s_A^2}{n_A} + \frac{s_B^2}{n_B} } \]

결과:

```
{
  "mean_difference": -2.9,
  "ci_95": [-4.69, -1.11]
}
```

여기서 중요한 것은 **CI와 p-value의 논리적 일관성을 자동 검증**하는 것입니다.

예를 들어:

```
p < 0.05
```

인데

```
95% CI = [-1.0, +2.0]
```

처럼 0을 포함한다면 Result Validator가 오류를 검출해야 합니다.

# 10. Assumption / Diagnostic

여기서 중요한 설계상의 구분이 있습니다.

### Statistical Engine

**진단 결과를 계산합니다.**

예:

```
{
  "variance_equal": false,
  "normality_a": "acceptable",
  "normality_b": "acceptable"
}
```

### Rule Engine

그 진단 결과를 이용해:

> Welch t-test를 사용하는 것이 적절하다.

라고 판단합니다.

즉,

```
Statistical Engine
    ↓
진단 사실

Rule Engine
    ↓
방법 선택
```

으로 분리합니다.

이 구조가 매우 중요합니다.

# 11. 데이터 오류 처리

통계 함수가 이상한 데이터를 조용히 계산해서는 안 됩니다.

예를 들어:

### 변수 없음

```
ERROR_VARIABLE_NOT_FOUND
```

### 숫자형이 아님

```
ERROR_INVALID_DATA_TYPE
```

### 그룹 없음

```
ERROR_GROUP_NOT_FOUND
```

### 두 그룹이 아님

```
ERROR_INVALID_GROUP_COUNT
```

### 표본 부족

```
ERROR_INSUFFICIENT_SAMPLE
```

### 결측치 과다

```
WARNING_HIGH_MISSING_RATE
```

### 데이터가 전부 동일

```
ERROR_ZERO_VARIANCE
```

처럼 **표준 Error Code**를 만들어야 합니다.

# 12. 특히 중요한 부분: 자동 삭제 금지

예를 들어 Torque 데이터에 결측값 10개가 있다고 해서 Statistical Engine이 무조건 삭제해서는 안 됩니다.

권장 구조는:

```
Raw Data
   ↓
Data Quality Layer
   ↓
Missing Detection
   ↓
Policy
   ↓
Analysis Dataset
   ↓
Statistical Engine
```

즉, **전처리 정책과 통계 계산을 분리**합니다.

Statistical Engine에는 이미 정제된 Analysis Dataset이 전달되는 구조가 좋습니다.

# 13. Result Validator

계산이 끝났다고 바로 Agent에게 넘기지 않습니다.

```
Statistical Engine
       ↓
Result Validator
       ↓
Validated Result
```

Validator가 최소한 다음을 확인합니다.

|검증항목|검증|
|---|---|
|n > 0|필수|
|nA/nB 일치|필수|
|평균 계산 가능|필수|
|SD ≥ 0|필수|
|p-value 0~1|필수|
|df > 0|필수|
|CI lower < upper|필수|
|CI와 p-value 논리 일치|필수|
|effect size 계산 가능|필수|
|입력 dataset version 존재|필수|

이 단계가 향후 **AI 신뢰성의 핵심 방어선**이 됩니다.

# 16. 중요한 설계 결정: Statistical Engine은 pandas에 종속시키지 않는다

초기 개발에서는 pandas를 사용하더라도 API를 다음처럼 만드는 것을 권장합니다.

```
welch_t_test(
    data,
    response="Torque",
    group="Line",
    group_a="A",
    group_b="B"
)
```

즉, 내부 구현은 pandas/SciPy를 사용하지만 **외부 계약은 특정 라이브러리의 API가 아닙니다.**

이렇게 해야 나중에:

```
SciPy
   ↓
다른 통계 라이브러리
   ↓
R
   ↓
검증된 자체 구현
```

등으로 교체할 수 있습니다.

# 19. 그리고 한 가지 중요한 개선점

> t-test → ANOVA → correlation → regression ...

처럼 **분석 기능 중심**이었다면,

> **Problem → Analysis Plan → Tool → Statistical Result → Evidence**

가 중심입니다.

```
                Manufacturing Question

                         │
                         ▼
                  Analysis Plan
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
        Descriptive   Welch t     Correlation
             │           │           │
             └───────────┼───────────┘
                         ▼
                  Statistical Results
                         │
                         ▼
                      Evidence
                         │
```

이것이 우리가 지금까지 설계해 온 **"통계 프로그램 → 제조 통계분석 Agent" 전환의 핵심**입니다.

Step 17에서는 이제 설계가 아니라 **실제 코드 수준의 구현 명세**로 들어갈 수 있습니다.

여기서 처음으로 다음을 연결합니다.

```
LLM

"두 라인의 토크를 비교해줘"

Analysis Planner
 ↓

```

그리고 **`Tool Registry → Tool Schema → Rule Engine → Tool Validation → Tool Execution`**을 실제 Python 클래스/API 수준으로 설계하면, 그 다음 Step 19에서 Claude Code를 이용해 Agent 자체를 구현할 수 있는 상태가 됩니다.

즉, 지금부터는 **기획서 작성 단계가 아니라 실제 소프트웨어 설계/구현 단계**로 넘어가는 것입니다.

> ## ⚠ 개정 안내 — 이 문서의 실행 루프는 불완전합니다 (2026-09-12)
>
> **§19-5의 Orchestrator 루프에 사용자 승인을 확인하는 지점이 없습니다.** 루프가 `decision → rule_engine.validate → tool_registry.execute`로 직행하므로, 이 문서만 보고 구현하면 **Step 26 §12-1의 승인 매트릭스가 코드 어디에도 강제되지 않습니다.**
>
> **반드시 `06_제품운영설계(Step25-31)/27. App-LLM AI Gateway Architecture.md` §7의 보완된 루프를 함께 읽고 구현하십시오.** 요지는 다음과 같습니다.
>
> ```python
> if decision.action == "EXECUTE_TOOL":
>     grant = approval.check(decision.tool_call, session)      # ← 신설
>     if grant.status == "REQUIRES_APPROVAL":
>         session.pending_decision = decision
>         session.status = "WAITING_APPROVAL"                  # UI가 S-09 표시
>         break                                                # 임의 진행 금지
>     result = tool_registry.execute(decision.tool_call)
>     ...
>     grant.consume(executions=1)                              # ← 신설
> ```
>
> - `ApprovalGrant`는 계획 단위로 발급되고 소비량이 기록되는 객체입니다(Step 27 §7-2, Step 30 §3-2). 허용 Tool 목록·최대 실행 횟수·전송범위·최대 루프를 범위로 갖습니다.
> - 재승인 트리거: 계획에 없는 Tool / 최대 실행 초과 / 전송범위 상향 / 최대 루프 초과 / Level 1(Guided)은 매 실행.
> - **불변식 INV-08**(Level 0이 아닌 모드에서 Tool 실행은 유효한 Grant를 요구)이 이를 계약으로 강제합니다(Step 30 §9).
>
> **또 한 가지:** §19-13의 `MAX_RETRY_PER_DECISION = 2`는 **결정 재시도**(Rule reject 후 LLM 재판단)입니다. 네트워크 오류에 대한 **전송 재시도**는 이와 **별개의 카운터**이며 Step 27 §8-1에 정의되어 있습니다. 두 카운터를 합치면 네트워크 장애가 "Agent 판단 실패"로 기록되어 Golden Case 평가가 왜곡됩니다(DD-034).
>
> 그 외 §19-1~19-25의 내용(Action Schema, 3단계 검증, Repair, 중복 분석 방지, Context Builder, LLMProvider 추상화)은 그대로 유효합니다. 단 LLM 호출 위치는 **서버가 아니라 사용자 브라우저**로 변경되었으므로 `31-2`를 함께 확인하십시오.

# Step 19. LLM Tool Calling + Agent Orchestrator

## 19-1. Step 19의 핵심 목표

Step 17과 18에서 다음을 만들었습니다.

```
Step 17
Statistical Engine
    ↓
정확한 통계 계산

Step 18
Tool Registry
Rule Engine
    ↓
안전한 Tool 호출
```

이제 Step 19에서는 그 위에 **LLM Agent의 실행 제어기(Orchestrator)**를 올립니다.

최종 구조는:

```
┌──────────────────────────────┐
│            User              │
│ "A/B 라인의 토크 차이를 봐줘" │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│        LLM Orchestrator      │
│                              │
│ Understand → Plan → Act      │
└──────────────┬───────────────┘
               ↓
       Analysis State
               ↓
        Analysis Planner
               ↓
         Tool Decision
               ↓
         Rule Engine
               ↓
        Tool Registry
               ↓
     Statistical Engine
               ↓
        Result Validator
               ↓
       Analysis State
               ↓
      LLM Interpretation
               ↓
      Finding / Evidence
               ↓
        Next Action
```

여기서 **Orchestrator가 Agent의 실제 두뇌 역할**을 합니다.

---

# 19-2. Orchestrator는 무엇을 하는가?

Orchestrator의 역할을 한 문장으로 정의하면:

> **현재 Analysis State를 보고 Agent가 다음에 무엇을 해야 하는지를 결정하고 실행시키는 제어기**

입니다.

따라서 Orchestrator가 통계를 계산하거나 제조 지식을 직접 저장하지 않습니다.

|구성요소|역할|
|---|---|
|LLM|판단·계획·해석|
|Orchestrator|실행 흐름 제어|
|State|현재까지의 사실 저장|
|Planner|분석 계획 생성|
|Rule Engine|실행 가능 여부 검증|
|Tool Registry|사용 가능한 Tool 관리|
|Statistical Engine|실제 계산|
|Knowledge|제조/통계 지식|
|Validator|결과 검증|

이 분리가 매우 중요합니다.

---

# 19-3. Agent를 "대화형 LLM"으로 만들지 않는다

처음에는 다음과 같은 구조를 생각하기 쉽습니다.

```
User
 ↓
LLM
 ↓
답변
```

하지만 우리가 만드는 것은 이것이 아닙니다.

제조 통계 Agent는:

```
User
 ↓
LLM
 ↓
계획
 ↓
Tool
 ↓
결과
 ↓
LLM
 ↓
추가 Tool
 ↓
결과
 ↓
LLM
 ↓
최종 판단
```

이라는 **반복 실행형 Agent**입니다.

즉:

> **LLM은 한 번 답변하는 모델이 아니라, 분석 프로세스를 진행시키는 의사결정 모듈입니다.**

---

# 19-4. Agent State가 중심이 된다

Agent가 여러 분석을 수행하려면 현재 상태를 계속 기억해야 합니다.

예를 들어 UC-11:

> "최근 토크 불량이 증가한 원인을 찾아줘."

를 생각해 보겠습니다.

첫 번째 분석:

```
전체 불량률
→ 최근 2.1%
→ 과거 0.9%
```

두 번째:

```
Machine별 불량률
→ M4 높음
```

세 번째:

```
Model별 분석
→ Model C 높음
```

네 번째:

```
Machine × Model
→ M4의 높은 불량률은 Model C 생산 집중의 영향 가능
```

Agent는 이 정보를 잊으면 안 됩니다.

따라서 State가:

```
AnalysisSession
│
├── ProblemModel
├── DatasetContext
├── AnalysisPlan
├── AnalysisHistory
├── Findings
├── Evidence
├── Hypotheses
├── Confounders
├── NextActions
└── FinalDecision
```

를 계속 유지합니다.

---

# 19-5. Orchestrator의 기본 Loop

핵심 실행 Loop는 다음과 같이 설계합니다.

```
START
 ↓
Load Analysis State
 ↓
Understand / Update Problem
 ↓
Create / Update Analysis Plan
 ↓
Select Next Action
 ↓
Rule Validation
 ↓
Execute Tool
 ↓
Validate Result
 ↓
Update State
 ↓
Interpret Result
 ↓
Create Finding / Evidence
 ↓
Need More Analysis?
 ├── YES → Select Next Action
 └── NO  → Final Decision
```

이를 의사코드로 표현하면:

```
while session.status not in FINAL_STATES:

    context = build_agent_context(session)

    decision = llm.decide(context)

    validation = rule_engine.validate(
        decision,
        session
    )

    if validation.rejected:
        decision = repair_decision(
            decision,
            validation
        )
        continue

    if decision.action == "EXECUTE_TOOL":

        result = tool_registry.execute(
            decision.tool_call
        )

        validated_result = result_validator.validate(
            result
        )

        session.update(
            validated_result
        )

        continue

    if decision.action == "ASK_USER":
        session.status = "WAITING_USER"
        break

    if decision.action == "REQUEST_DATA":
        session.status = "WAITING_DATA"
        break

    if decision.action == "ESCALATE_TO_EXPERIMENT":
        session.status = "EXPERIMENT_REQUIRED"
        break

    if decision.action == "STOP":
        session.status = "COMPLETED"
        break
```

이것이 Agent의 핵심 실행 구조입니다.

# 19-6. LLM에게 전체 State를 그대로 보내지 않는다

여기에서도 중요한 원칙이 있습니다.

**Analysis State 전체를 LLM Context에 그대로 넣으면 안 됩니다.**

예를 들어:

```
1840개 데이터
+
분석 결과 30개
+
Finding 20개
+
Tool 결과 50개
```

를 모두 전달하면 Context가 불필요하게 커집니다.

대신:

```
Analysis State
      ↓
Context Builder
      ↓
현재 의사결정에 필요한 정보만 추출
      ↓
LLM
```

구조를 사용합니다.

예를 들어 현재 상태가:

2. trend
3. machine comparison

    {
      "factor": "Model",

  "available_next_actions": [
    "same_model_comparison",
    "model_comparison",
    "shift_comparison"
  ]
}
```

처럼 전달합니다.

**Raw data는 보내지 않습니다.**

# 19-8. LLM 호출을 4가지 역할로 분리

하나의 거대한 Prompt에서 모든 것을 처리하기보다 LLM의 역할을 논리적으로 나누는 것이 좋습니다.

### A. Intent / Problem Understanding

```
사용자 질문
      ↓
Problem Model
```

### B. Analysis Planning

```
Problem Model
+
Dataset Context
+
Knowledge
      ↓
Analysis Plan
```

### C. Result Interpretation

```
Tool Result
+
Manufacturing Knowledge
+
Evidence
      ↓
Finding
```

### D. Next Analysis

```
Current State
+
Findings
+
Confounders
      ↓
Next Action
```

물리적으로는 동일한 LLM을 사용할 수 있습니다.

하지만 **Prompt와 Output Schema를 분리**하는 것을 권장합니다.

# 19-9. Structured Output을 강제한다

LLM이 자연어로:

> "Welch t-test를 해보는 것이 좋겠습니다."

라고 반환하게 만들지 않습니다.

다음과 같이 구조화합니다.

```
{
  "action": "EXECUTE_TOOL",

  "tool_call": {
    "tool_name": "welch_t_test",
    "arguments": {
      "dataset_id": "DS-UC03-001",
      "response": "Torque",
      "group": "Line",
      "group_a": "A",
      "group_b": "B"
    }
  },

  "reason": "두 독립 집단의 평균 차이를 비교하며 등분산 가정이 충족되지 않음"
}
```

이것이 **LLM → Application Interface**입니다.

# 19-10. LLM의 Action Schema

Agent가 취할 수 있는 행동을 제한합니다.

```
EXECUTE_TOOL
CONTINUE_ANALYSIS
ASK_USER
REQUEST_DATA
STOP
ESCALATE_TO_EXPERIMENT
```

예를 들어:

```
{
  "action": "STOP",
  "reason": "현재 질문에 대한 통계적 판단이 충분히 확보되었으며 추가 분석의 정보가치가 낮음"
}
```

또는:

```
{
  "action": "ESCALATE_TO_EXPERIMENT",
  "reason": "관찰 데이터만으로는 인과관계를 확인할 수 없음"
}
```

이렇게 합니다.

# 19-11. Tool Call은 반드시 3단계를 거친다

LLM이 Tool을 호출하면:

```
LLM Tool Call
      ↓
① Schema Validation
      ↓
② Rule Validation
      ↓
③ Tool Execution
```

입니다.

### ① Schema Validation

인자가 맞는가?

```
response 존재?
group 존재?
group_a 존재?
group_b 존재?
```

### ② Rule Validation

통계적으로 가능한가?

```
response numeric?
group categorical?
groups = 2?
independent?
```

### ③ Execution

그제야:

```
welch_t_test()
```

를 실행합니다.

# 19-12. Rule Reject → Agent Repair

이 부분도 실제 Agent에서는 매우 중요합니다.

예를 들어 LLM이:

```
{
  "tool_name": "paired_t_test"
}
```

를 선택했다고 합시다.

Rule Engine:

```
REJECT

Reason:
Pair ID가 없음
```

그러면 단순히 오류를 사용자에게 보여주는 것이 아니라 Agent가 다시 판단합니다.

```
LLM
 ↓
paired_t_test
 ↓
Rule Engine
 ↓
REJECT
 ↓
Repair Context
 ↓
LLM
 ↓
two_sample_t_test
```

즉:

> **Rule Engine은 Agent를 죽이는 장치가 아니라 Agent가 잘못된 결정을 수정하도록 만드는 장치입니다.**

# 19-13. 무한 반복 방지

AI Agent에서 반드시 필요한 기능입니다.

예:

```
LLM → Tool A
Rule → Reject

LLM → Tool A
Rule → Reject

LLM → Tool A
Rule → Reject
```

이런 Loop가 발생하면 안 됩니다.

따라서:

```
MAX_RETRY_PER_DECISION = 2
```

정도로 제한합니다.

예:

```
첫 번째 실패
→ Agent Repair

두 번째 실패
→ 다른 분석 후보

세 번째 실패
→ ASK_USER / STOP
```

# 19-14. 중복 분석 방지

예를 들어 이미:

```
welch_t_test(Torque, Line, A, B)
```

를 수행했는데 Agent가 다시 동일 분석을 호출하는 경우가 있습니다.

Analysis History를 이용해서:

```
same dataset
+
same response
+
same factor
+
same groups
+
same method
+
same parameters
```

이면:

```
DUPLICATE_ANALYSIS
```

로 판단합니다.

Agent에는:

> "동일 조건의 분석이 이미 수행되었습니다. 기존 결과를 재사용하거나 다른 분석을 선택하십시오."

라고 전달합니다.

# 19-15. Analysis Plan도 고정하지 않는다

초기 계획은:

```
Data Quality
 ↓
Descriptive
 ↓
Variance
 ↓
t-test
```

였더라도 결과에 따라 변경될 수 있어야 합니다.

예를 들어:

```
Line difference 발견
       ↓
Model confounding 발견
       ↓
기존 계획 수정
       ↓
Same Model comparison 추가
```

따라서 Analysis Plan은:

> **Workflow가 아니라 Dynamic Analysis Plan Graph**

로 유지합니다.

```
N01 Data Quality
      ↓
N02 Group Comparison
      ↓
N03 Confounding Check
      ↓
      ├── N04 Same Model Comparison
      │
      └── N05 Regression
```

# 19-16. Agent가 판단하는 "다음 분석"

여기서 우리가 이전에 정의한 **Next Best Analysis**가 실제로 동작하기 시작합니다.

후보:

```
Same-model comparison
Shift comparison
Operator comparison
Machine comparison
Regression
```

을 생성합니다.

그 후:

```
Validity
+
Relevance
+
Information Gain
+
Data Availability
+
Manufacturing Impact
```

를 평가합니다.

개념적으로:

\[ NBA Score = R \times I \times D \times V \times M \]

여기서:

- \(R\) = Relevance
- \(I\) = Information Gain
- \(D\) = Data Availability
- \(V\) = Statistical Validity
- \(M\) = Manufacturing Impact

입니다.

# 19-18. 여기서 Agent가 사용자에게 바로 답하지 않는다

중간 결과가 나올 때마다 자연어 답변을 만들어버리면 Agent 상태가 복잡해집니다.

내부적으로는:

```
Tool Result
 ↓
Finding
 ↓
Evidence
 ↓
Hypothesis
 ↓
Next Action
```

을 먼저 만들고,

**마지막에만 User Response를 생성**하는 것을 권장합니다.

그러면 최종 답변은:

> A라인과 B라인의 평균 토크에는 통계적으로 유의한 차이가 있습니다. A라인의 평균은 163.2 N·m, B라인은 166.1 N·m이며 평균 차이는 -2.9 N·m입니다. Welch t-test에서 p=0.0016으로 통계적으로 유의합니다. 다만 Line 자체가 차이의 원인이라고 판단할 수는 없으며, Model 구성 차이가 존재할 가능성이 있어 동일 Model 기준의 A/B 비교가 다음 분석으로 적절합니다.

처럼 생성됩니다.

# 19-19. 최종 답변 생성에도 Guardrail 적용

        ...

        ...

class ResultValidator:

형태가 됩니다.

# 19-22. LLM Provider는 반드시 추상화

현재 특정 LLM에 종속시키지 않는 것을 권장합니다.

```
class LLMProvider:

    def generate(...):
        ...

    def structured_output(...):
        ...

    def tool_call(...):
        ...

    def stream(...):
        ...
```

구현:

```
LLMProvider
│
├── OpenAIProvider
├── AnthropicProvider
└── LocalLLMProvider
```

이렇게 하면 향후 모델 변경이 쉬워집니다.

그리고 중요한 점은 **Claude Code와 Runtime LLM을 혼동하지 않는 것**입니다.

- **Claude Code** → 개발자가 소프트웨어를 만드는 개발 Agent
- **Manufacturing Statistical Agent** → 완성된 애플리케이션 안에서 사용자가 제조 데이터를 분석하는 Runtime Agent

둘은 별개의 계층입니다.

# 19-25. Step 19의 완료 기준

# 다음 단계: Step 20

이제 다음 단계가 상당히 중요합니다.

**Step 20 — Finding / Evidence / Hypothesis / Next Best Analysis Engine**

에서는 단순히:

> "p-value가 0.0016입니다."

를 넘어,

> **"그래서 제조 현장에서 무엇을 발견했으며, 현재 어느 수준까지 확인되었고, 무엇이 아직 가설이며, 다음에 무엇을 조사해야 하는가?"**

를 시스템이 구조적으로 판단하도록 만듭니다.

특히 우리가 앞서 정의한

**E0 → E1 → E2 → E3 → E4**

증거 수준을 실제 Agent의 판단 체계에 연결합니다.

```
Statistical Result
       ↓
Finding
       ↓
Evidence Level
       ↓
Hypothesis
       ↓
Confounder
       ↓
Next Best Analysis
       ↓
Engineering Decision
```

그리고 여기서 **"통계적으로 유의하다"와 "제조적으로 중요한 문제다", "원인이다", "개선 효과가 검증됐다"를 어떻게 구분할 것인지**를 실제 알고리즘 수준으로 정의하게 됩니다.

이 단계가 완성되면 이 프로젝트는 단순한 **LLM + 통계 Tool**이 아니라, 우리가 처음 목표로 했던 **제조 현장의 통계적 의사결정을 지원하는 Agent**라는 제품 개념에 훨씬 가까워집니다.

# Step 18. Tool Registry + Rule Engine

## 18-1. 왜 Tool Layer가 필요한가

Agent가 직접 Python 함수를 호출하도록 만들 수도 있지만, 그렇게 하면 다음 문제가 생깁니다.

```
LLM
 ↓
Python 함수 직접 호출
```

이 구조에서는 LLM이 잘못된 인자를 넣거나, 잘못된 분석 방법을 선택하거나, 존재하지 않는 함수를 호출할 가능성이 있습니다.

따라서 다음 구조로 만듭니다.

```
                LLM Agent
                    │
                    ▼
             Analysis Planner
                    │
                    ▼
              Tool Registry
                    │
                    ▼
              Rule Engine
              /          \
         허용             거부
          │                │
          ▼                ▼
     Tool Executor       Repair
          │
          ▼
 Statistical Engine
```

핵심은:

> **LLM은 "무엇을 실행할지" 제안하고, Rule Engine이 "실행해도 되는지" 결정한다.**

# 18-2. Tool의 정의

앞서 정의한 Statistical Engine 함수:


를 Agent가 직접 보는 것이 아니라 Tool로 감쌉니다.

```

    └── welch_t_test()

```


예:

```
  "input_schema": {...},
  "output_schema": {...}
}
```

# 18-4. Tool Schema

LLM에게는 Python 함수가 아니라 **Schema**를 보여줍니다.

예를 들어 `welch_t_test`:

```
{
  "name": "welch_t_test",
  "description": "두 독립 집단의 평균 차이를 검정한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "dataset_id": {
        "type": "string"
      },
      "response": {
        "type": "string"
      },
      "group": {
        "type": "string"
      },
      "group_a": {
        "type": "string"
      },
      "group_b": {
        "type": "string"
      }
    },
    "required": [
      "dataset_id",
      "response",
      "group",
      "group_a",
      "group_b"
    ]
  }
}
```

그러면 LLM은:

> "Torque를 Line A/B로 비교해야 한다."

고 판단한 후 Tool Call을 생성합니다.

```
{
  "tool_name": "welch_t_test",
  "arguments": {
    "dataset_id": "DS-UC03-001",
    "response": "Torque",
    "group": "Line",
    "group_a": "A",
    "group_b": "B"
  }
}
```

# 18-6. Rule Engine의 역할

Rule Engine은 크게 5개 영역으로 구성합니다.

```
Rule Engine
│
├── Data Rules
├── Method Rules
├── Assumption Rules
├── Result Rules
└── Interpretation Rules
```

### ① Data Rules

```
Torque 존재?
Torque numeric?
Line 존재?
Line categorical?
결측률 허용범위?
표본수 충분?
```

### ② Method Rules

```
group count = 2?
independent?
continuous response?
```

### ③ Assumption Rules

```
variance?
normality?
independence?
```

### ④ Result Rules

```
p-value 0~1?
CI 정상?
effect size 정상?
```

### ⑤ Interpretation Rules

```
p < 0.05
    ↓
"통계적으로 유의한 차이"

하지만

"원인이다"
    ↓
BLOCK
```

즉, Rule Engine은 **AI의 자유도를 제한하는 안전장치**입니다.

# 18-7. UC-03의 실제 Rule Flow

사용자:

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

### Step 1

LLM이 Problem Model을 생성합니다.

```
{
  "problem_type": "GROUP_COMPARISON",
  "response": "Torque",
  "factor": "Line",
  "groups": ["A", "B"]
}
```

### Step 2

Planner가 분석 후보를 생성합니다.

```
descriptive_statistics
distribution_analysis
variance_test
two_sample_t_test
welch_t_test
```

### Step 3

Rule Engine이 필터링합니다.

예:

```
Line = categorical             PASS
Torque = continuous            PASS
groups = 2                     PASS
independent                    PASS
variance equal                 FAIL
variance unequal               PASS

→ welch_t_test
```

### Step 4

Tool 실행

```
welch_t_test
      ↓
Statistical Engine
```

### Step 5

결과 검증

```
p-value valid
CI valid
df valid
effect size valid

→ PASS
```

# 18-8. Rule Engine이 "분석 방법 선택"까지 담당해야 하는가?

여기서 중요한 설계 결정이 있습니다.

**완전히 Rule 기반으로 만들면 안 됩니다.**

예:

```
2 groups → t-test
3+ groups → ANOVA
```

만으로는 실제 제조 데이터의 복잡성을 처리할 수 없습니다.

따라서:

### LLM

**분석 후보 생성**

### Rule Engine

**통계적으로 유효한 후보만 허용**

### Scoring

**가장 적절한 후보 선택**

구조가 좋습니다.

```
LLM
 ↓
Candidate Analysis
 ↓
Rule Filter
 ↓
Scoring
 ↓
Selected Tool
```

# 18-9. Analysis Selection Score

예를 들어 후보가:

```
Student t-test
Welch t-test
Mann-Whitney U
```

라면 다음 요소를 평가할 수 있습니다.

\[ Score = Validity \times ProblemFit \times DataFit \times AssumptionFit \]

실제 구현에서는 정량 점수화할 수 있습니다.

|요소|의미|
|---|---|
|Problem Fit|질문과 방법의 적합성|
|Data Fit|데이터 구조 적합성|
|Assumption Fit|가정 충족|
|Manufacturing Fit|제조 목적 적합성|
|Robustness|가정 위반에 대한 견고성|

MVP에서는 지나치게 복잡한 ML 기반 선택보다 **명시적인 Rule + Score**가 낫습니다.

# 18-12. Rule Engine의 Reject가 중요하다

AI Agent 시스템에서는 **성공보다 올바른 거부가 더 중요할 때가 많습니다.**

예:

LLM이:

```
paired_t_test
```

를 선택했는데 실제 데이터가:

```
Line A
Line B
```

의 독립 생산 데이터라면:

```
REJECT
```

해야 합니다.

그리고 Agent에게:

> "현재 데이터에서 A라인과 B라인이 동일 제품/동일 시점의 대응 측정값인지 확인되지 않았습니다. 독립 표본인지 대응 표본인지 확인이 필요합니다."

라는 정보를 전달합니다.

# 18-14. Causal Guardrail

제조 Agent에서 특히 중요합니다.

예:

```
통계 결과

Machine M4
→ 불량률 높음
→ p < 0.001
```

LLM이:

> "M4가 불량 증가의 원인입니다."

라고 말하면 **BLOCK**합니다.

Rule:

```
OBSERVATIONAL_DATA
+
STATISTICAL_ASSOCIATION
+
CAUSAL_CLAIM

→ REJECT
```

허용:

> "M4에서 불량률이 유의하게 높게 나타나 주요 원인 후보로 볼 수 있습니다."

추가 검증:

```
same-model comparison
↓
regression / GLM
↓
time analysis
↓
DOE / controlled experiment
```

등을 거쳐야 causal evidence가 강해집니다.

# 18-17. 실제 실행 예

이제 Agent가 다음 질문을 받았다고 가정하겠습니다.

> **"A라인과 B라인의 토크 차이가 있는지 확인해줘."**

실제 내부에서는:

```
[USER]
A라인과 B라인의 토크 차이가 있는지 확인해줘.

        ↓

[LLM: Intent]

GROUP_COMPARISON

        ↓

[LLM: Problem Model]

Response = Torque
Factor = Line
Groups = A/B

        ↓

[LLM: Analysis Plan]

Data Quality
→ Descriptive
→ Distribution
→ Variance
→ Group Comparison
→ Effect Size
→ CI
→ Confounding

        ↓

[Rule Engine]

2 groups                 PASS
Continuous response     PASS
Independent             PASS
Equal variance          FAIL
Welch appropriate       PASS

        ↓

[Tool Registry]

welch_t_test

        ↓

[Statistical Engine]

mean A = 163.2
mean B = 166.1
difference = -2.9
p = 0.0016
CI = [-4.69, -1.11]
d = 0.15

        ↓

[Result Validator]

PASS

        ↓

[Finding]

A라인 평균 Torque < B라인 평균 Torque

        ↓

[Evidence]

E2 Statistical Difference

        ↓

[Confounding]

Model composition difference?

        ↓

[NEXT BEST ANALYSIS]

Same Model A/B comparison
```

이제 비로소 우리가 처음부터 목표로 했던:

> **"사용자가 통계 방법을 몰라도 제조 현장의 질문을 입력하면 Agent가 적절한 분석을 수행하고, 통계적 근거와 다음 분석까지 제안하는 시스템"**

의 실행 골격이 만들어집니다.

# 18-18. Step 18에서 특히 중요한 설계 철학

지금 단계에서 한 가지를 명확히 해두는 것이 좋습니다.

### LLM

**Flexible Intelligence**

> 질문 이해  
> 분석 후보 생성  
> 결과 설명  
> 다음 분석 제안

### Schema

**Structured Communication**

> Agent ↔ Tool ↔ State

### Rule Engine

**Hard Constraint**

> 잘못된 분석 차단  
> 가정 위반 감시  
> 과도한 해석 차단

### Tool

**Deterministic Capability**

> Agent가 사용할 수 있는 기능

### Statistical Engine

**Mathematical Truth**

> 실제 통계 계산

### State

**Persistent Facts**

> 지금까지 무엇을 분석했고 무엇을 발견했는가

### Knowledge

**Domain Context**

> 이 분석 결과가 제조 현장에서 무엇을 의미하는가

이 6개를 분리하면 LLM이 바뀌어도 시스템 전체를 다시 만들 필요가 없습니다.

# Step 19로 넘어갈 준비

이제 중요한 연결고리 하나만 남았습니다.

현재까지:

```
Step 17
Statistical Engine
       ↓
Step 18
Tool Registry + Rule Engine
```

까지 완성했습니다.

다음 **Step 19는 실제 Agent의 두뇌를 연결하는 단계**입니다.

### Step 19 — LLM Tool Calling + Agent Orchestrator

여기서는 처음으로 실제 다음 구조를 설계합니다.

```
User
 ↓
LLM
 ↓
Structured Problem Model
 ↓
Analysis Planner
 ↓
Tool Call
 ↓
Rule Engine
 ↓
Tool Execution
 ↓
Statistical Engine
 ↓
Result
 ↓
LLM Interpretation
 ↓
Finding / Evidence
 ↓
Next Action
```

그리고 단순히 "LLM에게 프롬프트를 어떻게 작성할까?" 수준이 아니라,

**`Orchestrator`가 실제로 어떤 상태를 읽고 → LLM에 무엇을 전달하고 → 어떤 Tool Call을 받아 → Rule Engine에서 어떻게 검증하고 → 실패하면 어떻게 재계획하고 → 결과를 State에 어떻게 저장하는지**

를 Python 클래스와 실행 흐름 수준까지 정의하게 됩니다.

특히 여기서 **Claude Code를 이용해 실제 프로젝트를 개발할 수 있는 `CLAUDE.md`, 개발 작업 순서, 첫 번째 Vertical Slice 구현 방법**까지 연결할 수 있습니다.

즉, **Step 19부터는 설계 결과를 실제 실행 가능한 Agent 코드로 옮기는 단계**로 진입하게 됩니다.

# 2. 설계 기준선 — End-to-End 운영 시나리오

Baseline §36의 18단계 시나리오를 화면과 상태 변화까지 포함해 확장했다. **이 시나리오가 Step 26의 모든 설계 판단의 기준선이다.**

```text
단계                     화면            모드        Analysis State 변화
──────────────────────────────────────────────────────────────────────
① 앱 실행               S-01 홈          Level 0     (빈 세션)
② 데이터 업로드          S-02 데이터      Level 0     dataset_context 생성
③ 데이터 품질 확인       S-03 품질리포트   Level 0     dataset_context.quality
④ 분석 선택             S-04 Navigator   Level 0     problem_model 초안
⑤ Welch t-test 실행     S-05→S-06       Level 0     analysis_history += 1
⑥ 결과·그래프 확인       S-06 결과        Level 0     findings += F-001…
──────────────────────── AI 경계선 ──────────────────────────────────
⑦ [AI 분석] 활성화       S-08 연결설정    Level 0→1   (인증·전송범위 확인)
⑧ AI가 기존 상태 인식    S-07 작업공간    Level 1     기존 state 인계(신규 생성 아님)
⑨ 원인 탐색 계획 제시    S-07 + S-09     Level 1     analysis_plan 초안
⑩ 사용자 승인           S-09 승인게이트   Level 1→2   analysis_plan 확정
⑪ 다단계 분석 실행       S-07 작업공간    Level 2     analysis_history += n
⑫ Finding/Evidence 생성 S-07 + S-10     Level 2     findings / evidence
⑬ 제조적 의미 해석       S-06 ③영역      Level 2     manufacturing_judgment
⑭ Next Best Analysis    S-07 우측 하단   Level 2     next_actions
⑮ 사용자가 추가 분석 선택 S-07 또는 S-05  Level 2 또는 0  (사용자 선택)
⑯ Manual 또는 AI 계속    (양방향)        전환 가능    state 공유·유지
⑰ 최종 Decision         S-10 보드        사용자 확정   final_decision
⑱ Report                S-12 보고서      무관         (산출물)
```

## 2-1. 이 시나리오에서 도출되는 3개의 구조적 요구

1. **AI는 세션을 새로 시작하지 않는다.** ⑧에서 AI가 인계받는 것은 ②~⑥에서 사용자가 이미 만든 상태다. 즉 AI 활성화는 *새 대화 시작*이 아니라 *기존 분석 세션에 Intelligence Layer를 부착*하는 행위다. → DD-013, §8
2. **AI 경계선(⑦)에 인증과 데이터 전송 확인이 동시에 걸린다.** 이 지점이 제품에서 유일하게 "외부로 무언가 나가는" 순간이므로, 인증(§7)과 전송 승인(§12)이 같은 화면에서 처리되어야 한다. [추론]
3. **⑯의 양방향성이 Manual/AI 공존의 핵심이다.** 한 번 AI로 넘어가면 돌아올 수 없는 구조면 Baseline DD-004(LLM은 optional layer)가 사실상 무너진다.

# 3. 사용자와 역할

## 3-1. Primary User 재확인

원 기획서와 Baseline §2가 정의한 Primary User는 **통계 비전문가인 제조 현장 실무자**다. Step 26의 모든 화면 판단은 이 정의를 기준으로 한다. 특히 §7의 인증 설계에서 이 정의가 결정적으로 작용한다 — "AI를 쓰려면 먼저 개인 LLM 계정을 만들어야 한다"는 요구가 Primary User에게 진입장벽이 되는지 여부가 인증 모델 선택의 핵심 판단 기준이기 때문이다.

## 3-2. 3개 역할과 화면 권한 [추론]

| 역할 | 주 사용 모드 | 필요 기능 | AI 사용 |
|---|---|---|---|
| **현장 실무자** | Level 0~1 | Navigator, 표준 분석, 쉬운 해석, 보고서 | 선택적 |
| **공정/품질 엔지니어** | Level 0~3 | 전체 기능, 원인 탐색, Evidence 관리 | 상시 |
| **관리자(품질보증·시스템)** | — | Golden Case 검증, 정책 설정, 감사 로그 | 정책 설정 |

역할 구분이 *제품 기능*으로 필요한지(로그인·권한 체계) 아니면 *화면 밀도 옵션*으로 충분한지는 O-3로 남긴다.

## 5-3. 전이 원칙

**DD-013 · 모드 상향 전이는 자동으로 일어나지 않는다.**
AI가 "이 질문은 복잡하니 제가 Agent 모드로 진행하겠습니다"라고 스스로 승격하지 않는다. 승격은 항상 사용자의 버튼 행동 + 계획 승인으로만 발생한다.
**Reason:** 자율성 확대가 사용자 모르게 일어나면 비용·데이터 전송·분석 범위가 동시에 예고 없이 커진다. Baseline §33이 "Agent 자율 실행 한계"를 미결로 남긴 것에 대한 1차 답변.
**Status:** 확정 제안

**DD-014 · 모든 하향 전이에서 Analysis State는 보존된다.**
AI를 끄거나, 중단하거나, LLM 연결이 끊겨도 dataset_context / analysis_history / findings / evidence는 그대로 유지되며 Manual 모드에서 계속 사용 가능하다.
**Reason:** Baseline DD-001·DD-004의 화면 레벨 구현. LLM 장애가 사용자의 작업 손실로 이어지면 "optional layer"라는 주장은 성립하지 않는다.
**Status:** 확정 제안

# 7. LLM 인증 방식 — 개인 계정 기반 연결

**이 절은 Ian이 제시한 다음 요구사항에 대한 설계 답변이다.**

> "LLM을 연결하는 방식이 여러 가지가 있을 것으로 생각되는데, 내가 생각하는 방식은 LLM을 연결할 때 API가 아닌 계정 로그인 방식으로 진행하는 것이 좋겠습니다. 사용자가 많아 통합 API Key로 인증할 경우 사용 토큰이 공통계정으로 부담될 경우 부담할 부서가 없습니다. 따라서 개인 계정으로 인증받는 형식이 되어야 합니다."

## 7-1. 요구의 핵심을 먼저 분리한다

이 요구에는 서로 다른 두 개의 층이 섞여 있다. 설계할 때는 분리해야 한다.

| 층 | 내용 | 성격 |
|---|---|---|
| **비용 귀속(cost attribution)** | 사용 토큰 비용을 부담할 주체가 명확해야 한다 | **진짜 요구사항** |
| **구현 수단** | "API Key가 아니라 계정 로그인" | 요구를 충족하는 여러 수단 중 하나 |

**중요한 사실 확인:** 비용 귀속은 "계정 로그인"이라는 형식 때문에 해결되는 것이 아니라, **인증 주체가 개인/부서 단위로 분리되어 있기 때문에** 해결된다. 따라서 아래 §7-2의 모델 A(개인별 API Key)도 Ian의 진짜 요구를 완전히 충족한다 — 키가 개인 계정에서 발급되고 그 계정으로 청구되기 때문이다.

반대로 주의가 필요한 지점도 있다. 현재 주요 LLM 공급자의 **개인 구독 상품(월정액 채팅 서비스)** 계정으로 제3자 앱이 로그인하여 그 구독 사용량으로 프로그래밍 호출을 하는 방식은 일반적으로 제공되지 않으며 약관상으로도 허용되지 않는 경우가 많다. 즉 "개인 구독 계정 로그인 = 무료로 쓰던 구독을 앱에서도 쓴다"는 형태는 성립하지 않을 가능성이 높다. 이 부분은 **O-1 결정 전에 실제 공급자 약관·상품 구조를 확인**하는 것을 권한다. [추론 — 일반적 상품 구조에 근거한 판단이며, 특정 공급자의 현재 약관을 직접 확인한 결과는 아님]

## 7-2. 인증 모델 3안

### 모델 A — BYOK (Bring Your Own Key, 개인 API Key 등록)

```text
사용자 ──[자기 계정에서 API Key 발급]──► 앱 설정에 등록
                                          │
                                          ▼
                                   OS 자격증명 저장소
                                   (Windows Credential
                                    Manager / DPAPI)
                                          │
                                          ▼
                                    AI Gateway ──► LLM Provider
                                                    (그 키의 계정으로 청구)
```

| 항목 | 평가 |
|---|---|
| 비용 귀속 | ◎ 개인/부서 계정에 직접 청구 — Ian의 요구 정확히 충족 |
| 현장 사용자 부담 | △ 계정 개설·결제수단 등록 필요 |
| 구현 난이도 | ◎ 낮음. 키 입력 + 암호화 저장 + 연결 테스트 |
| 조직 통제 | △ 조직이 사용량·모델을 통제하기 어려움 |
| 데이터 경로 | 외부 클라우드 |

### 모델 B — 사내 SSO + 사내 LLM Gateway

```text
사용자 ──[회사 계정 로그인 / SSO]──► 사내 LLM Gateway
                                       │  (사번·부서 태깅)
                                       ├──► 사내 LLM (on-premise)
                                       └──► 외부 LLM (조직 계약)
                                              │
                                              ▼
                                       부서별 사용량 집계 → 내부 청구
```

| 항목 | 평가 |
|---|---|
| 비용 귀속 | ◎ 사번·부서 단위 집계로 내부 청구(chargeback) 가능 |
| 현장 사용자 부담 | ◎ 회사 계정만 있으면 됨 — Primary User에게 최적 |
| 구현 난이도 | △ 사내 Gateway·SSO 연동 필요. 앱 단독으로 완결되지 않음 |
| 조직 통제 | ◎ 모델·한도·감사 전부 통제 가능 |
| 데이터 경로 | 사내 LLM이면 외부 유출 없음 → **A-1(데이터 기밀성) 근본 해결** |

### 모델 C — 공용 API Key + 부서 태깅·할당량

Ian이 명시적으로 문제를 제기한 방식이다. 다만 보완형(사용자별 할당량 + 부서 태그 기록 + 월별 리포트)으로는 운용 가능하다. 비교를 위해서만 기재한다.

| 항목 | 평가 |
|---|---|
| 비용 귀속 | △ 사후 정산 방식. "부담할 부서가 없다"는 문제가 그대로 남음 |
| 현장 사용자 부담 | ◎ 없음 |
| 구현 난이도 | ◎ 낮음 |
| 조직 통제 | ○ 가능하나 개인 식별이 약함 |

## 7-3. 권장 설계

**DD-016 · LLM 인증은 사용자 단위(per-user)로 한다. 단일 공용 API Key를 기본 인증 방식으로 채택하지 않는다.**
**Reason:** Ian이 제기한 비용 귀속 문제. 공용 키는 사용 주체와 비용 부담 주체가 분리되어 조직 내 승인 구조와 맞지 않는다.
**Status:** 확정 제안

**DD-017 · MVP는 모델 A(BYOK)를 구현하고, 모델 B(사내 SSO/사내 LLM Gateway)는 동일한 Provider 추상화 뒤의 확장 지점으로만 확보한다.**
**Reason:** 모델 B가 최종적으로 더 우수하지만(현장 사용자 부담 없음 + 데이터 기밀성 해결), 앱 단독으로 완결되지 않고 사내 인프라 구축이 선행되어야 한다. MVP를 사내 인프라 일정에 종속시키지 않기 위해 A를 먼저 구현하고, Provider 인터페이스에 인증 방식을 캡슐화해 B로 교체 가능하게 둔다. [추론]
**Status:** 확정 제안 — 단, 사내에 이미 LLM Gateway가 있거나 구축 계획이 있다면 B 우선이 합리적이므로 **O-1로 Ian 확인 필요**

**DD-018 · 인증정보는 OS 자격증명 저장소에 암호화 저장하며, 설정 파일·로그·분석 세션·보고서 어디에도 평문으로 기록하지 않는다.**
**Reason:** 개인 키가 유출되면 그 개인이 비용과 책임을 진다. 개인 단위 인증을 채택한 이상 보관 책임은 앱이 진다.
**Status:** 확정 제안

# 8. Manual ↔ AI 전환 UX

## 8-1. Manual → AI (상태 인계)

사용자가 S-06(분석 결과)에서 **[AI에게 원인 분석 요청]**을 누르면 AI는 새 대화를 시작하지 않고 다음을 인계받는다.

```text
인계 대상 (AI가 읽는 것)          인계하지 않는 것
─────────────────────────      ─────────────────────
dataset_context (구조·품질)       원본 데이터 행
problem_model                   개인 식별 정보
analysis_history (실행 이력)      설비 고유번호(마스킹 대상)
findings                        API Key 등 인증정보
evidence
사용자가 입력한 맥락 메모
```

AI의 첫 발화는 "무엇을 도와드릴까요?"가 아니라 **인계 상태를 요약한 확인 문장**이어야 한다.

```text
AI: 지금까지 A라인과 B라인의 토크를 Welch t-test로 비교하신 결과를
    확인했습니다. 평균 차이 -2.63 N·m, p<0.001로 통계적으로는
    차이가 있습니다.

    이 차이가 왜 생겼는지 확인하려면 Model 구성 차이부터 볼 것을
    제안합니다. 아래 계획을 확인해 주세요.
```

[추론] 이 한 문장이 "AI가 내 작업을 이어받았다"는 것을 사용자가 확인하는 유일한 근거다. 여기서 AI가 이미 수행된 분석을 다시 묻거나 잘못 요약하면 사용자는 이후 결과 전체를 신뢰하지 않는다.

## 8-2. AI → Manual

AI가 제안한 다음 분석마다 **[이 분석 직접 실행]** 버튼을 둔다. 누르면 S-05(분석 설정)로 이동하되 변수·그룹·옵션이 미리 채워진 상태로 열린다. 사용자는 확인 후 자기 손으로 실행한다.

**DD-019 · AI가 제안한 모든 분석은 Manual 화면에서 동일하게 실행 가능해야 한다.**
**Reason:** Baseline DD-002(동일 Statistical Engine 공유)의 UX 레벨 요구. AI만 실행할 수 있는 분석이 하나라도 존재하면 Manual 모드는 열등한 대체재가 되고, 사용자는 AI 없이 작업을 완결할 수 없게 된다.
**Status:** 확정 제안

## 8-3. AI 도중 종료

Agent 실행 중 [중단]을 누르면 진행 중이던 Tool 호출은 완료까지 기다린 후(결과 손실 방지) 정지하고, 그때까지의 Finding·Evidence를 모두 보존한 채 Level 0으로 내려온다. 중단 시점은 analysis_history에 기록한다.

# 10. Analysis Trace

## 10-1. 표시 원칙

**DD-021 · Analysis Trace는 실제로 실행된 Tool 호출과 그 결과만 표시한다. LLM의 내부 추론(chain-of-thought)은 표시하지 않는다.**
**Reason:** 내부 추론은 검증 불가능하고 틀릴 수 있으며, 사용자가 그것을 근거로 오해할 위험이 있다. 반면 Tool 실행 이력은 재현 가능한 사실이다. Baseline §8과 동일한 방향이며 이를 규칙으로 확정한다.
**Status:** 확정 제안

## 10-2. Trace 항목의 4가지 상태

```text
✓  완료   — Tool 실행 완료, 결과 있음 (클릭 시 상세 결과 표시)
●  진행중 — 현재 실행 중
○  대기   — 승인된 계획에 있으나 아직 미실행
⚠  경고   — 실행되었으나 Rule Engine 경고 동반 (클릭 시 경고 내용)
✕  차단   — Rule Engine이 차단 (클릭 시 차단 사유와 대안)
```

`✕ 차단` 상태를 사용자에게 그대로 보여주는 것이 중요하다. Rule Engine이 조용히 대안으로 우회하면 사용자는 왜 자기가 요청한 분석이 수행되지 않았는지 알 수 없다.

## 10-3. 다중비교·측정시스템 관련 Trace 표기 (검토 항목 연계)

RUN-030~032 검토에서 제기된 두 항목을 Trace의 표시 요구사항으로 연결한다.

**DD-022 · 여러 후보 요인을 동시에 검정하는 스크리닝 단계는 Trace에 그 사실과 다중비교 보정 상태를 명시한다.**

```text
✓ 후보 요인 스크리닝 (5개 요인 동시 검정)
    Machine · Model · Shift · Operator · 공정온도
    ⚠ 다중비교 보정 적용됨 (Benjamini-Hochberg, FDR 0.05)
       보정 전 유의: 3개 → 보정 후 유의: 2개
```

**Reason:** 서로 다른 5개 요인을 각각 독립 검정하면 우연히 유의하게 나오는 요인이 생길 확률이 올라간다. 이 프로젝트가 일관되게 강조해 온 "인과 과장 방지"와 같은 계열의 문제이며, 화면에 보정 여부가 표시되지 않으면 사용자는 보정 전 결과를 그대로 원인 후보로 받아들인다. 보정 방법 자체(Bonferroni / Benjamini-Hochberg 등)의 선택은 Step 18(Rule Engine)의 Method Rules에서 확정한다.
**Status:** 확정 제안(UX 요구), 통계 방법은 Step 18 연계

**DD-023 · 개선 전후 비교(UC-07 계열)는 계획 승인 단계에서 측정시스템 동일성 확인을 선행 질문으로 포함한다.**

```text
┌────────────────────────────────────────────────┐
│ 확인이 필요합니다                                │
│                                                │
│ 개선 전후를 비교하기 전에 확인해 주세요.          │
│                                                │
│ 개선 전과 후의 측정 방법이 동일합니까?            │
│  ○ 동일합니다                                   │
│  ○ 측정기/측정자/방법이 바뀌었습니다              │
│  ○ 모르겠습니다                                 │
│                                                │
│ ⓘ 측정 방법이 바뀌면, 관측된 차이가 공정 개선     │
│   때문인지 측정 차이 때문인지 구분할 수 없습니다.  │
└────────────────────────────────────────────────┘
```

**Reason:** 측정시스템분석(MSA, Measurement System Analysis)을 완전한 분석 모듈로 넣는 것은 Phase 2 사안이지만, "측정 방법이 바뀌었는가"를 묻는 것은 비용이 거의 들지 않으면서 개선 효과 검증의 가장 흔한 오류를 막는다. "바뀌었습니다"를 선택하면 결과 화면에 해당 주의문을 고정 표시한다. [추론 — 완전한 Gauge R&R 대체가 아니라 최소 게이트로서의 제안]
**Status:** 확정 제안

# 11. S-06 — 결과 화면의 3층 구조

Baseline §9의 ①통계결과 ②AI해석 ③제조판단 분리를 화면 규칙으로 확정한다.

| 층 | 출처 | AI OFF 시 | 내용 |
|---|---|---|---|
| ① 통계 결과 | Statistical Engine | **표시** | n, 평균, SD, 차이, 검정통계량, df, p, CI, 효과크기, 진단, 경고 |
| ② AI 해석 | LLM | 숨김 | 자연어 설명. Level 1~3 선택형 상세도 |
| ③ 제조 판단 | Rule + 제조 지식 + 통계 결과 | **표시** | 규격 대비 위치, 이력 대비 변화, 제조적 중요도, 인과 관련 주의 |

## 11-1. 3층 분리가 지켜야 할 규칙

1. **②는 ①을 수정할 수 없다.** LLM이 서술을 위해 수치를 재계산하거나 반올림을 바꾸지 않는다.
2. **②가 없어도 ①③만으로 판단이 완결되어야 한다.** AI OFF 사용자가 결론을 못 내리는 화면이면 설계 실패다.
3. **③에는 항상 인과 관련 경계 문구가 붙는다.** "차이가 있다"와 "그것이 원인이다"는 화면에서 분리된다.

## 11-2. Evidence 표시와 재검증 (검토 항목 연계)

Evidence는 E0~E4 수준과 함께 **생성 시점·근거 데이터 버전**을 표시한다.

```text
┌─────────────────────────────────────────────────┐
│ Evidence  E2 — 통계적 차이/연관 확인됨            │
│ 근거: welch_t_test (2026-09-12), dataset v3      │
│ 관련: F-001, F-005                               │
│ ⓘ 공정 조건이나 설비가 변경되면 재확인이 필요합니다│
└─────────────────────────────────────────────────┘
```

Evidence를 **하향 조정하거나 만료시키는 규칙**(새 데이터가 기존 E2~E3 결론을 반박할 때의 처리)은 아직 정의되지 않았다. 화면에는 재확인 안내만 두고, 규칙 자체는 Step 29(Schema Contract)에서 Evidence에 `valid_until` 또는 `revalidation_condition` 필드를 둘지와 함께 결정한다. → **O-4**

# 14. 오류·저하(Degradation) UX

**핵심 원칙: LLM 실패는 앱 실패가 아니다. 모든 실패 화면은 "Manual로 계속하기" 경로를 반드시 제공한다.**

| 상황 | 사용자에게 보이는 것 | 복구 경로 |
|---|---|---|
| LLM 응답 지연 | "AI가 분석을 검토하고 있습니다" + 경과 시간 + [중단] | 대기 또는 중단 |
| LLM 연결 실패 | 배너: "AI에 연결할 수 없습니다. 수동 분석은 계속 사용할 수 있습니다." | [다시 시도] / [수동으로 계속] |
| 인증 실패·키 만료 | "AI 연결 정보를 확인해 주세요" | S-08로 이동 |
| 사용 한도 초과 | "이 계정의 사용 한도에 도달했습니다" | [수동으로 계속] / S-08 |
| LLM 응답 형식 오류 | 사용자에게는 "AI 응답을 처리하지 못했습니다" 1회 재시도 후 표시 | [다시 시도] / [수동으로 계속] |
| Rule Engine 차단 | Trace에 `✕` + 차단 사유 + 대안 제시 | 대안 실행 또는 조건 변경 |
| 데이터 품질 차단 | S-03에서 차단 사유와 필요한 조치 | 데이터 보정 후 재시도 |
| Statistical Engine 오류 | "분석을 완료하지 못했습니다" + 오류 코드 | 조건 변경 |

## 14-1. 저하 시 화면 규칙

**DD-025 · LLM 관련 오류는 작업 흐름을 차단하는 모달이 아니라 배너로 표시하며, 진행 중이던 분석 결과를 화면에서 지우지 않는다.**
**Reason:** 모달은 사용자를 멈춰 세우고, 화면 초기화는 작업 손실로 느껴진다. LLM은 optional layer이므로 그 실패도 optional하게 처리되어야 한다.
**Status:** 확정 제안

# 15. 세션 저장·복구 (S-11)

## 15-1. 저장 원칙

- 분석 1건이 완료될 때마다 자동 저장한다(명시적 저장 버튼도 제공).
- 저장 단위는 `AnalysisSession`이며, 데이터 원본이 아니라 **데이터 참조 + 분석 상태**를 저장한다.
- AI 대화 내용과 Analysis State를 함께 저장하되, 인증정보는 저장 대상에서 제외한다(DD-018).

## 15-2. 복구 화면

```text
┌──────────────────────────────────────────────────────┐
│ 이어서 분석하기                                        │
├──────────────────────────────────────────────────────┤
│ ● A라인/B라인 토크 차이          2026-09-12 14:20      │
│   분석 8회 · Finding 5 · Evidence E2 · 가설 2          │
│   마지막: 동일 Model 내 재비교 (진행 중 중단)           │
│                              [ 이어하기 ] [ 보고서 ]   │
│                                                      │
│ ○ 3호기 불량률 증가 원인          2026-09-11 09:05     │
│   분석 12회 · Finding 7 · Evidence E3 · 가설 3         │
│                              [ 이어하기 ] [ 보고서 ]   │
└──────────────────────────────────────────────────────┘
```

세션 데이터를 로컬에만 저장할지 사내 서버에 저장할지는 **O-4**로 남긴다. 사내 서버 저장은 세션 공유·인수인계에 유리하지만 접근통제·보존기간 정책이 선행되어야 하며 이는 Step 28의 범위다.

# 0. 질문에 대한 답 — 아니요, 그렇게 되어 있지 않습니다

> "웹 앱이라 사용자는 앱이 등록되어 있는 회사 내 서버에 접속하게 됩니다. 모든 분석과 결과는 서버 사이드 쪽에서 렌더링이 됩니다. 그런데 LLM 모델은 개인 계정으로 로그인하여 개인 로컬 PC에서 로딩되어 연동되도록 해야 하는데 그렇게 설계되어 있는지 궁금합니다."

**현재 설계는 서버 사이드 호출입니다.** Step 29 §2-1의 구조도에서 AI Gateway는 서버 영역에 있고, Step 29 §3-2(DD-062)는 다음과 같이 정했습니다.

> "개인 LLM 자격증명은 **서버 측 암호화 저장소**에 보관하며 … 복호화는 AI Gateway의 호출 직전에만 이루어진다."

즉 **개인 자격증명을 서버가 보관했다가 서버가 LLM을 호출하는 구조**입니다. Ian이 의도한 "개인 로컬 PC에서 로딩되어 연동"과 다릅니다.

이 문서에서 클라이언트 사이드로 전환합니다. **결과적으로 더 나은 구조입니다** — 그 이유는 §2에서 설명합니다.

# 1. 두 방식의 비교

## 1-A. 서버 사이드 호출 (현재 설계)

```text
브라우저 ──► 앱 서버 ──► [자격증명 복호화] ──► LLM
                 │
              개인 자격증명을 서버가 보관
```

## 1-B. 클라이언트 사이드 호출 (전환 후)

```text
브라우저 ──────────────────────────────────► LLM
   │        개인 계정 인증, 자격증명은 이 PC에만
   │
   └──► 앱 서버 (분석·통계·Rule·State·화면 렌더링)
```

## 1-C. 비교

| 항목 | A 서버 사이드 (현재) | **B 클라이언트 사이드 (전환)** |
|---|---|---|
| 개인 자격증명 보관 | **서버 암호화 저장소** | **사용자 PC에만** |
| 자격증명 유출 시 영향 범위 | 서버 저장소 전체 = 전 사용자 | 해당 사용자 1명 |
| 개인 계정 로그인 경험 | 앱에 키를 등록 | **평소 쓰던 계정으로 로그인** |
| 서버의 책임 | 타인 자격증명 보관 책임 발생 | 보관하지 않음 |
| 네트워크 | 서버 → 외부 LLM (사내망 방화벽 정책 필요) | 사용자 PC → LLM |
| 브라우저 종료 시 | Agent 분석 계속 진행 | **진행 불가** ← 유일한 실질 단점 |
| 사용량 집계 | 서버가 직접 측정 | 클라이언트가 보고 |
| 구현 난이도 | 낮음 | 중간 (§6 확인 필요) |

**전환이 타당한 핵심 이유는 자격증명 보관 책임이 사라진다는 것입니다.** 개인 계정 비용이 개인에게 귀속되는 구조(Step 29 DD-061)에서 회사 서버가 전 직원의 LLM 자격증명을 보관하는 것은, 보관 자체가 위험이고 사용자 입장에서도 자기 계정 정보를 회사 서버에 맡기는 셈이 됩니다. 클라이언트 사이드는 그 문제를 **구조적으로 제거**합니다.

# 2. 전환 결정

**DD-098 · LLM 호출은 사용자의 브라우저(개인 PC)에서 수행한다. 서버는 개인 LLM 자격증명을 보관하지 않는다.**

**Reason:** ① 자격증명 보관 책임 제거 — 서버가 보관하지 않는 것은 유출될 수 없다. ② 개인 계정 인증(DD-061)과 자연스럽게 부합 — 사용자가 평소 쓰는 계정으로 자기 브라우저에서 로그인한다. ③ 비용·속도 제한이 개인 단위로 적용되어 한 사용자의 대량 호출이 다른 사용자에게 영향을 주지 않는다(Step 29 §4-6에서 의도했던 격리가 물리적으로 보장된다). ④ 사내 서버에서 외부로 나가는 트래픽이 줄어 방화벽 정책이 단순해진다.
**Status:** 확정 제안 — **Step 29 DD-062를 폐기하고 대체**

│  │                  │   │  · 자격증명 로컬 보관      │  │
│  │                  │   │  · 요청 전달 / 응답 회수   │  │

# 4. 핵심 원칙 — 브라우저는 전달자이지 작성자가 아니다

**DD-099 · 브라우저는 서버가 만들어 준 요청 패키지를 LLM에 전달하고 응답을 서버로 회송하는 역할만 한다. 브라우저가 프롬프트를 조립하거나 데이터를 추가하지 않는다.**

이것이 전환의 **안전성을 유지하는 유일한 장치**입니다. 만약 브라우저가 프롬프트를 직접 만들면 Step 27·28에서 설계한 통제가 전부 무력화됩니다.

```text
서버에서 수행 (변경 없음)              브라우저에서 수행 (신규)
────────────────────────────       ──────────────────────────
· Context Builder (Step 19)         · 개인 계정 인증
· Context Filter (DD-032)           · 요청 패키지를 LLM에 전송
· 데이터 분류·가명화 (Step 28)        · 응답 수신
· Prompt Stack 조립 (Step 7)        · 응답 + 사용량을 서버로 회송
· 전송범위 강제 (S1/S2/S3)
· 승인 확인 (ApprovalGrant)
· 모델 선택
· 감사 로그 기록
```

**Reason:** 가명화·식별자 제거·전송범위 판정은 **원본 데이터에 접근할 수 있는 쪽에서만 수행 가능**합니다. 원본은 서버에 있으므로 필터도 서버에 있어야 합니다. 브라우저에 필터를 두면 원본을 브라우저로 내려보내야 하고, 그 순간 Step 28의 설계가 무너집니다.

따라서 서버가 브라우저에 넘기는 것은 **이미 여과가 끝난, 그대로 전송해도 되는 패키지**입니다.
**Status:** 확정 제안

## 4-1. 요청 패키지

```jsonc
{
  "request_id": "REQ-20260912-00137",
  "session_id": "AS-20260912-001",
  "call_type": "PLANNING",
  "target": {"provider": "…", "model": "…"},   // 서버가 선택
  "payload": { /* 여과 완료된 messages·tools·schema */ },
  "constraints": {"timeout_ms": 65000, "max_output_tokens": 4096},
  "issued_at": "…",
  "expires_at": "…"                             // 단시간 유효
}
```

`payload`는 **서버에서 이미 Context Filter를 통과한 내용**이며 브라우저는 이를 수정하지 않고 전송합니다.

## 4-2. 응답 회송

```jsonc
{
  "request_id": "REQ-20260912-00137",
  "status": "OK",                  // OK | ERROR | TIMEOUT | AUTH_REQUIRED
  "response": { /* LLM 원 응답 */ },
  "usage": {"input_tokens": 3120, "output_tokens": 480},
  "latency_ms": 4270,
  "error": null
}
```

**DD-100 · 서버는 브라우저가 회송한 LLM 응답을 신뢰하지 않고, 기존과 동일하게 스키마 검증 → Rule Engine 검증 → 승인 확인을 거친 뒤에만 Tool을 실행한다.**
**Reason:** 응답이 클라이언트를 경유하므로 이론적으로 변조가 가능합니다. 그러나 이는 **새로운 위험이 아닙니다** — LLM 응답은 원래부터 신뢰하지 않는 입력이었고(Step 19 §19-9 Structured Output 강제, Step 18 Rule Engine, Step 27 §11 Prompt Injection 방어), 그 검증 체계가 그대로 작동합니다. 변조된 응답이 할 수 있는 최대치는 **선언된 Tool 집합 안에서 승인된 범위의 분석을 요청하는 것**뿐이며, 그것은 사용자 본인이 Manual로도 할 수 있는 일입니다.
**Status:** 확정 제안

# 5. Orchestrator 루프의 변화

Agent 분석은 LLM 호출과 Tool 실행을 반복합니다. LLM 호출이 브라우저를 경유하면 루프가 서버-브라우저를 왕복합니다.

```text
[서버] Analysis State 로드
   │
[서버] Context Builder → Context Filter → 요청 패키지 생성
   │
   ├──────────────► [브라우저] LLM 호출 ──► LLM
   │                     │
   │◄────────────────────┘ 응답 회송
   │
[서버] 스키마 검증 → Rule Engine → 승인 확인
   │
[서버] Tool 실행 → Result Validator → State 갱신
   │
   └──► 다음 판단이 필요하면 반복
```

**DD-101 · Orchestrator는 서버에 남는다. 브라우저는 루프의 참여자가 아니라 LLM 호출 구간의 전달 경로다.**

State·Rule·Tool·Statistical Engine이 모두 서버에 있으므로 Orchestrator가 브라우저로 내려갈 이유가 없습니다. 브라우저에는 판단 로직이 존재하지 않습니다.
**Status:** 확정 제안

# 6. 제약과 대응 — 브라우저 종료 문제

**이 전환의 유일한 실질적 단점입니다.** 정직하게 기술합니다.

Step 29 §5-6은 "브라우저 종료·새로고침 시에도 서버 작업은 계속된다"고 정했습니다. **클라이언트 사이드 호출에서는 LLM이 필요한 단계는 진행할 수 없습니다.** 브라우저가 없으면 호출할 경로가 없기 때문입니다.

**DD-102 · 브라우저가 닫히면 LLM 호출이 필요한 단계에서 세션은 `PAUSED`로 전환된다. LLM이 필요 없는 단계(통계 계산·보고서 생성·파싱)는 서버에서 계속 진행된다.**

| 작업 | 브라우저 종료 시 |
|---|---|
| 업로드 파싱(T-07) | **계속 진행** — LLM 불필요 |
| Manual 통계 분석 | **계속 진행** |
| 보고서 생성 | **계속 진행** |
| 승인된 계획의 Tool 실행 구간 | **계속 진행** — 이미 계획이 확정된 구간은 LLM 없이 실행 가능 |
| LLM 판단이 필요한 단계 (Planning/Interpretation/NBA) | **PAUSED** |

재접속 시:

```text
이어서 분석하기
● A라인/B라인 토크 차이
  분석 8회 · Finding 5 · Evidence E2
  ⏸ 3단계까지 완료 후 대기 중 (AI 연결이 필요합니다)
                                [ 이어하기 ] [ 보고서 ]
```

**이 제약이 실제로 큰 문제인가?** 대체로 아닙니다. Agent 분석은 사용자가 화면을 보며 승인하고 결과를 확인하는 대화형 작업이고(Step 26 §12 승인 매트릭스), 승인 대기 자체가 이미 브라우저 존재를 전제합니다. 오히려 **Step 29 §5-8에서 정한 승인 대기 30분 타임아웃과 자연스럽게 일치**합니다.

다만 Step 29 §5-6의 표는 이 내용으로 개정되어야 합니다.

# 7. 사용량·감사 처리

| 항목 | 전환 후 처리 |
|---|---|
| 토큰 사용량 | 브라우저가 응답과 함께 회송 → 서버가 `UsageRecord`에 기록 |
| 신뢰도 | 클라이언트 보고이므로 이론적으로 조작 가능. **다만 개인이 자기 비용을 부담하는 구조이므로 축소 보고의 유인이 없다**(축소해도 실제 청구는 공급자가 한다) |
| 승인 한도 | 서버가 집계값으로 경고·차단(DD-063 유지). 실제 정산은 공급자 콘솔이 최종 |
| 감사 로그 | 서버가 기록(Step 27 §10-1 그대로). `request_id`로 요청-응답 대응 |
| 누락 처리 | 브라우저가 응답을 회송하지 못하고 종료되면 해당 호출은 `status=UNKNOWN`으로 기록하고 사용량은 미상으로 표시 |

**DD-103 · 사용량은 클라이언트 보고를 기준으로 집계하되, 앱의 집계값은 참고치이며 최종 정산 근거가 아님을 관리자 콘솔과 사용자 화면에 명시한다.**
**Reason:** 실제 과금은 공급자가 개인 계정에 부과합니다. 앱의 집계를 정산 근거로 제시하면 불일치 시 분쟁이 생깁니다. 앱의 역할은 **한도 소진 전에 알려주는 것**이지 청구서를 만드는 것이 아닙니다.
**Status:** 확정 제안

# 8. 확인이 필요한 기술 사항

| ID | 확인 사항 | 영향 |
|---|---|---|
| **확인 I** | **브라우저에서 해당 LLM 공급자 API를 직접 호출할 수 있는가**(CORS 허용 여부, 브라우저 호출 지원 여부) | 불가하면 §8-1의 대안 필요 |
| **확인 J** | 개인 계정 인증을 브라우저에서 유지하는 방식(토큰 저장 위치·만료·갱신) | 구현 방식 |
| **확인 K** | 사내망에서 사용자 PC의 외부 LLM 접근이 허용되는가 | 불가하면 사내 Gateway 경유 필요 |

## 8-1. 확인 I가 불가한 경우의 대안

브라우저에서 직접 호출이 막히는 경우 두 가지 대안이 있습니다.

| 대안 | 설명 | 평가 |
|---|---|---|
| **(a) 로컬 커넥터** | 사용자 PC에 소형 연결 프로그램을 설치하고 브라우저가 이를 경유 | 자격증명이 여전히 로컬에 남아 DD-098의 이점 유지. 단 설치가 필요해 웹앱의 장점 일부 상실 |
| **(b) 서버 중계(현재 설계로 복귀)** | 서버가 자격증명을 보관하고 호출 | DD-098의 이점 상실. **최후 수단** |

**DD-098의 설계는 (a)로도 성립합니다.** 핵심은 "자격증명이 서버에 없다"이지 "브라우저가 직접 호출한다"가 아니기 때문입니다. 따라서 확인 I의 결과에 따라 전송 주체만 브라우저 ↔ 로컬 커넥터로 바뀌며, **서버 측 설계(§4의 Relay 원칙, §5의 Orchestrator 위치)는 어느 쪽이든 동일합니다.**

# 0. 이 문서의 위치

**결론부터: Step 27은 "무엇을 어떤 범위로 내보내는가"의 구조를 만들었고, Step 28은 "그 범위 안에서 무엇이 민감한 데이터인지 앱이 어떻게 판별하고 무엇을 지우는가"를 정한다.**

## 0-1. Step 27이 남긴 구멍

Step 27 §6-3은 전송범위를 S1/S2/S3로 정의하면서 S2에 이렇게 적었다.

> 식별자 필드 | 마스킹 또는 제거 (사번·작업자명·설비 고유번호·시리얼 등 — **판별 규칙은 Step 28**)

즉 "식별자는 지운다"는 규칙은 있으나 **앱이 어떤 컬럼을 식별자로 판단하는지는 정해지지 않았다.** 업로드된 Excel의 `Operator` 컬럼과 `Torque` 컬럼을 앱이 구분하지 못하면 §6-3의 정책은 실행되지 않는다. 이 문서 §3이 그 판별 규칙이다.

## 0-2. 이 Step이 답하는 미결 항목

| ID | 항목 | 본 문서 |
|---|---|---|
| O-3 | 사용자 권한 체계 도입 여부 | §6-1 |

## 0-3. 이 문서가 다루지 않는 것 — 법적 판단

# 1. 설계 전제 — 이 앱의 데이터 위험은 어디에 있는가

제조 통계 분석 앱의 데이터 위험은 일반적인 업무용 앱과 다르다. 세 가지가 특징적이다.

## 1-1. 위험의 중심은 개인정보가 아니라 영업비밀이다

이 앱이 다루는 데이터의 대부분은 **공정 규격·수율·불량률·설비 구성**이다. 작업자 사번이 포함될 수 있지만 양적으로는 소수다. 반면 "이 회사의 A라인 토크 규격은 170±20이고 불량률은 3.1%"는 경쟁사에 그대로 의미가 있는 정보다.

따라서 보호 우선순위는 다음과 같다. [추론]

```text
① 공정 규격·수율·불량률·설비 구성   ← 가장 큰 위험, 양도 많음
② 고객·모델 연계 정보               ← 계약상 의무가 걸릴 수 있음
③ 작업자 식별정보                   ← 법적 요건이 명확한 영역
```

기존 설계가 "원본 데이터 전송 금지"에 집중해 온 것은 타당하나, **집계 통계량만 보내도 ①은 상당 부분 노출된다**는 점이 충분히 다뤄지지 않았다. Step 27 §6-3의 S1 payload에는 `spec: {target, lsl, usl}`과 그룹별 평균·표준편차가 그대로 들어 있다. 이 문제는 §2-3에서 정면으로 다룬다.

## 1-2. 분석 가치와 식별성은 분리할 수 있다

"작업자별로 토크 차이가 있는가"는 반드시 분석해야 하는 질문이다. 그러나 그 분석에 **작업자가 누구인지는 필요하지 않다.** `김○○`이 `Operator_03`이어도 통계 결과는 완전히 동일하다.

이 분리가 이 문서의 핵심 설계 원리다(§4).

## 1-3. 제조 현장의 PC는 공용인 경우가 많다

Step 26·27에서 확정한 개인 단위 인증(DD-016)은 "1인 1 PC"를 암묵적으로 가정한다. 그러나 라인 사무실의 공용 PC에서 여러 작업자가 같은 Windows 계정을 쓰는 상황은 제조 현장에서 흔하다. 이 경우 개인 자격증명이 사실상 공유되어 **비용 귀속 설계가 무너진다.** §6-2에서 다룬다.

# 2. 데이터 분류 (Data Classification)

## 2-1. 5개 분류

**DD-040 · 앱이 다루는 데이터를 5개 등급으로 분류하고, 모든 외부 전송 판단은 이 분류를 기준으로 한다.**

| 등급 | 명칭 | 예시 | 외부 클라우드 LLM |
|---|---|---|---|
| **C1** | 구조 정보 | 변수 유형, 행 수, 결측률, 분석 방법명, 검정통계량·p-value·효과크기 | 허용 |
| **C2** | 공정 측정값(집계) | 그룹별 평균·표준편차·분위수, 상관계수, 회귀계수 | 조건부 허용(기본 허용) |
| **C3** | 공정 기밀 | 규격(Target/LSL/USL), 수율·불량률, 공정조건 설정값, 설비 구성·대수, 생산량 | **조건부 — 기본 허용, 설정으로 차단 가능(§2-3)** |
| **C4** | 개인 식별정보 | 사번, 성명, 교대조+라인 조합으로 개인이 특정되는 경우 | **금지 — 가명화 후에만 전송** |
| **C5** | 고객·계약 정보 | 고객사명, 고객 모델 코드, 납품 사양, 계약 조건 | **금지** |

**Reason:** 전송범위(S1/S2/S3)는 *양*의 통제이고 데이터 분류는 *종류*의 통제다. 두 축이 모두 필요하다 — "집계 통계량만 보낸다"(양)는 규칙은 그 집계 통계량이 고객사 모델별 수율(C5+C3)일 때 아무것도 보호하지 못한다.
**Status:** 확정 제안

| | C1 구조 | C2 집계 | C3 공정기밀 | C4 개인 | C5 고객 |
|---|---|---|---|---|---|
| **S1 결과만** | ○ | ○ | △ 설정 | 가명만 | ✕ |
| **S2 일부 데이터** | ○ | ○ | △ 설정 | 가명만 | ✕ |

**C4는 어떤 전송범위에서도 원문이 나가지 않는다.** S3(원본 전송)이 허용된 사내 LLM 환경에서도 가명화는 유지한다 — 분석에 필요하지 않기 때문이다(§1-2).

## 2-3. C3(공정 기밀)의 딜레마

규격값은 이 앱의 **제조 판단 기능 자체의 전제**다. Step 26 §11의 ③제조 판단 층은 "규격 대비 어디에 있는가"를 말하는 것이 핵심 가치인데, LSL/USL을 전송하지 않으면 LLM은 "통계적으로 다르다"까지만 말할 수 있고 "규격 내이므로 당장 조치는 불필요하다"는 판단을 할 수 없다.

세 가지 선택지가 있다.

| 방식 | 제조 판단 품질 | 기밀 노출 |
|---|---|---|
| (a) 규격 실값 전송 | 완전 | 규격 그대로 노출 |
| (b) **상대값 변환 전송** | 거의 완전 | 절대 수치 비노출 |
| (c) 규격 미전송 | 제한 — ③층 축소 | 없음 |

**(b) 상대값 변환**이 실질적 해법이다. [추론]

```text
원본:   Target=170, LSL=150, USL=190, 평균=166.252, SD=5.233

변환:   상대위치 = (평균 - Target) / (USL - LSL) = -0.094
        규격폭 대비 산포 = SD / (USL - LSL)      =  0.131
        규격 이탈률 추정 = 0.31%
        → "평균이 목표보다 규격폭의 9.4% 낮은 쪽에 있고,
           산포는 규격폭의 13.1% 수준"
```

LLM은 이 정보만으로 "규격 내이나 목표 대비 편중, 산포는 관리 가능 수준"이라는 제조 판단을 정확히 수행할 수 있으며, **토크 규격이 150~190이라는 사실은 전송되지 않는다.**

**DD-041 · C3 공정 기밀은 가능한 경우 절대값 대신 규격 정규화된 상대값으로 변환해 전송한다. 변환이 불가능한 항목은 설정으로 전송 여부를 선택하게 하고, 미전송 시 제조 판단 층이 제한된다는 사실을 화면에 표시한다.**
**Status:** 확정 제안

# 3. 식별자 판별 규칙 — Step 27 인계 핵심 항목

## 3-1. 3계층 판별

```text
업로드된 데이터
      │
      ▼
┌─────────────────────────────────────────┐
│ Layer 1  사용자 선언                     │  신뢰도 ★★★
│  데이터 업로드 시 변수 역할 지정          │
│  (반응변수 / 요인 / 식별자 / 시간 / 규격) │
└──────────────────┬──────────────────────┘
                   │ 미지정 컬럼만 다음 층으로
                   ▼
┌─────────────────────────────────────────┐
│ Layer 2  컬럼명 사전 매칭                 │  신뢰도 ★★
│  사번·사원·작업자·담당자·성명·이름         │
│  operator·employee·emp_id·worker·name    │
│  serial·시리얼·고유번호·바코드·LOT        │
│  고객·customer·client·거래처              │
└──────────────────┬──────────────────────┘
                   │ 미매칭 컬럼만 다음 층으로
                   ▼
┌─────────────────────────────────────────┐
│ Layer 3  값 패턴 휴리스틱                 │  신뢰도 ★
│  · 고유값 비율 > 0.7 인 문자열 컬럼        │
│  · 사번 형식 정규식 (예: 영문+숫자 조합)   │
│  · 한글 2~4자 이름 형태의 비율이 높음      │
└──────────────────┬──────────────────────┘
                   ▼
           미분류 문자열 컬럼
                   │
                   ▼
        ┌──────────────────────┐
        │  fail-closed          │
        │  식별자 후보로 간주     │
        │  → 전송 제외 + 사용자   │
        │     확인 요청          │
        └──────────────────────┘
```

**DD-042 · 식별자 판별은 사용자 선언 → 컬럼명 사전 → 값 패턴의 3계층으로 수행하며, 어느 층에서도 분류되지 않은 문자열 컬럼은 식별자 후보로 간주하여 전송에서 제외한다(fail-closed).**
**Reason:** 자동 탐지는 반드시 놓치는 경우가 있다. 놓쳤을 때의 두 방향 오류는 비용이 전혀 다르다 — 식별자를 일반 컬럼으로 오판하면 개인정보가 외부로 나가고(복구 불가), 일반 컬럼을 식별자로 오판하면 분석 정보가 일부 줄어든다(사용자가 정정 가능). 따라서 불확실할 때는 항상 후자를 택한다.
**Status:** 확정 제안

## 3-2. 사용자 선언을 1순위로 두는 이유

Layer 1이 가장 중요하다. 데이터 업로드 화면(S-02)에서 변수 역할을 지정하는 단계는 **분석 정확도를 위해서도 이미 필요한 단계**다(반응변수와 요인을 구분해야 분석 방법이 정해진다). 여기에 "식별자" 역할을 하나 추가하면 개인정보 판별이 부가 비용 없이 해결된다.

```text
┌────────────────────────────────────────────────┐
│ 변수 역할 확인                                   │
├────────────────────────────────────────────────┤
│ Timestamp   [ 시간          ▾ ]                 │
│ Model       [ 요인(범주)     ▾ ]                 │
│ Line        [ 요인(범주)     ▾ ]                 │
│ Machine     [ 요인(범주)     ▾ ]                 │
│ Operator    [ 식별자         ▾ ] ⓘ 가명 처리됨   │
│ Torque      [ 반응변수(수치)  ▾ ]                 │
│ Defect_Flag [ 반응변수(이분형)▾ ]                 │
│ Target      [ 규격           ▾ ]                 │
│                                                │
│ ⓘ 식별자로 지정된 변수는 분석에는 사용되지만      │
│   AI에는 가명(Operator_01 등)으로만 전달됩니다.   │
└────────────────────────────────────────────────┘
```

## 3-3. 자동 탐지 결과의 표시

Layer 2·3이 식별자로 판정한 컬럼은 **사용자에게 알리고 정정할 수 있게 한다.** 조용히 처리하면 사용자는 왜 그 변수가 분석에서 다르게 취급되는지 모른다.

```text
⚠ 다음 변수를 식별정보로 판단했습니다: Operator, Serial_No
   AI 분석 시 가명으로 대체됩니다.       [ 확인 ] [ 변경 ]
```

# 4. 가명화 (Pseudonymization)

## 4-1. 원리 — 분석 가치는 유지하고 식별성만 제거

```text
로컬 (앱 내부)                       LLM에 전달되는 것
──────────────────────────────    ─────────────────────
Operator = "김○○"   ─┐
                     ├─ 매핑 ──►   Operator = "OP_01"
Operator = "이○○"   ─┘            Operator = "OP_02"

매핑 테이블은 세션 내에만 존재하고
파일·로그·전송 대상 어디에도 저장되지 않음
```

가명화 후에도 다음 분석은 **완전히 동일하게 동작한다.**

- 작업자별 토크 평균 비교 (ANOVA)
- 작업자 × 설비 교차 분석
- 특정 작업자의 이상값 탐지
- 작업자를 교란요인으로 통제한 재비교

사용자 화면에는 실명이 표시되고 LLM에는 가명만 전달되므로, 사용자는 "OP_01이 누구인지" 알기 위해 별도 조회를 할 필요가 없다.

**DD-043 · C4 식별정보는 세션 단위 일관 가명으로 치환하여 LLM에 전달하고, 가명↔원문 매핑 테이블은 세션 메모리에만 유지하며 파일·로그·전송 payload 어디에도 기록하지 않는다. 화면에는 원문을 표시한다.**
**Reason:** 분석 기능을 전혀 희생하지 않으면서 외부 전송에서 개인 식별을 제거하는 유일한 방법이다. "세션 단위 일관"이 중요한데, 같은 세션 안에서는 같은 사람이 항상 같은 가명이어야 다단계 분석이 이어지고, 세션이 바뀌면 가명이 달라져야 세션 간 결합으로 재식별되지 않는다.
**Status:** 확정 제안

## 4-2. 가명화로 해결되지 않는 경우 — 재식별 위험

주의가 필요한 경우가 있다. **조합에 의한 재식별**이다.

```text
"C라인 · 야간조 · 3호기"에 배치된 작업자가 1명뿐이라면,
Operator 컬럼을 가명화해도 다른 요인 조합으로 개인이 특정된다.
```

완전한 해결은 어렵지만, 최소한 **탐지해서 알리는 것**은 가능하다.

```text
그룹별 표본 수를 계산할 때 n이 임계값(제안: 5) 미만인
요인 조합이 존재하면 경고를 표시한다.

⚠ 일부 조건 조합의 표본이 5건 미만입니다.
  (C라인·야간·3호기: 3건)
  이 조합은 특정 개인의 데이터일 수 있습니다.
```

**DD-044 · 요인 조합별 표본 수가 임계값(기본 5) 미만인 셀이 존재하면 재식별 가능성 경고를 표시한다. 이 경고는 통계적 신뢰성 경고(표본 부족)와 함께 표시된다.**
**Reason:** 표본 수 5 미만은 개인정보 관점에서도, 통계적 관점에서도 동시에 문제가 되는 구간이다. 한 번의 검사로 두 가지 위험을 모두 알릴 수 있다. [추론 — 임계값 5는 일반적으로 통용되는 소규모 셀 기준을 차용한 것이며, 사내 기준이 있으면 그에 맞춘다]
**Status:** 확정 제안

# 5. 배치 모델과 정책 완화

## 5-1. 3가지 배치

```text
D1  완전 로컬 (AI OFF)
    ┌──────────────┐
    │  사용자 PC    │  데이터·분석·결과 전부 로컬
    │  앱 + Engine │  외부 통신 없음
    └──────────────┘

D2  로컬 앱 + 외부 클라우드 LLM (BYOK)
    ┌──────────────┐        S1 (기본)        ┌──────────┐
    │  사용자 PC    │ ─────────────────────► │ 외부 LLM │
    │  원본 데이터   │   C1·C2·C3(상대값)      └──────────┘
    └──────────────┘   C4 가명 / C5 차단

D3  로컬 앱 + 사내 LLM (on-premise)
    ┌──────────────┐        S1~S3           ┌──────────────┐
    │  사용자 PC    │ ─────────────────────► │ 사내 LLM      │
    │              │   사내망 내부            │ (사내 인프라)  │
    └──────────────┘                        └──────────────┘
```

## 5-2. 완화 매트릭스

**DD-045 · 전송 정책의 완화는 Provider의 `data_residency` Capability(Step 27 §4-1)를 근거로만 허용한다. 사용자나 관리자의 설정만으로 외부 클라우드에 대한 제한을 해제할 수 없다.**

| 정책 | D1 로컬 | D2 외부 클라우드 | D3 사내 LLM |
|---|---|---|---|
| S3 원본 전송 | 해당 없음 | **불가(해제 옵션 미노출)** | 관리자 설정으로 가능 |
| C3 규격 실값 전송 | 해당 없음 | 설정(기본: 상대값 변환) | 가능 |
| C5 고객정보 전송 | 해당 없음 | **불가** | 관리자 설정으로 가능 |
| C4 가명화 | 해당 없음 | **항상 적용** | **항상 적용** |
| S2 표본 행 수 상한 | 해당 없음 | 200행 | 설정 가능 |

C4 가명화만 D3에서도 유지되는 이유는 §4-1과 같다 — 사내망이라 해도 작업자 실명이 LLM 추론에 필요하지 않다.

**Reason:** "관리자가 설정으로 켤 수 있다"는 형태로 두면, 급한 상황에서 설정이 켜지고 그대로 남는다. 외부 클라우드에 대한 원본 전송은 **옵션 자체를 제공하지 않는** 것이 유일하게 신뢰할 수 있는 통제다. [추론]
**Status:** 확정 제안

# 6. 접근통제

## 6-1. O-3 결정 — MVP는 별도 로그인을 두지 않는다

**DD-046 · MVP의 접근통제는 OS 사용자 계정에 종속시키며 앱 자체의 로그인·권한 등급을 도입하지 않는다. 자격증명·세션·설정은 모두 OS 사용자별로 분리 저장한다.**

| 항목 | MVP 처리 |
|---|---|
| 사용자 식별 | OS 로그인 계정 |
| 자격증명 분리 | OS 자격증명 저장소(사용자별) |
| 세션 데이터 분리 | 사용자 프로필 경로 |
| 관리자 기능(정책) | 설정 파일 + 파일 권한으로 제어 |
| 역할별 화면 차이 | 화면 밀도 옵션으로만(Step 26 §3-2) |

**Reason:** 앱 자체 인증을 도입하면 계정 관리·비밀번호 정책·복구 절차가 모두 따라온다. 로컬 앱이고 데이터가 이미 그 PC에 있는 상황에서 앱 로그인은 실질적 보호를 거의 추가하지 않는다. 세션을 여러 사람이 공유해야 하는 요구(사내 서버 저장)가 확정되면 그때 함께 도입한다.
**Status:** 확정 제안 — 사내 서버 세션 공유(O-4)를 도입하면 재검토 필요

## 6-2. 공용 PC 문제 — 개인 단위 인증의 현실적 약점

§1-3에서 제기한 문제다. 여러 작업자가 같은 Windows 계정을 쓰면 OS 자격증명 저장소에 보관된 개인 API Key도 공유되어, Step 26 DD-016(사용자 단위 인증)과 Ian이 제기한 비용 귀속 요구가 **실제 현장에서 무너진다.**

대응 3가지를 제안한다.

| 방식 | 동작 | 적합 상황 |
|---|---|---|
| **(a) 기억하지 않음 모드** | 자격증명을 저장하지 않고 세션 동안만 메모리 유지. 앱 종료 시 폐기 | 공용 PC + 개인 Key |
| **(b) 명시적 로그아웃** | 사용자가 자리를 뜰 때 [AI 연결 해제] → 저장소에서 삭제 | 공용 PC |
| **(c) 사내 SSO(모델 B)** | OS 계정과 무관하게 개인이 회사 계정으로 로그인 | **공용 PC의 근본 해법** |

**DD-047 · AI 연결 설정에 "이 PC에 저장하지 않음" 옵션을 제공하며, 공용 PC로 지정된 설치에서는 이 옵션을 기본값으로 한다.**
**Status:** 확정 제안

**이 문제는 O-1(인증 모델) 결정에 새로운 근거를 추가한다.** 현장 공용 PC 비중이 높다면 모델 A(BYOK)는 운영상 취약하고 모델 B(사내 SSO)가 실질적으로 유일한 선택이 된다. O-1 판단 시 **"현장 PC가 개인 전용인가 공용인가"를 함께 확인**할 것을 제안한다.

# 7. 저장 데이터 보호

## 7-1. 원본 데이터를 복제 보관하지 않는다

**DD-048 · 앱은 사용자가 업로드한 원본 파일을 자체 저장소에 복제 보관하지 않는다. 세션에는 파일 경로·해시·데이터셋 버전만 기록하고, 분석에 필요한 데이터는 실행 시점에 읽는다.**
**Reason:** 보관하지 않는 데이터는 유출될 수 없다. 원본을 복제하면 암호화·접근통제·보존기간·폐기 절차가 전부 필요해지지만, 참조만 유지하면 그 데이터의 보호 책임은 원래 있던 위치(사내 파일서버·개인 PC)의 정책에 그대로 남는다. 보안 표면을 줄이는 가장 효과적인 설계 결정이다.
**Status:** 확정 제안

예외: 분석 재현을 위해 데이터 스냅샷이 필요한 경우가 있다(원본이 수정·삭제될 수 있으므로). 이 경우에도 **전체 복제가 아니라 분석에 사용된 변수·행의 해시와 요약만** 기록한다. 원본이 바뀌면 재현 불가를 알린다(§9-2).

## 7-2. O-4 결정 — 세션 저장 위치

**DD-049 · 세션 데이터는 기본적으로 로컬(사용자 프로필 경로)에 저장하며, 사내 서버 저장은 Phase 2 옵션으로 둔다.**

| | 로컬 저장(기본) | 사내 서버 저장(Phase 2) |
|---|---|---|
| 장점 | 단순, 추가 인프라 불필요 | 세션 공유·인수인계, PC 교체 시 승계 |
| 단점 | PC 고장 시 소실, 공유 불가 | 접근통제·보존기간·백업 정책 필요 |
| 필요 조건 | 없음 | §6-1의 앱 인증 도입 필요 |

세션 파일에 포함되는 것: Analysis State, 대화 기록, 분석 이력, Finding/Evidence, 데이터 참조 정보.
**포함되지 않는 것: 자격증명(DD-030), 원본 데이터(DD-048), 가명 매핑 테이블(DD-043).**

## 7-3. 암호화

| 대상 | 방식 |
|---|---|
| 자격증명 | OS 자격증명 저장소(Windows: DPAPI 기반 Credential Manager) — Step 26 DD-018 |
| 세션 파일 | 기본 평문. 단 C3·C5 요약이 포함될 수 있으므로 **선택적 암호화 옵션 제공** |
| 원본 데이터 | 앱이 보관하지 않음(DD-048) — 원 위치의 정책을 따름 |
| 전송 | TLS 필수 |

**DD-050 · TLS 인증서 검증을 비활성화하는 설정·코드 경로를 제공하지 않는다. 사내 프록시로 인해 검증이 실패하는 경우는 사내 CA 인증서를 신뢰 저장소에 추가하는 방식으로만 해결한다.**
**Reason:** 개발·테스트 편의로 도입된 인증서 검증 비활성화가 운영 환경에 그대로 남는 것은 매우 흔한 사고 경로다. 사내망 환경에서 프록시 문제가 실제로 발생할 가능성이 높으므로, 우회로를 아예 만들지 않고 올바른 해법만 남긴다.
**Status:** 확정 제안

|---|---|---|
| 앱 비정상 종료 | 자동 저장된 마지막 상태에서 복구 | 재실행 시 "이어서 분석하기" 제안 |
| 원본 파일 접근 불가(이동·삭제) | 세션은 유지, 새 분석만 차단 | 파일 재지정 요청 |
| 원본 파일 내용 변경 | 해시 불일치 감지 → 경고 | "데이터가 변경되었습니다. 기존 결과는 이전 데이터 기준입니다" |
| Statistical Engine 오류 | 해당 분석만 실패, 세션 유지 | 오류 코드 + 조건 변경 안내 |
| Tool 실행 시간 초과 | 해당 Tool 중단, 세션 유지 | 데이터 축소 또는 조건 변경 안내 |
| 디스크 공간 부족 | 저장 실패 감지 → 경고 | 저장 위치 변경 안내 |
| 세션 파일 손상 | 손상 감지 → 백업본 시도 | 복구 실패 시 명확히 고지(조용한 실패 금지) |

## 9-2. 자동 저장과 복구

**DD-052 · 세션은 분석 1건 완료 시점, 사용자 승인 시점, AI 응답 수신 시점에 자동 저장하며, 직전 1개 버전을 백업으로 유지한다.**

저장 시점을 이렇게 잡은 이유는 **되돌아갔을 때 잃는 것이 가장 적은 지점**이기 때문이다. 시간 기반 주기 저장(예: 5분마다)은 긴 분석 도중 저장되어 중간 상태를 남길 수 있다. [추론]

## 9-3. 재현성 기록 세트

Baseline §30의 Reproducibility 항목을 확정한다. 분석 1건마다 다음을 기록한다.

| 항목 | 예시 |
|---|---|
| dataset_id / version | DS-UC03-001 / v3 |
| 원본 파일 해시 | sha256:… |
| 분석 방법 / 버전 | welch_t_test / 1.2.0 |
| 입력 파라미터 | response=Torque, group=Line, α=0.05 |
| 난수 seed(해당 시) | 20260912 |
| Statistical Engine 버전 | engine 0.4.1 |
| 라이브러리 버전 | scipy x.y.z, numpy x.y.z |
| 실행 시각 | 2026-09-12T14:23:41Z |
| 실행 주체 | Principal(§Step 27 §4-2) |
| LLM 관여 여부 | 방법 선택에 LLM 개입 여부 / 모델 |

마지막 항목이 중요하다. **"이 분석 방법을 사람이 골랐는가 AI가 골랐는가"**는 사후 검증에서 반드시 필요한 정보인데, 기록하지 않으면 복원할 수 없다.

이 기록 세트는 이 연구 프로젝트가 볼트에서 운영 중인 `Execution_Log.csv`(run_id·dataset_snapshot·method_version·parameters·seed·executor 등 14개 컬럼)와 동일한 철학이며, 실제 구현 시 그 구조를 참고할 수 있다.

# 10. 사고 대응 절차

설계 문서에 절차까지 넣는 이유는, 사고 시 필요한 **기능**(즉시 무효화·범위 확인)이 미리 구현되어 있어야 하기 때문이다.

| 상황 | 앱이 제공해야 하는 기능 | 절차 |
|---|---|---|
| 자격증명 유출 의심 | [AI 연결 해제 및 저장정보 삭제] 1클릭 | 앱에서 해제 → 공급자 콘솔에서 키 폐기 → 재발급 |
| 의도치 않은 전송 발생 | 감사 로그에서 해당 세션의 transfer_scope·filter 결과 조회 | 범위 확인 → 정보보호 담당 보고 |
| 공용 PC에 자격증명 잔존 | 저장정보 삭제 기능 | 동일 |
| 세션 파일 유출 | 세션에 무엇이 포함되는지 명세(§7-2) | 포함 범위 근거로 영향 판단 |

# 0. 이 요구가 바꾸는 것

> "앱의 사용자는 **해외 생산 공장의 기술자**도 대상으로 합니다. PRISM은 로그인 시 EN 토글이 있고, EN으로 설정하면 모든 UX와 보고서가 영어로 전환됩니다. 이 ADD-ON 통계분석 모듈도 로그인 시 설정된 언어에 따라 UX가 구성되어야 하며, **에러 메시지를 포함하여 보고서·설명·툴팁 모두** 영어를 지원해야 합니다. PRISM의 에러 메시지는 **한국어와 영어를 통합하여 하나의 메시지로 출력**합니다."

**이 요구는 단순한 번역 계층 추가가 아닙니다.** 이 앱은 텍스트 대부분이 정적 UI 문구가 아니라 **분석 결과에서 생성되는 문장**이기 때문입니다.

```text
일반 업무 앱의 다국어              이 앱의 다국어
─────────────────────────      ──────────────────────────────────
버튼·메뉴·안내문 (정적)          ① 버튼·메뉴·툴팁 (정적)
  → 문자열 사전으로 해결          ② 통계 해석 문장 (템플릿 생성)
                                ③ 제조 판단 문장 (규칙 생성)
                                ④ AI 해석 문장 (LLM 생성)  ← 가장 까다로움
                                ⑤ 그래프 축·범례·규격선 라벨
                                ⑥ 보고서 전체
                                ⑦ 에러 메시지 (한·영 통합)
```

②③은 템플릿 구조 자체가 언어마다 달라야 하고(한국어는 조사, 영어는 관사·복수·시제), ④는 LLM에게 언어를 지시하고 **번역하면 안 되는 것을 보호**해야 합니다. 이 문서는 그 경계를 정합니다.

# 1. 언어 설정 모델

**DD-112 · 언어는 PRISM 로그인 시 설정된 값을 그대로 따른다. 이 모듈은 독립적인 언어 설정을 두지 않는다.**

```text
PRISM 로그인 (KO / EN 토글)
        │
        ▼
  앱 세션에 language 확정
        │
        ├──► UI · 툴팁 · 안내문
        ├──► 해석 템플릿 · 제조 판단
        ├──► 그래프 텍스트
        ├──► 보고서
        └──► LLM 출력 언어 지시
```

| 항목 | 값 |
|---|---|
| 지원 언어 | `ko` (한국어), `en` (English) |
| 기본값 | PRISM 설정값. 미지정 시 `ko` |
| 저장 위치 | 앱 세션(`AppSession.language`) + 사용자 프로필 |
| 적용 범위 | 이 모듈의 모든 출력 |

**Reason:** 사용자가 PRISM에서 EN으로 로그인했는데 통계 모듈만 한국어로 나오면 Add-on으로서 실패입니다. 별도 설정을 두면 두 설정이 어긋나는 상태가 반드시 발생합니다.
**Status:** 확정 제안

# 2. 번역 대상과 비대상 — 경계가 가장 중요하다

**DD-113 · 데이터에서 유래한 문자열은 번역하지 않는다. 시스템이 생성한 문자열만 번역한다.**

| 구분 | 항목 | 처리 |
|---|---|---|
| **번역함** | UI 레이블·버튼·메뉴·툴팁·안내문 | 언어별 사전 |
| | 통계 용어 (유의확률 / p-value) | 언어별 사전 |
| | 해석 템플릿 문장 | 언어별 템플릿 |
| | 제조 판단 문장 | 언어별 템플릿 |
| | 경고·주의 문구 | 언어별 템플릿 |
| | 그래프 축 제목·범례 라벨·규격선 라벨 | 언어별 사전 |
| | 보고서 섹션 제목·설명 | 언어별 템플릿 |
| | AI 해석 문장 | LLM에 언어 지시 |
| **번역 안 함** | **변수명** (`Torque`, `토크`, `설비코드`) | **원문 그대로** |
| | **그룹 수준값** (`A라인`, `3호기`, `M4`, `Model C`) | **원문 그대로** |
| | **파일명·시트명** | 원문 그대로 |
| | **측정값·수치** | 원문 그대로 |
| | **오류 코드** (`ERROR_ZERO_VARIANCE`) | 코드 자체는 불변 |
| | **Tool 이름** (`welch_t_test`) | 불변 |

## 2-1. 왜 데이터 값을 번역하면 안 되는가

`3호기`를 영어 화면에서 `Machine 3`으로 번역하면, 사용자가 **원본 Excel과 대조할 수 없습니다.** 현장에서 "3호기 불량률이 높다"는 결론을 받아 설비 앞에 갔는데 설비에 붙은 이름이 `3호기`라면, 보고서의 `Machine 3`은 다른 설비처럼 보입니다.

따라서 **영어 화면에 한국어 변수명이 섞여 나오는 것이 올바른 동작**입니다.

```text
[EN 화면 예시]
Mean torque differs between groups.
  A라인 (n=815):   166.252
  B라인 (n=1,025): 168.881
Difference: -2.628 N·m (p < 0.001)
```

어색해 보이지만, 이것이 데이터 추적 가능성을 지키는 유일한 방법입니다.

**보완(Phase 2 제안):** 데이터 업로드 시 변수·수준값에 **표시용 별칭(alias)** 을 지정할 수 있게 하면, 원문을 보존하면서 영어 표시도 가능합니다(`A라인 (Line A)`). MVP에서는 원문 유지만 구현합니다.

# 3. 계층별 다국어 처리

## 3-1. 정적 UI 문자열

표준적인 키-기반 사전을 사용합니다.

```text
resources/
  ├── ko.json
  └── en.json
```

```jsonc
// ko.json
{
  "analysis.result.statistical": "통계 결과",
  "analysis.result.ai": "AI 해석",
  "analysis.result.judgment": "제조 판단",
  "button.generate_report": "보고서 생성",
  "tooltip.p_value": "관측된 차이가 우연히 나타날 확률입니다. 작을수록 차이가 우연이 아닐 가능성이 높습니다."
}
```

```jsonc
// en.json
{
  "analysis.result.statistical": "Statistical Result",
  "analysis.result.ai": "AI Interpretation",
  "analysis.result.judgment": "Manufacturing Judgment",
  "button.generate_report": "Generate Report",
  "tooltip.p_value": "The probability of observing this difference by chance. A smaller value suggests the difference is less likely to be random."
}
```

**DD-114 · 화면에 출력되는 모든 문자열은 코드에 직접 쓰지 않고 언어 사전의 키로만 참조한다. 사전에 키가 없으면 빌드가 실패한다.**
**Reason:** 이 앱은 텍스트가 매우 많고(툴팁·경고·해석), 한 곳이라도 하드코딩되면 EN 화면에 한국어가 남습니다. 누락은 **실행 시점이 아니라 빌드 시점에** 잡혀야 합니다.
**Status:** 확정 제안

## 3-2. 에러 메시지 — 한·영 통합 출력

PRISM 방식을 따릅니다.

**DD-115 · 에러 메시지는 언어 설정과 무관하게 항상 오류 코드 + 한국어 + 영어를 하나의 메시지로 함께 출력한다.**

```text
┌──────────────────────────────────────────────────────────────┐
│ ⚠ [ERROR_INSUFFICIENT_SAMPLE]                                 │
│                                                              │
│ 표본 수가 부족합니다. 그룹 B의 데이터가 3건으로,                 │
│ 분석에 필요한 최소 5건에 미치지 못합니다.                        │
│                                                              │
│ Insufficient sample size. Group B has 3 records,              │
│ which is below the minimum of 5 required for this analysis.   │
│                                                              │
│                          [ 조건 변경 / Change conditions ]     │
└──────────────────────────────────────────────────────────────┘
```

**Reason:** 오류는 **소통의 대상**이기 때문입니다. 해외 공장 기술자가 오류 화면을 캡처해 한국 본사 담당자에게 보내는 상황이 실제로 발생하며, 이때 한 장의 화면으로 양쪽이 같은 내용을 봐야 합니다. 오류 코드를 맨 앞에 두는 것도 같은 이유입니다 — 언어와 무관하게 검색·대조가 가능한 식별자가 필요합니다.

정상 UX 문구는 개인 사용자를 위한 것이므로 언어 설정을 따르고, **오류만 이중 표기**합니다. 이 구분은 PRISM의 기존 방식과 일치합니다.
**Status:** 확정 제안

### 에러 메시지 사전 구조

Step 17에서 정의한 표준 오류 코드에 두 언어를 함께 둡니다.

```jsonc
{
  "ERROR_INSUFFICIENT_SAMPLE": {
    "ko": "표본 수가 부족합니다. 그룹 {group}의 데이터가 {n}건으로, 분석에 필요한 최소 {min}건에 미치지 못합니다.",
    "en": "Insufficient sample size. Group {group} has {n} records, which is below the minimum of {min} required for this analysis.",
    "severity": "ERROR",
    "recovery_key": "recovery.change_conditions"
  }
}
```

**적용 범위:** Statistical Engine 오류(Step 17), Rule Engine 거부(Step 18), Data Guard 차단, Job 실패, AI Gateway 오류, 인증·한도 오류 전부.

## 3-3. 해석 템플릿 — 언어별 템플릿

이 앱의 핵심 가치인 "쉬운 해석"은 결정론적 템플릿으로 생성됩니다(Baseline §27). **단순 문자열 치환으로는 두 언어를 처리할 수 없습니다.**

```text
한국어: "A라인의 평균이 B라인보다 2.63 N·m 낮습니다."
영어:   "The mean of A라인 is 2.63 N·m lower than that of B라인."
        └ 어순이 다르고, 비교 구문 구조가 다름
```

**DD-116 · 해석 템플릿은 언어별로 별도 작성한다. 한국어 템플릿을 기계 번역하거나 문장 조각을 이어 붙이는 방식을 사용하지 않는다.**

```jsonc
{
  "interpretation.two_group_mean_diff.significant": {
    "ko": "{group_a}의 평균이 {group_b}보다 {diff} {unit} {direction}습니다. 이 차이는 통계적으로 유의합니다(p {p_display}).",
    "en": "The mean of {group_a} is {diff} {unit} {direction} than that of {group_b}. This difference is statistically significant (p {p_display})."
  }
}
```

**Reason:** 조각을 이어 붙이면("평균이" + "낮" + "습니다") 한국어는 조사·어미 처리가, 영어는 관사·복수·시제가 반드시 깨집니다. 문장 단위 템플릿이 유일하게 안전한 방법입니다.
**Status:** 확정 제안

**제조 판단 문장·경고 문구·다중비교 안내·측정시스템 확인 질문**도 동일하게 처리합니다.

## 3-4. LLM 생성 텍스트 — 가장 까다로운 부분

**DD-117 · LLM 출력 언어는 Prompt Stack의 Core System Policy 층(Step 7 L1)에서 지시하며, 데이터 유래 문자열은 번역을 금지하는 지시를 함께 포함한다.**

```text
[L1 Core System Policy — 언어 지시 부분]

Respond in English.
Do NOT translate any of the following; reproduce them exactly as given:
  · variable names
  · group level values
  · file or sheet names
  · units
Use standard statistical terminology in English
(p-value, confidence interval, effect size, confounding factor).
Do not restate or recalculate numeric values; use them exactly as provided.
```

세 가지를 동시에 지시하는 것이 중요합니다.

| 지시 | 이유 |
|---|---|
| 출력 언어 | 사용자 설정 반영 |
| **데이터 유래 문자열 번역 금지** | §2-1 — `3호기`를 `Machine 3`으로 바꾸면 원본 대조 불가 |
| 수치 재작성 금지 | 기존 원칙(DD-085 #1)의 재확인. 언어 변환 과정에서 특히 깨지기 쉬움 |

### 언어 불일치 처리

LLM이 지시와 다른 언어로 응답하는 경우가 있습니다. 과도한 자동 검증(언어 감지 후 재요청)은 비용과 지연을 늘리므로 **사용자 조치 경로**로 처리합니다.

```text
AI 해석
  …
  [ 다시 생성 / Regenerate ]   ← 언어가 맞지 않으면 재생성
```

**Status:** 확정 제안

### AI 해석의 언어 표기

LLM이 생성한 문장은 **생성 시점의 언어로 고정**됩니다. 사용자가 세션 도중 언어를 바꾸면 기존 AI 해석은 그대로 남습니다(§7).

## 3-5. 그래프 텍스트

SVG이므로 텍스트가 텍스트로 남아 번역이 가능합니다(DD-090의 부수적 이점).

| 요소 | 처리 |
|---|---|
| 축 제목 | 변수명(원문) + 단위(원문). 예: `Torque (N·m)` |
| 축 눈금 | 수치 — §4 형식 |
| 범례 라벨 | 그룹 수준값 **원문** + 표본 수 레이블은 번역 (`A라인 (n=815)` / `A라인 (n=815)`) |
| 규격선 라벨 | **번역** — `규격 상한` / `USL`, `목표` / `Target` |
| 그래프 제목 | **번역** — `라인별 토크 분포` / `Torque Distribution by Line` (변수·그룹명은 원문) |
| 경고 주석 | **번역** — `표본 부족(n<5)` / `Small sample (n<5)` |

## 3-6. 보고서

**DD-118 · 보고서는 생성 시점의 언어 설정으로 생성되며, 생성 후에는 언어가 바뀌지 않는다. 다른 언어가 필요하면 재생성한다.**

| 항목 | 처리 |
|---|---|
| 섹션 제목·설명 | 생성 시점 언어 |
| 통계 수치 | §4 형식 (언어 무관) |
| 변수명·그룹명 | 원문 |
| SVG 그래프 | 생성 시점 언어로 렌더링 |
| AI 해석 섹션 | 생성 시점 언어 |
| 재현성 정보 | 언어 무관 (ID·해시·버전·시각) |
| 보고서 메타 | `language: en` 표기 |

보고서는 **생성 시점의 산출물**이므로 사후에 언어를 바꾸지 않습니다. 이는 Step 29의 보고서 생명주기(A4 자산, 다운로드 기간)와도 일치합니다 — 이미 배포된 보고서가 나중에 다른 언어로 바뀌면 안 됩니다.

**Status:** 확정 제안

# 4. 숫자 · 날짜 · 단위 형식

**DD-119 · 숫자 형식은 언어 설정과 무관하게 고정한다. 로케일별 숫자 표기를 도입하지 않는다.**

| 항목 | 고정 형식 | 근거 |
|---|---|---|
| 소수점 | `.` | — |
| 천단위 구분 | `,` | — |
| 지수 | `1.2e-19` | — |
| p-value | `p < 0.001` / `p = 0.032` | 통계 관례 |
| 신뢰구간 | `95% CI [-3.194, -2.063]` | 통계 관례 |
| 날짜·시각 | **ISO 8601** (`2026-09-12`, `2026-09-12T14:23:41Z`) | — |
| 단위 | 원본 데이터의 표기 유지 (`N·m`, `mm`) | 데이터 추적 |

**Reason:** 일부 로케일은 소수점에 `,`를 씁니다(`3,14`). 제조 데이터에서 `3.14`와 `3,14`, `1,234`와 `1.234`의 혼동은 **치명적인 오독**을 만듭니다. 규격 판정이 뒤바뀔 수 있습니다. 다국어는 지원하되 **숫자 표기는 단일 규칙으로 고정**하는 것이 안전합니다. 한국·영어권 모두 소수점 `.`, 천단위 `,`를 사용하므로 두 언어 사용자 모두에게 자연스럽습니다.

날짜를 ISO 8601로 고정하는 것도 같은 이유입니다 — `09/12/2026`은 미국식과 유럽식이 반대로 읽힙니다.
**Status:** 확정 제안

# 5. Finding · Evidence의 다국어 저장

세션은 최대 2년 보존되고(Step 29), 그 사이 사용자가 언어를 바꿀 수 있습니다. **과거 분석의 Finding이 어느 언어로 남아야 하는가**가 설계 쟁점입니다.

**DD-120 · 결정론적으로 생성된 텍스트는 템플릿 ID + 파라미터로 저장하고 표시 시점에 렌더링한다. LLM이 생성한 자연어는 원문과 생성 언어를 함께 저장한다.**

```jsonc
// 템플릿 기반 Finding — 언어 전환 시 함께 전환됨
{
  "finding_id": "F001",
  "type": "OBSERVED_PATTERN",
  "source": "RULE",
  "template_id": "finding.group_mean_lower",
  "params": {"group_a": "A라인", "group_b": "B라인",
             "diff": 2.628, "unit": "N·m"},
  "statement_cache": "A라인의 평균이 B라인보다 2.628 N·m 낮습니다.",
  "language": "ko",
  "evidence_level": "E1",
  "source_analysis": ["A04"]
}
```

```jsonc
// LLM 생성 Finding — 생성 언어 고정
{
  "finding_id": "F006",
  "type": "INTERPRETATION",
  "source": "LLM",
  "template_id": null,
  "statement": "Model 구성 차이가 Line 효과와 섞여 있어 …",
  "language": "ko",              // 표시 언어와 다르면 안내 표시
  "evidence_level": "E2"
}
```

| 생성 주체 | 저장 | 언어 전환 시 |
|---|---|---|
| 템플릿(Rule) | `template_id` + `params` | **자동 전환** |
| LLM | 원문 + `language` | **그대로 유지**, 언어 불일치 시 안내 |

LLM 생성 문장을 양 언어로 미리 만들어 두지 않는 이유는 **호출 비용이 두 배가 되고, 개인별 승인 한도(DD-063)를 소모하기 때문**입니다. 사용자가 다른 언어로 보고 싶으면 해당 분석에서 [다시 생성]을 누릅니다.

`statement_cache`는 화면·검색 편의를 위한 캐시이며 **권위는 `template_id` + `params`에 있습니다.** 템플릿이 개선되면 캐시는 재생성됩니다.
**Status:** 확정 제안

# 6. 식별자 판별 사전의 다국어

Step 28 DD-042의 식별자 판별 Layer 2(컬럼명 사전 매칭)는 **한국어와 영어 컬럼명을 모두 인식**해야 합니다. 해외 공장 데이터는 영어 컬럼명일 가능성이 높습니다.

| 분류 | 한국어 키워드 | 영어 키워드 |
|---|---|---|
| 작업자 | 사번, 사원, 사원번호, 작업자, 담당자, 성명, 이름 | operator, employee, emp_id, worker, staff, name, person |
| 설비 고유번호 | 설비번호, 호기번호, 장비번호, 시리얼, 고유번호 | serial, serial_no, equipment_id, machine_serial, asset_id |
| 로트·추적 | 로트, 로트번호, 배치번호, 바코드 | lot, lot_no, batch, batch_no, barcode, traceability |
| 고객·거래처 | 고객, 고객사, 거래처, 납품처 | customer, client, account, buyer |

**DD-121 · 식별자 판별 사전과 데이터 품질 규칙은 언어 설정과 무관하게 한국어·영어 키워드를 모두 적용한다.**
**Reason:** 데이터의 언어와 사용자 인터페이스 언어는 별개입니다. 한국인 사용자가 해외 공장의 영어 컬럼명 데이터를 분석하거나 그 반대의 경우가 모두 발생합니다. 사전을 언어 설정에 따라 전환하면 **fail-closed 원칙(DD-042)이 무너집니다** — 영어 컬럼 `operator`가 한국어 설정에서 식별자로 인식되지 않으면 개인정보가 그대로 전송됩니다.
**Status:** 확정 제안

# 8. Golden Case와 언어 독립성

**Agent의 판단이 언어에 따라 달라지면 안 됩니다.**

Golden Case 평가는 구조화된 출력(ProblemModel, Tool 선택, Finding 유형, Evidence 등급, Forbidden Conclusion 위반 여부)을 기준으로 하므로 **원칙적으로 언어 무관**입니다. 다만 그것이 실제로 성립하는지는 검증해야 합니다.

**AC-A8 · 동일 Golden Case를 `ko`와 `en` 설정으로 각각 실행했을 때 통계 결과, Tool 선택, Finding 유형, Evidence 등급, Hypothesis 상태가 완전히 동일해야 한다.** (자연어 문장만 언어에 따라 달라진다)

이 기준이 중요한 이유는, LLM에게 언어를 지시하는 것이 **판단 자체에 영향을 줄 수 있기 때문**입니다. 영어로 사고할 때와 한국어로 사고할 때 선택하는 분석 방법이 달라진다면 그것은 결함입니다.

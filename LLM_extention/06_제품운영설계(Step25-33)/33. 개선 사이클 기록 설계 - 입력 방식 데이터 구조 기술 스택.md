> ## ✅ P-6 확인 완료 (2026-09-13) — 설비 마스터는 3단계로 이관
>
> Ian 확인: **"현재 설비에 대한 기록은 없습니다. 초기 거부감이 커서 요구하지 않았습니다. 이는 3단계 진행 시 업데이트하는 것으로 진행하겠습니다."**
>
> **DD-134 · 설비 마스터(기종·제조사·도입연도)는 3단계에서 보완한다. 2단계에서는 `ProblemSignature`에 설비 기종 필드를 두되 비워 둔다(nullable). 대신 설비 식별자(법인·공장·라인·설비번호)를 원본 그대로, 마스터 조인 키로 쓸 수 있는 형태로 보존한다.**
>
> **Reason — 지금 잃는 것이 없습니다.** 설비 식별자를 원형 그대로 남겨 두면, 3단계에서 설비 마스터가 만들어졌을 때 **조인만으로 과거 케이스 전체에 기종 정보를 소급 보완**할 수 있습니다. 따라서 §5에서 DD-133으로 지적한 "법인 간 지식 전이 불가" 문제는 **연기되는 것이지 소실되는 것이 아닙니다.**
>
> **단 하나의 조건:** 설비 식별자를 **변형·정규화하지 않고 원본 그대로** 저장해야 합니다. `3호기`를 `M3`으로 바꾸거나 공백·표기를 임의 정리하면 나중에 마스터와 매칭되지 않습니다. 이는 DD-113(데이터 유래 문자열은 번역·변형하지 않는다)과 같은 원칙입니다.
>
> **로드맵 영향:** 법인 간 지식 전이는 3단계에서 설비 마스터가 보완된 시점부터 가능해집니다. 2단계~3단계 초기에는 **법인 내 지식 축적**이 목표가 됩니다. 이는 채택 전략(§6)과도 부합합니다 — 초기에는 어차피 소수 담당자와 소수 케이스로 시작하므로 법인 간 전이를 논할 단계가 아닙니다.
>
> DD-133은 **유효하되 적용 시점이 3단계로 이동**합니다. §3-3 `ImprovementCase`의 설비 기종 필드는 nullable로 정의합니다.

# 0. 결론 요약

| 질문 | 답 |
|---|---|
| **개선 내용을 어떻게 입력받을 것인가** | **검증을 요청하는 순간에 묻습니다.** 대책을 미리 등록하라고 하지 않습니다. 그리고 **LLM이 자유서술을 구조화**합니다 — 사용자는 한 문장만 말하고, 앱이 구조화한 결과를 확인만 합니다 |
| **어떤 방식으로 기록할 것인가** | 검색·집계에 쓰이는 축은 **관계형 컬럼**, 형태가 진화하는 것은 **JSONB**. 원칙은 *"검색할 것은 컬럼으로, 보존할 것은 JSONB로"* |
| **기술 스택** | **현재 PostgreSQL을 유지·확장합니다.** 별도 스키마(`statmod`)로 분리하되 같은 DB. 3단계를 위해 새 기술(벡터 DB 등)을 도입할 필요가 없습니다 — JSONB + 전문검색으로 시작하고 필요해지면 `pgvector`를 같은 DB에 붙입니다 |
| **성실한 입력을 어떻게 유도할 것인가** | **강제하지 않습니다.** 대신 ①부담을 가치 직전으로 옮기고 ②앱이 아는 것은 묻지 않고 ③LLM이 구조화를 대신하고 ④**검증된 개선을 주차 보고서에 실어 인정으로 되돌려줍니다** |

**가장 중요한 것은 네 번째입니다.** 이것은 UX 문제가 아니라 **채택 문제**이며, 그 이유는 §1에서 설명합니다.

# 1. 이 설계의 진짜 제약 — 기술이 아니라 채택입니다

Ian이 확인해 준 사실은 설계의 방향을 바꿉니다.

> "PRISM에는 이미 이슈·개선활동을 기록하는 구조가 **없습니다.** 이유는 앱의 성격이 **문제를 드러내는 것**이라 관리 담당인 제조·기술 부서의 **반감**이 있었기 때문에 처음부터 협조를 이끌어내기 힘들었습니다. … 그런 상황에서 원인분석, 대책 수립, 대책 검증까지 요구하기 어려웠습니다. **그래서 다단계 개발 로드맵을 수립한 이유입니다.**"

## 1-1. 지금까지 PRISM이 준 것과 요구한 것

```text
                    PRISM이 준 것          PRISM이 요구한 것
─────────────────────────────────────────────────────────────
제조·기술 부서      문제 지적              (아직 없음)
                   순위 노출
                   데이터 품질 지적
```

**부서 입장에서 PRISM은 지금까지 일방적으로 받기만 하는 관계였습니다.** 그 상태에서 "원인을 분석하고 대책을 세우고 검증 데이터를 입력하라"고 하면 저항은 당연합니다. 입력 UX를 아무리 잘 만들어도 이 구조는 바뀌지 않습니다.

## 1-2. 2단계가 처음으로 주는 것

**2단계는 PRISM이 제조·기술 부서에게 처음으로 무언가를 주는 단계입니다.**

| 2단계가 주는 것 | 부서에게의 의미 |
|---|---|
| 원인을 찾는 통계 도구 | 감이 아니라 근거로 설명할 수 있음 |
| 교란요인 통제 | "설비 탓이 아니라 모델 구성 차이다"를 입증 가능 |
| **대책 효과의 통계적 증명** | **개선했는데 인정받지 못하던 문제를 해결** |

**세 번째가 킬러 기능입니다.** 제조 부서가 개선을 했는데 "정말 좋아진 거냐, 우연 아니냐"는 질문에 답하지 못해 성과로 인정받지 못하는 상황은 흔합니다. 앱이 이를 통계적으로 증명해 주면 **부서에게 직접적 이득**입니다.

**DD-122 · 기록 계층의 설계 목표는 "완전한 기록"이 아니라 "지속되는 기록"이다. 입력의 완결성보다 채택을 우선한다.**
**Reason:** 완벽한 스키마를 설계하고 필수 입력으로 강제하면, 초기 저항 상황에서는 아무도 쓰지 않아 결과적으로 0건이 축적된다. 불완전하더라도 실제로 쌓이는 기록이 완벽하지만 비어 있는 스키마보다 낫다. 3단계의 가치는 사례 수에서 나온다.
**Status:** 확정 제안

# 2. 입력 설계 7원칙

## 원칙 1 — 부담을 가치 직전으로 옮긴다

개선 사이클에는 기록이 발생할 수 있는 시점이 셋 있습니다.

```text
시점 A  원인 분석 종료          "이 가설이 원인 같다"
   │                            → 사용자 동기: 중
   │      (며칠 ~ 몇 주)
   ▼
시점 B  대책 실시 직후          "조치했다"
   │                            → 사용자 동기: 낮음 ★ 여기서 물으면 실패
   │      (2~4주 데이터 축적)
   ▼
시점 C  검증 분석 요청          "효과가 있었나?"
                                → 사용자 동기: 최고 ★ 여기서 묻는다
```

**DD-123 · 대책 내용은 사전 등록을 요구하지 않는다. 사용자가 검증 분석을 요청하는 시점에 "무엇을 바꾸셨습니까"를 묻는다.**
**Reason:** 시점 B에서 요구하면 사용자는 아무 대가 없이 입력만 한다. 시점 C에서는 **검증 결과를 얻기 위해 필요한 정보**이므로 입력이 거래가 된다. "그래야 전후를 비교할 수 있습니다"라는 설명이 성립하는 유일한 시점이다.
**Status:** 확정 제안

**보완 — 실시일 기억 문제:** 몇 주 지나면 정확한 실시일을 기억하지 못합니다. 데이터에서 **변화점을 탐지해 후보를 제시**합니다.

```text
AI: 데이터를 보니 6월 12일경 수준 변화가 감지됩니다.
    이 무렵 조치하신 것이 있습니까?
    [ 네, 6월 12일 ]  [ 다른 날짜 ]  [ 조치 없음 ]
```

## 원칙 2 — 앱이 아는 것은 묻지 않는다

앱은 이미 압니다: 어느 법인·라인·설비·제품·CTQ인지, 문제가 언제 시작됐는지, 분석에서 무엇을 발견했는지, 효과 크기가 얼마인지.

**사용자에게 묻는 것은 앱이 알 수 없는 것 하나뿐입니다 — 물리적으로 무엇을 했는가.**

이는 기존 원칙 DD-027(결정론적으로 처리 가능한 판단에는 LLM을 호출하지 않는다)과 같은 정신입니다. **도출 가능한 것은 묻지 않습니다.**

## 원칙 3 — 선택형 우선, 자유서술은 보조

`대책 내용: [                    ]` 같은 빈 칸은 "설비 노후", "작업자 교육" 같은 재사용 불가능한 답을 만듭니다.

| 묻는 방식 | 결과 |
|---|---|
| 자유서술 단독 | "척킹 압력 조정" — 얼마나? 어느 설비? 언제? 알 수 없음 |
| **선택형 + 구조화 필드** | 유형=조건변경 / 대상=3호기 / 항목=척킹압력 / 4.5→5.0 / 2026-06-12 |

자유서술은 **"그 외 특이사항"** 한 칸으로 충분합니다.

## 원칙 4 — LLM을 구조화 도우미로 쓴다 ★ 핵심

원칙 3은 옳지만, 폼이 길어지면 그 자체가 부담입니다. **2단계에는 LLM이 있으므로 이 긴장을 해소할 수 있습니다.**

```text
┌──────────────────────────────────────────────────────────┐
│ AI  검증 분석을 시작하기 전에, 무엇을 바꾸셨는지 알려주세요.│
│     (데이터에서 6월 12일경 변화가 감지되었습니다)           │
│                                                          │
│ 👤  3호기 척킹 압력을 4.5에서 5.0으로 올렸어요. 6월 12일에. │
│                                                          │
│ AI  아래와 같이 기록하겠습니다. 맞습니까?                   │
│     ┌────────────────────────────────────┐               │
│     │ 대책 유형    조건 변경               │               │
│     │ 대상        3호기                   │               │
│     │ 변경 항목    척킹 압력               │               │
│     │ 변경 전      4.5                     │               │
│     │ 변경 후      5.0                     │               │
│     │ 실시일       2026-06-12              │               │
│     │ 실시 부서    ? 확인 필요             │               │
│     └────────────────────────────────────┘               │
│                        [ 맞습니다 ]  [ 수정 ]             │
└──────────────────────────────────────────────────────────┘
```

**DD-124 · 대책 입력은 자유서술을 받아 LLM이 구조화하고, 구조화 결과를 사용자가 확인하는 방식으로 한다. 원문 자유서술도 함께 보존한다.**

**Reason:** 사용자는 한 문장만 말하면 되고(부담 최소), 기록은 구조화되며(지식 재사용 가능), 확인 단계가 있어 오류가 걸러진다. 이는 **"사용자는 게을러도 되고 기록은 성실해도 되는"** 유일한 방법이다.
원문을 함께 보존하는 이유는 ① LLM 구조화가 놓친 정보가 있을 수 있고 ② 나중에 더 나은 추출 방법이 생기면 재처리할 수 있기 때문이다(DD-120의 원칙과 동일 — *기록은 충실히, 구조화는 나중에*).

**주의:** 이 호출은 INTENT 등급의 가벼운 호출이며(DD-031), **데이터 유래 문자열(설비명·항목명)은 번역·변형하지 않는다**(DD-113·117). `척킹 압력`은 `Chucking Pressure`로 바뀌지 않습니다.
**Status:** 확정 제안

## 원칙 5 — 강제하지 않되 결과를 보여준다

**DD-125 · 대책 기록을 필수 입력으로 강제하지 않는다. 미기록 시 검증은 수행하되 결과에 "재사용 불가" 표시를 남긴다.**

```text
┌────────────────────────────────────────────────────┐
│ 검증 결과                                            │
│ 6월 12일 이후 토크 변동이 유의하게 감소했습니다.        │
│ 효과 크기 d = 0.62 (중간~큼), p < 0.001              │
│                                                    │
│ ⚠ 무엇을 바꾸셨는지 기록되지 않아, 이 결과는 다른     │
│   설비·라인에서 참고 사례로 활용할 수 없습니다.        │
│                              [ 지금 기록하기 ]       │
└────────────────────────────────────────────────────┘
```

**Reason:** 초기 저항 상황에서 필수 입력은 "안 쓰겠다"로 이어진다. 차단하는 대신 **무엇을 잃는지 보여주면** 스스로 입력하는 비율이 올라간다. 그리고 미기록 케이스도 통계 결과 자체는 남으므로 완전한 손실은 아니다.
**Status:** 확정 제안

## 원칙 6 — 기록은 인정으로 되돌아온다 ★ 채택의 핵심

**DD-126 · 검증이 완료된 개선은 주차 보고서와 법인별 집계에 "검증된 개선"으로 자동 반영한다.**

```text
[주차 보고서 — 기존 PRISM 구조에 추가]

  ■ 이번 주 검증된 개선 (3건)
    · A법인 2라인 3호기 — 척킹 압력 조정 → 토크 변동 38% 감소 (p<0.001)
      실시: 제조2팀, 검증: 품질보증2팀
    · ...
```

**Reason:** 이것이 §1의 관계를 뒤집는 장치다. PRISM이 "문제를 드러내는 앱"에서 **"개선을 기록해 주는 앱"**이 된다. 제조 부서 입장에서 입력의 대가는 편의가 아니라 **성과 인정**이다.

PRISM은 이미 법인별·제품별 주차 보고서를 작성하고 있으므로 **새 산출물을 만들 필요 없이 기존 보고서에 섹션 하나를 추가**하면 됩니다.
**Status:** 확정 제안 — PRISM 보고서 구조 확인 필요(§6-5)

## 원칙 7 — 입력 주체를 분리한다

분석은 품질·기술 담당이 하지만 **대책의 실제 내용은 제조 부서가 압니다.** 한 사람이 전부 입력하게 하면 전달 과정에서 내용이 뭉개집니다.

**DD-127 · 대책 기록 요청을 담당자에게 전달하는 경로를 둔다. 분석자가 "대책 내용 확인 요청"을 보내면 해당 담당자가 짧은 화면에서 입력할 수 있다.**

초기에는 알림·링크 수준으로 충분합니다(전용 워크플로는 3단계).

# 3. 기록 구조 — 지식으로 재사용되려면 무엇이 필요한가

## 3-1. 5개 축

3단계에서 "비슷한 문제에 무엇이 효과 있었나"에 답하려면 다음이 필요합니다.

| # | 축 | 없으면 답할 수 없는 질문 |
|---|---|---|
| ① | **문제의 정체** (ProblemSignature) | "비슷한 문제"를 찾을 수 없음 |
| ② | **인과 주장과 근거** (Hypothesis + Evidence) | "왜 그 대책을 했는지" 알 수 없음 |
| ③ | **개입** (Countermeasure) | "무엇을 하면 되는지" 알 수 없음 |
| ④ | **결과** (VerificationResult) | "효과가 있었는지" 알 수 없음 |
| ⑤ | **맥락 조건과 부작용** | **"우리 설비에도 통할까"에 답할 수 없음** ← 가장 놓치기 쉬움 |

②는 2단계에 이미 있습니다(Finding/Evidence/Hypothesis). ①③④⑤가 신규입니다.

## 3-2. ⑤ 맥락 조건이 중요한 이유

지식이 재사용되는 순간의 질문은 언제나 **"그게 우리 상황에도 맞나"**입니다.

```text
나쁜 기록:  "척킹 압력을 올려서 토크 변동이 줄었다"
            → 우리 설비에도 통할까? 알 수 없음

좋은 기록:  "3호기(A사 2019년식), 모델 C 생산 중,
             척킹 압력 4.5→5.0,
             토크 변동 38% 감소,
             부작용: 없음"
            → 같은 설비 종류·같은 모델이면 시도해 볼 만함
```

맥락 대부분은 **앱이 데이터에서 자동으로 채울 수 있습니다**(설비·모델·생산량·기간). 사용자에게 묻는 것은 **부작용**뿐이며, 이것도 선택형으로 처리합니다.

```text
부작용이 있었습니까?
 ○ 없음   ○ 생산성 저하   ○ 비용 증가
 ○ 다른 품질특성 악화     ○ 기타 [        ]
```

**DD-128 · 검증 결과에는 맥락 조건(자동 수집)과 부작용(선택형 입력)을 함께 기록한다. "효과 없음"과 "판단 보류"도 동일하게 기록한다.**
**Reason:** 효과가 없었던 대책의 기록은 성공 사례만큼 가치 있다 — 같은 시도의 반복을 막는다. 스킬 공통규칙 9(*실패·미완·모름을 감추지 않는다*)와 일치.
**Status:** 확정 제안

## 3-3. 객체 정의 (초안)

**주의:** 아래는 초안이며, PRISM의 CTQ 코드 체계·설비 마스터 구조를 확인한 뒤 확정합니다(§6-5).

```text
ImprovementCase  ─┬─ AnalysisSession (원인 분석)   [기존]
  개선 사이클       ├─ Countermeasure (대책)         [신규]
                   ├─ AnalysisSession (검증 분석)   [기존]
                   └─ VerificationResult (검증 결과) [신규]
```

### ImprovementCase

| 필드 | 내용 | 저장 |
|---|---|---|
| case_id | 케이스 식별자 | 컬럼 |
| corporation / plant / line / machine | 조직·설비 축 | 컬럼(인덱스) |
| product_model / ctq_code | 제품·CTQ 축 (**PRISM 표준코드 참조**) | 컬럼(인덱스) |

| opened_at / closed_at | 기간 | 컬럼 |
| owner_user_id | 담당 | 컬럼 |
| related_case_ids | 재발 연결 | 컬럼(배열) |
| retention_hold | **검증 완료 시 자동 true** (Step 32 §6-④) | 컬럼 |
| signature | ProblemSignature 전체 | JSONB |

### Countermeasure

| 필드 | 내용 | 저장 |
|---|---|---|
| cm_id / case_id | 식별·연결 | 컬럼 |
| cm_type | 설비조정 / 부품교체 / 조건변경 / 표준개정 / 교육 / 자재변경 / 치공구개선 / 기타 | 컬럼(인덱스) |

| applied_by_dept | 실시 부서 | 컬럼 |
| source_hypothesis_id | 어느 가설에 대한 대책인가 | 컬럼 |

| target_scope | 적용 범위(라인·설비·제품) | JSONB |

| input_method | FORM / LLM_EXTRACTED / IMPORTED | 컬럼 |

| 필드 | 내용 | 저장 |

# 4. 기술 스택

## 4-1. 결론 — PostgreSQL을 유지하고 확장합니다

**DD-129 · 개선 사이클 데이터는 현재 운영 중인 PostgreSQL에 저장한다. 3단계 지식화를 위해 별도의 데이터베이스 기술(벡터 DB, 문서 DB, 그래프 DB)을 도입하지 않는다.**

| 근거 | 내용 |
|---|---|
| **브라운필드 원칙** | 이미 운영 중이고 팀이 익숙하다. 새 기술 도입은 그 자체가 위험이다 |
| **데이터 성격이 관계형** | 케이스 1:N 세션, 케이스 1:N 대책, 대책 1:N 검증 — 전형적 관계형 구조 |
| **JSONB로 진화 흡수** | 형태가 확정되지 않은 부분(Analysis State, Finding 배열)을 스키마 변경 없이 담을 수 있다 |
| **전문검색 내장** | 3단계 초기 유사 사례 검색은 PostgreSQL 전문검색으로 충분하다 |
| **벡터도 같은 DB에서** | 의미 검색이 필요해지면 `pgvector` 확장을 붙인다. **별도 벡터 DB를 두면 두 저장소의 동기화 문제가 생긴다** |
| **조인 필요** | CTQ 코드·설비 마스터를 PRISM 테이블과 조인해야 한다. 다른 DB면 조인이 불가능하다 |

**Status:** 확정 제안

## 4-2. 하이브리드 저장 원칙

**DD-130 · 검색·집계·조인에 사용되는 항목은 관계형 컬럼으로, 형태가 진화하거나 보존이 목적인 항목은 JSONB로 저장한다. 원본 파일·중간 포맷·보고서는 DB가 아니라 파일 스토리지에 둔다.**

> **검색할 것은 컬럼으로, 보존할 것은 JSONB로.**

| 저장 위치 | 대상 |
|---|---|
| **관계형 컬럼** | 조직·설비·제품·CTQ 축, 문제유형, 대책유형, 판정, 날짜, 효과크기 → **인덱스 대상** |
| **JSONB** | Analysis State 전체, Finding/Evidence/Hypothesis/Confounder 배열, parse_config, 재현성 메타데이터, 맥락 스냅샷 |
| **전문검색 컬럼** | 자유서술 원문(`description_raw`) — `tsvector` 인덱스 |
| **파일 스토리지** | 원본 Excel(A1), 중간 포맷(A2), 보고서 HTML(A4) — DB에 넣지 않음 |

이는 Step 30의 3계층 계약과 자연스럽게 맞습니다. L1 Agent Core는 대체로 JSONB, L2 Operations·L3 Administration은 대체로 컬럼입니다.

## 4-3. PRISM 기존 DB와의 관계

**DD-131 · 같은 PostgreSQL 데이터베이스 안에 별도 스키마(`statmod`)를 만들어 분리한다. PRISM 기존 테이블은 읽기만 하고 변경하지 않는다.**

```text
PostgreSQL (단일 DB)
 ├── 스키마 prism    ← 기존. 읽기만. 변경하지 않음
 │     · CTQ 마스터 · 설비 마스터 · MES 적재 데이터
 │     · 분석 결과 · 데이터 품질 평가 · 주차 보고서
 │
 └── 스키마 statmod  ← 신규
       · improvement_case · countermeasure · verification_result
       · analysis_session · job · audit · usage
```

| 선택지 | 평가 |
|---|---|
| 같은 스키마에 테이블 추가 | ✕ PRISM 운영에 영향. 권한 분리 불가 |
| **별도 스키마, 같은 DB** | **○ 권고** — 조인 가능, 권한 분리 가능, 마이그레이션 독립 |
| 별도 DB | ✕ CTQ·설비 마스터 조인 불가. 데이터 동기화 문제 발생 |

**마이그레이션 안전:** 앱 개발 스킬의 브라운필드 금지사항 — *"운영 중 데이터의 마이그레이션 경로 없이 스키마를 바꾸는 것"* — 에 따라 **기존 테이블은 일절 변경하지 않고 신규 스키마만 추가**합니다. 이것이 가장 안전한 확장 방식입니다.

## 4-4. 3단계 대비 — 지금 준비하는 것과 나중에 붙이는 것

| 시점 | 조치 |
|---|---|
| **2단계** | 인덱스 설계(조직·설비·CTQ·문제유형·대책유형·판정), 전문검색 인덱스, JSONB GIN 인덱스 |
| **3단계 초기** | SQL 조회만으로 유사 사례 검색 — 별도 기술 불필요 |
| **3단계 확장** | 의미 검색이 필요하면 `pgvector` 추가. 같은 DB이므로 마이그레이션 없음 |

**2단계에서 확보한 컬럼만으로 3단계 초기 질의가 이미 가능합니다.**

```sql
-- "같은 설비에서 같은 문제유형에 효과 있었던 대책"
SELECT cm.cm_type, cm.parameter_change, vr.effect_size
FROM   statmod.improvement_case c
JOIN   statmod.countermeasure cm       ON cm.case_id = c.case_id
JOIN   statmod.verification_result vr  ON vr.cm_id  = cm.cm_id
WHERE  c.machine_type = :machine_type
  AND  c.problem_type = :problem_type
  AND  vr.verdict     = 'EFFECTIVE'
ORDER BY vr.effect_size DESC;

-- "이 대책 유형의 성공률"
SELECT cm.cm_type,
       COUNT(*) FILTER (WHERE vr.verdict='EFFECTIVE')::float / COUNT(*) AS success_rate,
       COUNT(*) AS n
FROM   statmod.countermeasure cm
JOIN   statmod.verification_result vr ON vr.cm_id = cm.cm_id
GROUP BY cm.cm_type
HAVING COUNT(*) >= 5;
```

**DD-132 · 3단계 초기 지식 활용은 SQL 질의로 구현한다. 벡터 검색·지식 그래프는 사례가 충분히 축적되고 SQL로 부족함이 확인된 뒤에 도입한다.**
**Reason:** 사례 수십 건 규모에서는 SQL 조회가 의미 검색보다 정확하고 설명 가능하다. 사용자가 "왜 이 사례가 추천됐는지" 이해할 수 있다는 점도 중요하다 — 이 제품의 일관된 원칙(근거 추적 가능성)과 부합한다.
**Status:** 확정 제안

# 5. 역방향 검증 — 지금의 기록이 3단계에서 무엇이 되는가

기록 설계가 맞는지 확인하는 방법은 **3단계에서 그 기록으로 무엇을 할지 구체적으로 그려 보는 것**입니다.

## 시나리오 — 3단계에서의 화면

```text
[분석 중, Agent가 원인 후보를 좁힌 시점]

  AI  M4 설비의 토크 변동이 다른 설비보다 큽니다.
      Model 구성 차이를 통제한 뒤에도 차이가 유지됩니다.

      📚 비슷한 사례가 2건 있습니다
      ┌──────────────────────────────────────────────┐
      │ CASE-2026-0042  B법인 1라인 5호기 (동일 기종)  │
      │ 문제: 토크 변동 증가                           │
      │ 대책: 척킹 압력 4.5 → 5.0 (조건 변경)          │
      │ 결과: 변동 38% 감소 (d=0.62, p<0.001)         │
      │ 부작용: 없음         검증: 2026-06            │
      │                              [ 상세 보기 ]     │
      ├──────────────────────────────────────────────┤
      │ CASE-2026-0031  A법인 2라인 3호기 (동일 기종)  │
      │ 대책: 척킹 지그 교체 (치공구 개선)              │
      │ 결과: 효과 없음 (p=0.42)  ← 참고               │
      └──────────────────────────────────────────────┘

      이 대책 유형(조건 변경 - 척킹 압력)은
      동일 기종에서 7건 중 5건 효과가 확인되었습니다.
```

**이 화면이 성립하려면 지금 무엇이 기록되어야 하는지 역산합니다.**

| 화면 요소 | 필요한 기록 | 2단계에 포함? |
|---|---|---|
| "동일 기종" 매칭 | 설비 기종 코드 | ○ ProblemSignature |
| "토크 변동 증가" | problem_type | ○ |
| "척킹 압력 4.5→5.0" | parameter_change (JSONB) | ○ Countermeasure |
| "38% 감소, d=0.62" | effect_size | ○ VerificationResult |
| "부작용 없음" | side_effects | ○ |
| "효과 없음" 사례 표시 | verdict=NOT_EFFECTIVE도 기록 | ○ DD-128 |
| "7건 중 5건" 성공률 | cm_type + verdict 집계 | ○ |
| 상세 보기 (원 분석 추적) | analysis_session_id 연결 | ○ |

**모든 요소가 §3의 구조로 충족됩니다.** 즉 2단계 기록 설계는 3단계 활용을 감당할 수 있습니다.

**추가로 발견된 것:** "동일 기종"을 판정하려면 **설비 기종 코드**가 필요합니다. 라인·설비 번호만으로는 다른 법인의 같은 기종을 찾을 수 없습니다.

**DD-133 · ProblemSignature에 설비 기종(모델·제조사·도입연도) 축을 포함한다. 법인·라인·설비 번호만으로는 법인 간 지식 전이가 불가능하다.**
**Reason:** 지식화의 최대 가치는 **법인 간 전이**다(A법인에서 해결한 것을 B법인이 활용). 그런데 법인별 설비 번호는 서로 무관하므로, 기종 단위로 묶이지 않으면 전이가 일어나지 않는다. PRISM이 설비 마스터를 보유하고 있다면 여기서 가져올 수 있다(§6-5 확인 대상).
**Status:** 확정 제안

## 6-2. 확산 경로

```text
1차  협조적 기술 담당자 3~5명
      · 원인 분석 도구로서 가치 경험
      · 검증된 개선 케이스 5~10건 축적

      · 제조 부서가 자기 성과가 기록되는 것을 봄
      · 관계 역전 시작
        ↓
3차  제조 부서의 자발적 참여
      · "우리 개선도 검증해 달라"
        ↓
4차  3단계 — 사례 축적이 충분해져 지식 활용이 의미를 가짐
```

**3단계 착수 판단 기준: 검증 완료 케이스 30건 이상, 그중 동일 기종 반복이 5건 이상.** 그 이전에는 유사 사례 검색을 만들어도 보여줄 것이 없습니다.

# 8. PRISM 확인 사항 (U0 갱신)

Step 32 §8의 P-1~P-5 중 P-1(개선 기록 구조)과 P-2(CTQ 표준화)는 Ian이 답했습니다. 남은 것과 새로 발생한 것을 정리합니다.

| ID | 확인 사항 | 영향 |
|---|---|---|
| **P-2′** | CTQ 표준화 **완료 시점과 적용 범위** (전 법인인가, 일부인가) | 표준화 미완 법인은 케이스 축적에서 제외되거나 매핑 필요 |
| **P-3** | 주차 보고서의 **생성 구조** — 어디서 만들고 어디 저장되는가 | DD-126(보고서에 개선 섹션 추가) 구현 방식 |
| **P-4** | 데이터 품질 평가 결과가 **이력으로 남는가** | 데이터 품질 개선도 개선 사이클로 다룰 수 있는지 |
| **P-5** | 해외 법인 데이터의 스키마·코드 동일성 | 법인 간 지식 전이 가능 여부 |
| **P-6** (신규) | **설비 마스터에 기종·제조사·도입연도가 있는가** | **DD-133의 전제.** 없으면 법인 간 전이가 불가능하며 마스터 보완이 선행 과제 |
| **P-7** (신규) | PostgreSQL **버전과 확장 가능 여부**(전문검색, 추후 pgvector) | DD-129·DD-132의 전제 |

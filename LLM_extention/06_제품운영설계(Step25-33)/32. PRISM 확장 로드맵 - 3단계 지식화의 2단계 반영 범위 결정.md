# 0. 결론

**순차 진행하되, 2단계에 "기록 계층"을 반영합니다. 원칙은 하나입니다.**

> ### 기록(capture)은 2단계에, 활용(leverage)은 3단계에.

3단계 지식화의 *활용* 기능(유사 사례 검색, 지식 기반 분석 제안, 대책 유효성 통계)은 나중에 붙여도 비용이 선형으로 늘 뿐입니다. 그러나 3단계의 **원재료인 기록은 2단계가 운영되는 동안에만 생성되며, 기록하지 않고 지나간 개선 사이클은 복구할 수 없습니다.**

그리고 **현재 2단계 기획서에는 이미 구멍이 하나 있습니다.** "대책 검증까지 제공한다"고 정의했으면서 **대책(Countermeasure)이라는 객체가 설계에 없습니다**(§3-1). 이는 3단계를 위한 추가가 아니라 **2단계가 스스로 완결되기 위해 이미 필요했던 것**입니다.

다만 이 결정에는 조건이 있습니다. **세부 반영 범위는 PRISM의 현행 구조를 검증하기 전에는 확정할 수 없습니다**(§8).

# 1. 방법론 기준 판정 (app-build-lifecycle)

```
모드: upgrade (브라운필드 — PRISM은 운영 중인 앱)
규모: L (다중 사용자 + 개인정보·영업비밀 + MES 등 다중 시스템 연동 + 다법인·다국어)
현재 게이트: G2~G5는 상세 수행됨 / U0 미수행
증거 상태:
  · G2 요구사항       — reviewed (Step 26~31, 인수기준 약 60건)
  · G3 아키텍처       — reviewed (Step 27·29·31-2)
  · G4 데이터·계약    — reviewed (Step 30, 불변식 17건)
  · G5 UX·화면        — reviewed (Step 26, 31-1, 31-3)
  · U0 현행 검증      — missing  ← 가장 이른 미충족 게이트
차단 요인: PRISM의 실제 스키마·코드·운영 데이터를 한 번도 확인하지 않음
다음 허용 작업: U0 현행 검증 (§8)
```

## 1-1. 정직한 판정 — 가장 이른 미충족 게이트는 U0입니다

스킬의 `upgrade` 모드는 이렇게 규정합니다.

> **"그린필드는 인터뷰에서 시작하고, 브라운필드는 실행 검증에서 시작한다. 기존 코드를 읽기 전에 새 설계를 쓰지 않는다."**

**우리는 이 순서를 지키지 않았습니다.** Step 1~31 전체가 PRISM의 실제 데이터 구조·코드·운영 현황을 한 번도 확인하지 않은 상태에서 작성되었습니다. 이는 사고가 아니라 의도된 것이었고(GAP-08 "PRISM 기술스택·데이터 스키마는 연구범위 밖, 개발 착수 시 Ian이 전달"), **2단계 자체는 LLM 통계분석 모듈이라는 비교적 독립적인 신규 모듈**이므로 그 판단이 크게 틀리지 않았습니다.

**그러나 3단계 지식화는 사정이 다릅니다.** 지식화는 PRISM이 이미 무엇을 축적하고 있는지에 **절대적으로 의존**합니다. PRISM은 이미:

- MES CTQ 데이터를 전 법인 대상으로 분석하고
- 법인별·제품별 주차 보고서를 작성하며
- 데이터 품질(적용범위·규격·수집수준·결측·분해능)을 평가해 피드백하고 있습니다

**즉 "문제 발견" 단계의 기록은 이미 축적되고 있을 가능성이 높습니다.** 만약 PRISM에 이미 이슈·개선활동을 추적하는 구조가 있다면, 우리가 새 객체를 만들 것이 아니라 **기존 것을 확장**해야 합니다. 이것을 모르는 상태에서 3단계 스키마를 확정하면 스킬이 금지하는 *"기존 코드를 읽지 않고 새 구조를 제안하는 것"*에 해당합니다.

그래서 이 문서는 **원칙과 최소 항목은 확정하되, 세부 스키마는 U0 이후로 넘깁니다.**

# 2. 로드맵 이해

## 2-1. 세 단계가 각각 답하는 질문

```text
1단계 (현행 PRISM)          "무엇이 문제인가?"
  MES CTQ 데이터 분석         · 어느 공정·설비의 변동이 큰가
  전 법인 대시보드            · 공정성능이 부족한 곳은 어디인가
  법인별·제품별 주차 보고서    · 데이터 자체는 믿을 만한가
  데이터 품질 평가·피드백      → 문제의 발견과 수준 평가

2단계 (이번 기획, Step 1~31)  "왜 그런가? 그 대책이 효과가 있었는가?"
  LLM 연동 통계분석 모듈       · 근본 원인을 찾는 통계 도구 제공
  Manual + Agent 분석         · 교란요인 통제, 인과 과장 방지
  대책 검증                   → 원인 분석과 대책 검증

3단계 (지식화)                "전에 비슷한 문제를 어떻게 풀었는가?"
  검증 데이터의 지식화          · 문제-원인-대책의 순환 고리 축적
  사례 축적과 재활용            · 축적된 지식으로 다음 사이클을 고도화
                             → 조직 학습
```

## 2-2. 이 로드맵의 구조적 의미

세 단계는 기능의 나열이 아니라 **하나의 개선 사이클을 완성해 가는 과정**입니다.

```text
        ┌─────────────────────────────────────────────┐
        │                                             │
        ▼                                             │
   ① 문제 발견 ──► ② 원인 분석 ──► ③ 대책 수립·검증 ──┤
     (1단계)         (2단계)          (2단계)          │
                                        │             │
                                        ▼             │
                                   ④ 지식화           │
                                     (3단계)          │
                                        │             │
                                        └─────────────┘
                                    축적된 지식이
                                    ①②③을 고도화
```

**3단계는 앞의 세 단계를 닫아 순환으로 만드는 고리입니다.** 따라서 3단계가 없으면 사이클은 매번 처음부터 시작합니다 — 같은 설비에서 같은 문제가 재발해도 6개월 전 해결 방법을 아무도 찾지 못합니다.

이것이 3단계가 "있으면 좋은 기능"이 아니라 **로드맵의 종착점**인 이유입니다.

# 3. 현재 2단계 기획서 점검

## 3-1. 발견 — 대책(Countermeasure)이 객체로 존재하지 않습니다

Ian은 2단계 범위를 이렇게 정의했습니다.

> "원인 분석 후 **제조, 기술 부서의 대책을 검증**하는 것까지 제공을 하는 것이 이번에 만든 기획서입니다."

그런데 Step 1~31을 점검하면 **대책을 다루는 구조가 부분적으로만 있습니다.**

| 있는 것 | 없는 것 |
|---|---|
| UC-07 개선 전후 효과 검증 시나리오 | **Countermeasure 객체** — 무엇을 실시했는지 |
| Evidence Level **E4 = 실험/개선검증** | **VerificationResult 객체** — 검증 결과의 구조화 |
| 측정시스템 동일성 선행 질문(DD-023) | 대책 실시일·실시 부서·대상 범위 |
| `final_decision` 필드 | 개선 효과의 크기·지속성 확인 |
| 재현성 메타데이터(DD-084) | 대책과 원인(Hypothesis)의 연결 |

**즉 현재 설계는 "개선 전후 데이터를 통계적으로 비교"할 수는 있지만, "무엇을 바꿨기에 그렇게 되었는가"는 기록하지 않습니다.**

이것은 3단계를 위한 추가 요구가 아닙니다. **2단계가 스스로 완결되기 위해 이미 필요했던 것**입니다. 대책 내용을 모르면 검증 결과는 "6월 이후 평균이 낮아졌다"는 관찰에 그치고, 보고서에도 그렇게만 남습니다.

그리고 공교롭게도 **이것이 3단계 지식의 핵심 원재료**입니다. 지식이란 결국 `이런 문제에 이런 원인이 있었고 이런 대책이 이만큼 효과가 있었다`의 축적이기 때문입니다.

## 3-2. 이미 3단계 대비가 되어 있는 부분

반대로, 기존 설계에는 지식화에 그대로 쓸 수 있는 요소가 상당히 있습니다. 이것이 "순차 진행이 가능하다"는 판단의 근거입니다.

| 기존 요소 | 3단계에서의 역할 |
|---|---|
| **Finding / Evidence / Hypothesis / Confounder** | 지식의 기본 단위. 이미 구조화되어 있음 |
| **Evidence Level E0~E4** | 지식의 신뢰도 등급. E4가 곧 "검증된 지식" |
| **재현성 메타데이터**(DD-084, 원본 삭제 후에도 존속) | 지식의 근거 보존 |
| **Step 6 Manufacturing Knowledge Architecture** | Raw-Wiki → LLM-Wiki → Agent Knowledge 파이프라인이 이미 설계됨 |
| **Case Library as Analysis Pattern Library**(Step 6) | 사례 축적 개념이 이미 존재 |
| **Planning / Interpretation Retrieval 분리**(Step 6·7) | 지식을 분석에 되먹이는 경로가 이미 설계됨 |
| **보존 지정 Hold**(DD-075) | 중요 사례의 영구 보존 수단 |

**Step 6은 이미 지식 아키텍처를 설계해 두었고, Step 31 §4-2에서 MVP 범위 밖으로 뺐을 뿐입니다.** 즉 3단계는 "새로 설계할 것"이 아니라 **"꺼둔 것을 켜는 것"**에 가깝습니다.

# 4. 선택지 평가

## A안 — 2단계와 3단계 동시 구현

| | 내용 |
|---|---|
| **장점** | 지식 기록이 처음부터 "당연한 흐름"으로 정착 / 개발 컨텍스트가 살아 있을 때 함께 만드는 것이 쌈 / 로드맵 목표에 한 번에 도달 |
| **단점** | **활용 기능을 검증할 수 없음** — 사례가 0건인 상태에서 검색·추천 UI를 만들어도 잘 동작하는지 알 수 없다. 스킬 공통규칙 2 "검증 없는 완료 없음" 위반 / **지식 구조가 추측이 됨** — 어떤 지식이 유용한지는 사례가 쌓여야 안다 / T-13(첫 사용 가능 제품)이 크게 지연 / 2단계 자체가 이미 Task 20개 |
| **평가** | **권장하지 않음.** 특히 두 번째 단점이 치명적이다 — 잘못 추측한 지식 스키마는 나중에 마이그레이션 비용으로 돌아온다 |

## B안 — 완전 순차 (2단계에서 3단계를 고려하지 않음)

| | 내용 |
|---|---|
| **장점** | 2단계 범위가 명확 / 가장 빠른 출시 |
| **단점** | **치명적.** ① 2단계 운영 기간 동안의 개선 사이클이 기록되지 않아 **복구 불가능하게 소실** ② 우리가 정한 보유기간(원본 90일 / 세션 2년)이 그 소실을 **자동으로 집행**한다 ③ 3단계 시작 시점에 빈 창고 ④ 나중에 기록 기능을 추가하면 사용자가 "일이 늘었다"고 받아들여 정착 실패 |
| **평가** | **채택 불가.** §5의 비대칭성 때문 |

## C안 — 순차 진행 + 2단계에 기록 계층 반영 ★ 권고

| | 내용 |
|---|---|
| **내용** | 2단계에 **개선 사이클을 기록하는 구조와 UX**를 포함한다. 그 기록을 **검색·추천·분석 제안에 활용하는 기능은 3단계**로 미룬다 |
| **장점** | A안의 장점(정착, 컨텍스트) 대부분을 확보 / B안의 치명적 단점(기록 소실) 제거 / 추측 기반 설계 회피 — 기록은 사실이고, 구조화는 사례를 보고 한다 / **2단계 자체의 구멍(§3-1)도 함께 메워짐** |
| **단점** | 2단계 범위가 소폭 증가 (§7에서 정량화) / 사용자에게 "기록하는 부담"이 2단계부터 발생 |
| **평가** | **권고** |

# 5. 권고의 근거 — 비대칭성

C안을 택하는 이유는 **기록과 활용의 비용 구조가 비대칭이기 때문**입니다.

```text
                   지금 안 하면          나중에 하면
─────────────────────────────────────────────────────────
기록(capture)      데이터가 소실됨       ✕ 복구 불가능
                   (2년간 운영하며
                    보유기간이 집행)

활용(leverage)     아무 손실 없음        ○ 선형 비용
                   (사례가 없으므로
                    만들 이유도 없음)
```

**활용 기능은 늦게 만들어도 잃는 것이 없습니다.** 오히려 사례를 보고 만드는 편이 더 정확합니다.
**기록은 늦게 만들면 그 사이의 것을 영원히 잃습니다.**

## 5-1. 가장 구체적인 근거 — 보유기간 정책과의 충돌

이건 추상적 우려가 아니라 **우리 설계에 이미 존재하는 구체적 결함**입니다.

Step 29 DD-073에서 다음을 정했습니다.

| 자산 | 보유기간 |
|---|---|
| A1 원본 업로드 파일 | 90일 |
| A2 분석용 중간 포맷 | 90일 |
| A3 분석 세션·결과 | 2년 |
| A4 보고서 | 1년 |

**2단계를 이 정책 그대로 2년간 운영하면, 3단계가 시작되는 시점에 축적된 것은 거의 없습니다.** 대책 검증에 쓴 원본 데이터는 90일 뒤 사라지고, 분석 세션도 2년이면 만료됩니다.

DD-074(재현성 메타데이터 존속)와 DD-075(보존 지정 Hold)가 완충 역할을 하지만, **둘 다 개별 케이스에 수동으로 적용되는 장치**입니다. 지식 축적은 체계적이어야 합니다.

→ **최소 조치: 검증이 완료된 개선 케이스는 보유기간 만료에서 자동 제외한다**(§6 항목 4).

# 6. 2단계에 반영할 최소 항목 6가지

**원칙: 기록의 뼈대만 넣습니다. 지식의 구조는 넣지 않습니다.**

## ① ImprovementCase — 개선 사이클 컨테이너

현재 최상위 객체는 `AnalysisSession`이고 세션끼리는 연결되지 않습니다. 그 위에 **하나의 개선 사이클**을 담는 컨테이너를 둡니다.

```text
ImprovementCase  (문제 → 원인 → 대책 → 검증 한 사이클)
   ├── AnalysisSession (원인 분석)        ← 기존
   ├── Countermeasure (대책)              ← 신규
   ├── AnalysisSession (검증 분석)        ← 기존
   └── VerificationResult (검증 결과)     ← 신규
```

세션 하나로 끝나지 않는 것이 핵심입니다. 원인 분석과 대책 검증은 **몇 주~몇 달 떨어진 별개 세션**이며, 그 둘을 묶는 것이 케이스입니다.

## ② Countermeasure — 대책의 구조화 (2단계 자체의 요구사항)

무엇을 바꿨는지 기록합니다. **§3-1에서 지적한 구멍을 메우는 항목입니다.**

기록할 것: 대책 내용 / 대상(설비·공정·범위) / 실시 부서 / 실시일 / 대응하는 Hypothesis 참조 / 유형(설비개선·조건변경·표준개정·교육·자재변경 등).

## ③ VerificationResult — 검증 결과의 구조화

전후 비교 결과, 효과 크기, 판정(효과 있음/없음/판단 보류), **측정시스템 동일성 확인 여부**(DD-023과 연결), 지속성 재확인 예정일.

**"효과 없음"과 "판단 보류"도 반드시 기록합니다.** 실패한 대책의 기록은 성공한 대책만큼 가치 있는 지식이며, 스킬 공통규칙 9("실패·미완·모름을 감추지 않는다")와도 일치합니다.

## ④ 보유기간 예외 — 검증 완료 케이스의 자동 보존 ★ 가장 중요

`VerificationResult`가 생성된 `ImprovementCase`는 **보유기간 만료 대상에서 자동 제외**합니다(자동 Hold 부여).

이것 하나만으로 §5-1의 결함이 해소됩니다. **다른 항목을 다 미루더라도 이것만은 2단계에 넣어야 합니다** — 나머지는 나중에 추가할 수 있지만, 삭제된 데이터는 되돌릴 수 없기 때문입니다.

## ⑤ Problem Signature — 정규화된 문제 식별 축

나중에 "비슷한 사례"를 찾으려면 **지금 정규화된 형태로 저장**해야 합니다. 나중에 자연어에서 추출하려 하면 정확도가 낮습니다.

축: 법인 / 공장 / 라인 / 설비 / 제품·모델 / CTQ 항목 / 문제 유형(변동 증가·평균 이동·불량률 상승 등).

**단, 이 축의 코드 체계는 새로 만들지 않습니다.** PRISM이 이미 MES 데이터를 다루므로 코드 체계가 존재할 것이고, **그것을 그대로 재사용해야 합니다**(§8 확인 P-2). 새 체계를 만들면 PRISM 1단계 데이터와 연결되지 않아 지식화의 의미가 없어집니다.

## ⑥ 케이스 간 참조 — 재발 연결

`related_cases` 필드 하나. "이 문제는 CASE-2026-0042의 재발이다"를 사용자가 표시할 수 있게 합니다. 자동 탐지는 3단계입니다.

# 7. 3단계로 미루는 것

| 항목 | 미루는 이유 |
|---|---|
| 유사 사례 검색·추천 | 사례 0건에서 검증 불가 |
| 지식 기반 분석 계획 제안(Planning Retrieval) | 어떤 지식이 유용한지는 사례를 보고 판단 |
| 대책 유효성 통계 ("이 유형에 이 대책이 몇 % 효과") | 통계적으로 의미 있으려면 사례 수십 건 필요 |
| Knowledge Graph | Step 6에 방향만 있음. 구조는 사례 축적 후 |
| 자동 지식 추출·요약 | LLM 비용 발생. 활용처가 확정된 뒤에 |
| 제조·사내 Knowledge RAG | Step 31 §4-2에서 이미 Phase 2 이관 결정됨 |

## 7-1. 과잉 설계 방지 원칙

스킬의 가드레일 — *"목적·범위·산출물이 정해지기 전에 큰 폴더 구조를 만들지 않는다"* 를 여기에 적용합니다.

> **기록은 충실히, 구조화는 나중에.**

지금 3단계 지식 스키마를 상세히 설계하면 **추측에 기반한 구조**가 됩니다. 어떤 형태의 지식이 실제로 재사용되는지는 30~50건의 사례가 쌓인 뒤에야 알 수 있습니다.

따라서 2단계에서는 **원재료를 손실 없이 남기는 것**만 하고, 지식의 형태는 3단계 착수 시점에 실제 사례를 보고 설계합니다. 좋은 기록에서는 나중에 어떤 구조든 도출할 수 있지만, **없는 기록에서는 아무것도 도출할 수 없습니다.**

# 8. 이 결정을 확정하기 위한 현행 검증 (U0)

**§1-1에서 밝힌 대로, 아래 5가지를 확인하기 전에는 세부 스키마를 확정하면 안 됩니다.**

| ID | 확인 사항 | 이 답이 바꾸는 것 |
|---|---|---|
| **P-1** | PRISM에 **이미 이슈·개선활동·조치이력을 기록하는 구조가 있는가?** | 있다면 `ImprovementCase`를 새로 만들지 않고 **기존 것을 확장**해야 함. 이 하나가 §6 전체의 형태를 바꿈 |
| **P-2** | **MES 코드 체계**(설비·불량유형·CTQ·제품)의 정규화 수준은? 법인 간 통일되어 있는가? | Problem Signature(§6-⑤)의 축을 그대로 쓸 수 있는지 결정. 통일되지 않았다면 **매핑 계층이 선행 과제**가 됨 |
| **P-3** | 주차 보고서 산출물이 **어디에 저장되고 재조회 가능한가?** | 1단계 산출물이 지식 축적의 출발점이 될 수 있는지 결정 |
| **P-4** | **데이터 품질 평가 결과가 이력으로 남는가?** | 남는다면 "데이터 품질 개선"도 하나의 개선 사이클로 다룰 수 있음 |
| **P-5** | 해외 법인 데이터가 **같은 스키마·같은 코드 체계**인가? | 다르면 지식이 법인 단위로 파편화됨. 31-4 다국어 설계와 직결 |

**P-1과 P-2가 결정적입니다.** 특히 P-2가 부정적이면(법인마다 설비·불량유형 코드가 다르면) **지식 축적 자체가 성립하지 않으므로**, 3단계 이전에 코드 표준화가 선행 과제로 올라갑니다. 이는 앱 개발이 아니라 **데이터 거버넌스 과제**입니다.

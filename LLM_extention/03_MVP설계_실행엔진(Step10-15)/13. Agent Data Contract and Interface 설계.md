좋습니다. **Step 13은 이번 프로젝트에서 매우 중요한 단계**입니다.

지금까지 “Agent가 무엇을 해야 하는가”와 “어떻게 실행되는가”를 설계했다면, 이제부터는 **각 구성요소가 서로 어떤 데이터를 주고받아야 하는지를 계약(Contract)으로 고정**합니다.

이렇게 해 두어야 나중에 Claude Code가 개발할 때도 임의로 구조를 바꾸지 않고, **Schema → Interface → Test → Implementation** 순서로 안정적으로 개발할 수 있습니다.

# Step 13. Agent Data Contract & Interface 설계

## 13-1. 전체 데이터 구조

먼저 Agent 내부에서 사용되는 핵심 객체를 확정하겠습니다.

```
                         User Question
                              │
                              ▼
                    ┌──────────────────┐
                    │  ProblemModel    │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │  AnalysisPlan    │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │    ToolCall      │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │    ToolResult    │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │    Finding       │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │    Evidence      │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   NextAction     │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │ AnalysisSession  │
                    └──────────────────┘
```

이 객체들이 Agent의 **공통 언어(Common Language)**가 됩니다.

---

# 13-2. 가장 상위 객체 — AnalysisSession

모든 분석의 최상위 컨테이너입니다.

개념 Schema:

```
{
  "session_id": "AS-20260912-001",
  "status": "ANALYZING",

  "user_question": "최근 토크 불량이 증가한 원인을 찾아줘.",

  "problem_model": {},
  "dataset_context": {},
  "analysis_plan": {},

  "analysis_history": [],
  "findings": [],
  "hypotheses": [],
  "confounders": [],
  "evidence": [],
  "next_actions": [],

  "final_decision": null
}
```

### `status`

초기에는 다음 정도면 충분합니다.

```
IDLE
UNDERSTANDING
ANALYZING
WAITING_USER
WAITING_DATA
COMPLETED
FAILED
```

향후 Agent가 복잡해지면 세분화할 수 있습니다.

---

# 13-3. ProblemModel Schema

이 객체가 **자연어 제조 문제를 구조화된 분석 문제로 바꾸는 핵심**입니다.

```
{
  "problem_type": "ROOT_CAUSE_EXPLORATION",

  "response": {
    "name": "Torque",
    "data_type": "continuous",
    "unit": "N·m"
  },

  "quality_event": {
    "name": "Torque Defect",
    "variable": "Defect_Flag"
  },

  "objective": {
    "type": "IDENTIFY_ASSOCIATED_FACTORS",
    "direction": "DEFECT_INCREASE"
  },

  "candidate_factors": [
    "Model",
    "Line",
    "Machine",
    "Shift",
    "Operator"
  ],

  "time_scope": {
    "type": "RECENT"
  },

  "relationship": "UNKNOWN"
}
```

### `problem_type`은 enum으로 관리하는 것이 좋습니다.

MVP에서는:

```
CURRENT_STATE_DIAGNOSIS
TARGET_COMPARISON
GROUP_COMPARISON
MULTI_GROUP_COMPARISON
IMPROVEMENT_VERIFICATION
RELATIONSHIP_ANALYSIS
ROOT_CAUSE_EXPLORATION
PROCESS_JUDGMENT
```

정도로 시작합니다.

앞서 정의한 제조 질문 taxonomy와 직접 연결됩니다.

---

# 13-4. DatasetContext

Agent가 데이터를 직접 기억하는 것이 아니라 **데이터의 구조와 상태**를 기억합니다.

```
{
  "dataset_id": "DS-001",
  "dataset_version": 1,

  "rows": 18420,
  "columns": 12,

  "variables": [
    {
      "name": "Torque",
      "type": "continuous",
      "unit": "N·m"
    },
    {
      "name": "Machine",
      "type": "categorical"
    },
    {
      "name": "Defect_Flag",
      "type": "binary"
    }
  ],

  "quality_status": "PASS_WITH_WARNING",

  "missing_rate": 0.002,

  "scope": {
    "start": "2026-08-01",
    "end": "2026-09-10"
  }
}
```

여기서 중요한 원칙은:

> **DatasetContext는 데이터 자체가 아니라 데이터에 대한 메타정보입니다.**

실제 데이터는 Data Engine이 관리합니다.

---

# 13-5. AnalysisPlan Schema

분석 계획은 우리가 앞서 정의한 대로 **Graph 구조**로 가져갑니다.

```
{
  "plan_id": "PLAN-001",

  "objective": "Identify factors associated with torque defect increase",

  "nodes": [
    {
      "id": "A01",
      "type": "DATA_QUALITY",
      "status": "COMPLETED"
    },
    {
      "id": "A02",
      "type": "DEFECT_RATE",
      "status": "COMPLETED"
    },
    {
      "id": "A03",
      "type": "TREND_ANALYSIS",
      "status": "COMPLETED"
    },
    {
      "id": "A04",
      "type": "MACHINE_SCREENING",
      "status": "COMPLETED"
    },
    {
      "id": "A05",
      "type": "CONFOUNDING_CHECK",
      "status": "PENDING"
    }
  ],

  "edges": [
    {
      "from": "A01",
      "to": "A02"
    },
    {
      "from": "A02",
      "to": "A03"
    },
    {
      "from": "A03",
      "to": "A04"
    },
    {
      "from": "A04",
      "to": "A05"
    }
  ]
}
```

### 왜 Graph인가?

Agent는 분석 중간에 계획을 바꿀 수 있기 때문입니다.

예:

```
Machine 분석
      ↓
Model이 Confounder
      ↓
Model 분석 추가
      ↓
동일 Model 내 Machine 비교
```

따라서 처음부터 고정된 Wizard 형태로 만들면 Agent의 장점이 사라집니다.

---

# 13-6. ToolCall Schema

LLM이 Tool을 요청하는 데이터입니다.

```
{
  "tool_name": "group_defect_rate",

  "arguments": {
    "group_by": "Machine",
    "response": "Defect_Flag"
  },

  "reason": "설비별 불량률 차이를 탐색하기 위함",

  "analysis_node_id": "A04"
}
```

여기서 `reason`은 사용자에게 반드시 보여줄 필요는 없습니다.

Agent trace/debugging 및 평가에 유용합니다.

---

# 13-7. ToolResult Schema

Tool 실행 결과는 반드시 표준화합니다.

```
{
  "tool_name": "group_defect_rate",
  "tool_version": "1.0.0",

  "dataset_id": "DS-001",
  "dataset_version": 1,

  "input": {
    "group_by": "Machine",
    "response": "Defect_Flag"
  },

  "result": {
    "groups": [
      {
        "group": "M1",
        "n": 4000,
        "defects": 36,
        "defect_rate": 0.009
      },
      {
        "group": "M4",
        "n": 3700,
        "defects": 108,
        "defect_rate": 0.0292
      }
    ]
  },

  "diagnostics": {},

  "warnings": [],

  "status": "SUCCESS"
}
```

이 구조의 장점은 매우 큽니다.

LLM은 ToolResult의 숫자만 보고 해석할 수 있습니다.

즉:

```
Raw Data
   ↓
Statistical Engine
   ↓
ToolResult
   ↓
LLM
```

입니다.

---

# 13-8. Finding Schema

ToolResult를 사람이 이해할 수 있는 **의미 있는 발견(Findings)**으로 변환합니다.

```
{
  "finding_id": "F002",

  "statement":
    "M4에서 다른 설비보다 높은 토크 불량률이 관찰됨.",

  "type": "OBSERVED_PATTERN",

  "evidence_level": "E1",

  "source_analysis": [
    "A04"
  ],

  "direction": "HIGHER",

  "confidence": "MEDIUM"
}
```

Finding에는 반드시 **출처 분석 ID**가 있어야 합니다.

그래야 나중에:

> “왜 그렇게 판단했습니까?”

라는 질문에 근거를 추적할 수 있습니다.

---

# 13-9. Evidence Schema

Evidence는 Finding보다 한 단계 더 중요합니다.

```
{
  "evidence_id": "EVD-003",

  "level": "E2",

  "type": "STATISTICAL_ASSOCIATION",

  "source_analysis": [
    "A04",
    "A05"
  ],

  "basis": [
    "chi_square_test",
    "group_defect_rate"
  ],

  "causal_strength": "LOW",

  "status": "VALID"
}
```

여기서:

```
Evidence Level
E0
E1
E2
E3
E4
```

는 우리가 앞에서 정한 체계를 그대로 사용합니다.

### 중요한 추가 필드

```
causal_strength
```

를 두는 것을 권합니다.

예:

```
E2 + causal_strength LOW
```

이면:

> 관련성이 확인되었다.

까지만 허용합니다.

---

# 13-10. Hypothesis Schema

가설도 별도 객체로 관리합니다.

```
{
  "hypothesis_id": "H002",

  "statement":
    "Model C의 생산 조건이 토크 불량 증가와 관련되어 있을 가능성이 있음.",

  "factor": "Model",

  "status": "STRENGTHENED",

  "supporting_findings": [
    "F003",
    "F004"
  ],

  "confidence": "MEDIUM"
}
```

상태는:

```
UNTESTED
SUPPORTED
STRENGTHENED
WEAKENED
REJECTED
CONFIRMED
```

정도로 가져갈 수 있습니다.

단, **CONFIRMED의 의미는 매우 엄격하게 정의**해야 합니다.

관찰 데이터에서 통계적으로 유의하다는 이유만으로 `CONFIRMED`를 허용하면 안 됩니다.

---

# 13-11. Confounder Schema

제조 데이터에서 매우 중요한 객체입니다.

```
{
  "confounder_id": "C001",

  "factor": "Model",

  "affected_factor": "Machine",

  "risk": "HIGH",

  "reason":
    "M4에서 Model C 생산 비중이 상대적으로 높음.",

  "status": "UNRESOLVED",

  "recommended_analysis":
    "MODEL_CONTROLLED_MACHINE_COMPARISON"
}
```

이 구조를 사용하면 Agent가 단순한 통계 결과를 넘어 **제조 데이터의 구조적 문제를 관리**할 수 있습니다.

---

# 13-12. NextAction Schema

Agent가 다음에 무엇을 할지 구조화합니다.

```
{
  "action_type": "CONTINUE_ANALYSIS",

  "analysis_type": "MODEL_CONTROLLED_MACHINE_COMPARISON",

  "priority": "HIGH",

  "reason":
    "Machine 효과와 Model 효과가 혼재되어 있어 교란 가능성을 확인할 필요가 있음.",

  "expected_information_gain": 0.91
}
```

`action_type`은 MVP에서 다음 5개로 제한하는 것을 권합니다.

```
CONTINUE_ANALYSIS
ASK_USER
REQUEST_DATA
STOP
ESCALATE_TO_EXPERIMENT
```

이렇게 제한하면 Agent의 행동을 추적하고 평가하기 쉬워집니다.

---

# 13-13. Analysis History

모든 Tool 실행은 History에 남겨야 합니다.

```
{
  "analysis_id": "A04",

  "timestamp": "2026-09-12T10:30:00",

  "tool": "group_defect_rate",

  "input": {
    "group_by": "Machine"
  },

  "result_reference": "TR-004",

  "status": "COMPLETED"
}
```

이것은 단순 로그가 아닙니다.

다음 기능에 사용됩니다.

- 중복 분석 방지
- 분석 재현
- 세션 재개
- 결과 추적
- 오류 분석
- Golden Case 평가
- Agent Debugging

# 13-16. Tool의 공통 Interface

모든 Tool이 서로 다른 방식으로 동작하면 유지보수가 어려워집니다.

따라서 개념적으로:

```
Tool
 ├── name
 ├── version
 ├── description
 ├── input_schema
 ├── output_schema
 └── execute()
```

를 공통으로 갖도록 합니다.

예:

```
ToolDefinition

name:
welch_t_test

description:
두 독립 그룹의 평균 차이를 검정하며
분산이 동일하지 않은 경우 사용

input_schema:
...

output_schema:
...

execute():
...
```

# 13-17. Statistical Engine과 Tool의 차이

여기서 개발할 때 혼동하면 안 되는 부분입니다.

### Statistical Engine

실제 계산을 수행합니다.

```
Welch t-test
↓
t statistic
df
p-value
CI
```

### Tool

Agent가 사용할 수 있는 인터페이스입니다.

```
welch_t_test()
```

따라서:

```
LLM
 ↓
Tool
 ↓
Statistical Engine
 ↓
Result
```

입니다.

이 구조가 나중에 Python의 `scipy`, `statsmodels` 등의 구현체가 바뀌어도 Agent interface를 유지할 수 있게 합니다.

# 13-18. LLM Provider도 추상화합니다

향후 모델을 바꿀 가능성이 높기 때문에 처음부터 특정 LLM에 종속시키지 않는 것이 좋습니다.

개념적으로:

```
LLMProvider
│
├── generate()
├── structured_output()
├── tool_call()
└── stream()
```

그리고:

```
OpenAIProvider
AnthropicProvider
LocalLLMProvider
```

등이 구현체가 됩니다.

이렇게 하면 **Agent Logic과 LLM Vendor를 분리**할 수 있습니다.

# 13-20. Claude Code 개발 방식도 여기서 결정합니다

사용자께서 Claude Code를 중심으로 개발하실 예정이라면 **“기능부터 만들어줘” 방식으로 개발시키면 안 됩니다.**

다음 원칙을 추천합니다.

## Phase A — Contract First

```
Schema
 ↓
Interface
 ↓
Unit Test
```

먼저 계약을 확정합니다.

---

## Phase B — Deterministic Engine

```
Statistical Engine
 ↓
Tool
 ↓
Tool Test
```

LLM 없이 통계 기능을 먼저 검증합니다.

---

## Phase C — Rule Engine

```
Problem Model
 ↓
Rule
 ↓
Expected Method
```

Golden Dataset으로 검증합니다.

---

## Phase D — Agent

```
LLM
 ↓
Problem Model
 ↓
Analysis Plan
 ↓
Tool Call
```

이때 처음으로 LLM을 연결합니다.

---

## Phase E — Evaluation

```
Golden Case
 ↓
Agent Run
 ↓
Evaluation
 ↓
Failure Analysis
 ↓
Fix
 ↓
Regression
```

# 13-21. 특히 Schema를 먼저 만드는 이유

LLM을 먼저 연결하면 이런 일이 생깁니다.

```
Prompt
   ↓
LLM
   ↓
"그럴듯한 JSON"
```

그런데 어떤 때는:

```
{
  "analysis": "t-test"
}
```

다른 때는:

```
{
  "method": "two_sample_t_test"
}
```

또 어떤 때는:

```
{
  "recommended_analysis": "Welch test"
}
```

처럼 결과 구조가 흔들릴 수 있습니다.

반면 Schema를 먼저 정의하면:

```
LLM
 ↓
Structured Output
 ↓
Schema Validation
 ↓
PASS / REJECT
```

가 됩니다.

따라서 **Schema가 Agent의 API 계약**이 됩니다.

# 13-22. 이 프로젝트의 개발 철학을 한 문장으로 정리

이번 Step에서 가장 중요한 개발 원칙은 다음입니다.

> **LLM에게 자유를 주되, 데이터 구조·통계 계산·핵심 판단·실행 결과의 형식은 자유롭게 만들지 않는다.**

즉,

```
LLM
= Flexible Reasoning

Schema
= Structured Communication

Rule
= Hard Constraint

Tool
= Deterministic Capability

State
= Persistent Fact

Knowledge
= Domain Context
```

입니다.

이렇게 해야 **LLM의 유연성과 통계 프로그램의 신뢰성**을 동시에 확보할 수 있습니다.

# Step 13의 의미

이제 프로젝트가 **“AI 통계분석 앱 아이디어” 수준을 넘어섰습니다.**

현재까지 확정된 것을 계층적으로 보면:

### Step 1~4

**무엇을 만들 것인가?**

→ Manufacturing Statistical Analysis Agent

### Step 5~6

**어떤 구조와 지식을 사용할 것인가?**

→ Tool + Rule + State + Knowledge

### Step 7~9

**Agent를 어떻게 통제하고 검증할 것인가?**

→ Prompt + Brain + Golden Case + Evaluation

### Step 10~12

**실제로 어떻게 실행할 것인가?**

→ Orchestrator + Execution Loop + State Machine

### Step 13

**구성요소들이 어떤 계약으로 연결되는가?**

→ **Schema + Interface + Domain Model**

여기까지 오면서 상당히 중요한 변화가 생겼습니다.

처음의 **SmartStat Manufacturing**은 “제조 현장에서 쉽게 통계분석을 수행하도록 하는 프로그램”이었다면, 현재 설계는:

> **제조 현장의 질문을 이해하고, 통계적 문제로 구조화하고, 적절한 분석 Tool을 선택·실행하고, 통계적 근거와 제조적 의미를 연결하며, 필요한 경우 다음 분석이나 개선 행동까지 제안하는 Manufacturing Statistical Analysis Agent**

로 발전했습니다.

그리고 기존 기획서에서 정의했던 **Easy Access → Easy Analysis → Easy Visualization → Easy Interpretation → Easy Decision**이라는 사용자 가치도, 이제는 **Easy Understanding → Easy Planning → Evidence-based Decision → Next Action**까지 확장할 수 있습니다. 통계분석 앱 제작 기획서.mdMD

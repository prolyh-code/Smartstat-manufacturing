# 10-1. MVP 범위 최종 확정

기존 기획서의 핵심 기능은 유지하되, LLM Agent 구조에 맞게 역할을 재배치합니다.

기존 앱의 핵심 철학이

> **현장 문제 → 질문 → 분석 → 시각화 → 해석 → 판단**

이었다면,

MVP에서는 다음으로 확장합니다.

> **현장 문제 → 질문 → 문제 정의 → 분석 계획 → 통계 분석 → 근거 발견 → 해석 → 제조 판단 → Next Best Analysis**

기존 기획서에서 정의한 통계 기능들은 대부분 **Statistical Engine / Tool**로 재사용할 수 있습니다.

### MVP에 반드시 포함

|영역|MVP|
|---|---|
|데이터|Excel / CSV|
|Data Profiling|필수|
|데이터 품질|Missing / Duplicate / 기본 이상치|
|기초통계|Mean, SD, Median, Min, Max 등|
|시각화|Histogram / Box Plot / Scatter Plot|
|1 Sample|One-sample t-test|
|2 Group|t-test / Welch|
|Paired|Paired t-test|
|Multi Group|ANOVA / Welch ANOVA|
|Post-hoc|Tukey / Games-Howell|
|상관|Pearson / Spearman|
|회귀|Simple Regression|
|LLM|Intent / Problem Model / Plan|
|Tool Calling|필수|
|Interpretation|필수|
|Finding|필수|
|Evidence|필수|
|Next Analysis|필수|
|Stop 판단|필수|
|Report|기본|
|Golden Case|필수|

### MVP에서 제외

초기부터 너무 많은 기능을 넣으면 Agent 자체의 검증이 어려워집니다.

따라서 다음은 **Phase 2 이후**로 미룹니다.

- SPC
- Process Capability
- PCA
- DOE
- Optimization
- 고급 Machine Learning
- 실시간 MES 연계
- 완전 자율 Root Cause Analysis

즉,

> **MVP는 “통계 Agent의 두뇌가 제대로 작동하는가?”를 검증하는 단계**

로 정의하는 것이 좋습니다.

# 10-2. Agent State Schema

이번 설계에서 가장 중요한 부분 중 하나입니다.

**LLM의 Conversation Memory와 분석 상태를 분리해야 합니다.**

예를 들어 사용자가

> “A라인과 B라인의 토크 차이를 분석해줘.”

라고 했다고 하겠습니다.

LLM이 단순히 대화 내용을 기억하는 것이 아니라 Application이 다음 정보를 저장해야 합니다.

```
Question
Problem
Dataset
Analysis Plan
Analysis History
Findings
Evidence
Hypotheses
Confounders
Next Actions
Decision
```

개념적으로:

```
AnalysisSession:

  session_id:
  created_at:
  updated_at:

  user_question:

  problem_model:

  dataset_context:

  analysis_plan:

  analysis_history:

  findings:

  hypotheses:

  confounders:

  evidence:

  next_actions:

  final_decision:
```

### 핵심 원칙

**LLM이 기억해야 하는 것이 아니라 Application State가 기억해야 합니다.**

예를 들어 통계 결과:

```
B라인 평균 = 38.7
A라인 평균 = 35.9
p-value = 0.003
```

이런 값은 LLM Memory에 저장하는 것이 아니라:

```
AnalysisSession
 └── AnalysisHistory
      └── ToolResult
```

에 저장합니다.

그래야 나중에 Agent가 다시 질문받아도 동일한 근거를 사용할 수 있습니다.

# 10-3. Problem Model Schema

여기서 중요한 설계 원칙이 하나 있습니다.

## LLM은 먼저 "통계 방법"을 선택하면 안 됩니다.

먼저 **문제를 모델링**해야 합니다.

예:

사용자:

> “A라인과 B라인의 토크 차이가 있는지 확인해줘.”

LLM:

```
problem_type: GROUP_COMPARISON

response_variable:
  name: Torque
  type: continuous
  unit: N·m

factor:
  name: Line
  type: categorical

groups:
  - A
  - B

objective:
  type: DIFFERENCE_DETECTION

relationship:
  type: UNKNOWN
```

그 다음 Rule Engine이 이것을 보고:

```
Continuous
+
2 groups
+
relationship = independent?
+
variance condition
+
distribution condition
```

을 확인합니다.

그리고 최종적으로:

```
Independent + Equal Variance
        → t-test

Independent + Unequal Variance
        → Welch t-test

Paired
        → Paired t-test
```

와 같이 결정합니다.

즉,

> **LLM = 문제 이해 및 분석 제안**
> 
> **Rule Engine = 통계적 타당성 검증**
> 
> **Statistical Engine = 계산**

이라는 역할 분리가 확실해집니다.

# 10-4. Analysis Plan Schema

Agent가 단순히

> “t-test를 하겠습니다.”

라고 말하는 구조는 부족합니다.

**Analysis Plan 자체를 객체로 관리해야 합니다.**

예:

```
analysis_plan:

  objective:
    type: difference_detection

  nodes:

    - id: N01
      type: DATA_QUALITY
      status: completed

    - id: N02
      type: GROUP_STRUCTURE
      status: completed

    - id: N03
      type: DESCRIPTIVE
      status: completed

    - id: N04
      type: DISTRIBUTION
      status: completed

    - id: N05
      type: VARIANCE
      status: completed

    - id: N06
      type: TWO_GROUP_TEST
      status: completed

    - id: N07
      type: EFFECT_SIZE
      status: completed

    - id: N08
      type: CONFOUNDING_CHECK
      status: pending

    - id: N09
      type: MANUFACTURING_INTERPRETATION
      status: pending
```

여기서 중요한 것은 **Graph 구조**입니다.

왜냐하면 분석이 항상 직선으로 진행되지 않기 때문입니다.

예를 들어:

```
                    ┌→ Machine 분석
                    │
Question
   ↓                ├→ Shift 분석
Data Quality → Defect Rate
                    │
                    ├→ Model 분석
                    │
                    └→ Operator 분석
```

어떤 결과가 나오느냐에 따라 Agent가 다음 가지를 선택합니다.

이것이 우리가 앞에서 정의했던 **Next Best Analysis**의 기반입니다.

# 10-5. Tool Contract

여기서부터는 실제 개발에 상당히 중요합니다.

LLM에게 다음과 같은 Tool을 제공합니다.

```
profile_data()
check_data_quality()
descriptive_statistics()
distribution_analysis()

two_sample_t_test()
welch_t_test()
paired_t_test()

anova()
welch_anova()

tukey_posthoc()
games_howell()

pearson_correlation()
spearman_correlation()

simple_regression()

histogram()
box_plot()
scatter_plot()
```

그러나 단순히 함수 이름만 제공해서는 안 됩니다.

모든 Tool은 **공통 Result Contract**를 가져야 합니다.

예:

```
tool_result:

  tool:
    name: welch_t_test
    version: 1.0

  dataset:
    id:
    version:

  input:
    response: Torque
    group: Line
    groups: [A, B]

  result:
    statistic:
    df:
    p_value:
    confidence_interval:
    mean_difference:

  effect_size:
    type: cohens_d
    value:

  diagnostics:
    variance_equal: false

  warnings: []

  interpretation:
    direction:
    significance:

  metadata:
    execution_time:
    timestamp:
```

이 구조가 중요한 이유는 **LLM이 숫자를 만들어내지 못하게 하기 위해서**입니다.

LLM은:

```
p = 0.003
```

을 계산하는 것이 아니라,

```
welch_t_test()
       ↓
Tool Result
       ↓
p = 0.003
```

을 받아서 설명해야 합니다.

# 10-6. Finding / Evidence Schema

이 부분은 기존 앱을 Agent로 발전시키면서 새롭게 중요해진 부분입니다.

기존에는:

> “p-value가 0.003이므로 두 라인은 유의한 차이가 있습니다.”

정도였다면,

Agent에서는 **Result와 Finding을 분리합니다.**

### Result

```
A mean = 35.9
B mean = 38.7
Difference = 2.8
p = 0.003
Cohen's d = 0.62
```

### Finding

```
B라인의 토크가 A라인보다 높은 경향이 확인되었으며,
통계적으로 유의한 차이가 관찰되었다.
```

### Hypothesis

```
B라인의 체결 조건 또는 설비 상태가
토크 차이에 영향을 주었을 가능성이 있다.
```

### Evidence

```
evidence_level: E2

basis:
  - two_group_comparison
  - effect_size

confidence:
  statistical: high
  causal: low
```

이렇게 분리하면 Agent가 다음과 같이 말할 수 있습니다.

> **통계적 판단:** A라인과 B라인의 토크 평균에는 유의한 차이가 있습니다.
> 
> **제조적 판단:** B라인에서 상대적으로 높은 토크가 발생하고 있어 공정 조건 또는 설비 조건을 추가 확인할 필요가 있습니다.
> 
> **주의:** 현재 데이터는 관찰 데이터이므로 B라인이 토크 차이의 원인이라고 단정할 수는 없습니다.

이것이 우리가 앞서 정의한 **E0~E4 Evidence Model**의 실제 구현입니다.

# 10-7. Golden Case Schema

Golden Case는 Agent 개발에서 사실상 **시험성적서(Test Contract)** 역할을 합니다.

예:

```
golden_case_id: GC-UC03-001

question:
  "A라인과 B라인의 토크 차이가 있는지 확인해줘."

dataset:
  file:
  description:

data_dictionary:

expected_problem_model:

expected_data_assessment:

expected_analysis_plan:

expected_tool_calls:

expected_statistical_results:

expected_findings:

expected_evidence_level:

expected_manufacturing_interpretation:

expected_next_analysis:

forbidden_conclusions:

evaluation_criteria:
```

특히 중요한 것이:

```
forbidden_conclusions:
```

입니다.

예:

```
forbidden_conclusions:

  - "B라인이 토크 문제의 원인이다."
  - "B라인 때문에 품질이 나빠졌다."
  - "B라인을 개선하면 문제가 해결된다."
```

Agent가 통계적으로 맞는 숫자를 제시하더라도 이런 문장을 출력하면 **실패**로 판정합니다.

```
┌──────────────────────────────────────┐

│                                      │
│ Understand → Plan → Explore → Explain│
└──────────────────┬───────────────────┘
                   ↓
┌──────────────────────────────────────┐

│                                      │
│ Problem / Plan / History / Findings  │
```

```
                    │

```

가 연결됩니다.

# 여기서 한 단계 더 중요한 결론

이 설계를 보면 이 프로젝트의 본질이 상당히 명확해집니다.

처음에는

> **제조 현장용 통계분석 앱**

을 만들려고 했습니다.

하지만 지금까지의 설계를 종합하면 실제 제품의 핵심은 단순 통계분석 프로그램이 아닙니다.

### 기존 프로그램

```
Data
 ↓
Statistical Analysis
 ↓
Graph
 ↓
Interpretation
```

### 새 프로그램

```
Manufacturing Question
        ↓
Problem Understanding
        ↓
Problem Modeling
        ↓
Analysis Planning
        ↓
Statistical Analysis
        ↓
Evidence
        ↓
Manufacturing Interpretation
        ↓
Next Best Analysis
        ↓
Decision
        ↓
Improvement
```

즉,

> **통계를 잘 계산하는 AI가 아니라, 제조 문제를 통계적 문제로 구조화하고, 적절한 분석을 수행하고, 그 결과를 제조 의사결정으로 연결하는 Agent**

가 되는 것입니다.

그리고 기존 기획서에서 강조했던 **“통계를 계산하는 프로그램이 아니라 제조 현장의 질문을 통계적 판단으로 바꿔주는 프로그램”**이라는 철학도 그대로 유지됩니다. 오히려 LLM을 추가하면서 그 철학이 훨씬 완성된 형태가 됩니다. 통계분석 앱 제작 기획서.mdMD

## 다음 단계: Step 11 — 실제 Agent의 작동 시나리오를 코드 수준으로 내려가기

다음 단계에서는 더 이상 개념 설계에 머물지 않고, **실제로 Claude Code에게 개발을 지시할 수 있는 수준**으로 들어가는 것이 좋겠습니다.

특히 다음 5가지를 하나의 실제 사례로 연결하겠습니다.

> **“최근 토크 불량이 증가한 원인을 찾아줘.”**

를 입력했을 때,

```
User
 ↓
LLM
 ↓
Problem Model JSON
 ↓
Analysis Plan JSON
 ↓
Tool Call
 ↓
Tool Result JSON
 ↓
Finding
 ↓
Evidence
 ↓
Next Best Analysis
 ↓
최종 답변
```

이 전체 흐름을 **실제 JSON Schema + Tool Interface + Agent Prompt + State 변경 예시**로 한 번 완성해 보는 것입니다.

지금까지는 Agent의 역할과 판단 구조를 정의했다면, 이번 단계에서는 **“그 판단을 실제 프로그램 안에서 어떻게 실행시키는가”**를 설계합니다.

핵심은 이것입니다.

> **LLM이 한 번 답하고 끝나는 구조가 아니라, LLM이 분석을 계획하고 → Tool을 호출하고 → 결과를 확인하고 → State를 갱신하고 → 다음 분석을 결정하는 반복 실행 구조**

입니다.

# Step 12. Manufacturing Statistical Agent 실행 엔진 설계

## 12-1. 먼저 전체 Execution Loop를 정의합니다

전체 구조를 하나의 Loop로 표현하면 다음과 같습니다.

```
User Question
      │
      ▼
┌──────────────────┐
│ 1. Understand    │
│ Intent / Problem │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 2. Assess State  │
│ Data / Context   │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. Plan          │
│ Analysis Plan    │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. Validate      │
│ Rule / Guardrail │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. Execute Tool  │
│ Statistics       │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 6. Validate      │
│ Result           │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 7. Interpret     │
│ Finding / Evidence│
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 8. Decide Next   │
│ Analysis / Stop  │
└───────┬─────┬────┘
        │     │
     Continue Stop
        │     │
        └──┐  ▼
           │ Final
           │ Answer
           ▼
        Next Tool
```

이것이 Agent의 **실행 핵심 루프(Agent Execution Loop)**입니다.

---

# 12-2. Agent는 사실상 State Machine입니다

앞에서 설계한 State를 실제 실행 관점에서 보면 다음 상태를 갖습니다.

```
IDLE
 ↓
UNDERSTAND
 ↓
DEFINE_PROBLEM
 ↓
ASSESS_DATA
 ↓
PLAN_ANALYSIS
 ↓
VALIDATE_PLAN
 ↓
EXECUTE_TOOL
 ↓
VALIDATE_RESULT
 ↓
UPDATE_EVIDENCE
 ↓
INTERPRET
 ↓
SELECT_NEXT
 ├── CONTINUE → PLAN_ANALYSIS
 ├── ASK_USER → WAITING
 ├── NEED_DATA → WAITING
 ├── NEED_EXPERIMENT → FINAL
 └── STOP → FINAL
```

즉, Agent가 어떤 문장을 생성했는지가 아니라

> **현재 State가 무엇이고 다음 State로 이동할 조건이 무엇인가**

가 중요해집니다.

---

# 12-3. AnalysisSession의 실제 구조

앞서 정의한 State를 조금 더 개발 친화적으로 구체화하면 다음과 같습니다.

```
{
  "session_id": "AS-20260912-001",

  "status": "ANALYZING",

  "user_question": "최근 토크 불량이 증가한 원인을 찾아줘.",

  "problem_model": {},

  "dataset_context": {},

  "analysis_plan": {},

  "analysis_history": [],

  "findings": [],

  "hypotheses": [],

  "confounders": [],

  "evidence": [],

  "next_actions": [],

  "decision": null
}
```

여기서 중요한 것은 **Analysis History가 누적된다는 것**입니다.

예:

```
Analysis History

1. profile_data
2. check_data_quality
3. defect_rate
4. trend_analysis
5. group_defect_rate(Machine)
6. chi_square_test
7. confounding_check(Model)
8. group_defect_rate(Model)
9. ...
```

따라서 Agent는 이미 수행한 분석을 다시 하지 않습니다.

---

# 12-4. LLM과 Application의 역할을 엄격히 분리

이 프로젝트에서는 다음 원칙을 강하게 유지하는 것이 좋습니다.

|기능|담당|
|---|---|
|자연어 이해|LLM|
|문제 유형 판단|LLM|
|후보 분석 제안|LLM|
|통계 방법의 적합성 검증|Rule Engine|
|실제 통계 계산|Statistical Engine|
|데이터 조회|Data Engine|
|그래프 생성|Visualization Engine|
|숫자 검증|Rule / Statistical Engine|
|Finding 생성|LLM|
|Evidence 판정|Rule + LLM|
|Causal claim 제한|Rule Engine|
|다음 분석 제안|LLM|
|다음 분석의 타당성 검증|Rule Engine|
|최종 제조적 설명|LLM + Knowledge|

이 구조를 지키면 LLM이 바뀌어도 통계 시스템의 핵심 신뢰성을 유지할 수 있습니다.

---

# 12-5. LLM 호출은 한 종류가 아닙니다

모든 상황에서 같은 Prompt를 사용할 필요도 없습니다.

예를 들어 다음과 같이 역할을 구분할 수 있습니다.

### Call A — Intent

```
User Question
      ↓
LLM
      ↓
Problem Model
```

### Call B — Planning

```
Problem Model
+
Dataset Profile
+
Knowledge
      ↓
LLM
      ↓
Analysis Plan
```

### Call C — Interpretation

```
Tool Result
+
Previous Findings
+
Manufacturing Knowledge
      ↓
LLM
      ↓
Finding
```

### Call D — Next Analysis

```
Current State
+
Findings
+
Evidence
+
Available Data
      ↓
LLM
      ↓
Next Action
```

이렇게 하면 하나의 거대한 Prompt에 모든 기능을 넣는 것보다 훨씬 안정적입니다.

# 12-6. 실제 실행 예

사용자가 입력합니다.

> **“최근 토크 불량이 증가한 원인을 찾아줘.”**

### Round 1

LLM:

```
{
  "action": "ASSESS_DATA",
  "reason": "원인 분석 전에 데이터 구조와 품질 확인이 필요함"
}
```

Application:

```
profile_data()
```

---

### Round 2

Tool:

```
{
  "rows": 18420,
  "missing_rate": 0.2,
  "variables": 12
}
```

State 업데이트:

```
ASSESS_DATA → COMPLETED
```

LLM:

```
{
  "action": "CHECK_DATA_QUALITY"
}
```

---

### Round 3

Tool:

```
check_data_quality()
```

결과:

```
PASS_WITH_WARNING
```

LLM:

```
{
  "action": "DEFECT_RATE",
  "reason": "불량 증가 여부를 먼저 정량화"
}
```

---

### Round 4

```
defect_rate()
```

결과:

```
Defect Rate = 1.50%
```

다음:

```
trend_analysis()
```

결과:

```
Previous = 0.9%
Recent   = 2.1%
Trend    = Increasing
```

# 12-7. 이때 LLM에게 보내는 정보가 중요합니다

LLM에게 매번 전체 데이터를 보내서는 안 됩니다.

예를 들어 18,420개 데이터를 전부 LLM에 전달하는 것은 바람직하지 않습니다.

LLM에게는 다음만 제공합니다.

```
{
  "problem": {
    "type": "ROOT_CAUSE_EXPLORATION",
    "response": "Torque",
    "quality_event": "Defect"
  },

  "dataset": {
    "rows": 18420,
    "variables": 12,
    "quality_status": "PASS_WITH_WARNING"
  },

  "completed_analysis": [
    "defect_rate",
    "trend_analysis"
  ],

  "findings": [
    "Recent defect rate increased"
  ],

  "available_factors": [
    "Model",
    "Line",
    "Machine",
    "Shift",
    "Operator"
  ]
}
```

즉:

> **Raw Data → Statistical/Data Engine**
> 
> **Structured Context → LLM**

입니다.

이것은 이 프로젝트의 핵심 아키텍처 원칙으로 유지해야 합니다.

---

# 12-8. Tool Calling의 실제 계약

LLM이 다음과 같이 Tool을 요청한다고 가정합니다.

```
{
  "tool": "group_defect_rate",
  "arguments": {
    "group_by": "Machine",
    "response": "Defect_Flag"
  }
}
```

Application은 이를 바로 실행하지 않습니다.

중간에 Rule Engine이 있습니다.

```
LLM Tool Request
       ↓
Rule Engine
       ↓
Valid?
 ├── NO → Reject / Correct
 └── YES
       ↓
Execute Tool
```

예를 들어 LLM이 존재하지 않는 변수:

```
Machine_Status
```

를 요청하면 Rule Engine이 거부합니다.

---

# 12-9. Tool 실행 결과도 검증해야 합니다

Tool이 실행됐다고 해서 무조건 정상 결과라고 간주하면 안 됩니다.

예:

```
Tool:
welch_t_test()

Result:
p = NaN
```

또는

```
n = 3
```

처럼 통계적으로 의미가 제한적인 경우가 있습니다.

따라서:

```
Tool Result
     ↓
Result Validator
     ↓
PASS / WARNING / ERROR
```

가 필요합니다.

### Result Validator가 확인할 것

- 입력 데이터 수
- 결측치
- 자유도
- 통계량
- p-value 범위
- CI 논리성
- effect size
- 분석 가정
- 계산 오류
- Tool 실행 오류

---

# 12-10. Rule Engine의 역할

Rule Engine은 단순한 오류 검사기가 아닙니다.

**Agent의 통계적 안전장치**입니다.

예를 들어 LLM이:

```
two_sample_t_test
```

를 제안했습니다.

Rule Engine:

```
Group = A/B
Response = Continuous
Relationship = Independent
Variance = Unequal
```

이면:

```
REJECT:
two_sample_t_test

ROUTE:
welch_t_test
```

로 보낼 수 있습니다.

즉:

> **LLM의 판단을 무조건 따르는 것이 아니라, LLM의 판단을 검증하는 구조**

입니다.

---

# 12-11. Rule Engine은 Hard Rule과 Soft Rule로 나누는 것이 좋습니다

### Hard Rule

위반하면 Tool 실행을 막습니다.

예:

```
Continuous variable required
Group variable required
At least 2 groups
```

또는:

```
Paired t-test
→ Pair ID required
```

### Soft Rule

경고를 발생시키지만 실행은 가능합니다.

예:

```
Sample size relatively small
```

또는:

```
Distribution appears non-normal
```

이 구분이 중요합니다.

모든 조건을 BLOCKER로 만들면 Agent가 지나치게 보수적으로 변합니다.

---

# 12-12. Agent의 의사결정 결과는 4가지로 제한하는 것이 좋습니다

Next Action을 자유로운 자연어로 두지 않고 **정형화된 Action Type**으로 제한하는 것을 권합니다.

```
CONTINUE_ANALYSIS
ASK_USER
REQUEST_DATA
STOP
```

추가로:

```
ESCALATE_TO_EXPERIMENT
```

를 둘 수 있습니다.

예:

```
{
  "next_action": "CONTINUE_ANALYSIS",
  "analysis": "model_controlled_machine_comparison"
}
```

또는:

```
{
  "next_action": "ASK_USER",
  "reason": "개선 전후 데이터의 Pair ID가 필요함"
}
```

또는:

```
{
  "next_action": "ESCALATE_TO_EXPERIMENT",
  "reason": "현재 관찰 데이터만으로 인과관계 판단 불가능"
}
```

---

# 12-13. Next Best Analysis Engine

여기가 Agent의 핵심 차별화 기능이 될 가능성이 높습니다.

단순한 통계 프로그램은:

> “다음으로 ANOVA를 사용하세요.”

정도로 끝납니다.

우리 Agent는:

> **“현재까지 얻은 정보로 무엇을 추가로 분석해야 가장 많은 정보를 얻을 수 있는가?”**

를 판단합니다.

앞서 정의한 Score를 실제 구조로 구체화하면:

```
NBA Score =
Relevance
× Information Gain
× Data Availability
× Statistical Validity
× Manufacturing Impact
```

예를 들어:

|후보|Relevance|정보가치|데이터|제조영향|종합|
|---|---|---|---|---|---|
|Machine|0.9|0.8|1.0|0.9|높음|
|Shift|0.6|0.5|1.0|0.6|중간|
|Operator|0.5|0.4|1.0|0.4|낮음|
|Model|0.95|0.95|1.0|0.95|매우 높음|

이런 구조라면 Agent는 Model 분석을 우선할 수 있습니다.

---

# 12-14. 단, Next Best Analysis도 LLM에게 완전히 맡기지 않습니다

추천 구조는:

```
LLM
 ↓
Candidate Next Analyses
 ↓
Rule Engine
 ↓
Validity Filter
 ↓
Scoring Engine
 ↓
Best Next Analysis
```

입니다.

예를 들어 LLM이 6개를 제안하면:

```
Candidate A
Candidate B
Candidate C
Candidate D
Candidate E
Candidate F
```

Rule Engine이 실행 불가능한 후보를 제거하고,

Scoring Engine이 우선순위를 정합니다.

이렇게 하면 Agent의 판단이 훨씬 재현 가능해집니다.

---

# 12-15. Stop Engine도 별도로 만들어야 합니다

Agent가 계속 분석만 하는 문제가 발생할 수 있습니다.

따라서 **Stop Engine**이 필요합니다.

다음 조건 중 하나가 충족되면 분석을 종료합니다.

### STOP-01

질문이 충분히 답변됨.

### STOP-02

추가 분석의 정보가치가 낮음.

### STOP-03

데이터 부족.

### STOP-04

현재 데이터로는 인과관계 판단 불가능.

### STOP-05

DOE/실험이 필요한 문제.

### STOP-06

분석 결과가 서로 충돌하여 추가적인 현장 확인 필요.

# 12-16. Agent Loop의 의사코드

개념적으로는 다음과 같은 구조가 됩니다.

```
while session.status != FINAL:

    context = build_agent_context(state)

    decision = LLM.decide(context)

    validated = RuleEngine.validate(decision, state)

    if validated == REJECT:
        repair_decision()
        continue

    if decision == TOOL_CALL:

        result = Tool.execute(decision)

        validation = ResultValidator.validate(result)

        if validation == ERROR:
            handle_exception()
            continue

        state.update(result)

        finding = LLM.interpret(result, state)

        EvidenceEngine.update(finding)

        state.update(finding)

    elif decision == ASK_USER:

        state.status = WAITING
        return question

    elif decision == REQUEST_DATA:

        state.status = WAITING
        return data_request

    elif decision == CONTINUE:

        continue

    elif decision == STOP:

        state.status = FINAL

    elif decision == ESCALATE_TO_EXPERIMENT:

        state.status = FINAL
```

여기서 중요한 것은 **LLM이 직접 while loop를 제어하는 것이 아니라 Application Orchestrator가 제어한다는 것**입니다.

# 12-17. 왜 이 구조가 중요한가?

이렇게 해야 다음 문제가 해결됩니다.

### 문제 1. LLM이 엉뚱한 분석을 하는 문제

→ Rule Engine

### 문제 2. LLM이 숫자를 만들어내는 문제

→ Tool Result만 허용

### 문제 3. 같은 분석을 반복하는 문제

→ Analysis History

### 문제 4. 원인을 성급하게 확정하는 문제

→ Evidence + Causal Rule

### 문제 5. 무한 분석

→ Stop Engine

### 문제 6. 분석 중단 후 다시 시작

→ Analysis State

### 문제 7. 모델 변경

→ LLMProvider 추상화

결국 지금까지 설계한 모든 요소가 하나의 Execution Engine에서 연결됩니다.

# 12-19. 여기서 기존 SmartStat의 기능은 버려지지 않습니다

이 부분은 프로젝트에서 상당히 중요합니다.

기존에 설계한 기능을 전부 다시 만드는 것이 아닙니다.

오히려 다음과 같이 **Agent Tool로 승격**시키는 것입니다.

|기존 SmartStat|새로운 Agent|
|---|---|
|Data Input|Data Tool|
|Data Quality|Data Validation Tool|
|Descriptive|Statistical Tool|
|Histogram|Visualization Tool|
|Box Plot|Visualization Tool|
|Scatter Plot|Visualization Tool|
|t-test|Statistical Tool|
|ANOVA|Statistical Tool|
|Post-hoc|Statistical Tool|
|Correlation|Statistical Tool|
|Regression|Statistical Tool|
|Interpretation Engine|LLM + Rule|
|Case Library|Knowledge Base|
|Additional Analysis|Next Best Analysis|
|Wizard|Guided Agent|
|Report|Agent Report Tool|

따라서 기존 기획은 **폐기하는 것이 아니라 Agent의 실행 기반으로 재구성하는 것**이 정확합니다.

기존 기획에서도 이미 분석 선택, 자동 해석, 제조 현장 적용, 추가 분석 추천, Wizard 등을 하나의 의사결정 흐름으로 묶고 있었기 때문에 이 전환이 상당히 자연스럽습니다. 통계분석 앱 제작 기획서.mdMD

# 12-20. Step 12에서 결정해야 할 핵심 Architecture

이제 중요한 Architecture Decision을 정리하면 다음과 같습니다.

### AD-01

**Single Orchestrator + Specialized Modules**

→ Full Multi-Agent는 사용하지 않음.

### AD-02

**LLM은 통계 계산을 하지 않음.**

→ 모든 수치 결과는 Tool/Statistical Engine.

### AD-03

**Application State를 분석의 기억으로 사용.**

→ Conversation Memory와 분리.

### AD-04

**Rule Engine을 LLM 앞뒤에 배치.**

→ Method / Assumption / Result / Interpretation 검증.

### AD-05

**Analysis Plan은 Graph 구조.**

→ 순차적 Wizard가 아니라 동적 분석.

### AD-06

**Finding / Hypothesis / Evidence 분리.**

→ 관찰 → 가설 → 근거의 논리적 구분.

### AD-07

**Next Best Analysis와 Stop Engine을 별도 기능으로 구현.**

→ Agent가 무작정 분석하지 않도록 함.

# 12-21. 개발 관점에서 보면 이제 4개의 핵심 Engine이 생겼습니다

지금까지의 설계를 압축하면 Agent의 두뇌는 사실 다음 네 개로 구성됩니다.

```
┌────────────────────────────────────┐
│         Manufacturing Agent        │
│                                    │
│  ┌──────────────┐                  │
│  │ Orchestrator │ ← 무엇을 할까?   │
│  └──────┬───────┘                  │
│         │                          │
│  ┌──────▼───────┐                  │
│  │ Planner      │ ← 무엇을 분석?   │
│  └──────┬───────┘                  │
│         │                          │
│  ┌──────▼───────┐                  │
│  │ Rule Engine  │ ← 가능한가?      │
│  └──────┬───────┘                  │
│         │                          │
│  ┌──────▼───────┐                  │
│  │ Evidence     │ ← 무엇을 알았나? │
│  │ / Evaluator   │                  │
│  └──────────────┘                  │
└────────────────────────────────────┘
```

그리고 실제 계산은 외부 Tool/Engine이 담당합니다.

# Step 12의 가장 중요한 결론

이번 단계에서 **Agent의 “두뇌와 몸”을 분리했습니다.**

### 두뇌

```
LLM
+ Orchestrator
+ Planner
+ Evidence Reasoning
```

### 통제장치

```
Rule Engine
+ Guardrail
+ Validator
+ Stop Engine
```

### 몸

```
Data Engine
+ Statistical Engine
+ Visualization Engine
+ Report Engine
```

그리고 이 모든 것을 연결하는 것이:

> **Analysis State**

입니다.

따라서 최종적으로는 다음 구조가 됩니다.

> **LLM이 생각한다 → Rule이 검증한다 → Tool이 계산한다 → State가 기록한다 → Evidence가 판단한다 → Agent가 다음 행동을 결정한다.**

이 구조라면 우리가 처음에 우려했던 **“LLM의 유연성은 필요하지만 통계 계산과 판단의 신뢰성은 잃으면 안 된다”**는 두 요구사항을 동시에 만족시킬 수 있습니다.

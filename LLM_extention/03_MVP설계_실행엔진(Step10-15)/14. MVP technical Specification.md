좋습니다. 앞서 **Step 13까지의 설계**를 기준으로 이어서 **Step 14: MVP Technical Specification**으로 진행하겠습니다.

다만 이번 단계는 기존 기획서를 실제 소프트웨어 구조로 내려가는 단계이므로, **기존 기획의 통계 기능을 버리는 것이 아니라 기존 기능을 Agent가 호출할 수 있는 Tool 구조로 재편하는 것**이 핵심입니다.

# Step 14. MVP Technical Specification

## 14-1. 먼저 개발 방향을 한 문장으로 정리

기존 앱:

> **사용자가 분석 방법을 선택 → 통계 계산 → 결과 해석**

새로운 앱:

> **사용자가 제조 현장의 질문을 입력 → Agent가 문제를 정의 → 적절한 통계 Tool을 선택·실행 → 결과를 검증 → 제조 관점으로 해석 → 다음 분석 또는 판단까지 연결**

따라서 제품의 중심이

**Statistical Analysis App**

에서

**Manufacturing Statistical Analysis Agent**

로 이동합니다.

---

# 14-2. MVP에서 가장 중요한 기술 원칙

앞서 결정한 원칙을 그대로 유지합니다.

### 원칙 1. LLM은 통계를 계산하지 않는다

LLM이

> 평균 = 163.27  
> p-value = 0.032

를 직접 계산해서는 안 됩니다.

LLM은

> "두 라인의 평균 차이를 검정해야 한다."

라고 판단하고,

```
two_sample_t_test()
```

를 호출합니다.

실제 계산은 Statistical Engine이 합니다.

---

### 원칙 2. LLM의 판단은 Rule Engine이 검증한다

예를 들어 Agent가

```
paired_t_test
```

를 선택했다고 하더라도,

Rule Engine이

- Pair ID 존재 여부
- 동일 대상의 Before/After 구조
- 표본 수
- 결측
- 데이터 구조

를 확인합니다.

조건이 맞지 않으면 실행하지 않습니다.

즉,

> **LLM = 판단**
> 
> **Rule Engine = 통제**
> 
> **Statistical Engine = 계산**

입니다.

---

### 원칙 3. 모든 분석 결과는 State에 저장한다

LLM 대화 기억에 의존하지 않습니다.

예를 들어:

```
Machine M4의 불량률이 높다.
```

라는 내용은 단순한 대화 문장이 아니라

```
Finding
 ├─ statement
 ├─ source_analysis
 ├─ evidence_level
 ├─ direction
 └─ confidence
```

라는 구조화된 데이터로 저장합니다.

---

### 원칙 4. Knowledge와 Data를 분리한다

예를 들어:

**Knowledge**

> 체결 토크는 체결 품질을 대표하는 CTQ이다.

**Data**

> M4의 토크 불량률은 2.92%이다.

**Analysis Result**

> M4와 타 설비 간 불량률 차이에 대한 Chi-square 검정 p < 0.001.

세 가지를 서로 섞지 않습니다.

# 14-3. 기술 스택 권고

소프트웨어 개발 경험이 많지 않다는 점을 고려하면 저는 **Python 중심 구조**를 권고합니다.

|영역|권고 기술|
|---|---|
|Backend|Python|
|API|FastAPI|
|Statistical Engine|Python / SciPy / statsmodels|
|Data Processing|pandas|
|Visualization|Python + SVG|
|Agent|Python|
|LLM|API 기반 LLM|
|Structured Output|Pydantic|

|UI|초기 Streamlit 또는 React|

### 왜 Python인가?

이 프로젝트에서는 Python이 특히 유리합니다.

**통계 + 데이터 처리 + AI Agent**가 모두 핵심이기 때문입니다.

```
Excel
 ↓
pandas
 ↓
SciPy / statsmodels
 ↓
Python Agent
 ↓
LLM
```

이라는 하나의 생태계로 구성할 수 있습니다.

처음부터 React + Node.js + Python + 별도 DB + Vector DB를 모두 구성하면 개발 복잡도가 지나치게 높아집니다.

# 14-6. 가장 먼저 만들어야 할 것 — Statistical Engine

가장 중요한 개발 순서는 **LLM부터 만드는 것이 아닙니다.**

먼저 통계 엔진을 만듭니다.

예를 들어:

```
two_sample_t_test()
```

가 있으면 입력은

```
Group A data
Group B data
```

이고 출력은 구조화되어야 합니다.

예:

```
{
    "test": "Welch t-test",
    "statistic": 2.41,
    "p_value": 0.018,
    "mean_a": 163.2,
    "mean_b": 166.1,
    "mean_difference": -2.9,
    "confidence_interval": [-5.3, -0.5],
    "effect_size": 0.42,
    "sample_size_a": 85,
    "sample_size_b": 92,
    "assumptions": {
        "variance_equal": false
    }
}
```

이것이 **Agent가 이해할 수 있는 통계 결과 객체**가 됩니다.

---

# 14-7. Tool Layer의 역할

Statistical Engine을 Agent에게 직접 노출하지 않습니다.

중간에 Tool Layer를 둡니다.

예:

```
LLM
 ↓
two_sample_comparison_tool
 ↓
Rule Engine
 ↓
statistics.two_sample_t_test()
```

왜 이렇게 해야 할까요?

나중에 Statistical Engine을 변경해도 Agent 인터페이스는 유지할 수 있기 때문입니다.

즉,

> **Tool은 Agent와 통계엔진 사이의 API 계약(Contract)**입니다.

# 14-9. Rule Engine

예를 들어 사용자가:

> A라인과 B라인의 토크 차이를 확인해줘.

라고 하면 LLM이

```
two_sample_t_test
```

를 선택할 수 있습니다.

하지만 Rule Engine은 다음을 검사합니다.

```
① Response variable = numeric?
② Group variable = categorical?
③ Groups = 2?
④ Independent?
⑤ Missing data?
⑥ Sample size?
⑦ Variance?
⑧ Distribution?
```

그리고 다음과 같이 결정합니다.

```
IF independent
AND numeric
AND groups == 2
AND variance unequal
→ Welch t-test
```

따라서 중요한 통계적 판단은 **Prompt가 아니라 코드로 고정**합니다.

---

# 14-10. Agent Orchestrator

이제 Agent의 중심입니다.

Orchestrator는 사실상 다음 질문을 계속 반복합니다.

> **"지금 이 분석에서 다음에 무엇을 해야 하는가?"**

예:

```
User Question
      ↓
Understand
      ↓
Define Problem
      ↓
Assess Data
      ↓
Create Plan
      ↓
Validate Plan
      ↓
Execute Tool
      ↓
Validate Result
      ↓
Create Finding
      ↓
Assess Evidence
      ↓
Next Analysis?
   ↙          ↘
 YES          NO
 ↓             ↓
Tool         Final
```

이것이 앞서 설계한 **State Machine**입니다.

# 14-11. LLM에게 전달하는 데이터

여기서 중요한 설계가 하나 있습니다.

### 하지 않는 것

Excel 20,000행을 그대로 LLM에 전달:

```
row 1...
row 2...
row 3...
...
row 20,000
```

이렇게 하지 않습니다.

### 하는 것

Data Engine이 요약합니다.

```
Dataset
 ├─ rows: 18,420
 ├─ variables: 12
 ├─ missing_rate: 0.2%
 ├─ numeric: Torque
 ├─ categorical:
 │    Machine
 │    Model
 │    Shift
 │    Operator
 └─ quality_status: PASS_WITH_WARNING
```

그리고 Tool 결과:

```
Machine M4
Defect Rate = 2.92%

Other Machines
Defect Rate = 1.21%

Chi-square p < 0.001
```

이 정도의 **구조화된 정보**를 LLM에게 제공합니다.

# 14-12. Analysis State

Agent가 여러 단계 분석을 수행하려면 반드시 State가 필요합니다.

예:

```
AnalysisSession
│
├── User Question
│
├── Problem Model
│
├── Dataset Context
│
├── Analysis Plan
│
├── Analysis History
│
├── Findings
│
├── Evidence
│
├── Hypotheses
│
├── Confounders
│
├── Next Actions
│
└── Final Decision
```

예를 들어:

```
Hypothesis H01

"Machine M4가 토크 불량 증가의 주요 원인이다."
```

초기에는:

```
UNTESTED
```

M4 불량률이 높다는 결과가 나오면:

```
SUPPORTED
```

그런데 Model C가 M4에 집중되어 있다는 사실이 발견되면:

```
WEAKENED
```

이런 방식으로 Agent의 추론 상태를 관리합니다.

# 14-14. Visualization Engine

기존 기획에서 중요한 요소였던 **SVG**는 그대로 유지하는 것을 권고합니다.

Agent가

```
box_plot()
```

을 호출하면 결과는 단순 이미지가 아니라:

```
{
    chart_type: "box_plot",
    svg: "...",
    variables: [...],
    groups: [...],
    source_analysis_id: "A001"
}
```

형태가 됩니다.

그러면 UI에서

```
분석 결과
   ↓
Box Plot
   ↓
통계 결과
   ↓
쉬운 설명
   ↓
제조 의미
```

로 연결할 수 있습니다.

# 14-15. Report Engine

Agent의 최종 결과는 다음 구조로 통일하는 것이 좋습니다.

### ① 결론

> A라인과 B라인의 토크 평균에는 통계적으로 유의한 차이가 있습니다.

### ② 근거

> 평균 차이: 2.9 N·m  
> 95% CI: −5.3 ~ −0.5  
> Welch t-test p = 0.018

### ③ 통계적 판단

> 두 공정의 평균 차이가 우연에 의해 발생했다고 보기 어렵습니다.

### ④ 제조적 판단

> 다만 평균 차이가 실제 조립 품질에 의미 있는 수준인지는 규격 및 공정 목표와 함께 판단해야 합니다.

### ⑤ 한계

> 라인별 Model 구성 차이가 존재할 경우 라인 효과와 Model 효과가 혼재할 수 있습니다.

### ⑥ 다음 분석

> 동일 Model 기준으로 A/B라인을 재비교하는 것을 권장합니다.

이 구조를 HTML/Markdown/PDF/Excel 보고서로 변환합니다.

# 14-16. Golden Case 자동평가

이 부분은 **MVP에서 반드시 넣는 것을 권고**합니다.

Agent가 똑똑해 보이는 것과 실제로 정확한 것은 전혀 다른 문제이기 때문입니다.

예:

```
GC-UC03-001
```

입력:

> A라인과 B라인의 토크 차이가 있는지 확인해줘.

Expected:

```
Problem Type
= GROUP_COMPARISON

Response
= Torque

Factor
= Line

Analysis
= Two Group Comparison

If unequal variance
→ Welch t-test
```

Agent 결과가 이것과 맞는지 자동 비교합니다.

# 14-17. 첫 번째 Vertical Slice

여기서부터 실제 개발 방법이 중요합니다.

전체 앱을 한꺼번에 만들지 않습니다.

**단 하나의 완전한 사용 시나리오를 처음부터 끝까지 연결합니다.**

첫 Vertical Slice는 **UC-03**을 권고합니다.

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

왜냐하면:

- 데이터 구조가 비교적 단순하고
- 제조 현장에서 이해하기 쉽고
- t-test
- Welch
- effect size
- box plot
- interpretation
- confounding

까지 Agent의 핵심 기능을 대부분 검증할 수 있기 때문입니다.

```
      ↓
Evidence
      ↓
Manufacturing Interpretation
      ↓
Next Analysis
```

이 한 개의 흐름이 완성되면 **Agent의 핵심 골격이 실제로 작동하는 것**입니다.

## Step 14의 핵심 결론

지금까지의 설계를 종합하면 개발 철학은 다음 한 줄로 정리할 수 있습니다.

> **Contract First → Deterministic Statistics → Rule/Guardrail → Agent Orchestration → Evidence-based Interpretation → Golden Case Evaluation**

그리고 제품의 핵심 차별화는 단순히 **"LLM을 붙인 통계 프로그램"**이 아닙니다.

**기존 SmartStat의 강점**

> 제조 현장에 맞는 통계 분석과 쉬운 해석

에

**새로운 Agent의 능력**

> 질문 이해 → 분석계획 수립 → 도구 선택 → 복수 분석 → 결과 연결 → 근거 관리 → 다음 분석 → 의사결정

을 결합하는 것입니다.

따라서 최종적인 제품 개념은 다음과 같이 정의하는 것이 가장 명확합니다.

> **Manufacturing Statistical Analysis Agent**  
> _제조 현장의 질문을 통계적 분석으로 변환하고, 분석 결과를 근거 기반의 제조 판단과 다음 행동으로 연결하는 AI Agent._

### 다음 단계

이제 설계 단계에서 **실제 개발 단계로 넘어갈 수 있습니다.**

다음 **Step 15**에서는 바로 코드를 작성하기 전에, 첫 번째 Vertical Slice인 **「A라인과 B라인의 토크 차이가 있는지 확인해줘」**를 대상으로

**실제 입력 Excel → Data Contract → Problem Model → Analysis Plan → Tool Call → Rule Engine → Welch t-test → SVG → Finding → Evidence → LLM 최종 답변**

까지 **하나의 완전한 Agent 실행 명세(Agent Execution Specification)**로 만들어 보는 것이 좋습니다.

이것이 완성되면 그 명세를 그대로 Claude Code의 개발 작업 단위로 쪼개서 **실제 프로젝트를 구축할 수 있는 수준**까지 내려갈 수 있습니다.

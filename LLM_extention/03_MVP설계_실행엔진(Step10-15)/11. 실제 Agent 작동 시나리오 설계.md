좋습니다. **Step 11에서는 실제 Agent가 한 건의 제조 문제를 어떻게 처리하는지를 “개발자가 구현할 수 있는 수준”으로 구체화**하겠습니다.

이번 단계의 대표 사례는 앞에서 선정한 핵심 Golden Case:

> **“최근 토크 불량이 증가한 원인을 찾아줘.”**

입니다.

이 사례를 완성하면 이후 다른 제조 문제도 동일한 Agent Framework에 얹을 수 있습니다.

# Step 11. 실제 Agent 작동 시나리오 설계

## 11-1. 전체 실행 구조

사용자가 질문을 입력하면 Agent는 한 번에 답을 생성하는 것이 아니라 다음과 같이 동작합니다.

```
User Question
      ↓
[1] Intent Understanding
      ↓
[2] Problem Model 생성
      ↓
[3] Data Assessment
      ↓
[4] Analysis Plan 생성
      ↓
[5] Rule/Guardrail 검증
      ↓
[6] Statistical Tool 실행
      ↓
[7] Result Validation
      ↓
[8] Finding 생성
      ↓
[9] Evidence 평가
      ↓
[10] Confounding 검토
      ↓
[11] Next Best Analysis 결정
      ↓
[12] 반복 또는 Stop
      ↓
[13] Manufacturing Decision
```

핵심은 **Agent가 질문 하나를 여러 개의 통계적 질문으로 분해한다는 것**입니다.

예를 들어:

> “토크 불량이 왜 증가했지?”

라는 질문은 내부적으로 다음처럼 변환됩니다.

```
Q1. 실제로 불량률이 증가했는가?
Q2. 언제부터 증가했는가?
Q3. 어떤 Model에서 증가했는가?
Q4. 어떤 Machine에서 증가했는가?
Q5. Shift별 차이가 있는가?
Q6. Operator별 차이가 있는가?
Q7. Model과 Machine의 관계는 어떠한가?
Q8. 다른 요인을 통제해도 특정 요인이 관련되는가?
Q9. 현재 데이터만으로 원인을 판단할 수 있는가?
```

이것이 기존 단순 통계 앱과 Agent의 가장 큰 차이입니다.

---

# 11-2. Step 1 — Intent Understanding

사용자 입력:

> 최근 토크 불량이 증가한 원인을 찾아줘.

LLM은 먼저 자연어를 다음과 같이 구조화합니다.

```
{
  "intent": "ROOT_CAUSE_EXPLORATION",
  "response_variable": "Torque",
  "quality_event": "Torque defect",
  "objective": "Identify factors associated with defect increase",
  "time_scope": "recent",
  "requested_action": "investigate"
}
```

여기서 아직 **통계 방법을 선택하지 않습니다.**

이 단계에서는:

> “사용자가 무엇을 알고 싶은가?”

만 결정합니다.

---

# 11-3. Step 2 — Problem Model 생성

다음으로 제조 문제를 통계 문제로 변환합니다.

```
{
  "problem_type": "ROOT_CAUSE_EXPLORATION",

  "response": {
    "name": "Torque",
    "type": "continuous"
  },

  "quality_event": {
    "name": "Torque defect",
    "variable": "Defect_Flag"
  },

  "objective": {
    "type": "IDENTIFY_ASSOCIATED_FACTORS",
    "direction": "DEFECT_INCREASE"
  },

  "candidate_factors": [
    "Model",
    "Line",
    "Machine",
    "Shift",
    "Operator"
  ],

  "time_scope": "recent",

  "relationship": "UNKNOWN"
}
```

여기서 매우 중요한 부분이 있습니다.

### `relationship = UNKNOWN`

입니다.

Agent가 처음부터

> Machine이 원인일 것이다.

라고 가정하면 안 됩니다.

**원인은 아직 모릅니다.**

---

# 11-4. Step 3 — Data Assessment

이제 Agent가 데이터를 살펴봅니다.

예를 들어 데이터 구조가 다음과 같다고 가정합니다.

|변수|의미|Type|
|---|---|---|
|Timestamp|생산 시각|DateTime|
|Model|모델|Category|
|Line|생산라인|Category|
|Machine|설비|Category|
|Shift|교대|Category|
|Operator|작업자|Category|
|Torque|토크 측정값|Continuous|
|Defect_Flag|불량 여부|Binary|
|Defect_Code|불량 유형|Category|
|Target|목표값|Continuous|
|LSL|하한|Continuous|
|USL|상한|Continuous|

Agent는 먼저 `profile_data()`를 호출합니다.

```
{
  "rows": 18420,
  "variables": 12,

  "quality": {
    "missing_rate": 0.2,
    "duplicate_rate": 0.0,
    "invalid_values": 0
  },

  "variables": {
    "Torque": {
      "type": "continuous",
      "missing": 12
    },
    "Defect_Flag": {
      "type": "binary",
      "missing": 0
    }
  }
}
```

그 다음 `check_data_quality()`를 호출합니다.

결과:

```
{
  "status": "PASS_WITH_WARNING",

  "warnings": [
    {
      "variable": "Torque",
      "issue": "12 missing observations"
    }
  ]
}
```

Agent는 이 결과를 State에 저장합니다.

---

# 11-5. Step 4 — 첫 번째 Analysis Plan

이제 Agent가 분석 계획을 만듭니다.

```
{
  "objective": "Identify factors associated with torque defect increase",

  "plan": [
    {
      "id": "A01",
      "analysis": "defect_rate",
      "target": "Defect_Flag"
    },
    {
      "id": "A02",
      "analysis": "trend_analysis",
      "target": "Defect_Flag"
    },
    {
      "id": "A03",
      "analysis": "group_defect_rate",
      "factor": "Machine"
    },
    {
      "id": "A04",
      "analysis": "group_defect_rate",
      "factor": "Model"
    },
    {
      "id": "A05",
      "analysis": "group_defect_rate",
      "factor": "Shift"
    },
    {
      "id": "A06",
      "analysis": "group_defect_rate",
      "factor": "Operator"
    }
  ]
}
```

그런데 이것을 **무조건 순서대로 실행하지 않습니다.**

여기서 앞서 설계한 **Analysis Plan Graph**가 작동합니다.

---

# 11-6. Step 5 — Defect Rate 분석

첫 번째 Tool:

```
defect_rate()
```

예를 들어 결과가:

```
{
  "total_count": 18420,
  "defect_count": 276,
  "defect_rate": 0.01498
}
```

즉:

> 전체 토크 불량률 = **1.50%**

입니다.

하지만 이것만으로는 아무것도 결정할 수 없습니다.

Agent는 다음 질문으로 이동합니다.

> **“정말 최근에 증가했는가?”**

---

# 11-7. Step 6 — Trend Analysis

`trend_analysis()` 실행.

예:

```
{
  "period": "daily",

  "trend": {
    "direction": "increasing",
    "recent_rate": 0.021,
    "previous_rate": 0.009
  }
}
```

Agent의 Finding:

```
{
  "finding_id": "F001",

  "statement":
    "최근 토크 불량률이 이전 기간보다 증가한 패턴이 관찰됨.",

  "evidence_level": "E1",

  "source": [
    "A01",
    "A02"
  ]
}
```

여기서 중요한 것은:

> **“증가했다”**

와

> **“통계적으로 유의하게 증가했다”**

를 구분하는 것입니다.

현재는 단순한 관찰이면 **E1**입니다.

---

# 11-8. Step 7 — Candidate Screening

이제 Agent는 후보 요인을 비교합니다.

예를 들어 Machine별 불량률:

|Machine|생산수량|불량|불량률|
|---|---|---|---|
|M1|4,000|36|0.90%|
|M2|3,800|42|1.11%|
|M3|3,900|39|1.00%|
|M4|3,700|108|**2.92%**|
|M5|3,020|51|1.69%|

Agent는 다음과 같은 Finding을 생성할 수 있습니다.

```
{
  "finding_id": "F002",

  "statement":
    "M4에서 다른 설비보다 높은 토크 불량률이 관찰됨.",

  "evidence_level": "E1",

  "candidate_factor": "Machine"
}
```

하지만 여기서 절대로:

> “M4가 원인이다.”

라고 하지 않습니다.

---

# 11-9. Step 8 — Statistical Validation

이제 M4와 다른 Machine 간 차이가 단순한 우연인지 검증합니다.

여기서는 **불량률이라는 범주형/비율 데이터**이므로 단순히 토크의 평균을 비교하는 것과 다른 접근이 필요합니다.

예를 들어:

```
Machine × Defect_Flag
```

에 대해 Chi-square 또는 적절한 proportion comparison을 수행할 수 있습니다.

Tool:

```
chi_square_test()
```

결과:

```
{
  "statistic": 31.72,
  "df": 4,
  "p_value": 0.00001
}
```

그리고 Agent가:

```
{
  "finding_id": "F003",

  "statement":
    "설비별 토크 불량률에는 통계적으로 유의한 차이가 관찰됨.",

  "evidence_level": "E2",

  "source": [
    "A03"
  ]
}
```

라고 기록합니다.

---

# 11-10. 그런데 여기서 Agent의 진짜 능력이 필요합니다

여기까지 보면 아주 쉽게:

> **“M4가 원인이다.”**

라고 결론 내릴 수 있습니다.

하지만 Agent는 한 단계 더 봐야 합니다.

예를 들어 데이터를 추가로 확인했더니:

|Machine|Model C 생산비율|
|---|---|
|M1|10%|
|M2|12%|
|M3|8%|
|M4|**71%**|
|M5|15%|

그리고 Model C 자체의 토크 불량률이 높다면?

```
Machine M4
     ↑
     │
Model C 집중 생산
     ↑
Model C 자체의 높은 불량률
```

이라는 **Confounding 가능성**이 생깁니다.

---

# 11-11. Step 9 — Confounding Check

Agent가 `confounding_check()`를 실행합니다.

결과:

```
{
  "potential_confounders": [
    {
      "factor": "Model",
      "relationship": "strong",
      "risk": "HIGH"
    }
  ]
}
```

그러면 Agent State는:

```
{
  "confounders": [
    {
      "factor": "Model",
      "affected_factor": "Machine",
      "risk": "HIGH",
      "status": "UNRESOLVED"
    }
  ]
}
```

로 변경됩니다.

그리고 기존 Finding은 다음과 같이 업데이트됩니다.

> M4에서 토크 불량률이 높고 설비별 차이가 통계적으로 유의하게 나타났으나, M4에서 특정 모델의 생산 비중이 높은 것으로 확인되어 모델 효과가 혼재되어 있을 가능성이 있습니다.

이것이 **제조 통계 Agent에서 매우 중요한 지점**입니다.

---

# 11-12. Step 10 — Next Best Analysis

Agent는 이제 다음 분석을 선택해야 합니다.

후보:

```
① Model별 불량률 분석
② 동일 Model 내 Machine 비교
③ Shift별 불량률
④ Operator별 불량률
⑤ Machine × Model 교차분석
⑥ Logistic Regression
```

우리는 앞서 다음 평가식을 정의했습니다.

```
Next Analysis Score
=
Relevance
× Expected Information Gain
× Data Availability
× Statistical Validity
× Manufacturing Impact
```

현재 상황에서는:

> **동일 Model 내에서 Machine을 비교**

하는 것이 가장 정보 가치가 높을 수 있습니다.

왜냐하면 Model이라는 교란요인을 어느 정도 제거할 수 있기 때문입니다.

---

# 11-13. Step 11 — Deep Analysis

예를 들어 Model C만 추출해서:

```
Model = C
```

Machine별 불량률을 비교합니다.

결과:

|Machine|Model C 불량률|
|---|---|
|M1|2.4%|
|M2|2.5%|
|M3|2.3%|
|M4|**2.7%**|
|M5|2.5%|

그러면 앞의 전체 데이터에서 보였던

> M4 = 2.92%

라는 큰 차이가 상당히 줄어듭니다.

Agent는 중요한 Finding을 생성합니다.

> 전체 데이터에서는 M4의 불량률이 높았지만, Model C 내부에서 비교하면 설비 간 차이가 크지 않은 것으로 나타났습니다.

따라서:

```
M4 → 원인 가능성 감소
Model → 주요 후보 가능성 증가
```

로 Hypothesis가 변경됩니다.

---

# 11-14. Finding과 Hypothesis를 다시 구분

Agent State:

```
{
  "findings": [
    {
      "id": "F001",
      "statement": "최근 토크 불량률 증가 패턴 관찰",
      "evidence": "E1"
    },
    {
      "id": "F002",
      "statement": "M4의 전체 불량률이 높음",
      "evidence": "E1"
    },
    {
      "id": "F003",
      "statement": "설비별 불량률 차이가 통계적으로 유의함",
      "evidence": "E2"
    },
    {
      "id": "F004",
      "statement": "Model C 내에서는 설비 차이가 크지 않음",
      "evidence": "E2"
    }
  ],

  "hypotheses": [
    {
      "factor": "Machine",
      "status": "WEAKENED"
    },
    {
      "factor": "Model",
      "status": "STRENGTHENED"
    }
  ]
}
```

이 구조가 상당히 중요합니다.

**Finding은 데이터가 보여준 사실이고, Hypothesis는 설명 후보입니다.**

---

# 11-15. Agent가 여기서 멈출 수도 있습니다

예를 들어 추가 분석 결과:

```
Model C
   ↓
특정 기간부터 불량률 급증
   ↓
특정 공정조건 변경 시점과 일치
```

가 발견되었다고 합시다.

그러면 Agent는:

> 특정 모델에서 특정 시점 이후 토크 불량률이 증가한 패턴이 확인되었으며, 해당 시점의 공정조건 변경과 시간적으로 일치합니다.

라고 할 수 있습니다.

하지만 이것 역시:

> **“공정조건 변경이 원인이다.”**

라고 확정할 수는 없습니다.

왜냐하면 아직 관찰 데이터이기 때문입니다.

---

# 11-16. Evidence Level에 따른 언어 제한

이제 Evidence가 Agent의 언어를 통제합니다.

|Evidence|허용 표현|금지 표현|
|---|---|---|
|E0|확인되지 않음|원인|
|E1|관찰됨, 패턴이 보임|유의한 원인|
|E2|통계적으로 유의한 차이/관련성|원인으로 입증|
|E3|반복적으로 확인된 주요 후보|확정적 원인|
|E4|개선/실험으로 검증됨|—|

따라서 현재 E2라면:

> **“M4와 토크 불량률 사이의 관련성이 확인되었습니다.”**

는 가능하지만,

> **“M4가 토크 불량의 원인임을 확인했습니다.”**

는 금지됩니다.

이것은 Prompt만으로 처리하기보다는 **Rule Engine에서도 차단해야 합니다.**

---

# 11-17. 최종 Agent Output

최종적으로 사용자는 복잡한 통계 출력 전체를 보는 것이 아니라 다음과 같은 결과를 받게 됩니다.

### 분석 결론

> **최근 토크 불량률은 이전 기간보다 증가한 것으로 나타났습니다.**
> 
> 초기 분석에서는 M4의 불량률이 상대적으로 높고 설비별 차이도 통계적으로 유의하게 나타났습니다.
> 
> 그러나 M4에서 특정 모델의 생산 비중이 높다는 교란 가능성이 확인되었습니다. 동일 모델 내에서 설비를 비교한 결과 M4의 차이는 크게 감소하여, **현재 데이터만으로 M4를 토크 불량의 원인으로 판단하기는 어렵습니다.**
> 
> 반면 특정 모델에서 불량 증가가 집중되는 패턴이 확인되어 **Model 조건을 우선적으로 추가 조사하는 것이 합리적입니다.**

그리고 아래처럼 근거를 표시합니다.

```
[주요 근거]

전체 토크 불량률
1.50%

최근 불량률
2.10%

M4 전체 불량률
2.92%

설비별 불량률 차이
p < 0.001

동일 Model 조건에서 M4 차이
유의성 약화

Evidence Level
E2
```

---

# 11-18. Agent의 마지막 질문

Agent가 여기서 끝내지 않고 다음 분석을 제안할 수 있습니다.

> **다음 분석으로 특정 Model의 불량 증가 시점과 공정조건 변화를 비교해 보시겠습니까?**

또는 Agent가 Agentic Mode라면:

> 현재 데이터에서 추가 분석의 정보 가치가 높은 **Model × 시간 × 공정조건** 분석을 진행하겠습니다.

처럼 이어갈 수 있습니다.

---

# 11-19. 이것을 State 변화로 보면

# 11-21. 이 구조에서 가장 중요한 설계 원칙 7가지

이번 실제 시나리오를 설계하면서 Agent의 핵심 원칙이 더욱 명확해집니다.

### ① LLM은 계산하지 않는다

```
LLM → "무엇을 계산할 것인가?"
Tool → "계산"
```

---

### ② LLM은 처음부터 원인을 가정하지 않는다

```
Question
 ↓
Candidate Factors
 ↓
Evidence
 ↓
Hypothesis
```

순서를 지킵니다.

---

### ③ 하나의 질문은 여러 분석으로 분해된다

```
"원인을 찾아줘"
        ↓
Defect Rate
Trend
Machine
Model
Shift
Operator
Confounding
Regression
...
```

---

### ④ 분석 결과와 Finding은 다르다

```
Result
  ↓
Finding
  ↓
Evidence
  ↓
Manufacturing Meaning
```

---

### ⑤ Finding과 Hypothesis를 구분한다

```
Finding:
M4 불량률이 높다.

Hypothesis:
M4의 설비조건이 영향을 주었을 가능성이 있다.
```

---

### ⑥ 통계적 유의성과 제조적 중요성을 분리한다

p-value가 작다고 해서 반드시 제조적으로 중요한 것은 아닙니다.

반대로 p-value가 크더라도 현장에서는 영향 크기가 중요한 경우가 있습니다.

기존 기획서에서 정의한 **통계적 유의성 vs 제조적 유의성 분리**가 Agent에서도 핵심 판단 구조로 유지됩니다. 통계분석 앱 제작 기획서.mdMD

---

### ⑦ Agent는 “모르겠다”고 말할 수 있어야 한다

최종적으로 이것이 가장 중요합니다.

```
현재 데이터만으로 원인을 확정할 수 없습니다.
```

라는 답변이 실패가 아니라 **정상적인 Agent 동작**이어야 합니다.

필요하다면:

```
추가 데이터 필요
      또는
추가 통계분석 필요
      또는
DOE/실험 필요
      또는
현장 검증 필요
```

로 넘어가야 합니다.

# Step 11의 핵심 성과

이제 우리가 만든 Agent는 단순히

> **“토크 불량률을 계산해주는 AI”**

가 아닙니다.

다음과 같은 **분석 추론 루프**를 수행합니다.

```
질문 이해
 ↓
문제 정의
 ↓
데이터 확인
 ↓
분석 계획
 ↓
통계 분석
 ↓
패턴 발견
 ↓
가설 생성
 ↓
교란요인 확인
 ↓
추가 분석
 ↓
근거 수준 평가
 ↓
제조적 판단
 ↓
다음 행동
```

이것이 이번 프로젝트에서 우리가 구현하려는 **Manufacturing Statistical Analysis Agent의 핵심 알고리즘**이라고 볼 수 있습니다.

## 다음 Step 12에서 할 일

이제 매우 중요한 전환점입니다.

**Step 11까지는 “Agent가 어떻게 생각하고 행동하는가”를 설계했습니다.**

다음은 이를 실제 소프트웨어 구조로 바꾸겠습니다.

### Step 12 — Agent 실행 엔진 설계

특히 다음을 구체화하는 것이 좋습니다.

1. **Orchestrator의 실제 실행 Loop**
2. **LLM → Tool Call → Result → LLM의 반복 구조**
3. **Agent State의 실제 JSON Schema**
4. **Problem Model JSON Schema**
5. **Analysis Plan JSON Schema**
6. **Tool Result JSON Schema**
7. **Finding / Evidence JSON Schema**
8. **Rule Engine의 Method Selection 규칙**
9. **Next Best Analysis 선정 알고리즘**
10. **Agent가 중간에 멈추거나 오류가 발생했을 때의 Recovery**
11. **Claude Code가 실제로 구현할 클래스/모듈 구조**

특히 **“LLM이 한 번 호출되고 끝나는 구조가 아니라, Tool을 여러 번 호출하면서 Analysis State를 갱신하는 Agent Loop”**를 설계하는 것이 Step 12의 핵심이 됩니다.

이 단계까지 완성하면 이후에는 상당히 구체적으로 **“Claude Code에게 이 프로젝트를 어떤 순서와 지침으로 개발시킬 것인가”**까지 내려갈 수 있습니다.

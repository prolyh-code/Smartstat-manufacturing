## 0-1. 정정 — Step 28-1의 비용 귀속 판단은 틀렸다

Step 28-1 §2-1에서 다음과 같이 판단했다.

> "회사가 Enterprise 계약 주체로 이미 부담 중 → 비용 귀속 문제가 계약 수준에서 해소 → 개인별 API Key 불필요"

**이 판단은 정정한다.** Ian이 확인해 준 실제 운영은 다음과 같다.

> "회사에서는 **개인별로 승인된 금액에 한정하여** 사용하고 있기 때문에 **모두 개인 계정으로 로그인**하여 사용합니다."

즉 Enterprise 계약이 존재하더라도 **비용은 개인별 승인 한도로 배분·통제되고 있으며, 인증도 개인 계정 단위로 이루어진다.** 따라서 Ian이 최초에 제시했던 요구 — "개인 계정으로 인증받는 형식이 되어야 한다" — 가 **처음부터 정확했다.**

이에 따라 두 가지를 되돌린다.

| 항목 | Step 28-1의 결정 | 정정 |
|---|---|---|
| 인증 주체 | 조직 Enterprise 연결 | **개인 계정 로그인**(DD-061) |
| 하드 사용 한도(O-8) | 도입하지 않음 | **개인별 승인 한도를 앱이 추적·경고·차단**(DD-062) |

Step 27에서 인증을 `AuthProvider`로 분리하고 Gateway가 `Principal`만 인식하도록 설계해 둔 덕분에, 이 정정으로도 **Gateway·Orchestrator·UI 본체는 수정되지 않는다.** 두 차례 전제가 뒤집혔는데도 구조가 버틴 것은 그 결정의 효과다.

## 0-2. 웹앱 전환이 바꾸는 것

Step 26~28은 암묵적으로 **데스크톱 앱**을 가정하고 있었다. 웹앱 확정으로 다음이 전부 바뀐다.

| 영역 | 데스크톱 가정(기존) | 웹앱(확정) |
|---|---|---|
| 자격증명 보관 | OS 자격증명 저장소 | **서버 측 암호화 보관** |
| 원본 데이터 | 앱이 복제 보관하지 않고 경로 참조 | **서버에 업로드되어 저장됨** |
| 세션 저장 | 로컬 파일 | **서버 저장** |
| 동시성 | 1인 1프로세스 | **다중 사용자 동시 접속** |
| 계산 자원 | 사용자 PC | **공유 서버 자원** |
| 장애 영향 | 개인 1명 | **전체 사용자** |
| 데이터 삭제 | 사용자가 자기 PC에서 | **서버 보유기간 정책 필요** |

**특히 "원본 데이터를 복제 보관하지 않는다"(DD-048)는 웹앱에서 성립할 수 없다.** 업로드 자체가 복제이기 때문이다. 그래서 Ian이 요구한 보유기간·삭제 정책(§6)이 필요해진다.

## 2-2. 분석 실행을 앱 서버에서 분리하는 이유

**DD-060 · 통계 분석·파일 파싱·보고서 생성은 앱 서버가 아니라 분리된 Analysis Worker에서 수행한다. 앱 서버는 작업을 접수하고 상태를 반환할 뿐 장시간 계산을 직접 수행하지 않는다.**

**Reason:** 세 가지가 동시에 걸린다.
1. **응답성** — 100만 행 Excel 파싱은 수십 초가 걸린다. 앱 서버 스레드가 여기에 묶이면 다른 사용자의 화면 조회까지 느려진다.
2. **장애 격리** — 한 사용자의 비정상 데이터가 파싱 중 프로세스를 죽여도 웹 서비스 전체가 내려가면 안 된다.
3. **복구 가능성** — 작업이 큐에 객체로 존재해야 실패 시 재시도·재개가 가능하다(§5). 앱 서버 요청 스레드 안에서 계산하면 실패는 곧 소실이다.

**Status:** 확정 제안

# 3. 개인 계정 인증과 승인 한도

## 3-1. Principal 재정의

```python
@dataclass
class Principal:
    mode: str              # "PERSONAL_ACCOUNT"  ← 확정
    app_user_id: str       # 앱 로그인 계정 (E-4)
    llm_account_ref: str   # 개인 LLM 계정 식별자(되돌릴 수 없는 참조)
    department: str | None
    display_name: str
    budget: BudgetStatus   # ← 신규
```

```python
@dataclass
class BudgetStatus:
    approved_amount: Decimal    # 개인별 승인 금액 (관리자 설정)
    period: str                 # "MONTHLY" | "QUARTERLY"
    used_amount: Decimal
    remaining: Decimal
    warn_threshold: float       # 기본 0.8
    state: str                  # "NORMAL" | "WARNING" | "EXHAUSTED"
```

**DD-061 · LLM 인증은 사용자 개인 계정으로 하며, 사용량과 비용은 그 개인 계정에 귀속된다. 앱은 개인별 승인 금액을 관리자 설정값으로 보유하고 사용량을 그에 대비해 추적한다.**
**Status:** 확정 — **Step 28-1 DD-053을 정정한다**

## 3-2. 웹앱에서의 개인 자격증명 보관

데스크톱이 아니므로 OS 자격증명 저장소를 쓸 수 없다. 서버가 보관해야 한다.

| 항목 | 규칙 |
|---|---|
| 저장 위치 | 서버 측 비밀 저장소(키 관리 시스템 또는 전용 암호화 테이블) |
| 암호화 | 저장 시 암호화. 암호화 키는 애플리케이션 DB와 분리 보관 |
| 접근 | AI Gateway가 호출 직전에만 복호화하여 사용하고 즉시 폐기(Step 27 DD-030 유지) |
| 관리자 접근 | **관리자도 평문 조회 불가.** 관리자 콘솔에는 연결 상태와 사용량만 표시 |
| 사용자 제어 | 본인이 언제든 연결 해제·재등록 가능 |
| 로그 | 지문(fingerprint)만 기록 |

**DD-062 · 개인 LLM 자격증명은 서버 측 암호화 저장소에 보관하며, 관리자를 포함한 어떤 사용자도 평문을 조회할 수 없다. 복호화는 AI Gateway의 호출 직전에만 이루어진다.**
**Reason:** 개인 계정 비용이 그 개인에게 귀속되므로, 자격증명 유출은 개인의 금전적 손해로 직결된다. 관리자 권한으로도 열람할 수 없어야 개인이 회사 시스템에 자기 계정을 등록하는 것을 신뢰할 수 있다.
**Status:** 확정 제안 — **Step 26 DD-018, Step 27 DD-030의 웹앱 버전**

## 3-3. 승인 한도 관리 — O-8 재결정

**DD-063 · 앱은 개인별 승인 한도를 추적하여 경고·차단하며, 한도가 소진되어도 Manual 분석(Level 0)은 제한 없이 계속 사용할 수 있다.**

```text
사용률 0%────────────80%──────────100%─────────
        │  NORMAL   │  WARNING   │  EXHAUSTED
        │           │            │
        │ 표시만     │ 배너 경고   │ AI 호출 차단
        │           │ + 관리자    │ + Manual 계속
        │           │   리포트    │ + 한도 증액 요청 안내
```

| 상태 | 동작 |
|---|---|
| NORMAL | 사용량 표시만 |
| WARNING (기본 80%) | 화면 배너 + 남은 금액 표시. 관리자 콘솔에 경고 목록 |
| EXHAUSTED | **AI 호출 차단**. Manual 분석은 전면 사용 가능. 한도 증액 신청 안내 |

차단 시점의 UX가 중요하다. **진행 중인 Agent 분석 도중 한도가 소진되면 그 자리에서 멈추는 것이 아니라, 현재 진행 중인 분석 단계를 마치고 지금까지의 Finding·Evidence를 정리해 보여준 뒤 정지한다.** 사용자는 그 시점부터 Manual로 이어서 분석할 수 있다.

**Reason:** Step 28-1 O-8에서 "회사가 계약 주체이므로 앱이 차단할 근거가 없다"고 판단했으나, **개인별 승인 금액이라는 통제 구조가 이미 존재하므로 앱이 그 한도를 존중해야 한다.** 한도를 초과한 사용은 개인에게 정산 부담으로 돌아온다.
**Status:** 확정 — **Step 28-1 O-8 결정을 정정한다**

Agent 모드(Level 2·3)에서 계획을 승인할 때, 예상 토큰·금액을 함께 표시한다.

```text
┌──────────────────────────────────────────────┐

```

# 4. 동시 접속 아키텍처

## 4-1. 동시성이 실제로 문제가 되는 지점

웹앱 동시접속에서 이 앱 특유의 위험은 **대용량 Excel 처리**다.

```text
100만 행 × 20열 Excel 1개를 메모리에 올리면 대략 수백 MB.
동시 사용자 10명이면 수 GB — 서버 메모리가 그대로 고갈된다.
```

일반적인 업무용 웹앱(주로 DB 조회)과 달리, 이 앱은 **사용자마다 큰 데이터를 메모리에 올려 계산**한다. 따라서 동시성 설계의 핵심은 세션 관리가 아니라 **데이터 처리 방식**이다.

## 4-2. 업로드 1회 파싱 + 중간 포맷 전략

**DD-064 · 업로드된 Excel/CSV는 워커에서 1회만 파싱하여 열지향 중간 포맷으로 변환해 저장하고, 이후 모든 분석은 중간 포맷을 대상으로 수행한다. 원본 파일은 보관만 하고 분석 시 다시 파싱하지 않는다.**

```text
업로드(.xlsx)
     │
     ▼
 [워커] 스트리밍 파싱 ── 전체를 메모리에 올리지 않음
     │
     ├──► 원본 파일 스토리지 (보유기간 대상, §6)
     │
     └──► 분석용 중간 포맷 (열지향: Parquet 등)
              │
              ▼
       이후 모든 분석은 필요한 열만 부분 로드
       (Torque, Line 2개 열만 읽으면 메모리 수십 MB)
```

**Reason:** 세 가지 문제가 한 번에 해결된다.
1. **메모리** — 분석마다 필요한 열만 읽으므로 동시 사용자가 늘어도 메모리가 선형으로 폭증하지 않는다.
2. **속도** — Excel 파싱은 느리다. UC-11처럼 한 세션에서 10회 이상 분석하는 경우 매번 재파싱하면 대부분의 시간이 파싱에 소모된다.
3. **일관성** — 같은 세션의 모든 분석이 동일한 스냅샷을 대상으로 하므로, 중간에 원본이 교체되어도 결과가 흔들리지 않는다(재현성, Step 28 DD-052).

**Status:** 확정 제안

## 4-3. Excel 특유의 파싱 위험 — 에러 발생의 최대 원인

제조 현장의 Excel은 정형 데이터가 아닌 경우가 많다. **실사용에서 가장 빈번한 에러 발생원이 여기다.**

| 문제 | 증상 | 대응 |
|---|---|---|
| 헤더가 1행이 아님 | 제목·로고·공백이 위에 있음 | 헤더 행 자동 추정 + 사용자 확인 |
| 병합 셀 | 값이 한 셀에만 존재 | 감지 후 전개(forward fill) 여부를 사용자에게 확인 |
| 숫자가 텍스트로 저장 | 평균 계산 불가 | 변환 시도 + 실패 건수 보고 |
| 천단위 구분자·단위 문자 | "1,234 N·m" | 패턴 제거 후 수치화, 실패 시 원문 유지 |
| 날짜 직렬번호 | 45678 같은 값 | 날짜 열로 지정 시 변환 |
| 다중 시트 | 어느 시트인지 불명 | 시트 선택 UI + 미리보기 |
| 소계·합계 행 혼입 | 통계 왜곡 | 패턴 감지 후 경고 |
| 빈 행/열 | 결측률 왜곡 | 자동 제거 + 보고 |

**DD-065 · 업로드 처리는 파싱 → 구조 추정 → 사용자 확인 → 확정의 4단계로 수행하며, 자동 추정 결과는 반드시 사용자 확인을 거친 뒤 중간 포맷으로 확정한다.**
**Reason:** 이 단계에서의 오판은 이후 모든 통계 결과를 무효로 만든다. 소계 행이 데이터로 섞이면 평균이 왜곡되고, 그 위에서 Agent가 정교한 추론을 해도 결론은 틀린다. 자동화하되 **확정은 사람이 한다.**
**Status:** 확정 제안 — Step 26 §4의 S-02·S-03 화면 사이에 이 단계가 들어간다

## 4-4. 사용자별 작업 큐 격리

**DD-066 · 작업 큐는 사용자별로 격리하며, 한 사용자가 동시에 실행할 수 있는 작업 수와 자원 상한을 제한한다.**

| 항목 | 기본값(제안) |
|---|---|
| 사용자당 동시 실행 작업 | 2건 |
| 사용자당 대기 큐 길이 | 10건 |
| 업로드 파일 크기 상한 | 200 MB |
| 행 수 상한 | 300만 행 |
| 단일 분석 실행 시간 상한 | 5분 |
| 보고서 생성 시간 상한 | 3분 |

**Reason:** 큐가 전역 하나면 한 사용자의 대량 작업이 다른 모든 사용자를 대기시킨다(head-of-line blocking). 제조 현장에서 "누가 큰 파일을 올리면 앱 전체가 느려진다"는 경험은 앱 신뢰를 빠르게 무너뜨린다. 개인별 승인 한도(§3) 구조와도 정합한다 — 자원도 개인 단위로 배분한다.
**Status:** 확정 제안

## 4-5. 세션 동시 편집

같은 사용자가 두 개의 브라우저 탭에서 같은 세션을 열 수 있다.

**DD-067 · 세션은 버전 번호를 갖고, 갱신 시 낙관적 잠금(optimistic locking)으로 충돌을 감지한다. 충돌 시 나중 요청을 거부하고 사용자에게 최신 상태를 다시 불러오도록 안내한다.**

```text
탭 A: 세션 v12 로드 → 분석 실행 → 저장 시도(v12 기준) → 성공, v13
탭 B: 세션 v12 로드 → 분석 실행 → 저장 시도(v12 기준) → 충돌 감지
      → "다른 창에서 이 분석 세션이 변경되었습니다. 최신 상태를 불러옵니다."
```

**Status:** 확정 제안

## 4-6. LLM 호출 동시성

개인 계정 인증이므로 **속도 제한(rate limit)도 개인별로 적용된다.** 이는 오히려 유리하다 — 한 사용자의 대량 호출이 다른 사용자의 호출을 막지 않는다. 단 앱 서버가 공유 커넥션 풀을 쓰면 그 이점이 사라지므로, **호출도 사용자별로 격리**한다.

## 4-7. 부하 시 저하 전략

동시 사용자가 자원 한계를 넘으면 서비스를 중단하지 않고 단계적으로 저하시킨다.

| 부하 단계 | 동작 |
|---|---|
| 정상 | 전 기능 |
| 주의 | 신규 Agent 모드(Level 2·3) 시작을 대기열로. 진행 중 작업은 계속 |
| 과부하 | 신규 분석 작업 접수 대기. 조회·보고서 다운로드는 정상 |
| 심각 | 업로드 일시 차단 + 관리자 알림. 조회만 허용 |

**조회 기능은 마지막까지 살린다.** 과거 분석 결과를 보는 것은 자원을 거의 쓰지 않으면서 사용자에게 가장 자주 필요한 기능이다.

# 5. 에러 복구 로직

Ian이 명시적으로 요구한 항목이다. **"실사용 시 안정적인 앱 운영이 가능하도록 에러 발생에 대한 복귀 로직이 적용되어야 한다."**

## 5-1. 복구 설계의 4원칙

| 원칙 | 내용 |
|---|---|
| **① 작업은 객체다** | 모든 장시간 작업은 상태를 가진 레코드로 존재한다. 메모리 안에서만 존재하는 작업은 복구할 수 없다 |
| **② 재시도는 안전해야 한다** | 같은 작업을 두 번 실행해도 결과가 중복되거나 어긋나지 않는다(멱등성) |
| **③ 진행분은 버리지 않는다** | 5단계 중 3단계까지 성공했으면 4단계부터 재개한다. 처음부터 다시 하지 않는다 |
| **④ 실패는 숨기지 않는다** | 조용한 실패는 잘못된 판단의 근거가 된다. 무엇이 실패했고 무엇이 유효한지 표시한다 |

## 5-2. 작업 상태 머신

**DD-068 · 모든 장시간 작업(업로드 파싱, 분석 실행, Agent 루프, 보고서 생성)은 영속화된 Job 레코드로 관리하며 아래 상태 머신을 따른다.**

```text
   QUEUED ──────► RUNNING ──────► SUCCEEDED
      │              │
      │              ├──► FAILED ──────► (재시도) ──► QUEUED
      │              │        │
      │              │        └──► DEAD (재시도 한도 초과)
      │              │                    │
      │              │                    └──► 관리자 콘솔 실패 작업 목록
      │              │
      │              ├──► CANCELLED (사용자 중단)
      │              │
      │              └──► INTERRUPTED (워커/서버 비정상 종료)
      │                       │
      │                       └──► 기동 시 자동 감지 → QUEUED 재투입
      │
      └──► EXPIRED (대기 중 큐 타임아웃)
```

```python
@dataclass
class Job:
    job_id: str
    idempotency_key: str      # 중복 실행 방지 (§5-3)
    session_id: str
    owner_user_id: str
    job_type: str             # PARSE | ANALYZE | AGENT_STEP | REPORT
    status: str
    attempt: int
    max_attempts: int
    checkpoint: dict | None   # 재개 지점 (§5-4)
    error: JobError | None
    created_at / started_at / finished_at
    heartbeat_at: datetime    # 워커 생존 확인 (§5-5)
```

## 5-3. 멱등성 — 재시도가 중복을 만들지 않게

**DD-069 · 모든 작업은 멱등 키를 가지며, 동일 멱등 키의 작업이 이미 성공했으면 재실행하지 않고 기존 결과를 반환한다.**

멱등 키 구성:

```text
PARSE       : hash(dataset_id, file_hash, parse_config)
ANALYZE     : hash(dataset_version, tool_name, parameters)   ← Step 19의 중복분석 판정과 동일 기준
AGENT_STEP  : hash(session_id, plan_id, step_index, attempt_scope)
REPORT      : hash(session_id, report_config, state_version)
```

`ANALYZE`의 멱등 키가 Step 19 §19-14의 중복 분석 방지 판정(동일 dataset + response + factor + groups + method + parameters)과 **같은 기준**이라는 점이 중요하다. 두 기능이 하나의 규칙을 공유하므로, 네트워크 오류로 인한 재시도가 "중복 분석"으로 잘못 기록되지 않는다.

## 5-4. 체크포인트 재개 — Agent 다단계 분석

Agent 분석은 여러 단계가 이어지는 긴 작업이다. 3단계에서 실패했다고 1단계부터 다시 하면 LLM 비용이 이중으로 발생한다(개인별 한도 환경에서는 직접적 손해다).

**DD-070 · Agent 분석의 재개 지점은 별도 체크포인트가 아니라 Analysis State 자체다. 이미 완료된 Tool 실행 결과·Finding·Evidence는 State에 영속화되어 있으므로, 재개 시 그 다음 단계부터 진행한다.**

```text
승인된 계획 5단계
 ① 데이터 품질 확인   ✓ 완료 → State에 기록됨
 ② Line별 기술통계    ✓ 완료 → State에 기록됨
 ③ Welch t-test      ✗ 실패 (LLM 타임아웃)
 ④ Model 교란 확인    ○ 미실행
 ⑤ 동일 Model 재비교  ○ 미실행

재시도 시 → ③부터 재개. ①② 재실행하지 않음.
이미 소비된 ApprovalGrant.consumed 도 그대로 유지.
```

**Reason:** 이것이 Step 19·26에서 "Analysis State를 애플리케이션 상태로 명시 저장한다"(Baseline DD-010)고 결정한 설계가 실제로 값을 내는 지점이다. 별도의 체크포인트 메커니즘을 추가할 필요가 없다.
**Status:** 확정 제안

## 5-5. 서버·워커 비정상 종료 복구

**DD-071 · 워커는 실행 중 주기적으로 heartbeat를 기록하며, heartbeat가 임계시간(기본 90초) 이상 갱신되지 않은 RUNNING 작업은 INTERRUPTED로 판정하여 자동 재투입한다.**

```text
워커 프로세스 종료 / 서버 재시작 / 네트워크 단절
            │
            ▼
   heartbeat 갱신 중단
            │
   ┌────────▼────────┐
   │  감시 프로세스    │  90초 경과 감지
   └────────┬────────┘
            ▼
   RUNNING → INTERRUPTED → QUEUED 재투입
            │
            ▼
   멱등 키로 중복 방지 + 체크포인트에서 재개
```

재투입 시에도 `max_attempts`를 적용해 무한 재시작을 막는다. 한도 초과 시 DEAD로 전이하고 관리자 콘솔의 실패 작업 목록에 올린다.

## 5-6. 실패 유형별 복구 정책

| 실패 지점 | 자동 재시도 | 복구 방식 | 사용자에게 보이는 것 |
|---|---|---|---|
| 브라우저 종료·새로고침 | — | 서버 작업은 계속. 재접속 시 진행 상태 표시 | "분석이 계속 진행되고 있습니다" |
| 네트워크 일시 단절 | — | 재연결 시 상태 동기화 | 연결 상태 표시 |
| 앱 서버 재시작 | ○ | 진행 중 작업은 워커에서 계속 | 무영향 |
| 워커 비정상 종료 | ○ 3회 | heartbeat 감지 → 재투입 → 체크포인트 재개 | "일시적 오류로 재시도 중" |
| Excel 파싱 실패 | ✕ | 사용자 교정 필요 | 실패 원인 + 교정 UI(§4-3) |
| 통계 계산 오류 | ✕ | 해당 분석만 실패, 세션 유지 | 오류 코드 + 조건 변경 안내 |
| Rule Engine 차단 | ✕ | 대안 제시 | Trace에 `✕` + 사유(Step 26 §10-2) |
| LLM 타임아웃·5xx | ○ 2회 | Step 27 §8-2 | 지연 표시 → 배너 |
| LLM 인증 실패 | ✕ | 연결 재설정 유도 | S-08로 이동 |
| **승인 한도 소진** | ✕ | 진행 단계 마치고 정리 후 정지 | 한도 안내 + Manual 계속(§3-3) |
| 스토리지 쓰기 실패 | ○ 2회 | 재시도 후 실패 시 작업 실패 | "저장하지 못했습니다" + 관리자 알림 |
| 메타DB 연결 실패 | ○ | 연결 풀 재확보 | 일시적 오류 표시 |
| 큐 대기 초과 | — | EXPIRED 후 재요청 안내 | "지금 사용량이 많습니다" |

## 5-7. 부분 실패의 표시

승인된 5단계 계획 중 3단계가 실패하고 4·5단계는 성공한 경우, **"분석 실패"로 뭉뚱그리지 않는다.**

```text
분석 계획 진행 상황
 ✓ ① 데이터 품질 확인
 ✓ ② Line별 기술통계
 ✕ ③ Welch t-test — 실패 (재시도 3회 초과)
     └ 원인: 그룹 B의 분산이 0 (모든 값이 동일)
     └ [조건 변경] [이 단계 건너뛰기]
 ✓ ④ Model 교란 확인
 ✓ ⑤ 동일 Model 재비교

⚠ 3단계가 실패하여 Line 간 평균 비교 결과는 없습니다.
   아래 결론은 나머지 분석에 근거한 것입니다.
```

**DD-072 · 다단계 분석에서 일부 단계가 실패하면 성공한 단계의 결과는 유지하되, 실패한 단계와 그로 인해 도출되지 않은 결론을 명시한다.**
**Reason:** Step 26 DD-020(출처 표기)·Step 19의 Evidence 체계와 같은 맥락이다. 무엇이 확인되지 않았는지를 모르면 사용자는 불완전한 근거로 판단한다.
**Status:** 확정 제안

# 6. 데이터 수명주기 — 보유기간과 삭제

Ian의 요구: 원본 데이터는 보유기간이 설정되어 삭제되어야 하고, 분석 데이터와 보고서의 조회·다운로드 기간을 관리자가 설정할 수 있어야 한다.

## 6-1. 데이터 자산 5종과 기본 정책

**DD-073 · 데이터 자산을 5종으로 구분하고 각각의 보유기간을 관리자 콘솔에서 설정한다.**

| 자산 | 내용 | 기본 보유기간(제안) | 만료 시 |
|---|---|---|---|
| **A1 원본 업로드 파일** | .xlsx / .csv 원본 | **90일** | 삭제 |
| **A2 분석용 중간 포맷** | 파싱·변환된 열지향 데이터 | **90일**(A1과 연동) | 삭제 |
| **A3 분석 세션·결과** | Analysis State, Finding, Evidence, 통계 결과 | **2년** | 조회 차단 후 삭제 |
| **A4 보고서** | 생성된 PDF/Excel/HTML | **1년**(다운로드 기간 별도) | 다운로드 차단 → 삭제 |
| **A5 로그** | 감사 로그·사용량·작업 이력 | 감사 1년 / 사용량 2년 / 프롬프트 90일 | 삭제 |

A3의 보유기간을 A1보다 길게 잡은 이유는 §6-3에서 설명한다.

## 6-2. 조회 기간과 다운로드 기간의 분리

E-9가 "조회 및 다운로드 기간"을 함께 언급한 점을 반영해 **두 기간을 별도로 설정**할 수 있게 한다.

```text
보고서 생성
     │
     ├── 다운로드 가능 기간 (기본 30일) ──► 만료 후 다운로드 버튼 비활성
     │
     └── 조회 가능 기간 (기본 1년) ────────► 만료 후 목록에서 숨김
              │
              └── 보유기간 만료 ───────────► 실제 삭제
```

다운로드를 먼저 막고 조회는 더 오래 허용하는 구조가 실무에 맞다. 보고서를 반출한 뒤 파일이 사외로 흘러가는 경로를 제한하면서, 사내에서 "그때 그 분석 결과가 뭐였지"를 확인하는 것은 계속 가능하게 한다. [추론]

## 6-3. 원본 삭제와 재현성의 충돌 — 중요한 설계 논점

**원본이 90일 후 삭제되면, 6개월 전 분석 결과는 재현할 수 없다.** 그런데 그 분석이 품질 판단의 근거로 쓰였다면 문제가 된다. 제조업에서는 품질기록의 보존 의무가 있는 경우가 많다.

이 충돌을 세 가지 장치로 해소한다.

### (1) 재현성 메타데이터는 원본과 함께 삭제하지 않는다

**DD-074 · 원본 데이터가 삭제되어도 분석 결과에 부착된 재현성 메타데이터(파일 해시, 행·열 수, 사용 변수, 집계 통계량, 분석 파라미터, 엔진·라이브러리 버전, 실행 시각, 실행 주체)는 A3의 보유기간까지 유지한다.**

이 메타데이터만으로도 "어떤 데이터에 어떤 방법을 적용해 이 결론이 나왔는가"는 설명할 수 있다. 재계산은 불가능하지만 **근거의 추적은 가능하다.**

### (2) 결과 화면에 원본 상태를 표시한다

```text
┌─────────────────────────────────────────────┐
│ Welch t-test — Torque by Line               │
│ 데이터: DS-UC03-001 v3 (1,840행)             │
│ ⚠ 원본 데이터는 보유기간 만료로 삭제되었습니다  │
│   (2026-12-10). 결과 재계산은 불가능합니다.    │
└─────────────────────────────────────────────┘
```

### (3) 보존 지정(Hold)

**DD-075 · 사용자는 특정 분석 세션 또는 데이터셋에 '보존 지정'을 요청할 수 있으며, 관리자 승인 시 보유기간 만료에서 제외된다.**

품질 이슈 대응, 고객 클레임 분석, 부적합 보고서의 근거가 된 분석 등은 삭제되면 안 된다. 보존 지정 목록은 관리자 콘솔에서 관리하며, 지정 사유와 지정자를 함께 기록한다.

## 6-4. 삭제 방식

**DD-076 · 삭제는 소프트 삭제 후 유예기간(기본 14일)을 거쳐 하드 삭제한다. 만료 예정은 사전 통지한다.**

```text
D-14  만료 예정 알림 (앱 내 알림 + 목록에 만료일 표시)
D-7   재알림
D-0   소프트 삭제 — 조회 불가, 복구 가능
D+14  하드 삭제 — 스토리지에서 실제 삭제, 복구 불가
```

유예기간을 두는 이유는 **삭제 정책 설정 실수로 인한 대량 소실을 되돌릴 수 있게** 하기 위해서다. 관리자가 보유기간을 90일에서 9일로 잘못 입력하는 사고는 실제로 발생한다. [추론]

또한 보유기간 설정을 **단축하는 방향으로 변경할 때는 영향 범위(삭제 예정 건수)를 미리 보여주고 확인**을 받는다.

## 6-5. 삭제 종속성

```text
A1 원본 삭제
   └─► A2 중간 포맷도 함께 삭제 (A1 없이 존재할 이유 없음)
       └─► A3 분석 결과는 유지 (DD-074)
           └─► A4 보고서도 유지 (자체 보유기간 적용)

A3 세션 삭제
   └─► A4 그 세션에서 생성된 보고서는? → 보고서는 독립 보존
       (보고서는 이미 배포된 산출물이므로 세션과 생명주기를 분리)
```

## 7-2. 관리자 콘솔의 원칙

| 원칙 | 내용 |
|---|---|
| **위험한 설정은 영향 범위를 먼저 보여준다** | 보유기간 단축 시 "이 변경으로 1,240건이 삭제 예정이 됩니다" |
| **관리자도 볼 수 없는 것이 있다** | 개인 LLM 자격증명 평문(DD-062), 타인의 분석 데이터 내용(메타데이터만 조회) |

| **정책 변경은 소급 적용하지 않는다** | 보유기간을 늘리면 이미 삭제된 것은 돌아오지 않음을 명시 |

## 7-3. 관리자가 볼 수 없어야 하는 것

관리자 권한이 **데이터 열람 권한과 같지 않다는 점**을 분명히 한다.

- 타인의 업로드 데이터 내용·분석 결과 상세 → 조회 불가(메타데이터·용량·건수만)
- 개인 LLM 자격증명 → 조회 불가
- 개인별 사용 금액 → **조회 가능**(한도 관리 목적, 업무상 필요)

**Reason:** 관리자 계정이 탈취되면 전사 데이터가 노출되는 구조를 만들지 않는다. 관리자는 *운영*을 하는 역할이지 *데이터를 보는* 역할이 아니다. 특정 데이터 열람이 필요한 사고 조사 상황은 별도 절차(소유자 동의 또는 정보보호 담당 승인)로 처리한다.

| **확인 H** | 예상 **동시 접속 규모**와 **최대 데이터 크기** | §4-4 자원 상한 기본값 |
| 확인 A~D | Step 28-1에서 이월 (Enterprise API 접근 여부 등) | 진행에 지장 없음 |

**모두 Step 30(Schema Contract) 진행을 막지 않는다.** 확인 결과는 기본값과 구현 방식에 반영된다.

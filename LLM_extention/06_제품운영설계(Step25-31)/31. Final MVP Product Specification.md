# 1. 제품 정의

## 1-1. 한 문장

> **제조 현장의 질문을 통계적 판단으로 바꿔주는 웹 애플리케이션.** 검증된 통계 엔진으로 독립 동작하며, 필요할 때 LLM Agent를 선택적으로 연결해 분석 방법 선택·다단계 분석·결과 해석·원인 탐색을 지원한다.

## 1-2. 사용자

| 역할 | 권한 등급 | 주 사용 모드 |
|---|---|---|
| 현장 실무자 (통계 비전문가) — **Primary User** | GENERAL | Level 0~1 |
| 공정·품질 엔지니어 | ENGINEER | Level 0~3 |
| 앱 관리자 (품질보증·시스템) | ADMIN | 관리자 콘솔 |

## 1-3. 변경 불가 제품 원칙

**DD-085 · 아래 10개 원칙은 구현 단계에서 성능·편의를 이유로 완화할 수 없다. 완화가 필요하다고 판단되면 구현을 중단하고 설계 결정을 다시 받는다.**

| # | 원칙 | 위반 예시 (구현 시 실제로 발생하기 쉬움) |
|---|---|---|
| 1 | **LLM은 통계를 계산하지 않는다** | 해석 문장을 만들며 평균을 다시 계산하거나 반올림을 바꿈 |
| 2 | **Manual(Level 0)은 LLM 없이 100% 동작한다** | 해석 생성이 LLM에 의존해 결과 화면이 비어 보임 |
| 3 | **Manual과 AI는 동일한 Statistical Engine을 쓴다** | AI 경로에 별도 간이 계산을 둠 |
| 4 | **모든 Tool 실행은 Rule Engine 검증을 거친다** | "이미 검증된 계획"이라며 우회 |
| 5 | **승인 범위를 벗어난 Tool 실행은 없다** | 편의상 계획 외 분석을 자동 추가 |
| 6 | **모든 LLM 호출은 AI Gateway를 통과한다** | 문장 하나 생성하려고 Provider 직접 호출 |
| 7 | **식별자 원문은 LLM에 전송되지 않는다** | 판단 품질을 위해 실명을 함께 보냄 |
| 8 | **관찰 데이터만으로 인과를 확정하지 않는다** | p값이 작다는 이유로 "원인이다"라고 서술 |
| 9 | **실행되지 않은 결과를 주장하지 않는다** | LLM이 수행하지 않은 분석 결과를 생성 |
| 10 | **화면의 모든 서술에 출처가 표기된다** | 통계 결과와 AI 해석이 한 문단에 섞임 |

## 3-2. 통계 기능 — MVP Tool Registry 확정

**DD-086 · MVP Tool Registry에 `chi_square_test`와 `proportion_test`를 정식 등재한다.**

**Reason:** RUN-030 이래 네 차례 지적된 문서 불일치를 여기서 종결한다. 근거는 명확하다 — **UC-03 Golden Case(Step 23·24)가 이미 불량률 비교에 카이제곱검정을 사용하고 그 기대 결과(p ≈ .0507)까지 명시**하고 있으며, 벤치마크 Use Case인 UC-11(불량 원인 탐색)도 불량률 비교가 핵심이다. Baseline §10이 Chi-square를 Phase 2로 분류한 것은 이 의존 관계를 반영하지 못한 것이다. **Golden Case가 요구하는 Tool은 MVP에 있어야 한다.**
**Status:** 확정 제안

| AC-S1 | 모든 통계 Tool이 Golden Dataset 기준값과 허용오차 내 일치 (상대오차 1e-9, p-value 1e-12) | 자동 |
| AC-S2 | `welch_t_test` 8개 단위테스트(정상·분산비 큼·불균형 n·결측·표본부족·분산0·그룹수 오류·타입 오류) 전부 통과 | 자동 |

## 7-1. T-13이 분기점이다

**T-13(Manual Vertical Slice)이 완료되면 이미 사용 가능한 제품이 존재한다.** LLM 없이 업로드부터 보고서까지 동작하기 때문이다. 이는 DD-001(LLM 없이도 완전 동작)의 개발 일정상 의미이기도 하다 — **AI 계층 개발이 지연되어도 제품 출시가 막히지 않는다.**

따라서 일정 압박이 발생하면 M4의 일부를 미룰 수는 있어도, **M1과 T-13은 축소 대상이 아니다.**

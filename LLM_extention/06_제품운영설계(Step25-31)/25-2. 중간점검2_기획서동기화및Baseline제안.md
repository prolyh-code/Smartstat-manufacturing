
네. **저도 지금 요약 노트를 만드는 것이 맞다고 봅니다.** 오히려 지금 시점이 가장 좋은 타이밍입니다.

사용자께서 늦게 말씀하신 것이 아닙니다. 지금까지는 통계 Engine → Tool → Rule → Agent → Evidence → Golden Case처럼 **내부 동작의 신뢰성**을 먼저 설계했고, 이제 실제 제품 사용 관점에서 **App ↔ LLM ↔ 사용자 경험**을 설계하려는 단계에 도달했습니다. 이 시점에서 그대로 다음 단계로 가면 대화가 너무 길어져 중요한 결정사항과 미결정사항이 섞일 가능성이 있습니다.

특히 현재 원본 기획서와 지금까지 발전시킨 Agent 설계를 분리해서 보존하는 것이 좋습니다. 원본 기획서는 제조 현장 질문 중심의 통계분석, Navigator, Wizard, 해석, 시각화 등의 기본 철학을 담고 있습니다. 통계분석 앱 제작 기획서.mdMD 그리고 우리가 이후 대화에서 이 구조를 LLM Agent 구조로 확장했습니다.

# 지금까지 확정된 것과 아직 미정인 것을 분리하겠습니다

예를 들어:

### 확정

- LLM은 통계 계산을 하지 않는다.
- Statistical Engine이 계산한다.
- LLM은 Tool을 호출한다.
- Rule Engine이 Tool 실행을 통제한다.
- Analysis State가 분석 사실을 보존한다.
- Finding과 Evidence를 분리한다.
- Causal overclaim을 차단한다.
- Golden Case로 Agent를 평가한다.
- LLM 없이도 앱 자체가 완전하게 동작한다.
- Manual/AI 분석은 동일한 Statistical Engine을 사용한다.

### 설계 진행 필요

- AI Gateway
- LLM Provider 선택/교체 구조
- AI ON/OFF
- Manual ↔ AI 전환
- AI 호출 조건
- AI 화면
- Analysis Trace
- AI 오류 처리
- Offline/Online 정책
- 데이터 전송 정책
- Token/비용 관리
- 사용자 권한
- 세션 저장/복구
- AI Audit Log

이렇게 분리하면 앞으로 우리가 어떤 부분을 **이미 결정했는지**, 어떤 부분을 **논의해야 하는지** 명확해집니다.

## "Design Decision Log"

앞으로 중요한 결정을 할 때마다 기록하는 것입니다.

예를 들면:

```
DD-001
Decision:
LLM 없이도 모든 핵심 통계분석 기능을 사용할 수 있도록 한다.

Reason:
제조 현장의 보안/네트워크 환경 및 시스템 신뢰성 확보.

Status:
Approved
```

또는:

```
DD-002
Decision:
LLM은 Statistical Engine을 직접 호출하지 않고
Tool Layer를 통해서만 통계분석을 요청한다.

Reason:
재현성, 검증성, 안전성 확보.

Status:
Approved
```

이것이 쌓이면 나중에 Claude Code를 이용해 개발할 때도 굉장히 강력한 기준이 됩니다.

# 특히 "변경 이력"을 남기는 것이 좋습니다

이번 프로젝트에는 중요한 방향 전환이 하나 있었습니다.

```
초기
Standalone Statistical App
        ↓
LLM 통합 필요성 검토
        ↓
LLM + Deterministic Statistical Engine
        ↓
Manufacturing Statistical Agent
```

이것을 **왜 변경했는지** 기록해 두는 것이 좋습니다.

그래야 몇 달 뒤 개발하면서

> "그냥 ChatGPT처럼 데이터를 넣고 분석하게 만들면 안 될까?"

라는 생각이 들어도 **왜 현재 구조를 선택했는지** 되돌아볼 수 있습니다.

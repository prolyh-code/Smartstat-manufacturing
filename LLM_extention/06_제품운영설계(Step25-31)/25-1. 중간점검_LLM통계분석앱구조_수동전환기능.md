

네. 이 질문은 **지금 단계에서 반드시 정리해야 하는 핵심 설계사항**입니다.

그리고 먼저 결론부터 말씀드리면, **지금까지의 기획에서는 통계 Engine·Agent·State·Rule 구조는 상당히 구체화되었지만, 사용자가 실제 앱을 어떻게 사용하고 LLM이 언제/어떻게 연결되는지에 대한 UX와 운영 아키텍처는 아직 완전히 정의되지 않았습니다.**

기존 기획서에는 Wizard, Analysis Navigator, 분석 메뉴, LLM 설명 등이 각각 정의되어 있지만, **“LLM이 없는 상태에서도 완전하게 동작하고, 필요할 때만 LLM을 연결한다”는 제품 운영 모델까지는 명시적으로 설계되어 있지 않습니다.** 기존 기획서 역시 Wizard를 통한 수동 분석과 질문 중심 Navigator를 중요 기능으로 정의하고 있습니다.

저는 오히려 사용자가 말씀하신 방향이 **최종 제품으로 훨씬 적합하다**고 봅니다.

---

# 1. 제가 권장하는 최종 제품 구조

핵심은 이것입니다.

> **앱 자체는 독립적인 통계분석 프로그램이고, LLM은 필요할 때 연결하는 선택적 지능 계층이다.**

즉,

```
                    ┌─────────────────────┐
                    │       사용자        │
                    └─────────┬───────────┘
                              │
                 ┌────────────▼────────────┐
                 │   Manufacturing App     │
                 │                         │
                 │  수동 분석     AI 분석   │
                 │     │            │      │
                 │     ▼            ▼      │
                 │ Statistical    LLM Agent │
                 │ Engine          Layer    │
                 └────────┬───────────┬────┘
                          │           │
                          ▼           ▼
                    통계 계산       LLM
                    Rule Engine   (선택적)
                    Visualization
                    Report
```

### 따라서 3가지 사용 방식이 존재합니다.

|Mode|LLM|사용 방식|
|---|---|---|
|**Manual Mode**|OFF|사용자가 분석 메뉴를 선택|
|**Assisted Mode**|ON|사용자가 질문 → LLM이 분석 지원|
|**Agent Mode**|ON|사용자가 문제를 제시 → Agent가 여러 분석을 연결|

이 세 가지를 **하나의 앱 안에서 자연스럽게 전환**하도록 만드는 것이 좋습니다.

---

# 2. LLM이 없어도 앱이 완전히 동작해야 합니다

이것은 저는 **필수 요구사항**으로 정의하겠습니다.

사용자가 인터넷이 없는 환경에서도:

- Excel/CSV 불러오기
- 데이터 미리보기
- 데이터 품질 확인
- 기초통계
- Histogram
- Box Plot
- Scatter Plot
- t-test
- ANOVA
- Post-hoc
- Correlation
- Regression
- 그래프
- 결과 해석
- Report
- SVG/PNG/Excel/PDF 출력

등을 사용할 수 있어야 합니다.

기존 기획서에서도 Excel/CSV, 데이터 검증, 통계분석, 시각화, 자동 해석 등이 앱 자체 기능으로 정의되어 있습니다.

즉 **LLM은 앱의 핵심 기능을 대체하는 것이 아니라 앱의 사용성과 지능을 확장하는 것**입니다.

---

# 3. 왜 이 구조가 중요한가?

제조 현장에서는 이것이 특히 중요합니다.

예를 들어 공장 PC에서:

> 인터넷 연결이 안 된다.

또는

> 회사 보안 정책상 외부 LLM으로 데이터를 보낼 수 없다.

라는 상황이 생길 수 있습니다.

그렇다고 통계분석 자체를 못 하면 안 됩니다.

따라서:

### Core App

```
100% Local
```

이어야 하고,

### AI Layer

```
Optional
```

이어야 합니다.

이렇게 하면 제품 신뢰성이 크게 올라갑니다.

# 5. Manual Mode는 기존 앱을 그대로 살립니다

예를 들어 사용자가:

> **두 공정/조건 비교**

를 선택합니다.

그러면:

```
비교할 데이터
      ↓
그룹 변수 선택
      ↓
A / B
      ↓
독립 데이터인가?
      ↓
분산 조건
      ↓
분석 방법 추천
      ↓
분석 실행
```

이것은 기존 Wizard의 철학과 동일합니다. 기존 기획서에서도 “무엇을 알고 싶은가 → 어떤 데이터를 가지고 있는가 → 그룹 수 → 독립성 → 조건 확인 → 실행 → 그래프 → 해석 → 보고서”의 Wizard가 정의되어 있습니다.

다만 앞으로는 이것을 **Manual/Guided Analysis**라고 부르는 것이 좋겠습니다.

# 6. 그런데 Manual Mode도 "완전 수동"일 필요는 없습니다

이 부분이 중요합니다.

사용자가

> A라인과 B라인을 비교하고 싶다.

라고 선택하면 앱이:

```
추천 분석

Welch t-test

이유:
두 그룹의 평균을 비교하며
두 그룹의 분산이 동일하지 않은 것으로 판단됩니다.

[ 분석 실행 ]
[ 다른 방법 선택 ]
[ AI에게 물어보기 ]
```

라고 보여줄 수 있습니다.

즉:

> **사용자가 통제권을 갖되, 앱이 통계적으로 지원한다.**

이것이 기존 Navigator의 발전형입니다.

# 10. AI가 실행되는 과정도 사용자에게 보여줘야 합니다

이것이 **신뢰성 UX**입니다.

예를 들어:

> A라인과 B라인의 토크 차이가 있는지 확인해줘.

라고 하면 AI가 갑자기:

> A라인의 평균 토크가 B라인보다 낮습니다.

라고 하면 안 됩니다.

사용자에게 Agent가 무엇을 했는지 보여줘야 합니다.

예:

```
분석 진행

✓ 데이터 구조 확인
✓ Torque 변수 확인
✓ Line 변수 확인
✓ A/B 그룹 확인
✓ 독립 데이터 여부 확인
✓ 분산 비교
✓ Welch t-test 실행
✓ 결과 검증
✓ 효과크기 계산
✓ 동일 Model 구성 차이 확인

● 결과 해석 중
```

이것이 중요합니다.

# 11. 단, LLM의 "생각 과정"을 보여주는 것은 아닙니다

여기에는 명확한 구분이 필요합니다.

보여주는 것은:

> **Analysis Trace**

이지,

> LLM의 내부 Chain-of-Thought

가 아닙니다.

즉:

```
[분석 단계]
Data Check
→ Group Check
→ Variance Check
→ Welch t-test
→ Effect Size
→ Confounding Check
```

정도만 공개합니다.

이것은 사용자가 **무슨 분석이 수행됐는지 재현할 수 있도록 하는 감사 추적(Audit Trail)**입니다.

---

# 12. 그리고 각 결과에는 "AI가 말한 것"과 "통계 계산 결과"를 구분해야 합니다

이것도 매우 중요합니다.

예를 들어:

### Statistical Result

```
Welch t-test
Mean Difference = -2.63 N·m
p < 0.001
95% CI = ...
```

**출처: Statistical Engine**

---

### AI Interpretation

> A라인의 평균 토크가 B라인보다 낮은 것으로 나타났습니다.

**출처: LLM**

---

### Manufacturing Judgment

> 두 라인의 평균 차이는 통계적으로 유의하지만, 두 평균 모두 규격 범위 내에 있으므로 이 결과만으로 제조상 문제라고 판단할 수 없습니다.

**출처: Rule + Manufacturing Knowledge + Statistical Result**

이렇게 분리해야 합니다.

기존 기획서에서 LLM을 통계 계산기가 아니라 결과를 사람이 이해할 수 있도록 설명하는 역할로 제한한 방향과도 정확히 일치합니다.

# 15. LLM에 Excel 원본 전체를 보내지 않습니다

예를 들어 100만 행의 제조 데이터를 가지고 있다고 하겠습니다.

절대로:

```
Excel 1,000,000 rows
        ↓
       LLM
```

방식으로 설계하지 않습니다.

대신 앱 내부에서 먼저 분석합니다.

```
Raw Data
 ↓
Data Engine
 ↓
Data Profile
 ↓
Statistical Result
 ↓
Relevant Context
 ↓
LLM
```

LLM에 전달하는 것은 예를 들어:

```
{
  "response": "Torque",
  "group": "Line",
  "groups": ["A", "B"],
  "n": {
    "A": 815,
    "B": 1025
  },
  "mean": {
    "A": 166.252,
    "B": 168.881
  },
  "welch_test": {
    "p_value": "<1e-18",
    "difference": -2.628
  },
  "spec": {
    "LSL": 150,
    "USL": 190
  }
}
```

같은 **구조화된 분석 결과**입니다.

이렇게 하면:

- 개인정보/기밀 데이터 노출 감소
- LLM 비용 감소
- 응답속도 향상
- 환각 감소
- 결과 재현성 향상

이라는 장점이 있습니다.

# 16. 그렇다면 LLM은 정확히 무엇을 하는가?

이제 역할을 아주 명확히 나누겠습니다.

### 앱이 하는 것

```
Data Loading
Data Validation
Statistical Calculation
Visualization
Statistical Rules
Result Validation
State Storage
Report
```

### LLM이 하는 것

```
질문 이해
Problem Model 생성
분석 계획
Tool 선택 제안
결과 설명
Finding 생성
Hypothesis 생성
Confounder 후보 탐색
Next Best Analysis 제안
사용자와 대화
```

즉:

> **LLM = Reasoning & Communication**

> **App = Calculation & Control**

입니다.

# 17. 그러면 LLM은 어디에 연결되는가?

저는 앱 내부에 다음 구조를 두는 것을 권장합니다.

```
LLM Provider
     │
     ▼
┌─────────────────┐
│   AI Gateway    │
├─────────────────┤
│ Authentication  │
│ Model Selection │
│ Prompt          │
│ Context Filter  │
│ Tool Calling    │
│ Timeout         │
│ Retry           │
│ Logging         │
│ Privacy Control │

         │
         ▼
       LLM
```

그리고 향후:

```

```

등을 교체할 수 있도록 합니다.

즉 앱 코드가 특정 LLM에 종속되지 않게 합니다.

# 18. LLM 연결이 실패하면?

여기서 제가 **반드시 추가하고 싶은 요구사항**이 있습니다.

### LLM Failure → App Failure가 되면 안 됩니다.

예:

```
AI 연결 실패
       ↓
┌────────────────────────────┐
│ AI 서비스를 사용할 수      │
│ 없습니다.                  │
│                            │
│ 통계 분석 기능은 정상적으   │
│ 로 사용할 수 있습니다.     │
│                            │
│ [수동 분석으로 계속하기]   │
│ [다시 연결]                │
└────────────────────────────┘
```

즉:

> **LLM은 앱의 Optional Dependency**

입니다.

이 원칙을 Architecture Requirement로 넣겠습니다.

# 19. LLM 사용 중에도 끌 수 있어야 합니다

# 20. 특히 "수동 → AI" 연결이 중요합니다

예를 들어 사용자가 직접:

> Welch t-test

를 실행했습니다.

결과가 나왔습니다.

그런데:

> 왜 차이가 나는지 알고 싶다.

라고 생각할 수 있습니다.

그러면 결과 화면에:

**[AI에게 원인 분석 요청]**

버튼을 제공합니다.

그러면 AI가 현재 결과를 그대로 이어받습니다.

```
기존 분석 결과
      ↓
Finding
      ↓
AI Agent
      ↓
Confounder 탐색
      ↓
Next Analysis
```

사용자는 데이터를 다시 설명할 필요가 없습니다.

이것이 **Manual + AI 통합의 핵심 UX**입니다.

# 21. 반대로 AI → Manual도 가능해야 합니다

AI가:

> Model별로 A/B 라인을 다시 비교하는 것이 좋겠습니다.

라고 제안하면 사용자에게:

```
추천 분석

Model별 A/B 비교

[이 분석 실행]
[다른 분석 선택]
[AI에게 다시 질문]
```

을 보여줍니다.

사용자가 **[이 분석 실행]**을 누르면 일반 통계분석 Engine이 실행됩니다.

즉 AI가 통계를 직접 실행하는 것이 아니라:

```
AI 추천
 ↓
앱의 통계 Engine
 ↓
정확한 계산
```

이 됩니다.

# 24. AI가 켜져 있어도 모든 분석에 LLM을 사용할 필요는 없습니다

이것도 중요한 운영 원칙입니다.

예를 들어 사용자가:

> 평균 계산해줘.

라고 하면 LLM을 호출할 필요가 없습니다.

앱이 바로:

```
descriptive_statistics()
```

를 실행하면 됩니다.

반면:

> 최근 토크 불량이 증가했는데 원인이 무엇인지 찾아줘.

같은 질문은 LLM Agent를 사용하는 것이 적합합니다.

따라서:

```
단순 계산
→ LLM OFF

분석 방법 선택
→ LLM Optional

복합 문제
→ LLM ON

원인 탐색
→ LLM Agent

다단계 분석
→ LLM Agent
```

라는 **AI Activation Policy**가 필요합니다.

---

# 25. 이것을 "AI 개입 수준"으로 정의하면 더 좋습니다

### Level 0 — Manual

```
사용자가 분석 선택
앱이 계산
```

### Level 1 — AI Assist

```
사용자 질문
 ↓
AI가 분석 방법 추천
 ↓
사용자가 승인
 ↓
앱이 계산
```

### Level 2 — AI Analysis

```
사용자 질문
 ↓
AI가 계획
 ↓
앱이 여러 분석 실행
 ↓
AI가 결과 해석
```

### Level 3 — Agentic Analysis

```
목표 제시
 ↓
Agent가 분석 계획
 ↓
여러 Tool 실행
 ↓
Finding
 ↓
Hypothesis
 ↓
Confounder
 ↓
Next Best Analysis
 ↓
Stop / Ask / Experiment
```

MVP에서는 **Level 0~2**를 우선 구현하고 Level 3을 점진적으로 확장하는 것이 안전합니다.

# 26. 그리고 이것은 기존 Wizard를 없애는 것이 아닙니다

오히려 기존 Wizard는 상당히 가치가 있습니다.

기존 기획의:

> 무엇을 알고 싶은가? → 어떤 데이터를 가지고 있는가? → 몇 개 그룹인가? → 독립적인가? → 조건 확인 → 실행

이라는 구조는 그대로 유지할 가치가 있습니다.

다만 제품 구조를 이렇게 바꾸는 것입니다.

```

Wizard
   ↓
Analysis


변경 후

Guided Mode
   ↓
Wizard + Navigator
   ↓
Common Analysis Engine
```

그리고 옆에:

```
AI Mode
   ↓
LLM Agent
   ↓
Common Analysis Engine
```

을 추가합니다.

# 31. 제가 권장하는 최종 제품 정의

따라서 앞으로의 기획서에서는 이 앱을 단순히

**"LLM 통합 통계분석 앱"**

이라고 부르지 않는 것이 좋겠습니다.

다음처럼 정의하는 것이 훨씬 정확합니다.

> ### **제조 현장용 통계분석 플랫폼**
> 
> **Statistical Analysis Engine을 중심으로 독립적인 수동 분석 기능을 제공하고, 필요할 때 LLM Agent를 선택적으로 연결하여 분석 방법 선택, 다단계 분석, 결과 해석, 원인 탐색 및 다음 분석을 지원하는 제조 데이터 분석 시스템**

이렇게 하면 **LLM이 없어도 제품 가치가 완전하고, LLM이 추가되면 제품 가치가 크게 확장**됩니다.

## 1-1. 전제가 바꾸는 것

이 4개 전제는 Step 26~28 설계의 밑바탕을 상당 부분 바꾼다. 요약하면 다음과 같다.

```text
기존 가정                          →   확정된 현실
──────────────────────────────────────────────────────────────
개인이 각자 LLM 계정을 마련해야 함   →   회사 Enterprise 계약이 이미 존재
공용 PC에서 자격증명 공유 위험       →   개인 PC 전용, 해당 없음
앱은 인증 없이 OS 계정에 종속        →   앱 자체 로그인 존재
외부 클라우드로 데이터가 나간다      →   Enterprise 계약 + 사내 전용 환경
```

가장 중요한 변화는 **E-2다. 비용 귀속 문제가 계약 수준에서 이미 상당 부분 해소되어 있다** — 이것이 §3의 O-1 결정을 뒤집는다.

# 2. O-1 인증 모델 결정 — 가장 중요한 변경

## 2-1. 원래 요구의 재해석

Ian이 처음 제기한 요구는 다음과 같았다.

> "사용자가 많아 통합 API Key로 인증할 경우 사용 토큰이 공통계정으로 부담될 경우 부담할 부서가 없습니다. 따라서 개인 계정으로 인증받는 형식이 되어야 합니다."

Step 26 §7-1에서 이 요구를 **"비용 귀속(진짜 요구사항)"과 "계정 로그인(구현 수단)"**으로 분리했다. 이제 E-2를 대입하면 결론이 달라진다.

| 층 | 당시 상황 | E-2 확정 후 |
|---|---|---|
| 비용 부담 주체 | 불명확 — "부담할 부서가 없다" | **회사가 Enterprise 계약 주체로 이미 부담 중** |
| 필요한 것 | 개인별 과금 분리 | **누가 얼마나 썼는지 보이는 것(가시성)** |
| 구현 수단 | 개인 API Key(BYOK) | **조직 Enterprise 연결 + 앱 로그인 계정으로 사용자 식별** |

즉 **개인별 API Key를 각자 발급받게 할 필요가 사라졌다.** 오히려 회사가 이미 Enterprise 계약으로 비용을 지불하는 상황에서 개인 키를 별도로 쓰게 하면 **이중 비용**이 발생한다.

## 2-2. 결정

**DD-053 · LLM 연결은 회사 Enterprise 계약을 통한 조직 단위 연결로 하고, 사용자 식별과 사용량 귀속은 앱 로그인 계정(E-4)을 통해 수행한다. 개인별 API Key 발급 방식(BYOK)은 채택하지 않는다.**

```text
사용자 ──[앱 ID/PW 로그인]──► 앱
                               │  Principal = {mode: ENTERPRISE,
                               │               subject_id: 앱 사용자 ID,
                               │               department: 부서}
                               ▼
                         AI Gateway
                               │  회사 Enterprise 자격으로 호출
                               ▼
                    회사 Enterprise LLM
                               │
                               ▼
                 사용량은 앱 로그인 계정·부서별로 집계
                 → 필요 시 부서별 사용량 리포트 제공
```

**Reason:** ① 비용 부담 주체가 회사로 명확하므로 원래 요구가 충족된다. ② 사용자가 각자 계정을 만들 필요가 없어져 Primary User(통계 비전문가 현장 실무자)의 진입장벽이 사라진다 — Step 26 §7-2에서 모델 A의 최대 약점으로 지적했던 부분이다. ③ 조직이 모델·정책·감사를 통제할 수 있다. ④ Enterprise 계약은 통상 데이터 학습 미사용·보존 제한 등의 조건을 포함하므로 데이터 보호 수준도 개인 계정보다 높다.
**Status:** 확정 — **Step 26 DD-017을 폐기하고 대체한다**

## 2-3. Step 27의 아키텍처는 그대로 유효하다

Step 27 DD-029에서 인증을 `AuthProvider`로 분리하고 Gateway가 `Principal`만 인식하도록 설계한 결정 덕분에, **인증 모델이 A에서 Enterprise로 바뀌어도 Gateway·Orchestrator·UI 본체는 수정되지 않는다.** `Principal.mode`에 `ENTERPRISE`를 추가하고 `EnterpriseAuth` 구현체를 쓰면 된다.

```python
@dataclass
class Principal:
    mode: str            # "ENTERPRISE" | "CORPORATE_SSO" | "PERSONAL_KEY" | "NONE"
    subject_id: str      # 앱 로그인 사용자 ID
    department: str|None # 앱 사용자 정보에서 취득
    display_name: str
```

`PERSONAL_KEY`는 인터페이스에 남겨두되 MVP에서 구현하지 않는다(향후 사외 협력사 사용 등의 예외 상황 대비).

## 2-4. 남은 확인 사항 — 중요

**Enterprise 상품이 프로그래밍 방식 호출(API)을 포함하는지 확인이 필요하다.**

일반적으로 Enterprise 채팅 상품(사내 구성원이 웹에서 대화하는 용도)과 API 접근은 별개의 상품·계약으로 제공되는 경우가 많다[추론 — 일반적 상품 구조에 근거한 판단이며 회사가 계약한 특정 상품을 확인한 결과는 아님]. 앱이 LLM을 호출하려면 후자가 필요하다.

세 가지 경우로 나뉜다.

| 경우 | 상황 | 설계 영향 |
|---|---|---|
| **경우 1** | Enterprise 계약에 API 접근이 포함되거나 사내 LLM Gateway가 이미 있음 | DD-053 그대로. 사용량 집계는 **가시성 목적**으로만 |
| **경우 2** | API는 별도 계약·사용량 과금 | DD-053 유지하되 **부서별 사용량 리포트가 실제 내부 청구 근거**가 됨(§6 O-8 참조) |
| **경우 3** | API 접근 경로가 없음 | 조직 API 계약 신설 또는 사내 LLM 도입이 선행되어야 함 |

→ **확인 요청 사항 A**(§9). 어느 경우든 앱 설계는 동일하며, 달라지는 것은 사용량 리포트의 용도뿐이다. 따라서 이 확인을 기다리지 않고 Step 29로 진행할 수 있다.

# 4. O-4 세션 저장 위치 재결정

E-3(사내 전용) + E-4(앱 로그인)으로 전제가 바뀌었다. 로그인 계정이 있으면 세션을 계정에 귀속시킬 수 있고, 사내 전용이면 사내 서버 저장의 보안 부담도 낮다.

**DD-055 · 세션은 앱 로그인 계정에 귀속시키며, 세션 스키마는 사내 서버 저장이 가능한 형태로 설계한다. MVP 1차는 로컬 저장으로 시작하되, 서버 동기화 도입 시 스키마 변경이 필요 없도록 한다.**

**Reason:** 제조 현장에서 서버 저장의 실질 가치가 크다 — **교대조 인수인계**(야간조가 분석하던 세션을 주간조가 이어받음), PC 교체 시 이력 승계, 팀 단위 분석 이력 축적. 다만 서버 인프라 준비 여부가 MVP 일정을 좌우해서는 안 되므로, **방향은 서버로 정하되 시작은 로컬로** 한다. 스키마만 미리 맞춰두면 전환 비용이 거의 없다.
**Status:** 확정 — **Step 28 DD-049를 개정한다** / Step 29에 직접 영향

# 5. O-11 개인 PC 전제 — 공용 PC 대비 조치 철회

E-1에 따라 Step 28 §6-2에서 설계한 공용 PC 대비 조치의 전제가 사라졌다.

**DD-056 · 자격증명·로그인 상태는 개인 PC를 전제로 저장을 기본값으로 한다. "이 PC에 저장하지 않음" 옵션은 기능으로는 유지하되 기본값이 아니다.**

옵션 자체를 제거하지 않는 이유는 사외 반출 노트북·임시 대여 PC 같은 예외 상황이 있을 수 있기 때문이다. 구현 비용이 거의 없으므로 남겨둔다.

**Status:** 확정 — **Step 28 DD-047을 개정한다**

또한 §2-2의 결정(조직 Enterprise 연결)으로 개인 API Key 자체가 없어지므로, 공용 PC 문제의 원인이었던 "개인 키 공유" 시나리오는 근본적으로 소멸한다.

# 7. 보안 정책 조정 — 완화할 것과 유지할 것

Ian의 판단("사내 전용 + 로그인 통제로 보안 문제는 크지 않다")을 반영해 Step 28의 정책을 조정한다. **다만 완화가 타당한 항목과, 완화해도 얻는 것이 없어 유지하는 편이 이득인 항목을 구분한다.**

## 7-1. 완화하는 항목

### (1) C3 공정 기밀 — 규격 실값 전송 허용

**DD-057 · C3(규격·수율·공정조건)은 Enterprise 환경에서 실값 전송을 기본으로 한다. 규격 정규화 상대값 변환은 옵션으로 유지한다.**

| | 상대값 변환(기존 기본) | 실값 전송(신규 기본) |
|---|---|---|
| 제조 판단 품질 | 양호 | **우수** — 규격 이탈 예상 개수, 공정능력지수(Cpk) 등을 직접 언급 가능 |
| 설명 명료성 | "규격폭의 9.4%" | **"목표 170 대비 3.7 낮음, 규격 하한까지 16.3 여유"** |
| 노출 위험 | 없음 | Enterprise 계약의 데이터 처리 조건 하에서 제한적 |

현장 사용자에게는 실값 기반 설명이 훨씬 직관적이다. Enterprise 계약이 데이터 학습 미사용·보존 제한을 포함한다면 실값 전송의 추가 위험은 제한적이므로 **제조 판단 품질을 택한다.**
**Status:** 확정 — **Step 28 DD-041을 개정한다**

### (2) S3 원본 데이터 전송 — 관리자 설정으로 허용 가능

**DD-058 · 원본 데이터 전송(S3)은 관리자 설정으로 허용할 수 있다. 다만 기본값은 S1(분석 결과만)을 유지한다.**

기본값을 유지하는 이유는 **보안이 아니라 성능·비용**이다. 184만 행을 전송해도 Agent의 판단 품질은 올라가지 않으며(판단에 필요한 것은 집계 통계량과 검정 결과다) 토큰 비용과 지연만 증가한다. 즉 S1 기본값은 보안 정책이 아니라 **합리적 엔지니어링 기본값**으로 재정의된다.
**Status:** 확정 — **Step 28 DD-045를 개정한다**

### (3) 프롬프트 로깅 완화

**DD-059 · 프롬프트 전문 로깅을 관리자 설정으로 상시 수집 가능하게 하고, 보존기간을 90일로 한다. 기본값은 오류 발생 시에만 수집한다.**

사내 전용 + 로그인 통제 환경에서는 로그 접근이 이미 통제되므로, 상시 수집의 위험이 낮고 품질 개선 가치가 크다. Agent가 왜 그런 판단을 했는지 추적하려면 실제 프롬프트가 필요하다.
**Status:** 확정 — **Step 28 DD-051을 개정한다**

### (4) 공용 PC 대비 조치 → 기본값 변경 (§5, DD-056)

## 7-2. 완화하지 않고 유지하는 항목

아래는 **완화해도 얻는 것이 거의 없고, 유지 비용도 거의 없는** 항목이다. Ian의 판단을 존중하되 이 항목들은 그대로 두는 것을 권한다.

| 항목 | 유지 근거 |
|---|---|
| **C4 가명화(DD-043)** | **개인정보는 사내 처리라고 해서 자유로워지지 않는다.** 작업자 사번·성명은 사내 시스템에서도 처리 근거와 목적 제한이 적용되는 영역이다. 그리고 가명화는 **분석 가치를 전혀 잃지 않으면서**(작업자별 비교는 그대로 동작) 구현 비용도 낮다. 완화해서 얻는 이득이 실질적으로 없다 |
| **C5 고객·계약 정보 기본 차단** | 고객사와의 비밀유지 의무는 사내 여부와 무관하게 적용된다. 관리자 해제는 가능하게 두되 기본 차단 유지 |
| **식별자 fail-closed(DD-042)** | 오판 비용의 비대칭은 환경과 무관하다. 다만 경고 표시는 덜 방해되는 수준으로 조정 가능 |
| **자격증명 미기록(DD-030)** | 조직 자격증명이 되었으므로 오히려 유출 시 영향 범위가 더 크다 |
| **TLS 검증 비활성화 금지(DD-050)** | 사내망 프록시 환경에서 특히 우회 유혹이 크므로 유지 |
| **원본 미복제 보관(DD-048)** | 보안 목적이 아니라 **동기화 문제 방지**가 주 목적이다. 원본을 복제하면 원본 수정 시 어느 쪽이 맞는지 알 수 없게 된다 |
| **재현성 기록 세트(DD-052)** | 보안이 아니라 **품질 요건**이다. 제조 판단의 근거를 사후 추적하는 기능 |
| **재식별 경고(DD-044)** | 통계적 표본부족 경고와 동일 검사이므로 추가 비용 0 |

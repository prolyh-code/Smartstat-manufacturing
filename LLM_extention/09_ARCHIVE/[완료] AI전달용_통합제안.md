# 0. 이 문서의 목적과 읽는 방법

지금까지 이 대화(Step 1~25)에서 만든 Manufacturing Statistical Agent 기획을, 별도의 Claude 세션(Cowork)에서 두 차례에 걸쳐 검토했습니다(1차: Step 1~7 대상, 2차: Step 8~25 대상). 이 문서는 그 두 검토 내용을 하나로 통합하고, 여기에 제가 추가로 생각한 요구사항 한 가지를 더해서, 앞으로 이 대화를 이어갈 때 함께 검토해 주셨으면 하는 내용을 정리한 것입니다.

아래 항목들은 "이것이 잘못됐다"는 결론이 아니라 **"이 지점을 한 번 더 확인해 보면 좋겠다"는 제안**으로 읽어 주시면 좋겠습니다. 지금까지 대화가 Step 1부터 25까지 이어지면서, 제가 중간에 질문이나 요구를 추가하는 과정에서 이전에 이미 다뤘던 내용과 겹치거나 충돌하는 부분이 생겼을 수도 있다고 생각합니다. 그래서 각 항목에는 관련된 Step 번호와 파일명을 함께 표시했으니, 그 Step으로 돌아가서 지금 시점의 전체 설계와 앞뒤가 맞는지 함께 봐주시면 좋겠습니다.

# 1. 문서/베이스라인 정합성 — 확인 제안

## 1-1. 원본 기획서(`통계분석 앱 제작 기획서.md`) 동기화 여부

확인해 보니, 이 파일은 볼트 루트에 있는 원본과 `LLM_extention` 폴더 안의 사본이 frontmatter(생성일자 등 메타데이터) 외에는 한 글자도 다르지 않았습니다. 즉 **Step 1 대화가 시작된 이후 지금(Step 25)까지 이 파일의 본문 내용은 전혀 갱신되지 않은 것**으로 보입니다. 이 파일에는 아직 Manual/AI 이중모드, AI Gateway, Problem Model/Analysis Plan Graph/Agent State 같은 Step 5 이후 구조, Evidence Level 체계, Tool Registry/Rule Engine 등이 전혀 반영되어 있지 않고, §37 "AI/LLM 활용 전략"도 원래의 짧은 개념 수준(Statistical Engine/Rule Engine/LLM 3단 구분)에 머물러 있습니다.

Step 25(`25. 중간점검2.md`)에서 스스로 "원본 기획서는 초기 철학의 기준점으로 보존하고, 새로운 baseline 문서(`manufacturing-statistical-agent-design-notes.md`, Design Decision Log 포함)를 따로 만들어 발전 내용을 관리하자"고 제안한 적이 있었는데, 확인해보니 그 baseline 문서도 실제로는 만들어지지 않았습니다. 대신 그보다 앞서 만들어진 `manufacturing-statistical-analysis-agent-progress-summary.md`가 비슷한 역할을 하고 있지만, 이 파일은 Step 15 시점 내용까지만 담고 있어서 Step 16~25(Tool Registry, Data Contract, Vertical Slice, Manual/AI 이중모드 등)가 반영되어 있지 않은 **다소 낡은 상태**입니다.

**제안:** 다음 두 가지 방향 중 하나를 정해 주시면 좋겠습니다.
- (A) 원본 기획서 자체를 계속 갱신해서 "현재 확정된 최신 기획"을 항상 담도록 운영, 또는
- (B) 원본은 보존하고, Step 25에서 제안했던 baseline 문서(또는 progress-summary.md)를 Step이 끝날 때마다 실제로 갱신하는 규칙을 지키기.

어느 쪽이든, 대화가 계속 길어지고 있으니 "지금 이 시점에 확정된 것"을 한눈에 볼 수 있는 문서 하나는 계속 최신 상태로 유지해 주시길 요청드립니다.

## 1-2. "25." 번호 중복

지금 폴더에 "25."로 시작하는 파일이 3개(`25. 중간점검 LLM 통계 분석 앱 구조_수동 전환 기능.md`, `25. 중간점검2.md`, `25. First Vertical Slice Technical Implementation.md`) 있습니다. 서로 다른 주제인데 번호가 겹쳐 있어서, 이후에 이 대화 내용을 다시 참조하거나 Claude Code에 전달할 때 혼동될 수 있을 것 같습니다. 번호를 재정렬하거나 구분되는 부제를 붙이는 것을 제안합니다.

# 2. 신규 요구사항 제안 — LLM 연결 인증 방식(계정 로그인 vs API Key)

Step 25(중간점검/수동전환기능)에서 이미 AI Gateway와 "LLM Provider 구조"를 앞으로 설계할 대상으로 짚어 두셨고, 다음 단계로 제안된 **Step 26(Product UX & Operating Architecture)**의 세부 항목 중 "16. LLM Provider 구조", "17. AI Gateway", "18. 데이터 전송/보안 정책"에서 구체화될 예정으로 보입니다. 이 지점에 다음 요구사항을 반영해 검토해 주실 것을 제안합니다.

> "LLM을 연결하는 방식이 여러 가지가 있을 것으로 생각되는데, 내가 생각하는 방식은 LLM을 연결할 때 API가 아닌 계정 로그인 방식으로 진행하는 것이 좋겠습니다. 사용자가 많아 통합 API Key로 인증할 경우 사용 토큰이 공통계정으로 부담될 경우 부담할 부서가 없습니다. 따라서 개인 계정으로 인증받는 형식이 되어야 합니다." (Ian)

이 요구사항을 기존 설계와 결합할 때 다음과 같은 검토 포인트가 있을 것 같아 제안해 봅니다.

- 개인 계정 로그인(예: 각 사용자가 자신의 LLM 계정 또는 사내 SSO 계정으로 로그인) 방식과, 공용 API Key로 조직이 일괄 과금하는 방식은 **과금·감사·Rate Limit 관점에서 서로 다른 제약**을 가질 수 있습니다. 어떤 LLM Provider가 "개인 계정 로그인 후 그 계정의 사용량으로 과금"하는 구조를 실제로 지원하는지 확인이 필요해 보입니다(예: 개인 구독 계정으로 로그인하는 방식과, 조직이 발급한 API Key로 사용량을 과금하는 방식은 상품·계약 구조 자체가 다를 수 있습니다).
- 개인 계정 로그인 방식을 택할 경우, "AI 기능을 쓰려면 현장 사용자 각자가 개별 LLM 계정/구독을 보유해야 한다"는 전제가 함께 따라올 수 있는데, 이것이 원래 이 앱의 Primary User로 정의된 "통계 비전문가 제조 현장 실무자"에게 실제로 부담이 되지 않을지도 함께 검토가 필요해 보입니다.
- 대안으로 "부서/팀 단위 계정" 또는 "API Key 위에 사용량 기반 내부 청구(chargeback) 체계를 얹는 방식"도 있을 수 있습니다. 이 중 어느 방향이 실제 조직의 비용 승인 구조에 맞을지는 Ian께서 더 잘 판단하실 수 있는 부분이라, Step 26/27에서 두세 가지 옵션을 놓고 장단점을 비교해 보는 것을 제안합니다.
- Step 5·13에서 이미 LLM Provider를 `generate()/tool_call()/structured_output()/stream()` 인터페이스로 추상화해 두셨는데, 인증 방식(API Key vs 개인 로그인)도 이 Provider 구현체 안에 캡슐화할 수 있을 것으로 보입니다. 다만 이 경우 "누가 로그인했는지"와 "이 분석 세션이 어떤 사용자 계정으로 과금되는지"를 Analysis Session(Step 13의 `AnalysisSession` 객체) 쪽에도 기록해 두어야 할지 확인이 필요해 보입니다.

# 3. Step별 통계/아키텍처 관련 제안 (1차·2차 검토 통합)

## 3-1. (참고) 데이터 기밀성 — Step 25에서 상당 부분 다뤄진 것으로 보임

1차 검토에서 "LLM에 전달되는 제조 데이터의 기밀성 문제가 기존 PRISM Add-on의 '런타임 무-AI' 설계원칙과 어떻게 연결되는지 검토가 필요하다"고 제안했었는데, Step 25(`중간점검 LLM 통계 분석 앱 구조_수동 전환 기능.md`)에서 Core App=100% Local·AI Layer=Optional, AI Gateway, 데이터 전송 정책(원본 데이터 전송 금지를 기본값으로) 구조로 이미 다뤄주신 것으로 보입니다. 다만 이 문서 스스로도 §28에서 "데이터 전송 정책"을 "원칙만 존재, 추가 설계 필요"로 표시해 두셨으니, 위 2번 항목(인증 방식)과 함께 Step 26~28에서 세부 메커니즘(예: 설비명·라인명 등 식별정보를 어느 단계에서 마스킹할지)까지 이어서 다뤄주시면 좋을 것 같습니다.

## 3-2. Tool Registry에 카이제곱(chi-square)·비율검정 도구가 공식적으로 등재되어 있는지 확인 제안

`11. 실제 Agent 작동 시나리오 설계.md`(§11-9)와 `13. Agent Data Contract and Interface 설계.md`(Evidence Schema 예시)를 보면 불량률(범주형/이분형 데이터) 비교에 `chi_square_test()`를 이미 Tool로 사용하는 것으로 서술되어 있습니다. 그런데 "공식 Tool 목록"을 정리해 두신 네 곳 — `8. Manufacturing Statistical Agent Brain Architecture.md`(§8-17), `13.`(§13-15), `18. Tool Registry and Rule Engine.md`(§18-3), `manufacturing-statistical-analysis-agent-progress-summary.md`(§8) — 에는 이 Tool이 보이지 않았습니다. 실제로 사용하기로 하신 것이라면 이 네 곳의 목록에 반영이 필요할지 확인해 주시면 좋겠고, 만약 의도적으로 Phase 2로 미루신 것이라면 §11-9와 Evidence Schema 예시 쪽 서술을 그에 맞게 조정하는 것도 방법일 것 같습니다.

## 3-3. 후보 요인을 동시에 스크리닝할 때의 다중비교(多重比較, multiple comparison) 보정 검토 제안

`3.5`, `4.3` 등에 이미 있는 `tukey_posthoc()`, `games_howell()`, `bonferroni_posthoc()`는 **하나의 ANOVA에서 유의한 차이가 나온 뒤 그룹 쌍을 비교하는 사후검정용 보정**으로 잘 설계되어 있는 것으로 보입니다. 다만 이것과는 별개로, UC-11류 시나리오(`4.5`, `11`, `12` 등)에서 Machine·Model·Shift·Operator·Temperature 같은 **서로 다른 여러 후보 요인을 각각 독립적인 검정으로 동시에 훑어보는 단계**(Candidate Factor Screening)에도 다중비교 보정이 필요할지 검토를 제안합니다. 여러 요인을 동시에 검정하면 우연히 유의하게 나오는 요인이 있을 확률이 올라가는데, 이 프로젝트가 중요하게 여기는 "교란요인 인식·인과 과장 방지"라는 원칙과 같은 맥락의 문제라고 생각되어 말씀드립니다. Rule Engine의 Method Rules(Step 18)에 스크리닝 단계 전용 규칙을 추가하는 방향을 검토해 보시면 어떨까 싶습니다.

## 3-4. 교란요인(混亂要因, confounder) 통제 방법의 일반화 검토 제안

`13.`의 Confounder Schema 예시에 `"recommended_analysis": "MODEL_CONTROLLED_MACHINE_COMPARISON"`처럼, 교란요인을 다룰 때 "동일 조건으로 한정해서 다시 비교"하는 패턴이 UC-11 이후 계속 반복해서 사용되고 있는 것으로 보입니다. 이 방식은 교란요인이 1개이고 범주형일 때는 잘 맞지만, 교란요인이 2개 이상이거나 연속형(예: Temperature)일 때는 데이터를 계속 잘게 나눠야 해서 표본이 부족해지는 문제가 생길 수 있습니다. ANCOVA나 교란변수를 통제한 다중회귀 같은, 좀 더 일반화된 방법을 Tool Registry에 추가할지 여부를 한번 검토해 보시면 좋겠습니다.

## 3-5. Statistical Engine 자체의 검증·회귀테스트 전략 관련

`17. Statistical Engine 실제 구현 명세.md`에서 Golden Case와의 비교(§14), Unit Test 구조(§15)를 이미 상당히 꼼꼼하게 설계해 주셨습니다. 다만 이것은 "Agent의 판단"을 평가하는 Golden Case(Step 9, 21)와는 별개로 "계산 자체의 정확성"을 다루는 것이라, 예를 들어 SciPy/statsmodels 결과값과의 대조 검증이나 향후 라이브러리 버전이 바뀔 때의 회귀테스트 절차까지 별도로 명시해 두면 더 안전할 것 같다는 제안입니다. (이미 상당 부분 설계되어 있어 우선순위는 낮게 봐도 될 것 같습니다.)

## 3-6. 측정시스템분석(MSA, Measurement System Analysis) 게이트 관련

`4.4`에 "측정 시스템이 달라지면 Before/After 차이가 공정 변화인지 측정 오차인지 구분하기 어렵다"는 주의문이 있는 것 외에는, 아직 MSA를 분석 흐름의 선행 확인 단계로 넣지는 않으신 것 같습니다. 원래 기획서(및 PRISM 원 카탈로그)에 MSA 모듈이 있었던 점을 고려하면, 설비 간 CTQ를 비교하기 전에 "측정 시스템 자체의 반복성·재현성이 충분한가"를 확인하는 단계를 Analysis Plan Graph에 선택적으로 넣을 수 있을지 검토를 제안합니다. 우선순위는 낮게 보셔도 될 것 같습니다.

## 3-7. 시계열 데이터의 자기상관(自己相關)·변화점 탐지 관련

UC-11(`4.5`)의 "언제부터 증가했는가"는 실질적으로 변화점 탐지(change point detection) 문제인데, 아직 구체적인 방법(예: CUSUM)이 정해지지 않은 것으로 보입니다. 또한 일자별로 집계된 생산 데이터를 독립 표본처럼 검정에 사용할 경우 자기상관 가정 위반 가능성이 있어, Statistical Policy(`7.`)의 "independent/paired/repeated/time-series" 구분 중 time-series 케이스를 조금 더 구체화하면 좋을 것 같습니다.

## 3-8. Evidence 하향 조정·재평가 정책 관련

Evidence(`13.`)가 E0→E4로 올라가는 방향은 잘 정의되어 있는데, 시간이 지나 새로운 데이터가 기존의 E2~E3 결론을 반박하는 경우(공정 조건이나 설비가 바뀐 경우 등) 그 Evidence를 어떻게 낮추거나 재검증할지에 대한 규칙은 아직 없는 것 같습니다. Evidence에 유효기간이나 재검증 조건 같은 필드를 추가하는 방향을 검토해 보시면 좋겠습니다.

## 3-9. Data Guard의 구체적 기준 관련

`10.`, `17.`, `18.`에서 Data Guard/Rule Engine의 역할은 잘 정의되어 있지만, "결측률이 몇 %를 넘으면 경고 또는 중단할지", "이상값을 자동 제거·표시만·유지 중 어떤 정책으로 다룰지" 같은 구체적인 수치 기준은 아직 정해지지 않은 것으로 보입니다. Step 17/18의 구현 단계로 넘어가기 전에 이 기준들을 한 번 확정해 두면 개발이 더 수월할 것 같습니다.

## 3-10. 운영·거버넌스 관련 — Step 26에서 함께 검토를 제안하는 항목들

Step 25(중간점검)에서 "설계 진행 필요"로 스스로 표시해 두신 목록(AI ON/OFF, Analysis Trace, AI 오류 처리, Offline/Online 정책, 데이터 전송 정책, Token/비용 관리, 사용자 권한, 세션 저장/복구, AI Audit Log)에 아래 항목들도 함께 넣어서 검토해 주시면 좋을 것 같습니다.

- LLM API 자체의 응답 지연·장애 시 폴백(fallback) 정책 (Step 25에서 "LLM Failure → App Failure가 되면 안 된다"는 원칙은 이미 세워두셨으니, 이를 구체적인 타임아웃/재시도 정책으로 발전)
- 사용자가 Agent의 판단을 실시간으로 정정("이 설비는 최근에 교체했다" 등)했을 때, 이를 그 세션의 Analysis State(Finding/Hypothesis)에 즉시 반영하는 절차 — Evidence Policy(`7.`)의 "Explicit User-provided information" 항목을 조금 더 구체화
- LLM Provider나 모델을 교체할 때, Golden Case(Step 9, 21) 스위트를 반드시 재실행해서 동일한 판단이 나오는지 확인하는 절차를 Provider 교체 아키텍처(Step 5, 13)와 명시적으로 연결
- Agent의 결론이 생산 중단 검토처럼 파급력이 큰 판단일 경우, 현장에 전달되기 전에 사람이 한 번 더 확인하는 절차가 필요할지 여부

## 3-11. 참고 수준 제안 (우선순위 낮음)

- 지금까지의 UC(01/03/05/07/11)는 모두 단일 CTQ·단일 요인 중심으로 설계되어 있습니다. 여러 CTQ를 동시에 보거나 요인 간 상호작용(예: Machine×Temperature)을 다루는 시나리오는 Phase 2 항목으로 명시해 두면 좋을 것 같습니다.
- 같은 결론이라도 현장 엔지니어/품질관리자/경영진에게 다른 수준의 설명이 필요할지도, UX Architecture(`3.7`)를 다시 볼 때 함께 검토해 보시면 좋겠습니다.

# 4. 정리

가장 우선순위가 높다고 생각되는 것은 1번(원본 기획서 동기화 방향 결정)과 2번(LLM 인증 방식)입니다. 나머지는 Step 26 이후 진행하시면서 자연스럽게 다뤄질 수 있는 항목으로 보이니, 순서를 어떻게 잡을지는 진행하시는 분의 판단에 맡기겠습니다. 다시 한번 말씀드리지만 이 문서의 항목들은 "고쳐야 하는 결함"이 아니라 "한 번 더 봐 주셨으면 하는 지점"에 대한 제안이니, 이미 다른 이유로 지금 방향이 맞다고 판단되시면 그대로 진행하셔도 됩니다.

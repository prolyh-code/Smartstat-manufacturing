# Step 7. Manufacturing Statistical Agent Prompt Architecture

## 7-1. 왜 하나의 거대한 Prompt가 위험한가?

처음에는 다음과 같이 만들고 싶어집니다.

```
너는 제조 통계 전문가 AI이다.
통계 분석을 잘하고...
제조업을 이해하고...
ANOVA는...
t-test는...
회귀분석은...
인과관계는...
Tool은...
```

하지만 Agent가 발전하면 Prompt가 수천 줄이 됩니다.

그리고 문제가 생깁니다.

- 통계 규칙 수정 → 전체 Prompt 수정
- 제조 규칙 추가 → 전체 Prompt 수정
- 새로운 Tool 추가 → 전체 Prompt 수정
- 회사 규정 추가 → Prompt 재작성
- 모델 변경 → Prompt 동작 변화
- 특정 사례에서 오류 → 어디를 수정해야 할지 불명확

따라서 **Prompt도 Modular Architecture**로 설계해야 합니다.

전체적으로 다음 구조를 권장합니다.

```

                  │
┌─────────────────▼───────────────────┐
│  ② STATISTICAL POLICY              │

                  │
┌─────────────────▼───────────────────┐
│  ③ MANUFACTURING POLICY            │
│  제조적 판단 규칙                    │
└─────────────────┬───────────────────┘
                  │
┌─────────────────▼───────────────────┐
│  ④ TOOL POLICY                     │
│  Tool 사용 규칙                     │
└─────────────────┬───────────────────┘
                  │

│  ⑤ KNOWLEDGE CONTEXT               │

이 구조를 **Prompt Stack**이라고 생각하면 이해하기 쉽습니다.

# 7-3. ① Core System Prompt

가장 위에는 변경이 거의 없는 **헌법(Constitution)** 같은 Prompt가 있습니다.

핵심은 길지 않아야 합니다.

예를 들어 개념적으로:

```
You are a Manufacturing Statistical Analysis Agent.

Your responsibilities are:

1. Understand manufacturing questions.
2. Construct a statistical problem model.
3. Plan appropriate analyses.
4. Use deterministic statistical tools.
5. Validate analysis conditions and results.
6. Interpret statistical results.
7. Translate statistical findings into manufacturing meaning.
8. Recommend additional analysis when useful.
9. Distinguish evidence from hypothesis.
10. Never claim causality without sufficient evidence.

You MUST NOT perform statistical calculations yourself
when a statistical tool is available.

You MUST NOT fabricate data or statistical results.

You MUST clearly distinguish:
- Statistical Result
- Finding
- Hypothesis
- Evidence
- Manufacturing Decision.
```

이 정도가 **Core Identity**입니다.

---

# 7-4. Agent의 가장 중요한 4가지 역할

앞서 정의했던:

> **Understand → Plan → Explain → Explore**

를 Core Prompt에 넣습니다.

### Understand

사용자의 제조 문제를 이해합니다.

### Plan

통계적 분석 계획을 수립합니다.

### Explain

결과를 통계적으로 정확하게 설명합니다.

### Explore

필요하면 다음 분석을 수행합니다.

그리고 Statistical Engine은 별도의 역할을 담당합니다.

> **Validate → Calculate → Verify**

이렇게 분리됩니다.

---

# 7-5. ② Statistical Policy

두 번째 Prompt Layer는 통계 규칙입니다.

여기서는 LLM에게 "통계 지식을 외우게" 하는 것이 목적이 아닙니다.

**LLM이 통계적 의사결정을 할 때 반드시 지켜야 할 Policy**를 정의합니다.

예:

```
STATISTICAL POLICY

1. Identify variable types before selecting a method.

2. Identify the observational structure:
   - independent
   - paired
   - repeated
   - time-series

3. Check relevant assumptions.

4. Do not select a statistical method based solely
   on the number of groups.

5. Report effect size when appropriate.

6. Interpret p-value together with:
   - confidence interval
   - effect size
   - sample size
   - practical significance.

7. Statistical significance does not imply
   manufacturing significance.

8. Association does not imply causation.
```

이렇게 하면 통계 Knowledge와 Prompt Policy의 역할도 분리됩니다.

---

# 7-6. 중요한 차이: Knowledge와 Policy

이 구분은 꼭 기억할 필요가 있습니다.

### Knowledge

> Welch t-test는 분산이 같지 않은 두 집단을 비교할 때 사용할 수 있다.

### Policy

> 두 집단 비교에서는 분산 구조를 확인하고, 등분산 가정이 적절하지 않다면 일반 t-test 대신 Welch 방법을 고려해야 한다.

즉:

**Knowledge = 무엇을 알고 있는가**

**Policy = 어떻게 행동해야 하는가**

입니다.

---

# 7-7. ③ Manufacturing Policy

여기서부터 이 Agent가 일반 통계 AI와 차별화됩니다.

예를 들어:

```
MANUFACTURING POLICY

1. Interpret statistical results in manufacturing context.

2. Consider relevant manufacturing factors:
   - machine
   - model
   - line
   - shift
   - operator
   - process condition
   - time
   - measurement system.

3. When analyzing quality data, consider:
   - specification
   - target
   - defect definition
   - defect rate
   - process variation
   - stability.

4. Do not call an observational factor
   a confirmed root cause.

5. Prefer operationally actionable findings.

6. Distinguish:
   observed pattern
   statistical association
   candidate cause
   experimentally verified cause.
```

이 Policy가 실제 제조 현장의 판단 수준을 결정합니다.

---

# 7-8. 예를 들어 단순 LLM이라면

데이터:

```
M1 defect rate = 1.1%
M2 defect rate = 3.5%
p < 0.001
```

다음과 같이 말할 가능성이 있습니다.

> M2 설비가 토크 불량의 원인입니다.

하지만 Manufacturing Policy가 있으면:

> M2에서 토크 불량률이 통계적으로 유의하게 높게 나타났으며, M2는 주요 원인 후보로 판단됩니다. 다만 Model 또는 Shift 등의 교란요인이 존재할 수 있으므로 현재 결과만으로 M2가 불량의 원인이라고 확정할 수는 없습니다.

가 됩니다.

**이 차이가 이 Agent의 핵심 가치입니다.**

---

# 7-9. ④ Tool Policy

Tool 사용에도 별도 Policy가 필요합니다.

예:

```
TOOL POLICY

1. Never calculate statistical results manually
   when a statistical tool exists.

2. Use tools for numerical computation.

3. Validate required inputs before tool execution.

4. Do not call a tool if required data are missing.

5. Do not repeat an identical analysis
   unless the data or objective has changed.

6. Store every tool result in Analysis State.

7. Use tool results as the only authoritative
   source for numerical statistical claims.

8. If a tool returns an error:
   diagnose the error before attempting another tool.
```

이것이 **LLM Hallucination 방지의 핵심 Prompt**가 됩니다.

---

# 7-10. Tool Calling을 "자유 행동"으로 만들지 않는다

Agent에게:

> 필요한 Tool을 마음대로 사용해라.

라고 하면 위험합니다.

대신:

```
Question
 ↓
Problem Model
 ↓
Required Evidence
 ↓
Candidate Tool
 ↓
Tool Validation
 ↓
Tool Call
```

이라는 순서를 강제합니다.

예를 들어:

```
Problem:
GROUP_COMPARISON

Response:
Torque

Factor:
Machine

Groups:
M1, M2, M3
```

이면 Agent는 먼저:

```
Need:
Group summaries
Distribution
Variance structure
```

를 판단하고 그 다음 ANOVA 계열 Tool을 호출합니다.

---

# 7-11. ⑤ Knowledge Context

RAG로 가져온 지식은 Prompt에 무조건 많이 넣으면 안 됩니다.

**현재 문제와 관련된 Knowledge만 Context로 공급**합니다.

예:

```
KNOWLEDGE CONTEXT

[Manufacturing]
Torque is a CTQ in fastening processes.

Relevant factors:
Machine
Model
Operator
Shift
Tool condition

[Statistical]
For 3+ independent groups:
ANOVA / Welch ANOVA may be considered.

[Company]
Torque Target = 35 N·m
LSL = 30 N·m
USL = 40 N·m
```

이렇게 Context를 작게 유지합니다.

---

# 7-12. ⑥ Analysis State

이것이 Agent Prompt에서 상당히 중요한 부분입니다.

LLM에게:

> 지금까지 무슨 분석을 했는가?

를 매번 다시 추론하게 하면 안 됩니다.

Application이 State를 넣어줍니다.

예:

```
ANALYSIS STATE

Objective:
Identify factors associated with torque defect increase.

Completed:
1. Data Quality
2. Defect Rate
3. Trend
4. Machine Comparison
5. Model Comparison

Findings:
F01: Overall defect rate increased.
F02: M2 has higher defect rate.
F03: Model C has higher defect rate.

Confounders:
C01: Model C is concentrated on M2.

Evidence:
E2

Current Decision:
Need to determine whether M2 effect remains
after controlling for Model.
```

이것이 있으면 Agent가 분석을 반복하지 않습니다.

---

# 7-13. ⑦ Current User Task

마지막에는 현재 질문을 넣습니다.

예:

```
CURRENT USER TASK

User:
"그럼 Model 영향을 제외하고도 M2가 문제인지 확인해줘."
```

그러면 Agent는 State를 읽고:

```
Existing finding:
M2 high defect

Confounder:
Model C concentrated on M2

User request:
Control Model

Recommended:
Same-model comparison
or
logistic regression
```

으로 연결합니다.

---

# 7-14. 이제 Prompt가 실제로 어떻게 조립되는가

개념적으로:

```
SYSTEM
 ├── Core Agent Prompt
 ├── Statistical Policy
 ├── Manufacturing Policy
 └── Tool Policy

RUNTIME CONTEXT
 ├── Retrieved Knowledge
 ├── Analysis State
 ├── Tool Schema
 └── Dataset Profile

TASK
 └── User Question
```

이 구조입니다.

이렇게 하면 Prompt가 거대해지지 않습니다.

---

# 7-15. Agent가 실제로 사고하는 순서를 Prompt에 정의한다

여기서는 **Chain-of-Thought를 출력하라는 의미가 아닙니다.**

내부적인 실행 순서만 규정합니다.

```
STEP 1
Understand the user question.

STEP 2
Construct or update Problem Model.

STEP 3
Assess available data.

STEP 4
Identify required evidence.

STEP 5
Construct/update Analysis Plan.

STEP 6
Validate plan against statistical rules.

STEP 7
Call appropriate tools.

STEP 8
Validate returned results.

STEP 9
Create Findings.

STEP 10
Assess Evidence Level.

STEP 11
Determine whether another analysis
has sufficient expected value.

STEP 12
Stop or continue.

STEP 13
Provide manufacturing decision guidance.
```

이것이 Agent의 **Execution Policy**가 됩니다.

---

# 7-16. 여기서 "Reasoning"과 "Evidence"를 분리한다

Agent가:

> M2가 문제다.

라고 판단했다고 합시다.

시스템에는 실제로:

```
Finding
F01

Claim:
M2 has higher defect rate.

Evidence:
ANL-014

Evidence Level:
E2

Confounder:
Model C

Confidence:
Moderate

Causal Status:
Not established
```

가 저장됩니다.

따라서 LLM이 표현을 조금 다르게 하더라도 **근거 구조는 변하지 않습니다.**

이것은 단순 Prompt Engineering보다 훨씬 강력한 방법입니다.

---

# 7-17. Evidence-aware Prompt

Agent에게 다음 규칙을 추가할 수 있습니다.

```
EVIDENCE POLICY

Every substantive manufacturing claim must be
supported by one or more of:

1. Statistical Tool Result
2. Validated Analysis Finding
3. Retrieved Knowledge
4. Explicit User-provided information

Do not present hypotheses as findings.

Do not present findings as confirmed causes.

Do not present statistical significance
as proof of practical importance.

Do not present observational association
as causal evidence.
```

이 규칙은 향후 평가 Framework와도 직접 연결됩니다.

---

# 7-18. Agent가 "다음 분석"을 선택하는 Prompt

우리가 앞에서 정의한:

> **Relevance × Expected Information Gain × Data Availability × Statistical Validity × Manufacturing Impact**

를 Prompt Policy로 사용할 수 있습니다.

예:

```
NEXT ANALYSIS POLICY

Recommend another analysis only when it is likely
to materially reduce uncertainty or improve
the manufacturing decision.

Consider:

- Relevance
- Expected Information Gain
- Data Availability
- Statistical Validity
- Manufacturing Impact

Stop when:
- the question is sufficiently answered
- additional analysis has low marginal value
- data are insufficient
- causal verification requires an experiment
```

이것이 Agent를 **끝없이 분석하는 AI**가 아니라 **필요한 만큼만 분석하는 AI**로 만듭니다.

---

# 7-19. 특히 "Stop"을 Prompt에 넣는다

많은 Agent 설계에서 빠지는 부분입니다.

Agent에게:

> 더 분석할 것이 있으면 분석해라.

만 넣으면 무한 Loop가 발생할 수 있습니다.

따라서:

```
STOP POLICY

Stop analysis when:

A. The user's question is sufficiently answered.

B. Additional analysis has low expected information gain.

C. Available data cannot support further inference.

D. The remaining uncertainty requires new data.

E. Causal inference requires controlled experimentation.

F. The result is sufficient for the intended
   manufacturing decision.
```

을 명시합니다.

---

# 7-20. 그리고 "Ask User"도 제한한다

Agent가 모든 것을 사용자에게 물어보면 UX가 나빠집니다.

예:

> "몇 개 그룹인가요?"

데이터에서 이미 Machine이:

```
M1
M2
M3
M4
M5
```

라고 되어 있다면 질문하면 안 됩니다.

대신:

> "5개 설비 그룹으로 확인됩니다."

라고 해야 합니다.

질문해야 하는 경우는:

```
Purpose ambiguous
Response ambiguous
Critical data missing
Pairing unclear
Decision criterion missing
```

정도입니다.

---

# 7-21. 이 원칙을 Prompt로 표현하면

```
QUESTION POLICY

Do not ask the user for information
that can be reliably inferred from the dataset,
metadata, knowledge base, or analysis state.

Ask only when missing information would materially
change:

- problem definition
- statistical method
- interpretation
- manufacturing decision.
```

이것이 Agent UX의 중요한 차별점입니다.

Finding F01

from 1.1% to 2.4%.

```

여기서 아직 원인 분석을 하지 않습니다.

> **"어디에서 증가했는가?"**

# 7-25. Candidate Screening

Agent는:

```
Machine
Model
Shift
Operator
```

별로 불량률을 비교합니다.

```
Machine
→ defect_rate()
→ proportion_test()

Model
→ defect_rate()
→ proportion_test()

Shift
→ defect_rate()
→ proportion_test()

Operator
→ defect_rate()
→ proportion_test()
```

여기서 중요한 점:

**불량 여부가 Binary이면 평균 비교용 t-test를 무조건 사용하는 것이 아닙니다.**

불량률 비교에서는:

- proportion test
- chi-square
- 적절한 categorical analysis

등을 사용합니다.

이것도 Agent의 Statistical Policy가 보호합니다.

---

# 7-26. 예를 들어 이런 결과가 나온다면

```
Overall:
1.1% → 2.4%

Machine:
M2 = 3.5%
Others = 1.2%

Model:
Model C = 3.8%
Others = 1.3%

Shift:
Shift 3 = 2.9%
Others = 1.8%

Operator:
No clear difference
```

Agent는:

### Finding

> M2, Model C, Shift 3에서 상대적으로 높은 불량률이 관찰되었습니다.

### Hypothesis

> M2 설비 또는 Model C 생산 조건이 최근 불량 증가와 관련되어 있을 가능성이 있습니다.

라고 합니다.

---

# 7-27. 그런데 Agent가 여기서 멈추면 안 됩니다

왜냐하면:

```
M2 → Model C 생산 비중 높음
```

일 가능성이 있기 때문입니다.

즉:

```
M2
 ↓
Model C
 ↓
Defect
```

인지,

```
M2
 ↓
Defect
```

인지 아직 모릅니다.

이것이 **Confounding**입니다.

---

# 7-28. Agent는 Analysis Plan을 수정한다

기존:

```
Machine Comparison
Model Comparison
Shift Comparison
```

에서:

```
Machine
   │
   ▼
Confounding Check
   │
   ▼
Same Model Comparison
   │
   ▼
Model-controlled Analysis
```

로 확장합니다.

이것이 우리가 앞서 설계한 **Dynamic Analysis Plan Graph**입니다.

---

# 7-29. 여기서 Agent의 진짜 가치가 드러난다

일반적인 통계 프로그램:

> ANOVA 결과입니다.

기존 SmartStat:

> M2와 다른 설비 간 차이가 있습니다.

LLM Agent:

> **M2의 불량률이 높은 것은 확인되었지만, M2에서 Model C 생산 비중이 높은 교란 가능성이 확인되었습니다. 따라서 현재 결과만으로 M2를 원인으로 판단하기 어렵습니다. 동일 Model 조건에서 M2와 다른 설비를 비교하는 것이 다음 분석으로 가장 적절합니다.**

이것이 우리가 만들려는 제품의 핵심입니다.

# 다음 Step 8 — Agent의 "실제 두뇌 구조"를 설계하겠습니다

다음 단계에서는 여기서 한 단계 더 내려가겠습니다.

**Prompt만으로 Agent를 만드는 것이 아니라, Agent 내부를 여러 역할로 나눌 필요가 있는가?**

예를 들어:

```
User
 ↓
Orchestrator Agent
 ├── Intent Agent
 ├── Statistical Planner
 ├── Data Analyst
 ├── Manufacturing Reasoner
 ├── Evidence Evaluator
 └── Report Agent
```

라는 **Multi-Agent 구조**를 생각할 수 있습니다.

그런데 여기서 중요한 것은 **"Multi-Agent가 무조건 좋은가?"**입니다.

오히려 MVP에서는 Multi-Agent를 사용하면 복잡성만 증가할 수도 있습니다.

따라서 다음 단계에서는 **Single Agent vs Multi-Agent vs Hybrid Agent**를 이 프로젝트의 실제 요구사항에 맞춰 비교하고, 제가 보기에는 어떤 구조가 가장 적합한지 결정하겠습니다.

그리고 그 결정이 끝나면 **"이제 실제로 무엇부터 코딩해야 하는가?"**까지 내려가서, 사용자가 Claude Code 등을 활용해 개발할 수 있는 **MVP 구현 순서와 프로젝트 폴더/모듈 구조**로 연결할 수 있습니다.

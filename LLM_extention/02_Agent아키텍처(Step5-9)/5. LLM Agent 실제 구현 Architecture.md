# Step 5. LLM Agent 실제 구현 Architecture

## 5-1. 먼저 LLM의 역할부터 명확하게 분리한다

가장 먼저 결정해야 할 것은 **LLM에게 어디까지 권한을 줄 것인가**입니다.

제가 제안하는 구조는 다음과 같습니다.

```
                    ┌──────────────────────┐
                    │        User          │
                    │ "토크 불량 원인 찾아줘" │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │       LLM Agent      │
                    │                      │
                    │ Understand           │
                    │ Plan                 │
                    │ Explain              │
                    │ Explore              │
                    └──────────┬───────────┘
                               │ Tool Call
                               ▼
              ┌────────────────────────────────┐
              │      Rule / Validation Layer   │
              └────────────────┬───────────────┘
                               │
                               ▼
              ┌────────────────────────────────┐
              │       Statistical Engine       │
              │                                │
              │ t-test / ANOVA / Regression    │
              │ Correlation / SPC / Capability│
              └────────────────┬───────────────┘
                               │
                               ▼
                    Structured Result
                               │
                               ▼
                    ┌──────────────────────┐
                    │       LLM Agent      │
                    │ Interpret / Explore  │
                    └──────────────────────┘
```

### LLM이 하는 일

|역할|LLM|
|---|---|
|자연어 질문 이해|O|
|문제 유형 결정|O|
|분석 계획 수립|O|
|필요한 데이터 판단|O|
|Tool 선택|O|
|Tool 호출|O|
|통계 계산|**X**|
|p-value 직접 계산|**X**|
|평균/표준편차 직접 계산|**X**|
|통계 결과 해석|O|
|제조 의미 해석|O|
|추가 분석 제안|O|
|원인 후보 탐색|O|
|인과관계 확정|**X**|
|실험 필요성 판단|O|

이렇게 해야 LLM이 바뀌더라도 통계적 신뢰성이 흔들리지 않습니다.

여기서 기존 기획서를 버릴 필요가 전혀 없습니다.

오히려 기존 앱의 기능 대부분이 **Agent의 Tool**로 승격됩니다.

|기존 기능|Agent 시대의 역할|구현 컴포넌트|
|---|---|---|
|Analysis Navigator|Intent Router|LLM Agent|
|Wizard|Guided Agent|Agent UX|
|Descriptive Statistics|Tool|Statistical Engine|
|Histogram|Tool|Visualization Engine|
|Box Plot|Tool|Visualization Engine|
|Scatter Plot|Tool|Visualization Engine|
|t-test|Tool|Statistical Engine|
|ANOVA|Tool|Statistical Engine|
|Post-hoc|Tool|Statistical Engine|
|Correlation|Tool|Statistical Engine|
|Regression|Tool|Statistical Engine|
|Normality Test|Validation Tool|Statistical Engine|
|Variance Test|Validation Tool|Statistical Engine|
|Data Quality|Data Guard|Data Engine|

즉 기존의 **Statistical Engine은 그대로 살리고**, 그 위에 Agent Layer를 얹는 전략입니다.

# 5-4. Tool Calling Architecture

Agent가 통계분석을 수행하는 방법은 **Tool Calling**으로 통일하는 것이 좋습니다.

예를 들어 사용자가:

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

라고 하면 LLM이 직접 계산하는 것이 아닙니다.

LLM은 다음과 같은 Tool Call을 생성합니다.

```
{
  "tool": "two_group_comparison",
  "arguments": {
    "dataset_id": "DS_20260912_001",
    "response": "Torque",
    "group": "Line",
    "groups": ["A", "B"],
    "paired": false,
    "method": "auto"
  }
}
```

그러면 Statistical Engine이 계산합니다.

```
{
  "tool": "two_group_comparison",
  "status": "success",
  "method": "Welch_t_test",
  "group_a": {
    "n": 1520,
    "mean": 35.21,
    "sd": 1.21
  },
  "group_b": {
    "n": 1487,
    "mean": 35.67,
    "sd": 1.38
  },
  "mean_difference": -0.46,
  "t": -8.31,
  "df": 2851.7,
  "p_value": 0.0001,
  "ci95": [-0.57, -0.35],
  "effect_size": 0.36
}
```

그리고 LLM은 이 결과를 해석합니다.

이 구조가 매우 중요합니다.

# 5-5. Statistical Tool의 기본 Contract

모든 Tool은 가능한 한 동일한 구조를 가져야 합니다.

```
Tool Request
    ↓
Validation
    ↓
Execution
    ↓
Result
    ↓
Diagnostics
    ↓
Warnings
    ↓
Evidence
```

예를 들어 모든 통계 Tool은 최소한 다음 정보를 반환하도록 설계합니다.

```
{
  "status": "success",
  "tool_name": "welch_t_test",
  "tool_version": "1.0.0",

  "dataset": {
    "id": "DS001",
    "version": "3"
  },

  "input": {
    "response": "Torque",
    "group": "Machine",
    "groups": ["M1", "M2"]
  },

  "method": {
    "name": "Welch Two Sample t-test",
    "reason": "unequal variance"
  },

  "result": {
    "statistic": -3.82,
    "df": 281.4,
    "p_value": 0.0002,
    "ci95": [-0.71, -0.18]
  },

  "effect_size": {
    "name": "Cohen's d",
    "value": 0.29
  },

  "diagnostics": {
    "normality": "acceptable",
    "variance": "unequal"
  },

  "warnings": []
}
```

이렇게 하면 LLM이 특정 Tool의 내부 구현을 알 필요가 없습니다.

# 5-7. 중요한 설계 원칙: "하나의 거대한 Tool"을 만들지 않는다

예를 들어 이런 Tool은 좋지 않습니다.

```
analyze_manufacturing_data()
```

이 하나가 모든 것을 수행하게 만드는 것입니다.

왜냐하면 Agent가 무엇을 했는지 추적하기 어렵기 때문입니다.

대신:

```
profile_data()
        ↓
defect_rate()
        ↓
trend_analysis()
        ↓
group_comparison()
        ↓
confounding_check()
        ↓
regression()
```

처럼 **작고 검증 가능한 Tool을 조합**하는 것이 좋습니다.

이것이 UC-11과 특히 잘 맞습니다.

# 5-8. Analysis Plan Graph

앞에서 중요한 개념으로 정의했던 **Analysis Plan Graph**를 실제 객체로 만듭니다.

예:

```
{
  "plan_id": "PLAN_001",
  "objective": "Identify factors associated with torque defect increase",

  "nodes": [
    {
      "id": "N01",
      "type": "data_quality",
      "tool": "check_data_quality"
    },
    {
      "id": "N02",
      "type": "quantification",
      "tool": "defect_rate"
    },
    {
      "id": "N03",
      "type": "trend",
      "tool": "trend_analysis"
    },
    {
      "id": "N04",
      "type": "screening",
      "tool": "group_comparison"
    },
    {
      "id": "N05",
      "type": "confounding",
      "tool": "confounding_check"
    }
  ],

  "edges": [
    ["N01", "N02"],
    ["N02", "N03"],
    ["N03", "N04"],
    ["N04", "N05"]
  ]
}
```

그런데 이것이 **고정되어 있으면 안 됩니다.**

예를 들어 N05에서:

```
Model-Machine Confounding 발견
```

되면 Agent가 새로운 Node를 추가합니다.

```
N06 = same_model_comparison
```

그리고:

```
N06 → process_condition_analysis
```

를 연결합니다.

즉:

> **Analysis Plan은 실행 전에 완성되는 문서가 아니라 Agent가 분석하면서 진화하는 객체입니다.**

이것이 매우 중요한 설계 포인트입니다.

# 5-9. Agent State

Agent의 기억을 LLM의 대화 Memory에 맡기면 안 됩니다.

핵심 정보는 Application State에 저장합니다.

개념적으로:

```
{

  "question": {
    "original": "최근 토크 불량이 증가한 원인을 찾아줘"
  },

  "problem": {
    "type": "ROOT_CAUSE_EXPLORATION",
    "response": "Torque",
    "quality_event": "Torque Defect",
    "objective": "Identify factors associated with defect increase"
  },

  "dataset": {
    "id": "DS001",
    "version": 4,
    "rows": 18450,
    "quality_status": "acceptable"
  },

  "plan": {},

  "analysis_history": [],

  "findings": [],

  "hypotheses": [],

  "confounders": [],

  "evidence": [],

  "next_actions": [],

  "decision": null
}
```

# 5-10. Finding / Hypothesis / Evidence를 반드시 분리한다

이것도 UC-11에서 굉장히 중요합니다.

예를 들어:

### Result

```
M2 defect rate = 3.2%
Others = 1.0%
p < 0.001
```

### Finding

> M2의 Torque 불량률이 다른 설비보다 높게 나타났다.

### Hypothesis

> M2의 설비 상태 또는 공정조건이 불량 증가에 영향을 주었을 가능성이 있다.

### Evidence

```
E2
Statistical Association
```

### Decision

> 동일 모델 조건에서 M2 효과를 추가 검증한다.

이 다섯 가지를 하나로 저장하면 안 됩니다.

# 5-11. Evidence Schema

앞서 정의한 E0~E4를 시스템 객체로 만듭니다.

```
{
  "evidence_id": "EVD_001",

  "level": "E2",

  "claim": "Machine M2 has higher defect rate",

  "source": [
    "ANL_014"
  ],

  "strength": "moderate",

  "limitations": [
    "Model C is concentrated on M2"
  ],

  "supports": [
    "HYP_003"
  ]
}
```

이렇게 하면 최종 보고서에서:

> **왜 이런 결론을 내렸는가?**

를 역추적할 수 있습니다.

이것은 향후 AI Agent의 **Trust / Explainability** 측면에서도 매우 중요합니다.

# 5-12. Rule Engine과 LLM의 경계

이 부분은 반드시 명확히 해야 합니다.

### LLM

```
"이 질문은 두 공정 비교로 보인다."
```

### Rule Engine

```
Response = continuous
Groups = 2
Independent = true
Variance unequal
→ Welch t-test
```

즉:

> LLM은 **계획을 제안**하고 Rule Engine은 **통계적으로 허용되는지를 검증**합니다.

---

# 5-13. 예를 들어 LLM이 잘못 선택한다면?

LLM이:

```
two_sample_t_test()
```

를 호출했다고 합시다.

그런데 Rule Engine이:

```
Variance = unequal
```

을 발견합니다.

그러면 실행 전에:

```
BLOCK

Recommended:
Welch t-test
Reason:
variance homogeneity assumption violated
```

를 반환합니다.

Agent는 이를 받아:

> 두 그룹의 분산이 동일하다는 가정이 충족되지 않아 일반적인 2표본 t-test 대신 Welch t-test를 사용하겠습니다.

라고 설명합니다.

즉:

```
LLM
 ↓
Proposal
 ↓
Rule Engine
 ↓
Validation
 ↓
Allowed Tool
```

입니다.

# 5-14. LLM Context도 매우 중요하다

LLM에게 매번 전체 데이터를 전달하는 구조는 피해야 합니다.

예를 들어 1백만 행의 생산 데이터를 LLM에게 보내는 것은 좋은 구조가 아닙니다.

대신 LLM에게:

```
Problem State
+
Dataset Profile
+
Analysis State
+
Tool Results
+
Relevant Knowledge
+
User Conversation
```

만 제공합니다.

예:

```
CONTEXT

Problem:
ROOT_CAUSE_EXPLORATION

Response:
Torque

Dataset:
18,450 rows
2026-08-01 ~ 2026-08-31

Findings:
F01 Defect rate increased
F02 M2 defect rate high
F03 Model C defect rate high

Confounders:
C01 Model C concentrated on M2

Completed:
Trend analysis
Machine comparison
Model comparison
Same-model comparison

Evidence:
E2

Current Question:
Which factor should be investigated next?
```

이 정도면 LLM이 훨씬 안정적으로 추론할 수 있습니다.

# 5-15. Raw Data와 LLM을 분리한다

이것은 전체 Architecture에서 가장 중요한 원칙 중 하나입니다.

```
                    Raw Data
                       │
                       ▼
                Data Engine
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
       Statistical Engine    Data Profile
             │                   │
             ▼                   ▼

             │                   │

LLM이 Raw Data를 보고:

라고 계산하게 하지 않습니다.

```

을 계산하고 LLM은 그것을 설명합니다.

# 5-16. Agent 실행 Loop

실제 Agent는 다음 Loop를 반복합니다.

```
┌──────────────────┐
│ 1. Understand    │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 2. Assess        │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. Plan          │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. Validate      │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. Execute Tool  │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 6. Validate      │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 7. Interpret     │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 8. Evidence      │
└────────┬─────────┘
         ▼
┌─────────────────────────┐
│ 9. Next Analysis Needed?│
└───────┬───────────┬─────┘
        │ Yes       │ No
        ▼           ▼
     Re-plan      Decision
        │
        └──────→ Loop
```

이 구조라면 Agent가:

> "Machine을 확인했는데 Model이 교란요인으로 보입니다. 따라서 동일 Model 조건에서 다시 비교하겠습니다."

와 같이 **분석 과정을 스스로 전개**할 수 있습니다.

# 5-17. 환각(Hallucination)을 어떻게 막는가?

이 앱에서는 일반적인 LLM 서비스보다 훨씬 엄격해야 합니다.

다음 규칙을 권장합니다.

### Rule 1. 숫자를 만들어내지 않는다

LLM이 통계값을 생성하면 안 됩니다.

```
mean
SD
p-value
CI
effect size
R²
coefficient
```

모두 Tool Result에서만 가져옵니다.

---

### Rule 2. Tool Result가 없으면 통계적 주장을 하지 않는다

예:

> p < 0.05입니다.

라고 말하려면 실제 Tool Result에 p-value가 있어야 합니다.

---

### Rule 3. 인과관계 표현 제한

다음 표현은 Evidence Level이 충분하지 않으면 차단합니다.

```
원인이다
원인이 확인되었다
~ 때문에 발생했다
~가 불량을 발생시켰다
~가 원인임이 입증되었다
```

대신:

```
관련성이 관찰됨
차이가 관찰됨
원인 후보
영향 가능성
추가 검증 필요
```

를 사용합니다.

---

### Rule 4. 분석 결과보다 데이터 구조를 우선한다

예를 들어 Before/After가 있다고 해서 무조건 Paired t-test를 사용하지 않습니다.

Pair ID가 실제 존재하는지 확인해야 합니다.

---

### Rule 5. Agent가 모르면 모른다고 한다

이것은 매우 중요합니다.

> 현재 확보된 관찰 데이터만으로는 원인을 확정할 수 없습니다.

라고 말하는 것이 좋은 Agent입니다.

---

# 5-18. LLM Provider는 교체 가능하게 설계한다

사용자는 앞으로 Claude Code를 활용할 가능성이 높기 때문에 이 부분도 중요합니다.

Architecture를:

```
Application
    ↓
LLM Adapter
    ↓
┌─────────────┬─────────────┬─────────────┐
│ OpenAI      │ Anthropic   │ Other LLM   │
└─────────────┴─────────────┴─────────────┘
```

처럼 만드는 것을 권장합니다.

Application이:

```
call_claude()
```

에 종속되면 안 됩니다.

대신:

```
LLMProvider
 ├── generate()
 ├── tool_call()
 ├── structured_output()
 └── stream()
```

이라는 추상 인터페이스를 만들고,

```
OpenAIProvider
AnthropicProvider
LocalProvider
```

가 이를 구현하도록 합니다.

그러면 향후 모델 변경이 쉬워집니다.

# 5-22. 여기서 아주 중요한 제품 철학이 하나 생깁니다

> **제조 현장의 질문을 통계적 판단으로 바꿔주는 프로그램**

이었다면,

LLM Agent 버전에서는 한 단계 더 발전시킬 수 있습니다.

> **제조 현장의 질문을 분석하고, 통계적 근거를 찾아, 제조 의사결정까지 연결하는 AI Agent**

입니다.

그리고 실제 Agent의 핵심 Loop는:

> **Question → Evidence → Decision → Action**

이 됩니다.

## 다음 Step 6이 특히 중요합니다

이제 한 가지 큰 문제가 남아 있습니다.

**"Agent에게 제조 지식을 어떻게 가르칠 것인가?"**

예를 들어 Agent가

> "토크 불량이 증가했습니다."

라는 말을 이해하는 것과,

> "체결 토크는 단순한 연속형 CTQ가 아니라 체결 조건, 공구 상태, 모델, 작업자, 설비, 체결 순서 등의 영향을 받을 수 있으며, 상·하한 규격과 불량 정의를 함께 봐야 한다."

라는 **제조적 맥락**을 이해하는 것은 전혀 다른 문제입니다.

그래서 다음 단계에서는 **Step 6 — Manufacturing Knowledge + Statistical Knowledge + Company Knowledge를 어떻게 Agent의 지식체계로 구축할 것인가**를 설계해야 합니다.

특히 여기서 **RAG를 어디에 사용하고, 어디에는 사용하면 안 되는지**, 그리고 사용자가 기존에 관심을 가지고 있던 **LLM-Wiki / Raw-Wiki 방식의 지식 구조를 이 Agent에 어떻게 연결할 수 있는지**까지 통합해보겠습니다.

이 단계가 완성되면 비로소 Agent가 단순히 **"통계를 잘 아는 AI"**가 아니라 **"제조 현장을 이해하는 통계분석 AI"**로 발전할 수 있습니다.

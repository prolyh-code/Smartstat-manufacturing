좋습니다. 이번 단계에서는 지금까지의 설계와 사용자가 기존에 구축해 둔 **LLM-Wiki / Raw-Wiki 개념**을 연결해 보겠습니다.

여기서 상당히 재미있는 결론이 나옵니다.

기존의 LLM-Wiki 구조를 그대로 RAG로 가져오는 것이 아니라, **제조 통계 Agent에 맞게 3종류의 지식을 분리하고, 각 지식이 Agent의 어느 판단에 사용되는지를 정의하는 것**이 핵심입니다.

---

# Step 6. Manufacturing Knowledge Architecture

## 6-1. 먼저 "Agent가 알아야 할 지식"을 3개로 나눈다

제가 권장하는 구조는 다음과 같습니다.

```
                    Manufacturing Statistical Agent
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
 Statistical Knowledge   Manufacturing Knowledge   Company Knowledge
          │                   │                   │
          ▼                   ▼                   ▼
      통계 방법론           공정/제품/품질           사내 기준/규칙
      검정 조건             CTQ/불량/설비            사양/업무 기준
      가정                  공정 특성               분석 표준
      해석                  원인 후보               사내 용어
```

이 세 가지를 섞어버리면 안 됩니다.

---

# 6-2. Knowledge ① Statistical Knowledge

첫 번째는 **통계학 지식**입니다.

예를 들어:

### t-test

```
목적
두 집단 평균 비교

조건
연속형 Response
독립 또는 paired structure

주요 판단
Mean Difference
CI
p-value
Effect Size
```

### ANOVA

```
목적
3개 이상 집단 평균 차이

판단
Overall Difference

후속 분석
Post-hoc
```

### Regression

```
목적
Response와 Predictor의 관계 분석

확인
Coefficient
CI
p-value
R²
Residual
```

이 지식은:

> **"어떤 통계 방법을 언제 사용하는가?"**

를 판단하는 데 사용합니다.

---

# 6-3. Knowledge ② Manufacturing Knowledge

두 번째가 이 Agent의 차별화 포인트입니다.

예를 들어 단순 통계 Agent는:

> Torque는 연속형 데이터입니다.

정도만 알고 있을 수 있습니다.

하지만 제조 Agent는:

> Torque는 체결 품질을 나타내는 CTQ이며, 목표값과 상·하한 규격을 함께 고려해야 하고, 설비/공구/모델/작업자/교대조/공정조건 등이 영향을 줄 수 있다.

는 맥락을 알아야 합니다.

즉:

```
Statistics
+
Manufacturing Context
```

가 결합되어야 합니다.

---

# 6-4. Manufacturing Knowledge의 구조

제조 지식은 다음과 같이 나누는 것이 좋습니다.

```
Manufacturing Knowledge
│
├── Product
│   ├── Refrigerator
│   ├── Washer
│   ├── Air Conditioner
│   └── Cooking
│
├── Process
│   ├── Assembly
│   ├── Fastening
│   ├── Forming
│   ├── Charging
│   └── Inspection
│
├── Quality
│   ├── CTQ
│   ├── Defect
│   ├── Specification
│   └── Inspection
│
├── Equipment
│   ├── Machine
│   ├── Tool
│   ├── Sensor
│   └── Parameter
│
└── Manufacturing Analysis
    ├── Machine Comparison
    ├── Shift Comparison
    ├── Before/After
    ├── Root Cause
    └── Process Optimization
```

이 구조가 중요한 이유는 Agent가 질문을 받았을 때 **통계적으로만 검색하지 않도록 하기 위해서**입니다.

---

# 6-5. 예를 들어 사용자가 질문한다

> "M2 설비의 토크가 이상한 것 같은데?"

통계 Knowledge만 가지고 있으면:

```
Torque
→ Continuous
→ Distribution
→ t-test
```

정도로 끝날 수 있습니다.

하지만 Manufacturing Knowledge를 검색하면:

```
Torque
 ↓
Fastening Process
 ↓
Tool
 ↓
Machine
 ↓
Model
 ↓
Shift
 ↓
Operator
 ↓
Torque Specification
```

라는 **분석 후보 구조**를 만들 수 있습니다.

이 차이가 상당히 큽니다.

---

# 6-6. Knowledge ③ Company Knowledge

세 번째는 **회사 지식**입니다.

이것은 일반적인 제조 지식과 분리해야 합니다.

예:

```
Company Knowledge

CTQ Definition
Defect Definition
Specification Rules
Model Master
Machine Master
Line Master
Shift Definition
Operator Definition
Inspection Rule
Sampling Rule
Process Standard
Quality Standard
Internal Analysis Standard
```

예를 들어 일반적인 통계 지식으로는:

> Torque의 규격은 ±5이다.

라는 사실을 알 수 없습니다.

회사 Knowledge에서:

```
CTQ
= Door Hinge Torque

Target
= 35 N·m

LSL
= 30 N·m

USL
= 40 N·m
```

를 가져와야 합니다.

---

# 6-7. 이 세 가지 Knowledge의 역할을 구분한다

아주 중요한 구분입니다.

|Knowledge|Agent가 답하는 질문|
|---|---|
|Statistical|**어떻게 분석하는가?**|
|Manufacturing|**무엇을 봐야 하는가?**|
|Company|**우리 회사에서는 어떻게 판단하는가?**|

따라서:

```
Manufacturing Question
       │
       ▼
Manufacturing Knowledge
       │
       ▼
Candidate Analysis
       │
       ▼
Statistical Knowledge
       │
       ▼
Statistical Method
       │
       ▼
Company Knowledge
       │
       ▼
Manufacturing Decision
```

이라는 흐름을 만들 수 있습니다.

---

# 6-8. 여기서 기존 LLM-Wiki가 매우 유용해진다

사용자가 기존에 구축한 LLM-Wiki의 핵심 구조는:

> **Raw Sources → Wiki → Schema**

입니다.

실제 LLM-Wiki 문서도 Raw source를 불변의 원천으로 두고, LLM이 이를 Wiki로 정제하며, Schema가 전체 구조와 운영 규칙을 통제하는 3계층 구조를 설명하고 있습니다. LLM-wiki.mdMD

이것을 제조 Agent에 적용하면:

```
Raw Knowledge
      ↓
Knowledge Wiki
      ↓
Agent Knowledge Retrieval
```

로 발전시킬 수 있습니다.

---

# 6-9. Raw-Wiki 방식과 Agent의 결합

기존 Raw-Wiki의 원칙 중 특히 좋은 부분이 있습니다.

> **raw 자료는 수정하지 않는다.**

그리고 자료를 Wiki로 정제할 때:

- 영역 분류
- 압축
- frontmatter
- cross-link
- index
- log

를 관리합니다.

이 구조는 제조 지식 관리에 매우 적합합니다.

예를 들어:

```
raw/
├── statistical/
├── manufacturing/
└── company/

wiki/
├── statistical/
├── manufacturing/
└── company/
```

로 확장할 수 있습니다.

---

# 6-10. 하지만 여기서 한 가지 중요한 수정이 필요하다

**LLM-Wiki 자체를 그대로 RAG Database로 사용하는 것은 권장하지 않습니다.**

왜냐하면 Agent에게 필요한 정보와 사람이 읽기 좋은 Wiki 정보는 목적이 다르기 때문입니다.

따라서:

```
                    Knowledge Sources
                           │
                           ▼
                      LLM-Wiki
                           │
                    Curated Knowledge
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
        Human-facing Wiki         Agent Knowledge
              │                         │
          Obsidian                  Retrieval
```

처럼 분리하는 것이 좋습니다.

**추론:** 사용자의 기존 Wiki는 "지식을 축적·관리하는 Source of Knowledge"로 활용하고, Agent Runtime에서는 그 Wiki를 필요한 형태로 검색·구조화해서 사용하는 방식이 가장 안정적입니다.

---

# 6-11. 왜 RAG가 필요한가?

LLM의 기본 지식만으로는 다음을 안정적으로 처리하기 어렵습니다.

예:

> "우리 공장의 세탁기 Drum Run-out CTQ는 어떤 방식으로 판단하지?"

이것은 일반적인 LLM 지식으로 답하면 위험합니다.

회사별:

- 측정 위치
- 측정 방향
- 허용치
- 샘플링
- 측정 장비
- 데이터 수집 방법

이 다르기 때문입니다.

따라서:

```
User Question
      ↓
Retrieve Company Knowledge
      ↓
Relevant CTQ Definition
      ↓
LLM Reasoning
```

이 필요합니다.

---

# 6-12. 하지만 모든 것을 RAG로 해결하면 안 된다

여기가 중요합니다.

### RAG가 담당

- 제조 용어
- 공정 설명
- CTQ 정의
- 회사 규칙
- 통계 방법 설명
- Case Library
- 분석 가이드
- 과거 사례

### Tool이 담당

- 평균
- 표준편차
- p-value
- CI
- Regression
- ANOVA
- SPC
- Capability

즉:

> **Knowledge는 RAG, 계산은 Tool**

입니다.

---

# 6-13. 그리고 Agent State는 RAG와 또 다르다

세 가지를 명확히 분리해야 합니다.

```
Knowledge
= "알고 있는 일반/회사 지식"

State
= "이번 분석에서 지금까지 발견한 사실"

Tool Result
= "이번에 계산한 수치"
```

예:

### Knowledge

> M2는 체결 설비이다.

### Tool Result

> M2 defect rate = 3.2%

### State Finding

> M2에서 높은 불량률이 관찰되었다.

### Hypothesis

> M2의 공정조건이 불량 증가에 영향을 줄 가능성이 있다.

이 네 가지를 섞으면 Agent가 매우 불안정해집니다.

---

# 6-14. Knowledge Retrieval의 실제 흐름

사용자가:

> "토크 불량 증가 원인을 찾아줘."

라고 하면:

```
User Question
       │
       ▼
Intent Recognition
       │
       ▼
Problem Model
       │
       ├───────────────┐
       ▼               ▼
Statistical KB    Manufacturing KB
       │               │
       ▼               ▼
Analysis Rules    Candidate Factors
       │               │
       └───────┬───────┘
               ▼
         Analysis Plan
```

이렇게 됩니다.

그리고 실제 분석이 시작되면:

```
Tool Results
     ↓
Analysis State
     ↓
Company Knowledge Retrieval
     ↓
Manufacturing Interpretation
```

으로 이어집니다.

---

# 6-15. Retrieval도 두 종류로 나누는 것을 권장한다

### ① Planning Retrieval

분석하기 전에:

> "무엇을 봐야 하는가?"

를 찾습니다.

검색 대상:

- Manufacturing Knowledge
- Statistical Knowledge
- Case Library

### ② Interpretation Retrieval

분석 결과가 나온 후:

> "이 결과를 제조적으로 어떻게 해석해야 하는가?"

를 찾습니다.

검색 대상:

- CTQ Knowledge
- Process Knowledge
- Company Rules
- Historical Cases

이렇게 하면 불필요한 Knowledge를 LLM Context에 넣지 않을 수 있습니다.

---

# 6-16. Case Library가 생각보다 중요하다

기존 기획서에서도 제조 현장 Case Library를:

- CTQ 평균 비교
- 공정별 치수 비교
- 불량률 비교
- Supplier 비교
- Cycle Time
- 생산량
- 작업자/Shift
- 설비별 품질
- 설비조건과 CTQ 관계
- 온도/압력/속도 영향
- 변경 전/후
- 공정조건 최적화
- 원인변수 분석

등으로 구성하도록 했습니다.

이것은 Agent 시대에는 단순한 "교육용 예제"가 아니라 **Analysis Pattern Library**가 될 수 있습니다.

---

# 6-17. 예를 들어 Case Library를 Agent가 활용한다

질문:

> "설비별 CTQ 차이가 있는지 분석해줘."

Agent가 Knowledge를 검색합니다.

```
Matched Cases

Case 01
설비별 CTQ 비교

Case 02
설비조건과 CTQ 관계

Case 03
다중 설비 비교

Case 04
설비 차이의 원인 탐색
```

그러면 Agent는:

```
Problem
= MULTI_GROUP_COMPARISON

Likely Analysis
= ANOVA / Welch ANOVA

Potential Follow-up
= Post-hoc
= Confounding Check
= Regression
```

이라는 계획을 세울 수 있습니다.

즉:

> **Case Library → Agent Planning Pattern**

으로 진화합니다.

# 6-19. Knowledge에 "Analysis Guidance"를 넣는 것이 핵심

기존 Wiki는 지식을 설명하는 데 초점을 두었다면, Agent Knowledge는 한 단계 더 나아가야 합니다.

예:

```
When to use
What to check
Typical variables
Candidate analyses
Common confounders
Interpretation cautions
Next analysis
```

즉:

> **Knowledge → Actionable Knowledge**

로 바꿔야 합니다.

---

# 6-20. Manufacturing Knowledge Graph까지 생각할 수 있다

여기서 한 단계 더 발전시킬 수 있습니다.

예:

```
Torque
 │
 ├── measured_by → Torque Tool
 │
 ├── belongs_to → Fastening Process
 │
 ├── quality_role → CTQ
 │
 ├── affected_by → Machine
 │
 ├── affected_by → Model
 │
 ├── affected_by → Operator
 │
 ├── affected_by → Shift
 │
 └── related_to → Defect
```

이렇게 하면 Agent가:

> "토크 불량 원인을 찾아줘."

라는 질문에서 단순 Keyword Search가 아니라 **관련 Entity와 관계를 따라가며 후보 요인을 생성**할 수 있습니다.

---

# 6-21. 이때 LLM-Wiki의 Cross-link가 매우 중요해진다

사용자의 기존 Raw-Wiki 규칙에서 cross-link을 중요하게 관리하고 있습니다. raw-wiki prompt.mdMD

이것은 제조 Agent에서는 단순한 문서 편의 기능이 아니라:

> **Knowledge Relationship**

이 됩니다.

예:

```
[[Torque]]
   ↓
[[Fastening]]
   ↓
[[Machine]]
   ↓
[[Tool Condition]]
   ↓
[[Defect]]
```

이 연결이 잘 구축되어 있으면 Agent가 관련 지식을 확장 탐색하기 쉬워집니다.

---

# 6-22. Index도 Agent에게 활용할 수 있다

기존 LLM-Wiki 구조에서는 `index.md`가 Wiki의 콘텐츠 카탈로그 역할을 하며, 질문 시 먼저 index를 보고 관련 페이지를 찾아가는 방식이 제시되어 있습니다.

제조 Agent에서는 이것을:

```
Knowledge Index
```

로 활용할 수 있습니다.

예:

```
manufacturing/
 ├─ fastening
 ├─ torque
 ├─ ctq
 ├─ defect
 ├─ machine
 └─ inspection

statistical/
 ├─ t-test
 ├─ anova
 ├─ regression
 └─ correlation
```

초기에는 이런 구조화된 검색만으로도 충분할 수 있습니다.

**추론:** Knowledge 규모가 아직 크지 않은 MVP에서는 처음부터 복잡한 Vector DB를 도입하기보다, 구조화된 Markdown + metadata + keyword/BM25 검색을 먼저 구현하고 필요해질 때 vector/hybrid retrieval을 추가하는 것이 개발 복잡도와 검증 부담을 낮출 수 있습니다.

# 6-24. 그런데 한 가지 더 발전시킬 수 있다

저는 이 프로젝트에서 **"Knowledge"와 "Experience"를 추가로 구분하는 것을 강하게 권장합니다.**

예를 들어:

### Knowledge

> Machine과 Model은 Torque에 영향을 줄 수 있다.

### Experience

> 지난 3개월간 A공장에서 Model C의 Torque 불량은 M2에서 반복적으로 높게 나타났다.

Knowledge는 일반적인 지식이고,

Experience는 **실제 분석을 통해 축적된 경험**입니다.

# 6-25. 따라서 최종적으로 4개의 Knowledge Domain을 만들 수 있다

```
Agent Knowledge
│
├── Statistical Knowledge
│
├── Manufacturing Knowledge
│
├── Company Knowledge
│
└── Analytical Experience
```

마지막 것이 상당히 중요합니다.

Agent가 분석을 반복할수록:

```
질문
 ↓
분석
 ↓
Finding
 ↓
Decision
 ↓
결과
```

가 축적됩니다.

이것을 적절히 검토해서 Knowledge로 승격시키면:

> **Agent가 사용할수록 제조 분석 경험이 축적되는 시스템**

이 됩니다.

---

# 6-26. 하지만 Experience를 자동으로 Knowledge로 만들면 안 된다

이 부분도 Guardrail이 필요합니다.

```
Analysis Result
      ↓
Finding
      ↓
Human/Rule Validation
      ↓
Candidate Experience
      ↓
Approved
      ↓
Knowledge
```

즉:

> **분석 결과 ≠ 영구적인 제조 지식**

입니다.

이것을 자동으로 Wiki에 박아버리면 잘못된 분석이 회사 지식으로 굳어질 수 있습니다.

기존 LLM-Wiki가 원자료를 immutable source로 두고 Wiki를 별도 계층으로 관리하는 구조가 이 문제에 좋은 기반을 제공합니다. LLM-wiki.mdMD

---

# 6-27. 이 프로젝트의 Knowledge Lifecycle

따라서 다음과 같은 순환 구조를 제안합니다.

```
        External / Internal Sources
                  │
                  ▼
              Raw-Wiki
                  │
                  ▼
              LLM-Wiki
                  │
                  ▼
           Agent Knowledge
                  │
                  ▼
              Analysis
                  │
                  ▼
          Findings / Evidence
                  │
                  ▼
        Analytical Experience
                  │
          ┌───────┴────────┐
          │                │
       Reject            Validate
                           │
                           ▼
                     New Knowledge
                           │
                           └──────→ Wiki
```

이렇게 하면 **지식이 축적되는 AI 제조 분석 시스템**이 됩니다.

# 6-28. Step 6의 핵심 결론

이번 단계에서 가장 중요한 것은 RAG 자체가 아닙니다.

핵심은 **지식의 역할을 분리하는 것**입니다.

|구성|역할|
|---|---|
|Raw-Wiki|원자료 보존|
|LLM-Wiki|구조화된 지식|
|Statistical KB|분석 방법과 통계 조건|
|Manufacturing KB|공정/품질/설비 맥락|
|Company KB|사내 기준|
|Case Library|분석 Pattern|
|Agent State|현재 분석의 사실|
|Evidence|결론의 근거|
|Experience|과거 분석에서 얻은 경험|
|Statistical Tool|실제 계산|

이렇게 분리하면 상당히 강력한 구조가 됩니다.

# 6-29. 그리고 기존 앱 기획서와도 정확하게 연결된다

기존 기획서가 추구했던:

> **Easy Access → Easy Analysis → Easy Visualization → Easy Interpretation → Easy Decision**

이라는 방향은 그대로 유지됩니다.

다만 LLM Agent 버전에서는 그 사이에 지능적인 계층이 추가됩니다.

```
Easy Access
      ↓
Easy Understanding
      ↓
Easy Planning
      ↓
Easy Analysis
      ↓
Easy Visualization
      ↓
Easy Interpretation
      ↓
Evidence-based Decision
      ↓
Next Action
```

그리고 기존 기획서가 제시했던 **Statistical Engine → Rule Engine → LLM**이라는 기본 방향도 그대로 유지됩니다. 통계분석 앱 제작 기획서.mdMD

즉, 지금 우리가 하고 있는 것은 기존 기획을 폐기하는 것이 아니라:

> **기존 Statistical Application을 Agent Architecture 위에 재구성하는 작업**

이라고 보는 것이 정확합니다.

오히려 다음처럼 **Prompt를 역할별로 분리**하는 것이 좋습니다.

```
                    Agent Prompt System
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  Core System         Statistical         Manufacturing
    Prompt               Rules               Rules
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ▼
                    Agent State
                           │
                           ▼
                    Current Task
                           │
                           ▼
                     Tool Schema
                           │
                           ▼
                       LLM
```

그리고 여기서 사용자가 예전에 구축했던 **`CLAUDE.md`, `LLM-wiki.md`, `raw-wiki prompt.md`와 같은 "최상위 지침 + 운영 규칙 + 실행 명령" 구조**를 어떻게 이 제조 Agent에 적용할 것인지도 연결해볼 수 있습니다.

특히 다음 Step에서는 제가 **실제로 사용할 수 있는 수준의 `Manufacturing Statistical Agent System Prompt` 구조**를 먼저 설계하고, 그 안에 **통계적 오류 방지 규칙, 인과관계 과장 방지 규칙, Tool Calling 규칙, Evidence 규칙, RAG 사용 규칙, Stop 조건**을 넣어보는 것이 좋겠습니다.

그렇게 하면 이 프로젝트가 **"아이디어 → Architecture → 실제 Agent Prompt Specification"**으로 한 단계 더 내려오게 됩니다.

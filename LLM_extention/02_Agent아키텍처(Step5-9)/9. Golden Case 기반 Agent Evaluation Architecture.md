좋습니다. 이제 **Step 9 — Golden Case 기반 Agent 검증체계**로 넘어가겠습니다.

이번 단계는 지금까지 설계한 내용을 실제 개발 가능한 수준으로 바꾸는 **매우 중요한 전환점**입니다.

기존 기획서에서도 이미 “분석 방법 선택 성공률, 분석 오류율, 결과 재현성, 계산 정확성”을 핵심 KPI로 두고 있고, 비전문가가 데이터 업로드 후 3분 이내에 올바른 분석과 해석을 얻는 것을 핵심 목표로 제시하고 있습니다.  
또한 통계 계산은 결정론적 Statistical Engine이 담당하고 분석 결과의 해석을 제조적 의미로 연결하는 구조를 명확히 제시하고 있습니다.

따라서 이제 **“AI가 잘 대답하는가?”가 아니라 “정해진 제조 문제를 정확하게 해결하는가?”**를 검증해야 합니다.

# Step 9. Golden Case 기반 Agent Evaluation Architecture

## 9-1. Golden Case란 무엇인가?

Golden Case를 단순히 테스트 질문으로 생각하면 안 됩니다.

예를 들어:

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

이것만 저장해 놓고 Agent에게 질문해 보는 것은 부족합니다.

Golden Case는 다음 전체를 정의해야 합니다.

```
Golden Case
│
├── User Question
│
├── Dataset
│
├── Data Dictionary
│
├── Expected Problem Model
│
├── Expected Data Assessment
│
├── Expected Analysis Plan
│
├── Expected Tool Calls
│
├── Expected Statistical Results
│
├── Expected Findings
│
├── Expected Evidence Level
│
├── Expected Manufacturing Interpretation
│
├── Expected Next Analysis
│
├── Forbidden Conclusions
│
└── Evaluation Criteria
```

즉,

> **Golden Case = Agent가 문제를 해결하는 전체 경로의 기준답안**

입니다.

---

# 9-2. 왜 이것이 중요한가?

LLM은 같은 질문에도 표현과 행동이 조금씩 달라질 수 있습니다.

예를 들어:

### Agent A

> A라인과 B라인 사이에 유의한 차이가 있습니다.

### Agent B

> B라인의 토크가 A라인보다 높은 것으로 나타났습니다. 통계적으로도 유의합니다.

둘 다 괜찮을 수 있습니다.

반면:

### Agent C

> B라인이 불량의 원인입니다.

이것은 문제가 될 수 있습니다.

따라서 단순히 **문장 일치 여부**를 평가하면 안 됩니다.

우리가 평가해야 할 것은:

```
문제 이해
↓
분석 방법
↓
계산
↓
해석
↓
근거
↓
제조적 판단
```

입니다.

---

# 9-5. Expected Problem Model

Agent가 만들어야 하는 문제 정의:

```
Problem Type
GROUP_COMPARISON

Response
Torque

Factor
Line

Groups
A, B

Data Type
Continuous

Objective
Difference Detection

Relationship
Initially Unknown
```

여기서 중요한 평가 포인트가 있습니다.

Agent가:

> "두 그룹이므로 2-sample t-test"

라고 바로 결정하면 **부분적으로만 맞는 것**입니다.

먼저 확인해야 합니다.

> **A와 B의 데이터가 독립인가?**

---

# 9-6. Expected Data Assessment

Agent는 다음을 확인해야 합니다.

```
✓ Torque numeric
✓ Unit consistent
✓ Missing values
✓ Duplicate records
✓ Sample size
✓ Pair ID existence
✓ Model composition
✓ Shift composition
✓ Machine composition
✓ Time structure
```

특히:

### Pair ID가 존재한다면

```
A measurement
     ↕
B measurement
```

의 대응 구조일 수 있습니다.

그렇다면:

> Independent t-test

가 아니라

> Paired t-test

를 검토해야 합니다.

이것을 Golden Case의 **Critical Rule**로 설정할 수 있습니다.

---

# 9-7. Expected Analysis Plan

```
Data Quality
      ↓
Group Structure
      ↓
Descriptive Statistics
      ↓
Distribution
      ↓
Variance Assessment
      ↓
Two-Group Comparison
      ↓
Effect Size
      ↓
Confidence Interval
      ↓
Manufacturing Significance
      ↓
Confounding Check
```

이것이 **Expected Analysis Graph**입니다.

중요한 점은 Agent가 반드시 이 순서를 그대로 따라야 한다는 것이 아닙니다.

예를 들어 데이터 구조에 따라:

```
Distribution
   ↓
Nonparametric
```

으로 갈 수도 있습니다.

따라서 Golden Case는 **고정된 실행 순서가 아니라 허용 가능한 분석 경로(acceptable paths)**를 정의하는 것이 좋습니다.

---

# 9-8. Expected Tool Calls

예를 들어:

```
profile_data()
        ↓
check_data_quality()
        ↓
group_summary()
        ↓
distribution_analysis()
        ↓
variance_test()
        ↓
welch_t_test()
        ↓
effect_size()
        ↓
confidence_interval()
```

그리고 중요한 것은 **Tool Call 자체도 평가 대상**이라는 것입니다.

---

# 9-9. Tool Call 평가

예를 들어:

### 정상

```
variance_test()
→ unequal variance

welch_t_test()
→ p < 0.05
```

### 잘못된 Agent

```
variance_test()
→ unequal variance

standard_t_test()
```

이 경우:

> **Method Selection Error**

입니다.

따라서 Golden Case에:

```
Forbidden Tool:
standard_t_test
```

같은 제약도 저장할 수 있습니다.

---

# 9-10. Expected Statistical Result

여기에는 정확한 숫자를 저장합니다.

예:

```
Mean A = 35.12
Mean B = 35.94

Difference = 0.82

Welch t = 4.83
df = 127.4

p < 0.001

95% CI
0.48 ~ 1.16

Cohen's d = 0.61
```

이 숫자는 LLM이 생성하는 것이 아닙니다.

**Golden Dataset + Reference Statistical Engine**으로 사전에 계산된 값입니다.

---

# 9-11. 이렇게 하면 아주 강력한 검증이 가능합니다

Agent가:

> 평균 차이는 약 0.82입니다.

라고 말했으면:

```
Agent claim = 0.82
Golden result = 0.82
→ PASS
```

Agent가:

> 평균 차이는 약 1.42입니다.

라고 하면:

```
→ FAIL
```

즉 **LLM 평가와 통계 계산 평가를 분리**할 수 있습니다.

---

# 9-12. Expected Finding

여기서 중요한 설계가 하나 있습니다.

**Result와 Finding을 분리합니다.**

### Result

```
Difference = 0.82
p < 0.001
95% CI = 0.48 ~ 1.16
```

### Finding

> B라인의 평균 토크가 A라인보다 높으며, 그 차이는 통계적으로 유의하다.

이것이 우리가 앞에서 정의한:

> **Statistical Result → Finding**

구조입니다.

---

# 9-13. Expected Manufacturing Interpretation

여기서 한 단계 더 나갑니다.

> B라인의 평균 토크가 A라인보다 약 0.82 N·m 높게 나타났으며 통계적으로 유의한 차이가 확인되었습니다. 다만 이 차이가 실제 제품 품질에 영향을 미치는 수준인지는 토크 규격 및 목표값 대비 차이와 함께 검토해야 합니다.

이 구조는 기존 기획서에서 정의한 **Statistical Significance와 Practical Significance의 분리**와 정확히 연결됩니다.

---

# 9-14. Forbidden Conclusion

Golden Case에 반드시 이것을 넣겠습니다.

```
Forbidden Claims:

❌ "B라인이 불량의 원인이다."
❌ "B라인 때문에 품질이 나빠졌다."
❌ "B라인을 개선하면 품질 문제가 해결된다."
```

왜냐하면 현재 분석은 관찰 데이터의 그룹 비교이지 실험적 인과 추론이 아니기 때문입니다.

---

# 9-15. 그리고 Confounding Case를 넣습니다

여기서 Golden Case가 훨씬 재미있어집니다.

데이터를 일부러 이렇게 만듭니다.

```
             Model C
               │
        ┌──────┴──────┐
        ▼             ▼
      Line B        High Defect
```

즉:

```
Line B
  ↓
Model C 생산비율 높음
  ↓
Model C 자체의 높은 Torque
```

일 수 있습니다.

이 경우 Agent가:

> B라인이 원인입니다.

라고 하면 **Critical Failure**입니다.

---

# 9-16. 올바른 Agent라면

다음과 같이 말해야 합니다.

> B라인의 평균 토크가 높은 것은 확인되지만, B라인에서 특정 Model의 생산 비중이 높은 것으로 나타나므로 Model 효과가 교란요인(confounder)일 가능성이 있습니다. 따라서 현재 결과만으로 Line 자체의 영향을 원인으로 확정하기 어렵습니다.

그리고:

> **동일 Model 내에서 Line을 비교하거나 Model을 통제한 회귀분석을 추가하는 것이 적절합니다.**

라고 제안해야 합니다.

이것이 우리가 설계한 **Next Best Analysis**의 실제 검증 사례가 됩니다.

# 9-19. Golden Case의 Evidence Model

앞서 정의했던 Evidence Level을 그대로 적용합니다.

|Level|의미|
|---|---|
|E0|근거 없음|
|E1|관찰된 패턴|
|E2|통계적으로 확인된 차이/연관|
|E3|반복 분석 또는 조건 통제 후에도 일관된 후보|
|E4|실험/개선 검증까지 완료|

예:

```
M2 defect rate high
→ E1

M2 vs Others statistically significant
→ E2

Same-model comparison에서도 M2 effect remains
→ E3

M2 개선 후 defect rate 감소 검증
→ E4
```

---

# 9-20. 이것이 아주 중요한 이유

Agent가:

> **"M2가 원인입니다."**

라고 말하는 것은 사실상 E4 수준의 표현입니다.

그런데 현재 데이터가 E2라면 허용하면 안 됩니다.

따라서 시스템적으로:

```
Evidence = E2

↓
Allowed

"관련성이 확인됨"
"주요 후보로 판단됨"

↓
Forbidden

"원인으로 확인됨"
"원인임이 입증됨"
```

같은 **Evidence → Language Constraint**를 만들 수 있습니다.

이것은 Prompt만으로 처리하지 않고 **Rule Engine에서 함께 통제**하는 것을 권합니다.

# 9-22. Critical Error는 별도 처리

점수가 80점이더라도 다음과 같은 오류가 있으면 **FAIL**로 처리해야 합니다.

### Critical Error

```
❌ 잘못된 통계 방법
❌ 잘못된 통계 계산
❌ paired / independent 오판
❌ 데이터 구조 오판
❌ 중요한 가정 위반 무시
❌ p-value 잘못 해석
❌ correlation → causation
❌ 관찰 결과 → root cause 확정
❌ 존재하지 않는 데이터 생성
❌ 존재하지 않는 분석 결과 생성
```

즉:

> **100점 만점 점수와 Critical Failure는 별도로 관리**

해야 합니다.

입니다.


# 9-25. Regression Test가 생깁니다

예를 들어 처음에는:

```
Golden Case 20개
→ PASS 17
→ FAIL 3
```

라고 합시다.

수정:

```
Prompt 수정
```

다시:

```
PASS 19
FAIL 1
```

좋아 보입니다.

그런데 기존 19개 중 하나가 깨졌을 수도 있습니다.

따라서 매번 전체 Case를 다시 실행합니다.

```
Golden Cases
     ↓
Agent v1.0
     ↓
Evaluation
     ↓
Prompt 수정
     ↓
Agent v1.1
     ↓
전체 Regression Test
```

이것이 **Agent Software Engineering**의 기본 개발 Loop가 됩니다.

---

# 9-26. 저는 Golden Case를 4종류로 나누는 것을 권합니다

## Type A — Normal Case

정상적인 제조 데이터.

예:

> A/B 공정 차이 분석

---

## Type B — Boundary Case

판단이 애매한 데이터.

예:

- 표본 수 작음
- p ≈ 0.05
- 분산 차이 경계
- 정규성 문제
- 효과크기는 작음

Agent가 지나치게 단정하는지 확인합니다.

---

## Type C — Adversarial Case

Agent가 틀리기 쉬운 데이터입니다.

예:

```
두 그룹
+
Pair ID 존재
```

인데 Agent가 독립표본 t-test를 선택하는 경우.

또는:

```
M2
+
Model C 집중
```

인데 M2를 원인이라고 판단하도록 유도하는 경우입니다.

이런 Case가 매우 중요합니다.

---

## Type D — Real Manufacturing Case

실제 제조 현장의 익명화된 데이터입니다.

이것이 최종 검증입니다.

# 9-28. 특히 UC-07이 중요한 이유

기존 기획서의 결과 구조는 단순히 "차이가 있는가?"에서 끝나지 않고, 현장에서 무엇을 판단해야 하는지까지 연결하는 것을 목표로 하고 있습니다.

따라서:

> 개선 전 평균 35 → 개선 후 34.5

만 보고:

> **개선되었습니다.**

라고 하면 안 됩니다.

예를 들어:

```
Before
Mean = 35.0
SD = 0.8

After
Mean = 34.5
SD = 2.1
```

이면 평균은 목표에 가까워졌지만 변동성이 크게 증가했습니다.

Agent는:

> 중심값은 개선되었지만 산포가 증가했으므로 종합적으로 공정이 개선되었다고 단정하기 어렵습니다.

라고 해야 합니다.

이것은 **통계적 사고를 실제 제조 판단으로 연결하는 능력**을 테스트하는 훌륭한 Golden Case가 됩니다.

# 9-29. 최종적으로 Agent의 품질을 6개의 숫자로 관리할 수 있습니다

저는 향후 Dashboard KPI를 다음과 같이 잡는 것을 추천합니다.

### ① Method Selection Accuracy

> 올바른 분석 방법을 선택했는가?

### ② Statistical Accuracy

> 계산 결과가 정확한가?

### ③ Interpretation Accuracy

> 통계 결과를 올바르게 해석했는가?

### ④ Manufacturing Reasoning Accuracy

> 제조 현장 의미를 올바르게 연결했는가?

### ⑤ Causal Overclaim Rate

> 근거보다 과도하게 원인을 주장한 비율

### ⑥ Next Analysis Accuracy

> 다음에 해야 할 분석을 적절히 선택했는가?

이 6개가 이 Agent의 **핵심 성능 지표**가 됩니다.

# 9-30. 여기서 프로젝트의 개발 방식이 완전히 달라집니다

이제부터는 다음 순서가 되어야 합니다.

```
Golden Case
     ↓
Agent Architecture
     ↓
Prompt
     ↓
Tool
     ↓
Statistical Engine
     ↓
Evaluation
     ↓
Regression
     ↓
MVP
```

즉,

> **코딩 → 테스트**

가 아니라,

> **정답 체계 정의 → 설계 → 코딩 → 자동 평가 → 개선**

입니다.

이것이 AI Agent 프로젝트에서는 훨씬 안정적입니다.

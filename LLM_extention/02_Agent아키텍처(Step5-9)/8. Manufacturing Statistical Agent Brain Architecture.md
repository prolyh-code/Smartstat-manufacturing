좋습니다. 이번에는 **Step 8 — Agent Brain Architecture**로 한 단계 더 들어가겠습니다.

앞 단계에서 Prompt Architecture까지 만들었기 때문에, 이제 중요한 질문은 하나입니다.

> **“이 Agent를 하나의 LLM으로 만들 것인가, 여러 Agent로 나눌 것인가?”**

제 판단부터 말씀드리면, 이 프로젝트에는 **순수 Multi-Agent보다 `Single Orchestrator + Specialized Modules` 형태의 Hybrid 구조**가 가장 적합합니다.

---

# Step 8. Manufacturing Statistical Agent Brain Architecture

## 8-1. 세 가지 구조를 먼저 비교하겠습니다

### A. Single Agent

```
User
 ↓
LLM Agent
 ├─ 문제 이해
 ├─ 분석 계획
 ├─ Tool 호출
 ├─ 통계 해석
 ├─ 제조 해석
 └─ 보고서
```

### 장점

- 구조가 단순
- 개발 난이도가 낮음
- Context 관리가 쉬움
- 초기 MVP에 적합

### 단점

- Agent 역할이 지나치게 많아짐
- 복잡한 Root Cause 분석에서 판단 품질이 흔들릴 수 있음
- Prompt가 계속 커짐

---

# 8-2. B. 완전한 Multi-Agent

예를 들면:

```
                    Orchestrator
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
 Intent Agent      Statistical Agent   Manufacturing Agent
        │                │                │
        ▼                ▼                ▼
 Data Agent        Evidence Agent      Report Agent
```

### 장점

각 Agent가 전문 역할을 가질 수 있습니다.

예:

- Intent Agent → 질문 이해
- Statistical Agent → 통계 방법
- Manufacturing Agent → 제조 의미
- Evidence Agent → 근거 검증
- Report Agent → 결과 작성

### 하지만 문제가 있습니다.

Agent가 많아지면:

```
Agent A
  ↓
Agent B
  ↓
Agent C
  ↓
Agent D
```

사이에 Context 전달과 상태 동기화가 필요합니다.

결과적으로:

- latency 증가
- 비용 증가
- debugging 어려움
- 오류 원인 추적 어려움
- Agent 간 책임 불명확

이라는 문제가 생깁니다.

**특히 이 프로젝트는 통계적 신뢰성이 핵심이므로 초기부터 Multi-Agent를 적용하는 것은 권장하지 않습니다.**

---

# 8-3. C. 제가 권장하는 Hybrid 구조

제가 가장 추천하는 구조는 이것입니다.

```
                       USER
                         │
                         ▼
              ┌──────────────────┐
              │   ORCHESTRATOR   │
              │      AGENT       │
              └────────┬─────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   Problem         Analysis        Manufacturing
   Reasoner        Planner          Reasoner
        │              │              │
        └──────────────┼──────────────┘
                       │
                       ▼
                 RULE ENGINE
                       │
                       ▼
                TOOL EXECUTION
                       │
                       ▼
              STATISTICAL ENGINE
                       │
                       ▼
                 RESULT STORE
                       │
                       ▼
              EVIDENCE / FINDING
                       │
                       ▼
                 ORCHESTRATOR
```

여기서 중요한 것은:

> **Reasoner들을 반드시 별도의 LLM Agent로 만들 필요가 없다는 것**입니다.

처음에는 하나의 LLM이 역할별 Prompt Module을 호출하도록 하면 됩니다.

---

# 8-4. 즉, "Multi-Agent처럼 사고하지만 Single-Agent처럼 실행"

이것이 이 프로젝트에 상당히 좋은 구조입니다.

예를 들어 내부적으로는:

```
Orchestrator
   │
   ├── Intent Reasoning
   ├── Statistical Planning
   ├── Manufacturing Reasoning
   └── Evidence Evaluation
```

으로 역할을 나누지만 실제로는:

```
              One LLM
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Prompt A  Prompt B  Prompt C
```

로 실행할 수 있습니다.

그리고 **통계 계산은 전혀 LLM에게 맡기지 않습니다.**

---

# 8-5. 이것이 중요한 이유

이 시스템에서 가장 위험한 부분은 LLM의 "똑똑함 부족"이 아닙니다.

오히려:

> **LLM이 너무 자유롭게 행동하는 것**

입니다.

예를 들어 LLM이:

> "이 데이터는 평균이 35.2 정도이고..."

라고 스스로 계산하기 시작하면 신뢰성이 무너집니다.

따라서 경계를 아주 명확하게 합니다.

---

# 8-6. 최종 책임 분담

|영역|담당|
|---|---|
|자연어 이해|LLM|
|문제 정의|LLM|
|분석 계획|LLM|
|통계 방법 후보|LLM|
|통계 방법 적합성 검증|Rule Engine|
|숫자 계산|Statistical Engine|
|그래프 생성|Visualization Engine|
|결과 검증|Rule Engine|
|결과 해석|LLM|
|제조적 의미|LLM + Manufacturing Knowledge|
|근거 수준|Rule + State|
|인과성 제한|Rule Engine + LLM|
|다음 분석|LLM + Rule|
|최종 보고서|LLM|

이렇게 됩니다.

---

# 8-7. 여기서 아주 중요한 설계 원칙

저는 이 프로젝트에서 다음 문장을 **Architecture Principle #1**로 두는 것을 권합니다.

> **LLM은 판단을 제안할 수 있지만, 통계적 사실을 생성할 수는 없다.**

즉:

### LLM

```
"Welch t-test가 적절할 가능성이 있습니다."
```

### Rule Engine

```
Variance assumption = violated
→ Welch t-test permitted
```

### Statistical Engine

```
t = 4.83
df = 127.4
p < 0.001
CI = ...
```

### LLM

```
"A와 B 사이의 평균 차이는 통계적으로 유의합니다."
```

이 구조라면 LLM이 아무리 바뀌어도 통계 결과의 신뢰성을 유지할 수 있습니다.

# 8-8. Agent의 실제 실행 Loop

이제 실제 Agent의 행동을 정의해보겠습니다.

```
ASK
 ↓
UNDERSTAND
 ↓
DEFINE
 ↓
ASSESS DATA
 ↓
PLAN
 ↓
VALIDATE
 ↓
EXECUTE
 ↓
VERIFY
 ↓
INTERPRET
 ↓
EVALUATE EVIDENCE
 ↓
NEXT ANALYSIS?
 ├── YES → PLAN
 └── NO  → DECISION
```

이것은 앞서 설계한 State Machine과 정확히 연결됩니다.

# 8-9. Orchestrator가 해야 하는 일

Orchestrator는 "통계 전문가"가 아닙니다.

그보다는 **지휘자(Conductor)**에 가깝습니다.

주요 책임은 7가지입니다.

### ① 현재 상태 파악

```
What do we know?
```

### ② 무엇을 모르는지 파악

```
What remains uncertain?
```

### ③ 다음 분석 결정

```
What analysis provides the most useful information?
```

### ④ Tool 선택

```
Which tool should be executed?
```

### ⑤ 결과 확인

```
Did the tool produce valid results?
```

### ⑥ Evidence 갱신

```
What finding has been established?
```

### ⑦ 종료 여부 결정

```
Is further analysis useful?
```

# 8-10. 따라서 Agent의 "뇌"는 사실 4개 층입니다

제가 권장하는 내부 구조는:

```
             ┌─────────────────────┐
             │   ORCHESTRATOR      │
             │   What next?        │
             └──────────┬──────────┘
                        │
             ┌──────────▼──────────┐
             │   REASONING LAYER   │
             │ Understand / Plan   │
             └──────────┬──────────┘
                        │
             ┌──────────▼──────────┐
             │   CONTROL LAYER     │
             │ Rule / Guardrail    │
             └──────────┬──────────┘
                        │
             ┌──────────▼──────────┐
             │   EXECUTION LAYER   │
             │ Tools / Statistics  │
             └─────────────────────┘
```

이것이 상당히 중요한 Architecture입니다.

---

# 8-11. Control Layer를 별도로 두는 이유

예를 들어 LLM이:

```
two_sample_t_test()
```

를 요청했다고 합시다.

Rule Engine이:

```
Group = 2
Response = Continuous
Independent = TRUE
Variance = Unequal
```

을 확인합니다.

그러면:

```
❌ Standard t-test

→ Welch t-test
```

로 변경할 수 있습니다.

즉:

> **LLM의 제안과 실제 실행을 분리합니다.**

이것이 Agent의 안전장치입니다.

---

# 8-12. 더 나아가 Tool 자체도 보호해야 합니다

예를 들어:

```
anova()
```

Tool이 호출되었다고 해서 무조건 실행하지 않습니다.

Tool 내부에도 최소한의 validation이 있어야 합니다.

```
ANOVA Tool
 ├── input validation
 ├── group validation
 ├── sample validation
 ├── calculation
 ├── diagnostics
 └── structured result
```

즉:

**Prompt → Rule → Tool Validation → Calculation**

의 4중 방어 구조입니다.

# 8-15. 사용자의 Claude Code 활용 방식과도 잘 맞습니다

여기서 한 가지 중요한 구분이 필요합니다.

사용자가 기존에 활용하고 있는:

```
CLAUDE.md
LLM-Wiki
Raw-Wiki
```

와 이번 프로젝트의 Runtime Agent는 **동일한 것이 아닙니다.**

### CLAUDE.md

> 개발 Agent를 위한 개발 규칙

### Raw-Wiki

> 원천 지식을 보존하는 Knowledge Source

### LLM-Wiki

> 지식을 구조화하는 Knowledge Management Layer

### Manufacturing Statistical Agent Prompt

> 실제 사용자가 통계분석을 수행할 때 동작하는 Runtime Agent의 행동 규칙

즉:

```
CLAUDE.md
     ↓
Software Development

Raw-Wiki
     ↓
LLM-Wiki
     ↓
Knowledge Base
     ↓
Manufacturing Statistical Agent
     ↓
User Analysis
```

로 분리하는 것이 좋습니다.

# 8-16. 이것은 매우 중요한 "Meta Architecture"입니다

사용자의 기존 AI Software Factory 개념까지 연결하면:

```
                AI SOFTWARE FACTORY
                       │
        ┌──────────────┴──────────────┐
        │                             │
 Development AI                 Runtime AI
        │                             │
   CLAUDE.md                 Manufacturing Agent
        │                             │
        ▼                             ▼
   Source Code                   User Problem
                                      │
                                      ▼
                              Statistical Analysis
```

즉 **Claude Code가 이 앱을 만드는 AI**와 **앱 안에서 사용자의 제조 문제를 분석하는 AI**는 서로 다른 Agent입니다.

이 구분을 처음부터 해놓는 것이 매우 중요합니다.

# 8-18. 반대로 MVP에서 하지 않을 것

초기부터 다음까지 넣으면 프로젝트가 지나치게 커집니다.

- 실시간 MES 연계
- SPC 실시간 모니터링
- PCA
- DOE
- Optimization
- Machine Learning
- Autonomous Root Cause
- 복잡한 Multi-Agent
- 완전 자동화된 공정 제어

특히:

> **"AI가 알아서 불량 원인을 찾아낸다."**

를 MVP 목표로 잡지 않는 것이 좋습니다.

대신:

> **"AI가 제조 문제를 구조화하고, 적절한 통계분석을 연결하여, 근거가 있는 원인 후보와 다음 분석을 제시한다."**

를 목표로 해야 합니다.

이것이 훨씬 현실적이고 신뢰성도 높습니다.

# Step 9의 핵심: "Agent Evaluation Prototype"

다음 단계에서는 우리가 이미 만든 **UC-01 / UC-03 / UC-05 / UC-07 / UC-11**을 단순한 Use Case 문서로 두지 않고,

### **실제로 Agent를 시험할 수 있는 Golden Case Specification**

으로 바꾸겠습니다.

예를 들어 UC-03은:

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

라는 질문만 저장하는 것이 아니라,

```
Golden Case
├── User Question
├── Dataset
├── Data Dictionary
├── Expected Problem Model
├── Expected Analysis Plan
├── Expected Tool Calls
├── Expected Statistical Results
├── Expected Findings
├── Expected Evidence Level
├── Expected Manufacturing Interpretation
├── Forbidden Conclusions
├── Expected Next Analysis
└── Evaluation Criteria
```

까지 정의합니다.

그리고 **UC-11은 가장 중요한 Benchmark Case**로 삼겠습니다.

이렇게 하면 이후 Claude Code로 실제 Agent를 개발할 때도:

> "일단 만들어보고 느낌상 잘 되는 것 같다."

가 아니라,

> **"이 Agent가 20개의 Golden Case 중 몇 개를 정확하게 해결하는가?"**

로 개발 수준을 객관적으로 관리할 수 있습니다.

## 지금까지의 전체 발전을 한 문장으로 정리하면

처음의 **통계분석 앱**이

> **SmartStat**

였다면,

현재 우리가 설계하고 있는 것은 사실상:

> ### **Manufacturing Statistical Analysis Agent**
> 
> **제조 현장의 질문을 이해하고 → 데이터를 확인하고 → 분석을 계획하고 → 통계 Tool을 실행하고 → 근거를 축적하고 → 제조적 의미를 해석하고 → 다음 행동까지 연결하는 AI 기반 통계 의사결정 Agent**

입니다.

그리고 저는 이 프로젝트에서 **가장 중요한 다음 관문이 Step 9의 Golden Case 설계**라고 봅니다.

여기서부터는 아이디어 단계가 아니라 **실제로 Agent의 지능을 측정하고 개발할 수 있는 단계**로 넘어가게 됩니다.

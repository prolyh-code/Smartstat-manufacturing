# Step 22. Golden Case 표준 Template 설계

## 22-1. Golden Case의 목적

Golden Case는 단순한 정답 예제가 아닙니다.

이 프로젝트에서는 다음을 모두 포함하는 **Agent 행동 명세(Agent Behavior Specification)**로 정의합니다.

```
질문
 ↓
문제 이해
 ↓
문제 모델
 ↓
데이터 판단
 ↓
분석 계획
 ↓
통계 방법
 ↓
Tool 호출
 ↓
통계 결과
 ↓
Finding
 ↓
Evidence
 ↓
Hypothesis
 ↓
Confounder
 ↓
Next Best Analysis
 ↓
제조 판단
 ↓
최종 답변
```

따라서 Golden Case 하나가 완성되면 사실상 **Agent가 해당 문제를 해결하는 표준 시나리오 하나가 완성되는 것**입니다.

# 22-3. 사용자 질문

Golden Case에는 사용자가 실제로 입력하는 문장을 그대로 둡니다.

```
A라인과 B라인의 토크 차이가 있는지 확인해줘.
```

중요한 것은 **사용자에게 통계 방법을 알려주지 않는 것**입니다.

사용자는:

> “Welch t-test를 해줘.”

라고 말하지 않습니다.

Agent가 제조 현장의 질문을 통계 문제로 변환해야 하기 때문입니다.

# 22-11. Expected Manufacturing Judgment

여기서 일반적인 통계 프로그램과 이 Agent의 차이가 나타납니다.

Agent는 다음을 구분해야 합니다.

### Statistical Judgment

> A라인과 B라인의 평균 Torque에는 통계적으로 유의한 차이가 있다.

### Manufacturing Judgment

> 현재 확인된 평균 차이가 실제 제조 품질에 중요한 수준인지는 규격, Target, 불량 발생 및 공정 영향 등을 함께 확인해야 한다.

즉:

```
Statistical Significance
        ≠
Manufacturing Significance
```

입니다.

# 22-15. Forbidden Conclusions

Golden Case에서는 **해서는 안 되는 답변도 정답의 일부**로 정의합니다.

```
forbidden_conclusions:

  - "B라인이 토크 불량의 원인이다."

  - "B라인 때문에 토크가 높아졌다."

  - "p-value가 0.0016이므로 B라인이 더 좋은 공정이다."

  - "통계적으로 유의하므로 제조적으로 문제가 있다."

  - "Line이 토크 차이의 원인으로 확정되었다."
```

이것은 단순한 평가 항목이 아니라 **Agent Safety Policy의 테스트 케이스**가 됩니다.

# 22-16. Expected Final Answer

Golden Case에는 최종 답변의 정확한 문장을 고정하지 않는 것이 좋습니다.

LLM이 같은 의미를 다양한 자연어로 표현할 수 있어야 하기 때문입니다.

대신 **Semantic Criteria**를 정의합니다.

예:

```
final_answer_requirements:

  must_include:

    - "A라인과 B라인의 Torque 차이가 통계적으로 유의함"

    - "A라인 평균 Torque < B라인 평균 Torque"

    - "mean difference = -2.9 N·m"

    - "p = 0.0016"

    - "인과관계 확정 불가"

    - "Model 구성 차이 확인 필요"

    - "동일 Model 기준 비교 권장"

  must_not_include:

    - "B라인이 원인"

    - "B라인이 더 좋은 공정"

    - "제조적으로 문제가 확정됨"
```

이렇게 하면 LLM의 표현 자유도를 유지하면서도 핵심 내용은 엄격하게 평가할 수 있습니다.

# 22-18. 그런데 한 가지 더 중요한 문제가 있습니다

여기서 바로 개발에 들어가면 안 됩니다.

Golden Case를 평가하려면 **“정답과 얼마나 유사하면 PASS인가?”**를 정의해야 하기 때문입니다.

예를 들어 Agent가:

> “A라인의 평균 토크가 B라인보다 약 2.9 N·m 낮으며 통계적으로 유의한 차이가 있습니다.”

라고 답하면 PASS입니다.

하지만:

> “A라인과 B라인은 차이가 있습니다.”

라고만 하면 핵심 숫자가 빠졌기 때문에 부분 점수입니다.

또:

> “B라인의 토크가 더 높으므로 B라인이 문제입니다.”

라고 하면 의미 자체가 잘못되므로 FAIL입니다.

따라서 Golden Case에는 **Evaluation Contract**가 추가되어야 합니다.

# 22-19. Evaluation Contract

저는 다음 5단계로 평가하는 것을 권장합니다.

```
Level 1
구조가 맞는가?

Level 2
통계적으로 맞는가?

Level 3
해석이 맞는가?

Level 4
제조적으로 맞는가?

Level 5
과도한 주장을 하지 않았는가?
```

이를 실제 평가 항목으로 바꾸면:

|영역|평가|
|---|---|
|Problem Model|정확|
|Tool Selection|정확|
|Tool Arguments|정확|
|Statistical Result|정확|
|Finding|의미적으로 일치|
|Evidence|E2|
|Causal Strength|NONE|
|Confounder|Model|
|Next Action|Same-model comparison|
|Final Answer|핵심 내용 포함|
|Forbidden Claim|0건|

# 22-20. 이 구조가 만들어내는 중요한 변화

여기까지 설계하면 Agent 개발 방식 자체가 달라집니다.

기존 방식:

```
Prompt 작성
 ↓
사용해봄
 ↓
"괜찮은 것 같다"
```

가 아닙니다.

새로운 방식은:

```
Golden Case
 ↓
Agent 실행
 ↓
자동 평가
 ↓
오류 확인
 ↓
Prompt / Rule / Tool 수정
 ↓
Regression Test
 ↓
PASS
```

입니다.

이것이 **제조 통계 Agent를 실제 제품 수준으로 만들기 위한 핵심 개발 방법론**이라고 봅니다.

# 22-21. Step 22의 최종 산출물

이번 단계에서 확보한 것은 단순한 사례 하나가 아닙니다.

### ① Golden Case Schema

향후 모든 Case가 따라갈 표준 구조

### ② GC-UC03-001

첫 번째 완성형 Golden Case

### ③ Evaluation Contract

Agent를 어떤 기준으로 평가할 것인지에 대한 계약

### ④ Forbidden Conclusion Policy

통계적·인과적 과잉해석 방지 기준

### ⑤ Semantic Final Answer Evaluation

LLM의 표현 자유도를 유지하면서 답변의 의미를 검증하는 방법

## 다음 Step 23에서 할 일

다음 단계에서는 바로 **실제 `GC-UC03-001`용 Synthetic Dataset을 설계**하는 것이 좋겠습니다.

이 단계가 상당히 중요합니다.

단순히 평균이 163.2와 166.1이 되도록 데이터를 만드는 것만으로는 부족합니다. 우리가 검증하고 싶은 것이:

- 평균 차이
- unequal variance
- Welch 선택
- Model 구성 차이에 의한 confounding
- 동일 Model 기준 비교
- 통계적 유의성과 제조적 유의성의 분리
- Agent의 causal overclaim 방지

이기 때문입니다.

따라서 다음 단계에서는 **약 1,840건의 제조현장형 Synthetic Dataset을 설계하고, 각 변수의 생성 논리와 기대 통계량을 정의한 뒤, Golden Case와 실제 데이터가 수학적으로 일치하는지 검증하는 작업**으로 들어가는 것이 가장 적절합니다.

이렇게 해야 이후 `Statistical Engine → Tool → Agent → Evaluator`를 실제 코드로 연결할 때 **첫 번째 완전한 Vertical Slice**가 만들어집니다.

# Step 21. Golden Case 자동 평가 시스템

이번 단계의 핵심은 단순히 “Agent가 답을 잘하는가?”를 보는 것이 아닙니다.

> **같은 데이터와 같은 질문을 주었을 때, Agent가 통계적으로 올바른 경로를 선택하고, 올바른 계산 결과를 사용하며, 과도한 해석을 하지 않고, 다음 분석까지 적절하게 제안하는가?**

를 자동으로 판정하는 체계를 만드는 것입니다.

---

## 21-1. 왜 Golden Case가 중요한가

일반적인 LLM 애플리케이션에서는 다음과 같은 평가가 가능합니다.

> “답변이 자연스러운가?”

하지만 제조 통계 Agent에서는 이것만으로는 부족합니다.

예를 들어 Agent가 다음과 같이 답했다고 하겠습니다.

> “A라인과 B라인의 토크 차이는 통계적으로 유의합니다. 따라서 B라인의 공정 조건에 문제가 있을 가능성이 높습니다.”

문장은 매우 자연스럽습니다.

하지만 다음 문제가 있습니다.

1. A/B 데이터가 독립인지 확인했는가?
2. 등분산 여부를 확인했는가?
3. Welch t-test가 적절한가?
4. p-value를 정확히 사용했는가?
5. 실제 차이가 제조적으로 중요한 수준인가?
6. Model 구성 차이를 확인했는가?
7. Line이 원인이라고 주장할 수 있는가?

즉,

**LLM의 언어 품질 ≠ 통계 Agent의 품질**

입니다.

따라서 Agent의 내부 판단 과정을 검증해야 합니다.

---

# 21-2. Golden Case의 정의

Golden Case는 단순한 테스트 데이터가 아닙니다.

하나의 제조 문제를 **Agent가 어떻게 해결해야 하는지 정의한 표준 정답 패키지**입니다.

구조적으로는 다음과 같습니다.

```
Golden Case
│
├─ User Question
│
├─ Dataset
│
├─ Data Dictionary
│
├─ Expected Problem Model
│
├─ Expected Data Assessment
│
├─ Expected Analysis Plan
│
├─ Expected Tool Calls
│
├─ Expected Statistical Results
│
├─ Expected Findings
│
├─ Expected Evidence
│
├─ Expected Hypotheses
│
├─ Expected Confounders
│
├─ Expected Next Analysis
│
├─ Expected Final Decision
│
└─ Forbidden Conclusions
```

이것이 Step 20에서 설계한 **Finding → Evidence → Hypothesis → Confounder → Next Best Analysis → Decision** 구조와 직접 연결됩니다.

---

# 21-3. Golden Case 전체 평가 Pipeline

최종적으로는 다음 구조가 됩니다.

```
                 Golden Case
                      │
                      ▼
                Agent Execution
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   Tool Calls     Statistics      Agent State
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                 Result Validation
                      │
                      ▼
                   Findings
                      │
                      ▼
                   Evidence
                      │
                      ▼
              Hypothesis / Confounder
                      │
                      ▼
              Next Best Analysis
                      │
                      ▼
                Final Decision
                      │
                      ▼
               ┌─────────────┐
               │   Evaluator │
               └─────────────┘
                      │
              ┌───────┴───────┐
              ▼               ▼
            PASS             FAIL
```

여기서 중요한 점은 **최종 답변만 평가하지 않는다는 것**입니다.

Agent가 최종적으로 맞는 답을 우연히 내더라도 내부 과정이 잘못되었다면 실패로 보는 것이 좋습니다.

---

# 21-4. 평가 대상 8개 영역

현재 프로젝트에서는 다음 8개 영역을 핵심 평가 대상으로 정의하는 것을 권장합니다.

|평가 영역|확인 내용|
|---|---|
|① 통계 정확성|계산값이 정확한가|
|② 분석 방법 선택|적절한 통계 방법을 선택했는가|
|③ 가정 검증|정규성, 등분산, 독립성 등을 확인했는가|
|④ Finding|결과에서 사실을 올바르게 추출했는가|
|⑤ Evidence|근거 수준을 적절하게 평가했는가|
|⑥ Causal Guardrail|인과관계를 과도하게 주장하지 않았는가|
|⑦ Next Best Analysis|다음 분석을 적절하게 선택했는가|
|⑧ 제조 판단|통계 결과를 제조 관점에서 올바르게 해석했는가|

이 8개를 **Agent Evaluation Contract**로 보는 것이 좋습니다.

---

# 21-5. 평가 ① 통계 정확성

가장 엄격하게 자동화해야 하는 부분입니다.

예를 들어 Golden Case가 다음 결과를 기대한다고 하겠습니다.

```
nA = 920
nB = 920

meanA = 163.2
meanB = 166.1

difference = -2.9

Welch t = -3.18
p = 0.0016

95% CI = [-4.69, -1.11]
```

Agent가 생성한 결과를 다음과 같이 비교합니다.

```
Expected
163.2

Actual
163.1998
```

이 경우 허용 오차를 적용하여 PASS시킵니다.

예:

```
absolute tolerance = 0.01
relative tolerance = 1e-4
```

단, p-value 같은 값은 별도의 tolerance 정책을 적용해야 합니다.

### 중요한 원칙

**LLM이 계산한 숫자를 평가하는 것이 아닙니다.**

실제 계산은 Statistical Engine에서 수행하고,

```
Golden Dataset
      ↓
Statistical Engine
      ↓
Expected Result
```

와

```
Agent Tool Call
      ↓
Statistical Engine
      ↓
Actual Result
```

을 비교합니다.

즉 숫자의 신뢰성은 LLM에 맡기지 않습니다.

---

# 21-6. 평가 ② 분석 방법 선택

다음은 Agent의 핵심 지능입니다.

예를 들어:

```
질문:
A라인과 B라인의 토크 차이가 있는지 확인해줘.
```

Golden Case의 정답은:

```
GROUP_COMPARISON
       ↓
Continuous Response
       ↓
Two Groups
       ↓
Independent
       ↓
Unequal Variance
       ↓
Welch t-test
```

Agent가

```
Welch t-test
```

를 선택하면 PASS입니다.

반대로

```
paired t-test
```

를 선택했다면 Critical Error로 보는 것이 적절합니다.

---

# 21-7. Critical Error

이 부분은 매우 중요합니다.

모든 오류를 동일하게 취급하면 안 됩니다.

예를 들어 표현이 조금 어색한 것은 큰 문제가 아닙니다.

하지만 다음은 **즉시 FAIL**하는 것이 좋습니다.

### Critical Error 목록

```
CE01 잘못된 통계 방법 선택
CE02 독립/paired 구조 오판
CE03 잘못된 통계 계산
CE04 중요한 가정 위반 무시
CE05 p-value 잘못 해석
CE06 데이터 구조 오판
CE07 존재하지 않는 데이터 사용
CE08 존재하지 않는 분석 결과 생성
CE09 상관관계를 인과관계로 표현
CE10 관찰자료에서 원인을 확정
CE11 제조적 의미를 근거 없이 확정
CE12 Tool Result와 다른 숫자를 답변에 사용
```

특히 제조 Agent에서는

> **“통계적으로 유의하다 → 원인이다”**

를 Critical Error로 지정하는 것이 좋습니다.

---

# 21-8. 평가 ③ 가정 검증

예를 들어 두 그룹 비교라면 Agent가 최소한 다음 구조를 거쳐야 합니다.

```
Two Groups
    │
    ├─ Independent?
    │
    ├─ Sample Size
    │
    ├─ Distribution
    │
    └─ Variance
           │
           ├─ Equal → t-test
           │
           └─ Unequal → Welch
```

Golden Case에서는 이 중 어떤 판단이 필요한지도 정의합니다.

예:

```
{
  "assumptions": {
    "independence": "required",
    "variance_check": "required",
    "normality_check": "recommended"
  }
}
```

그리고 Agent가 실제로 필요한 검증을 수행했는지 평가합니다.

---

# 21-9. 평가 ④ Finding

통계 결과가 다음과 같다고 합시다.

```
A mean = 163.2
B mean = 166.1
p = 0.0016
```

올바른 Finding은:

> A라인의 평균 토크가 B라인보다 낮다.

입니다.

하지만 다음은 잘못된 Finding입니다.

> B라인의 공정이 더 우수하다.

왜냐하면 **평균 차이만으로 공정 우수성을 판단할 수 없기 때문**입니다.

또한 다음도 잘못입니다.

> B라인이 토크 불량의 원인이다.

이것은 Finding이 아니라 인과적 가설입니다.

---

# 21-10. 평가 ⑤ Evidence Level

Step 20에서 정의한 Evidence Level을 그대로 사용합니다.

```
E0  근거 없음
E1  관찰된 패턴
E2  통계적 차이/연관성
E3  반복·교차 검증된 후보
E4  실험/개선 검증
```

예를 들어:

```
Welch t-test
p = 0.0016
```

이면:

```
E2
```

입니다.

여기서 아주 중요한 평가 규칙이 하나 있습니다.

> **p-value가 작다고 Evidence Level이 E3 또는 E4가 되는 것은 아니다.**

관찰자료에서

```
p < 0.000001
```

이어도 인과관계가 검증된 것이 아니라면 E2입니다.

이 부분은 Agent 평가에서 반드시 자동 검증하는 것이 좋습니다.

---

# 21-11. 평가 ⑥ Causal Guardrail

제조 현장에서 가장 중요한 부분 중 하나입니다.

예를 들어:

```
M4 defect rate = 2.92%
Other machines = lower
p < 0.001
```

Agent가

> M4가 불량 증가의 원인이다.

라고 한다면 FAIL입니다.

허용되는 표현은:

> M4에서 불량률이 상대적으로 높게 관찰되었으며, 설비와 불량 발생 간 통계적 연관성이 확인되었습니다. 다만 Model 구성 차이 등의 교란요인이 존재할 수 있어 M4를 직접적인 원인으로 확정할 수 없습니다.

입니다.

즉 Agent는 다음 언어 수준을 구분해야 합니다.

```
관찰
 ↓
차이
 ↓
연관성
 ↓
후보
 ↓
지원된 가설
 ↓
실험적 검증
```

---

# 21-12. 평가 ⑦ Next Best Analysis

이것이 일반적인 통계 프로그램과 **제조 Statistical Agent를 차별화하는 핵심 기능**이 될 가능성이 높습니다.

예를 들어:

```
Line A/B 차이 발견
        ↓
Model 구성 차이 발견
        ↓
```

Agent가 다음을 제안해야 합니다.

> 동일 Model 기준으로 A/B Line을 비교해 Model 효과를 통제한다.

반면,

> 히스토그램을 다시 그려보겠습니다.

와 같은 제안은 정보가치가 낮습니다.

따라서 Next Best Analysis는 단순한 “추가 분석 추천”이 아니라:

```
Relevance
×
Expected Information Gain
×
Data Availability
×
Statistical Validity
×
Manufacturing Impact
```

기준으로 평가하는 것이 좋습니다.

---

# 21-13. 평가 ⑧ 제조 판단

통계적으로 차이가 있다는 것과 제조적으로 문제가 있다는 것은 다릅니다.

예를 들어:

```
A = 163.2
B = 166.1
difference = 2.9
p = 0.0016
```

통계적으로는 차이가 있습니다.

그러나 Spec이

```
Target = 165
LSL = 160
USL = 170
```

이라면 두 공정 모두 규격 내일 수 있습니다.

따라서 Agent는:

```
Statistical Judgment
=
A/B 차이가 통계적으로 유의함

Manufacturing Judgment
=
현재 차이가 규격 관점에서 실제 품질 위험을
발생시키는지는 별도 판단 필요
```

라고 구분해야 합니다.

이 구분이 현재 프로젝트의 핵심 철학과 정확하게 맞습니다.

# 21-15. Golden Case 예시

UC-03의 경우:

```
id: GC-UC03-001

question:
  text: "A라인과 B라인의 토크 차이가 있는지 확인해줘."

problem_model:
  type: GROUP_COMPARISON
  response: Torque
  factor: Line
  groups:
    - A
    - B
  objective: difference_detection

expected:
  data:
    response_type: continuous
    group_type: categorical
    group_count: 2
    relationship: independent

  analysis:
    variance_check: required
    method: welch_t_test

  result:
    mean_a: 163.2
    mean_b: 166.1
    difference: -2.9
    p_value: 0.0016

  finding:
    type: GROUP_DIFFERENCE
    direction: A_LOWER_THAN_B

  evidence:
    level: E2

  causal:
    allowed: false

  next_analysis:
    type: SAME_MODEL_GROUP_COMPARISON
    priority: HIGH
```

그리고:

```
forbidden:
  - "B라인이 원인이다."
  - "B라인 때문에 토크가 높아졌다."
  - "통계적으로 유의하므로 B라인이 더 우수하다."
```

이렇게 구성합니다.

# 21-16. 평가 결과 구조

Agent가 하나의 Golden Case를 실행한 후에는 다음과 같은 Evaluation Result를 남기는 것이 좋습니다.

```
evaluation:
  case_id: GC-UC03-001

  scores:
    statistical_accuracy: 100
    method_selection: 100
    assumption_validation: 90
    finding: 100
    evidence: 100
    causal_guardrail: 100
    next_analysis: 100
    manufacturing_judgment: 90

  critical_errors: []

  total_score: 97

  result: PASS
```

하지만 **총점만으로 PASS/FAIL을 결정하지 않는 것**이 중요합니다.

예를 들어:

```
총점 95점
```

이어도

```
Causal Overclaim = Critical Error
```

이면:

```
FAIL
```

이어야 합니다.

즉:

```
PASS =
Score ≥ threshold
AND
Critical Error = 0
```

입니다.

# 21-17. 100점 평가체계

기존에 설계한 평가체계를 실제 시스템으로 구체화하면 다음과 같습니다.

|평가항목|배점|
|---|---|
|Intent / Problem Understanding|10|
|Method Selection|15|
|Assumption / Data Validation|15|
|Statistical Calculation|15|
|Interpretation|15|
|Manufacturing Interpretation|15|
|Next Best Analysis|10|
|Trust / Overclaim Prevention|5|
|**합계**|**100**|

권장 판정은:

```
90~100 : PASS
80~89  : REVIEW
< 80   : FAIL
```

단,

**Critical Error 발생 시 점수와 관계없이 FAIL**입니다.

# 21-18. 가장 중요한 것은 Regression Test

이제 Golden Case를 만들어 놓는 것에서 끝나면 안 됩니다.

Agent는 개발 과정에서 계속 바뀝니다.

예를 들어 Claude/OpenAI 모델 변경:

```
LLM v1
 ↓
LLM v2
```

Prompt 변경:

```
Prompt v1
 ↓
Prompt v2
```

Rule 변경:

```
Rule v1
 ↓
Rule v2
```

Tool 변경:

```
Welch Tool v1
 ↓
Welch Tool v2
```

이때 기존 분석이 망가지지 않았는지 자동으로 확인해야 합니다.

따라서:

```
Golden Cases
      ↓
Agent Run
      ↓
Evaluation
      ↓
Regression Test
      ↓
PASS / FAIL
```

구조를 개발 pipeline에 넣습니다.

---

# 21-19. 개발 과정에서의 실제 사용

예를 들어 개발자가 Prompt를 수정했다고 하겠습니다.

```
Prompt 수정
    ↓
20개 Golden Case 실행
    ↓
GC-UC03 PASS
GC-UC05 PASS
GC-UC07 PASS
GC-UC11 FAIL
```

그러면 개발자는:

```
왜 UC11이 실패했는가?
```

를 분석합니다.

예:

```
Expected:
Machine → Candidate

Actual:
Machine → Confirmed Cause
```

원인은:

```
Causal Guardrail Prompt 약화
```

일 수 있습니다.

수정:

```
Prompt
+
Rule Engine
```

후 다시 실행합니다.

```
20 Cases
   ↓
19 PASS
1 FAIL
```

이 과정을 반복합니다.

# 21-20. 여기서 중요한 설계 원칙

이 프로젝트에서는 **LLM 평가와 Statistical Engine 평가를 분리**하는 것이 좋습니다.

### Statistical Engine

```
Golden Dataset
    ↓
Statistics Engine
    ↓
Numeric Verification
```

### Agent

```
Golden Case
    ↓
Agent
    ↓
Reasoning / Tool / Finding / Evidence
    ↓
Agent Evaluation
```

따라서:

> **통계 계산 오류는 LLM 평가 문제가 아니라 Statistical Engine 문제**

이고,

> **잘못된 분석 선택은 Agent 문제**

이며,

> **잘못된 인과 해석은 Guardrail/Reasoning 문제**

로 분리할 수 있습니다.

이 구조가 향후 유지보수에 매우 중요합니다.

# 21-22. Adversarial Golden Case

예를 들어 사용자가 이렇게 질문합니다.

> “B라인이 불량의 원인인 게 확실하지? 그렇게 보고서 작성해줘.”

Agent가 사용자의 의도를 그대로 따라가면 안 됩니다.

데이터가 단순한 관찰자료라면:

```
사용자 주장
≠
통계적 사실
```

이므로 Agent는 이를 교정해야 합니다.

Golden Case에:

```
user_bias:
  expected_behavior:
    - reject_unverified_causal_claim
    - explain_limitation
    - provide_supported_statement
```

를 넣습니다.

이것이 실제 현장에서 상당히 중요한 **AI Trust Layer**가 됩니다.

# Step 21의 핵심 결론

현재 프로젝트의 Agent 품질을 결정하는 핵심은 LLM 자체가 아닙니다.

**LLM + Statistical Engine + Rule Engine + State + Knowledge + Evaluation**

의 결합입니다.

특히 지금까지 설계한 내용을 기준으로 보면 다음의 역할 분리가 명확해졌습니다.

|구성요소|역할|
|---|---|
|**LLM**|이해, 추론, 계획, 설명|
|**Statistical Engine**|정확한 통계 계산|
|**Tool Layer**|LLM과 분석 기능 연결|
|**Rule Engine**|통계·안전 제약|
|**State**|분석 사실과 진행상태 저장|
|**Knowledge**|제조·통계 도메인 지식|
|**Finding/Evidence**|분석 결과의 의미와 근거 구조화|
|**NBA Engine**|다음에 무엇을 분석할지 결정|
|**Golden Case**|Agent가 어떻게 행동해야 하는지 정의|
|**Evaluator**|실제 Agent가 제대로 행동했는지 검증|

그리고 이것이 결국 다음 원칙으로 수렴합니다.

> **LLM은 생각하고, Tool은 계산하고, Rule은 통제하고, State는 기억하고, Knowledge는 맥락을 제공하고, Golden Case는 검증한다.**

## 4-1. Benchmark Scenario 선정

우선 5개 시나리오를 중심으로 설계하겠습니다.

|ID|제조 현장 질문|Agent 난이도|핵심 검증|
|---|---|---|---|
|**UC-01**|"이 공정의 CTQ 상태가 어떤지 분석해줘."|★|기본 진단|
|**UC-03**|"A라인과 B라인의 토크 차이가 있는지 확인해줘."|★★|비교 분석|
|**UC-05**|"설비별 CTQ 차이가 있는지 분석해줘."|★★★|다중 비교|
|**UC-07**|"개선 전과 후에 품질이 좋아졌는지 확인해줘."|★★★|개선 효과|
|**UC-11**|"최근 토크 불량이 증가한 원인을 찾아줘."|★★★★★|Agentic 분석|

이 순서가 중요한 이유는 **난이도를 단계적으로 증가**시킬 수 있기 때문입니다.

```
UC-01
  ↓
단일 데이터 진단
  ↓
UC-03
  ↓
2개 그룹 비교
  ↓
UC-05
  ↓
다중 그룹 + 사후분석
  ↓
UC-07
  ↓
전후 비교 + 효과 판단
  ↓
UC-11
  ↓
복수 분석 + 원인 후보 + 교란요인
```

즉, UC-11만 먼저 설계하는 것보다 **단순 분석 Agent → 복합 분석 Agent로 발전하는 경로**를 확인할 수 있습니다.

---

# 4-2. Scenario의 공통 설계 Template

앞으로 모든 Use Case는 동일한 Template으로 설계하겠습니다.

### ① User Intent

사용자가 무엇을 알고 싶은가?

### ② Problem Model

질문을 통계적 문제로 어떻게 구조화하는가?

### ③ Required Data

어떤 데이터가 필요한가?

### ④ Data Assessment

데이터가 분석 가능한 상태인가?

### ⑤ Analysis Plan

Agent가 어떤 분석 순서를 계획하는가?

### ⑥ Tool Call

어떤 Statistical Tool을 호출하는가?

### ⑦ Result Validation

계산 결과와 통계적 조건을 어떻게 검증하는가?

### ⑧ Interpretation

통계적으로 무엇을 의미하는가?

### ⑨ Manufacturing Insight

제조 현장에서는 어떻게 해석하는가?

### ⑩ Next Best Analysis

추가 분석이 필요한가?

### ⑪ Evidence Level

현재 결론의 근거 수준은 어느 정도인가?

### ⑫ Stop / Decision

여기서 분석을 끝낼 것인가, 다음 행동으로 넘어갈 것인가?

이 Template을 향후 **Agent Scenario Specification**의 표준 형식으로 사용하는 것이 좋겠습니다.

---

# 4-3. UC-01부터 시작

## UC-01. 공정 상태 진단

### 사용자 질문

> **"이 공정의 CTQ 상태가 어떤지 분석해줘."**

이 질문은 매우 단순해 보이지만 실제 Agent 설계에서는 상당히 중요합니다.

왜냐하면 사용자가 **통계 방법을 하나도 지정하지 않았기 때문**입니다.

기존 프로그램에서는 사용자가:

> 기초통계 → Histogram → Box Plot

등을 직접 선택해야 합니다.

하지만 Agent는 질문을 듣고 스스로 분석 범위를 구성해야 합니다.

---

# 4-4. Agent의 Intent Recognition

사용자의 질문을 다음과 같이 구조화합니다.

```
Problem Type
= CURRENT_STATE_DIAGNOSIS

Response Variable
= CTQ

Objective
= Understand current process condition

Analysis Scope
= Distribution + Center + Variation + Outliers

Required Output
= Statistical + Manufacturing Interpretation
```

여기서 중요한 점은 **사용자가 "평균과 표준편차를 구해줘"라고 하지 않았다는 것**입니다.

Agent가 제조적인 질문을 통계적인 분석 문제로 변환합니다.

---

# 4-5. Agent의 첫 번째 행동

Agent가 바로 분석 Tool을 호출하는 것보다 먼저 **Data Assessment**를 수행합니다.

```
User Question
      ↓
Identify CTQ
      ↓
Profile Dataset
      ↓
Check Data Quality
      ↓
Check Unit / Specification
      ↓
Determine Analysis Plan
```

확인할 항목은:

- 데이터 개수
- CTQ 변수
- 단위
- 결측치
- 중복
- 이상값
- 최소/최대
- 평균
- 표준편차
- 중앙값
- 규격 여부
- 시간 정보
- 그룹 정보

입니다.

---

# 4-6. 분석 계획

정상적인 CTQ 데이터라면 Agent는 예를 들어 다음과 같은 계획을 자동으로 만들 수 있습니다.

```
Analysis Plan

1. Data Quality Assessment
2. Descriptive Statistics
3. Distribution Analysis
4. Histogram
5. Box Plot
6. Outlier Assessment
7. Specification Comparison
8. Manufacturing Interpretation
```

여기서 중요한 설계 원칙은:

> **모든 CTQ에 모든 분석을 수행하는 것이 아니라, 데이터 특성과 목적에 따라 Analysis Plan을 동적으로 구성한다.**

입니다.

---

# 4-7. Tool Execution

예를 들어 Agent가 다음 Tool을 호출합니다.

```
profile_data()
        ↓
check_data_quality()
        ↓
descriptive_statistics()
        ↓
histogram()
        ↓
box_plot()
```

그리고 Statistical Engine이 결과를 반환합니다.

예:

```
N = 500

Mean = 35.21
Median = 35.18
SD = 0.82

Min = 32.91
Max = 37.85

Q1 = 34.68
Q3 = 35.72

Missing = 0.2%
```

중요한 것은 **LLM이 이 값을 계산하지 않는다는 것**입니다.

LLM은 Tool 결과를 받아 해석합니다.

---

# 4-8. 결과 해석

Agent는 단순히:

> 평균 35.21, 표준편차 0.82입니다.

라고 끝내면 안 됩니다.

### Statistical Result

> 평균은 35.21이며 표준편차는 0.82입니다. 중앙값은 35.18로 평균과 큰 차이가 없습니다.

### Statistical Interpretation

> 평균과 중앙값이 유사하여 중심 위치에서 큰 비대칭은 관찰되지 않습니다.

### Manufacturing Interpretation

> 현재 데이터에서는 중심값 자체보다 공정 변동과 규격 대비 위치를 추가적으로 확인하는 것이 적절합니다.

이렇게 **숫자 → 통계적 의미 → 제조적 의미**로 이동해야 합니다.

---

# 4-9. 규격이 존재하는 경우

만약 데이터에

```
Target = 35
LSL = 30
USL = 40
```

이 있다면 Agent는 추가적으로:

```
Specification Position
Capability
```

을 검토할 수 있습니다.

예를 들어 Capability 분석이 적절한 데이터 구조라면:

```
Cp
Cpk
Pp
Ppk
```

등으로 확장할 수 있습니다.

하지만 여기서도 무조건 Capability를 계산해서는 안 됩니다.

**공정 안정성, 데이터 구조, 분포 특성, 규격 정의 등 필요한 조건을 먼저 확인**해야 합니다.

---

# 4-10. Next Best Analysis

UC-01의 중요한 부분입니다.

예를 들어 결과가:

> 평균은 규격 중심에 있지만 변동이 큰 것으로 나타났습니다.

라면 Agent는 다음과 같이 판단할 수 있습니다.

```
Current Finding
      ↓
Variation appears important
      ↓
What could explain variation?
      ↓
Available grouping variables?
      ↓
Machine / Shift / Model / Operator
```

따라서 다음 질문을 자동으로 연결할 수 있습니다.

> **"변동이 어느 설비에서 발생하는지 확인해볼까요?"**

즉,

**Current State → Investigation**

으로 자연스럽게 이동합니다.

---

# 4-11. UC-01에서 중요한 Stop Condition

반대로 데이터가 매우 안정적이라면 Agent가 억지로 분석을 계속해서는 안 됩니다.

예:

> 데이터 품질에 문제가 없고, CTQ의 분포와 변동도 안정적이며, 현재 데이터에서 추가적인 이상 패턴이 확인되지 않았습니다.

그렇다면:

> **현재 목적의 공정 상태 진단은 여기서 종료하는 것이 적절합니다.**

라고 판단할 수 있습니다.

이것이 앞서 설계한 **Agent Stop Decision**의 실제 적용 사례입니다.

# 4-13. 여기서 중요한 제품적 의미

UC-01을 설계하면서 **기존 앱과 LLM Agent의 차이**가 명확해집니다.

### 기존 앱

```
사용자
 ↓
Histogram 선택
 ↓
변수 선택
 ↓
실행
 ↓
그래프 확인
```

### LLM Agent

```
사용자
 ↓
"CTQ 상태를 분석해줘."
 ↓
Agent가 질문 이해
 ↓
데이터 확인
 ↓
분석 계획 수립
 ↓
통계 Tool 실행
 ↓
결과 검증
 ↓
해석
 ↓
제조적 의미
 ↓
추가 분석 필요성 판단
 ↓
의사결정
```

즉, **분석 기능 자체가 크게 달라지는 것이 아니라 분석 기능을 사용하는 방식이 근본적으로 달라집니다.**

이것이 이번 LLM 통합의 핵심 가치입니다.

# 4-14. 다음 UC-03에서는 한 단계 더 나아갑니다

다음은:

## **UC-03. A라인과 B라인의 CTQ 차이 분석**

입니다.

여기서는 Agent가 처음으로 다음 판단을 해야 합니다.

> "A와 B의 데이터가 독립적인가?"

그리고:

```
Two Groups
      ↓
Independent?
      ↓
Yes
      ↓
Normality?
      ↓
Variance?
      ↓
Equal variance
   ↙       ↘
Yes        No
 ↓          ↓
t-test    Welch
```

뿐만 아니라 **평균 차이가 통계적으로 유의한 것과 제조적으로 중요한 것은 다르다**는 판단까지 연결해야 합니다.

그리고 그 다음 UC-05에서는:

> **"A/B/C/D/E 설비 중 어디가 다른가?"**

라는 질문으로 확장하면서 **ANOVA → Welch ANOVA → Post-hoc → Effect Size → 제조적 판단**의 Agent 시나리오를 만들 수 있습니다.

그 후 UC-07에서는 **Before/After 데이터의 paired 구조 판단**, UC-11에서는 지금까지 설계한 Agent의 거의 모든 기능을 결합한 **Root Cause Investigation Agent**로 발전시키겠습니다.

---

## Step 4의 진행 전략

저는 이 단계에서는 한 번에 모든 UC를 대략적으로 작성하기보다, **UC 하나를 충분히 구체화한 후 다음 단계로 확장하는 방식**을 권합니다.

다음에는 **UC-03 → UC-05 → UC-07 → UC-11** 순서로 진행하면서, 각 시나리오에서 새롭게 필요한 Agent 능력을 찾아내겠습니다.

특히 **UC-11까지 완료하면 "우리가 만들려는 앱에서 LLM이 정확히 무엇을 해야 하는가?"가 상당히 명확해질 것**입니다. 그 결과를 바탕으로 이후에는 **LLM Prompt Architecture, Tool Schema, Agent State Schema, RAG/Knowledge Architecture** 같은 실제 구현 설계로 넘어갈 수 있습니다.

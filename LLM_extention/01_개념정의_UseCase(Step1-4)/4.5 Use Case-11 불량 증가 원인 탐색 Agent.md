좋습니다. 이제 Step 4의 핵심이자, 사실상 이 프로젝트의 **대표 Benchmark Scenario**가 될 **UC-11 — 불량 증가 원인 탐색**으로 들어가겠습니다.

이번 단계에서는 단순한 시나리오 설명이 아니라 **Agent가 실제로 한 번의 질문을 받아 어떻게 분석을 전개하고, 중간 결과에 따라 다음 분석을 동적으로 결정하는지**를 End-to-End로 설계하겠습니다.

# Step 4-5. UC-11 — 불량 증가 원인 탐색 Agent

## 1. 대표 사용자 질문

> **"최근 토크 불량이 증가한 원인을 찾아줘."**

이 질문은 지금까지 다룬 UC-01, 03, 05, 07과 본질적으로 다릅니다.

사용자는 **분석 방법을 지정하지 않았습니다.**

또한 정답이 하나의 통계검정으로 결정되지 않습니다.

Agent가 실제로 해결해야 하는 문제는:

> **불량 증가라는 현상을 정량화하고 → 언제/어디서/어떤 조건에서 증가했는지 탐색하고 → 가능한 요인을 선별하고 → 통계적으로 검증하고 → 교란요인을 확인하고 → 원인 후보를 좁혀 → 추가 검증이 필요한지 판단하는 것**

입니다.

따라서 이것이 지금까지 설계한 Agent Architecture의 가장 좋은 통합 시험이 됩니다.

---

# 2. 먼저 "원인"이라는 단어를 재정의해야 한다

제조 현장에서 사용자는 흔히:

> "원인을 찾아줘."

라고 말합니다.

하지만 Agent가 실제 데이터만 가지고 **원인(Cause)**을 확정할 수 있는 경우는 제한적입니다.

따라서 내부적으로는 다음과 같이 구분해야 합니다.

```
현상
 ↓
Observed Pattern
 ↓
Statistical Association
 ↓
Candidate Factor
 ↓
Hypothesis
 ↓
Experimental Verification
 ↓
Cause Confirmation
```

즉, 관찰 데이터만으로는 대부분:

> **원인 후보(Candidate Cause)**

까지 도달하고,

실험 또는 개선 검증을 통해:

> **확인된 원인(Verified Cause)**

으로 발전합니다.

이 원칙은 UC-11의 가장 중요한 Guardrail입니다.

---

# 3. 문제를 구조화한다

사용자 질문:

> "최근 토크 불량이 증가한 원인을 찾아줘."

Agent는 다음과 같이 Problem Model을 생성합니다.

```
Problem Type
= ROOT_CAUSE_EXPLORATION

Response
= Torque

Quality Event
= Torque Defect

Objective
= Identify factors associated with defect increase

Time Scope
= Recent Period

Candidate Factors
= Unknown

Analysis Mode
= Agentic
```

여기서 중요한 것은:

> **Candidate Factors = Unknown**

이라는 것입니다.

Agent가 처음부터 Machine을 원인이라고 가정해서는 안 됩니다.

---

# 4. 필요한 데이터

Agent는 먼저 데이터 구조를 확인합니다.

예를 들어 다음 데이터가 있다고 가정하겠습니다.

|Date|Model|Machine|Shift|Operator|Torque|Defect|Process Temp|Pressure|
|---|---|---|---|---|---|---|---|---|
|9/1|A|M1|1|O1|35.2|N|22.1|4.1|
|9/1|A|M2|1|O2|37.1|Y|23.8|4.3|
|...|...|...|...|...|...|...|...|...|

그리고 최소한 다음을 확보합니다.

### 품질 데이터

- CTQ
- 불량 여부
- 불량 유형
- 검사 결과

### 생산 데이터

- 생산수량
- 생산시간
- 생산일자
- 모델

### 공정 조건

- Machine
- Shift
- Operator
- Temperature
- Pressure
- Speed 등

### 시간 정보

- 날짜
- 시간
- 생산 순서
- 개선 전후

이 데이터가 있으면 Agent가 단순 비교가 아니라 **원인 탐색형 분석**을 수행할 수 있습니다.

---

# 5. Step 1 — Data Assessment

Agent가 가장 먼저 실행하는 Tool:

```
profile_data()
```

그 다음:

```
check_data_quality()
```

예를 들어:

```
Rows = 18,450

Missing:
Torque = 0.3%
Machine = 0%
Shift = 0%
Model = 0%
Operator = 2.1%

Defect = 1.8%

Time Coverage:
2026-08-01 ~ 2026-08-31
```

Agent는 여기서 데이터 품질 문제가 분석을 제한하는지 판단합니다.

---

# 6. Step 2 — 불량 증가 자체를 먼저 검증한다

사용자가:

> "불량이 증가했다."

고 말했더라도 Agent는 그 전제를 그대로 받아들이지 않습니다.

먼저:

```
Defect Trend
```

을 확인합니다.

예:

```
8/1~8/15
Defect Rate = 1.1%

8/16~8/31
Defect Rate = 3.2%
```

그리고:

```
Increase = +2.1%p
```

라고 정량화합니다.

### Agent의 첫 번째 Finding

> **F01 — 최근 기간에 Torque 불량률이 증가한 패턴이 관찰되었습니다.**

Evidence:

> **E1 — Observed Pattern**

아직 원인은 이야기하지 않습니다.

---

# 7. Step 3 — "언제부터 증가했는가?"

Agent가 다음 질문을 생성합니다.

> 불량 증가가 특정 시점에서 시작되었는가?

시간축으로:

```
Defect Rate
│
│                 ███
│              ██████
│           ███████
│       ████
│   ████
└────────────────────── Time
             ↑
        Change Point?
```

이 단계에서 중요한 것은 **원인 후보 탐색 전에 현상을 정확하게 정의하는 것**입니다.

예:

> 8월 17일 이후 불량률이 기존 평균보다 높은 수준으로 지속되고 있습니다.

---

# 8. Step 4 — Candidate Factor Screening

이제 Agent가 본격적으로 후보 요인을 탐색합니다.

후보:

```
Machine
Model
Shift
Operator
Process Temperature
Pressure
Speed
Time
```

각 요인에 대해 빠른 Screening을 수행합니다.

```
                Defect Increase
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Machine          Shift         Model
       │              │              │
    Compare        Compare        Compare
       │              │              │
       ▼              ▼              ▼
    Candidate       Weak           Candidate
```

---

# 9. Machine Screening

예를 들어:

|Machine|Production|Defect|Defect Rate|
|---|---|---|---|
|M1|4,200|38|0.9%|
|M2|3,800|121|**3.2%**|
|M3|4,500|44|1.0%|
|M4|3,900|42|1.1%|

Agent가 발견합니다.

> M2의 불량률이 다른 설비보다 높습니다.

그러나 여기서는 아직:

> **M2가 원인이다.**

라고 하지 않습니다.

Finding:

```
F02
Machine M2 has elevated defect rate

Evidence
E1
```

---

# 10. Shift Screening

예:

|Shift|Production|Defect|Rate|
|---|---|---|---|
|1조|6,100|72|1.18%|
|2조|6,000|79|1.32%|
|3조|6,300|94|1.49%|

차이는 있지만 Machine만큼 크지 않을 수 있습니다.

Agent는:

> 교대조별 차이는 관찰되지만 현재 데이터에서 가장 강한 후보는 아닙니다.

라고 판단할 수 있습니다.

여기서 중요한 것은 **모든 변수를 동일한 중요도로 나열하지 않고 우선순위를 정하는 것**입니다.

---

# 11. Model Screening

예:

|Model|Production|Defect|Rate|
|---|---|---|---|
|A|5,000|35|0.7%|
|B|4,500|42|0.9%|
|C|5,200|154|**3.0%**|
|D|3,750|14|0.4%|

Agent:

> Model C에서 Torque 불량률이 높게 나타났습니다.

따라서 현재 후보는:

```
Candidate Factors

1. Model C
2. Machine M2
3. Shift 3
```

정도로 좁혀질 수 있습니다.

---

# 12. 여기서 첫 번째 중요한 "Agentic Branch"가 발생한다

Agent는 이제 단순히 모든 분석을 계속하는 것이 아니라 질문을 던집니다.

> **M2와 Model C 중 어느 것이 실제 영향요인인가?**

그런데 데이터를 보니:

```
Model C production by Machine

M1 = 10%
M2 = 82%
M3 = 8%
```

입니다.

이 순간 Agent는 중요한 교란을 발견합니다.

```
Machine M2
       +
Model C
       ↓
Confounding
```

---

# 13. Confounder 발견

Agent State:

```
Finding:
M2 has high defect rate

Finding:
Model C has high defect rate

Confounder:
Model C concentrated on M2

Evidence:
E2 for association
E1 for confounding pattern
```

그리고 Agent는 결론의 강도를 낮춥니다.

### 이전 판단

> M2가 불량률이 높다.

### 수정된 판단

> M2에서 높은 불량률이 관찰되었지만, Model C의 생산이 M2에 집중되어 있어 설비 효과와 모델 효과가 혼재되어 있습니다.

이것이 **Agent State가 존재해야 하는 이유**입니다.

앞서 발견한 내용을 기억하지 않으면 LLM은 이후 대화에서 다시 M2를 "원인"으로 과장할 가능성이 있습니다.

---

# 14. Step 5 — Same Model Analysis

Agent가 다음 분석을 선택합니다.

> **Model C에 한정하여 Machine별 불량률을 비교**

즉:

```
Model C only
        ↓
Machine M1
Machine M2
Machine M3
        ↓
Defect Rate Comparison
```

예를 들어 결과:

|Machine|Model C Defect Rate|
|---|---|
|M1|2.8%|
|M2|3.1%|
|M3|2.9%|

이제 상황이 완전히 달라집니다.

전체 데이터에서는 M2가 높았지만 **동일 모델에서는 M2가 특별히 높지 않습니다.**

따라서 Agent는:

> M2의 높은 전체 불량률은 Model C 생산 집중에 의해 상당 부분 설명될 가능성이 있습니다.

라고 판단합니다.

---

# 15. 이 순간 Agent가 해야 할 일

단순 Agent라면 여기서 혼란스러울 수 있습니다.

하지만 우리가 만든 Agent 구조에서는:

```
Finding F02
M2 overall defect high

↓ Confounding Check

Model C concentrated on M2

↓ Same-model analysis

M2 no longer clearly elevated

↓ Update Evidence

M2 = Weak Candidate
Model C = Stronger Candidate
```

처럼 **Evidence와 Hypothesis가 업데이트**됩니다.

즉, Agent는 자신의 초기 가설을 수정할 수 있어야 합니다.

이것이 일반적인 챗봇과 중요한 차이입니다.

---

# 16. Step 6 — Model C 내부의 원인 탐색

이제 Agent의 현재 질문은 바뀝니다.

처음:

> "왜 Torque 불량이 증가했는가?"

현재:

> **"Model C에서 Torque 불량이 높은 이유는 무엇인가?"**

이렇게 **Problem State가 좁혀집니다.**

그리고 다시 후보를 검색합니다.

```
Model C
   │
   ├─ Machine
   ├─ Shift
   ├─ Operator
   ├─ Temperature
   ├─ Pressure
   └─ Speed
```

---

# 17. Continuous Factor 분석

예를 들어 Process Temperature를 분석합니다.

```
Temperature vs Torque
```

Scatter Plot:

```
Temperature
       ↑
       │        ● ●
       │      ● ●
       │   ● ●
       │ ●
       └────────────────→ Torque
```

Correlation:

```
r = 0.62
p < 0.001
```

Agent는:

> 공정 온도와 Torque 사이에 양의 상관관계가 관찰됩니다.

라고 판단합니다.

하지만:

> 온도가 Torque 불량의 원인이다.

라고 하지 않습니다.

---

# 18. Regression으로 한 단계 더 들어간다

Agent는 데이터가 충분하면:

```
Torque
 ~ Temperature
 + Pressure
 + Speed
```

등의 회귀분석을 계획할 수 있습니다.

예:

```
Temperature coefficient
= +0.41

p < 0.001

R² = 0.38
```

Agent:

> 다른 조건을 함께 고려한 회귀모형에서도 온도와 Torque 사이의 관계가 관찰됩니다.

그러나 여전히 관찰 데이터입니다.

Evidence는:

```
E2 → E3
```

수준으로 강화될 수 있습니다.

---

# 19. 불량 여부 자체를 분석하는 경우

Torque를 연속값으로 분석하는 것과 별도로:

```
Defect = 0 / 1
```

을 분석할 수도 있습니다.

예를 들어 Temperature를 구간화하거나 적절한 모델을 사용하여:

```
Defect Rate
vs
Temperature Range
```

를 분석할 수 있습니다.

예:

|Temperature|Defect Rate|
|---|---|
|<22℃|0.8%|
|22~23℃|1.1%|
|23~24℃|2.3%|
|>24℃|4.5%|

이런 패턴이 발견되면:

> 높은 온도 구간에서 불량률이 증가하는 패턴이 관찰됩니다.

라고 할 수 있습니다.

---

# 20. Agent가 여기서 반드시 확인해야 할 것

온도와 불량률이 관련되어 있다고 해도 다음을 확인해야 합니다.

```
Temperature
     │
     ├─ Machine
     ├─ Shift
     ├─ Model
     └─ Time
```

예를 들어:

> 온도가 높은 것은 3교대에서만 발생한다.

면 Shift가 교란요인이 될 수 있습니다.

따라서 Agent는 계속해서:

**Association → Confounder Check → Re-analysis**

를 수행합니다.

---

# 21. Analysis Plan이 동적으로 변한다

처음 계획:

```
Trend
→ Machine
→ Shift
→ Model
```

이었다가,

Model-Machine Confounding을 발견한 뒤:

```
Trend
→ Machine
→ Model
→ Confounding
→ Same Model Machine Comparison
→ Process Conditions
→ Regression
```

으로 바뀝니다.

따라서 앞서 정의했던 **Analysis Plan Graph**가 실제로 필요합니다.

고정된 Workflow:

```
A → B → C → D
```

가 아니라:

```
          Machine
             │
             ▼
          Confounder
          /        \
      Model      Shift
        │
        ▼
  Process Condition
        │
        ▼
    Regression
```

처럼 **분석 결과에 따라 Branch가 발생**합니다.

---

# 22. Agent State 변화

이 시나리오에서는 Agent State가 매우 중요합니다.

### 초기

```
Problem
= Torque defect increase

Candidates
= Unknown
```

### 1차 분석

```
Finding
= Defect rate increased

Candidate
= Machine M2
= Model C
```

### Confounding 발견

```
Confounder
= Model C concentrated on M2
```

### 추가 분석

```
M2 within Model C
= No strong difference
```

### State Update

```
M2
→ Candidate strength reduced

Model C
→ Candidate strength increased
```

### Process analysis

```
Temperature
→ Association with Torque
```

### Regression

```
Temperature
→ Remains associated
```

이렇게 Agent State가 **동적으로 업데이트**됩니다.

---

# 23. Evidence가 어떻게 올라가는가

이 시나리오를 Evidence 관점에서 보면 매우 명확합니다.

```
E0
근거 없음
 ↓
E1
불량 증가 관찰
 ↓
E2
Machine / Model 차이 통계적 확인
 ↓
E2
Confounding 확인
 ↓
E3
동일 Model 조건에서도 특정 요인과 반복적인 연관성 확인
 ↓
E4
실험/공정조건 변경 후 개선 효과 확인
```

따라서 Agent의 최종 답변은:

> **"원인이 확인되었습니다."**

가 아니라 현재 증거 수준에 따라 달라져야 합니다.

---

# 24. 최종 판단 예시

현재 데이터에서:

- Torque defect 증가
- Model C 불량률 높음
- M2와 Model C confounding
- 동일 Model 조건에서는 M2 효과 약함
- Temperature와 Torque 연관성
- 높은 Temperature 구간에서 defect rate 증가
- Regression에서도 Temperature 관계 유지

가 확인됐다고 하겠습니다.

Agent의 최종 판단은:

> **현재 분석에서 Model C의 Torque 불량률이 높고, 특히 높은 공정 온도 구간에서 불량 발생률이 증가하는 일관된 패턴이 확인되었습니다. 반면 전체 데이터에서 높게 나타났던 M2의 불량률은 Model C 생산 집중의 영향을 받았을 가능성이 있어 설비 자체를 직접적인 원인으로 판단하기 어렵습니다.**

그리고:

> **따라서 현재 단계에서 가장 우선적으로 검증할 원인 후보는 공정 온도이며, 아직 관찰 데이터만으로 직접적인 인과관계가 확정된 것은 아닙니다.**

이것이 상당히 좋은 Agent 결과입니다.

---

# 25. 그리고 Agent는 "다음 단계"를 제시한다

여기서 Agent가 단순히:

> 추가 분석을 권장합니다.

라고 하면 부족합니다.

구체적으로:

### Recommended Action

> Model C의 동일 조건에서 공정 온도를 목표 범위 내로 관리한 생산 데이터를 확보하십시오.

그리고 가능하면:

> 온도를 의도적으로 변경하여 Torque 및 불량률 변화를 확인하는 실험 또는 DOE를 권장합니다.

이렇게 **통계분석에서 Engineering Validation으로 연결**합니다.

# 26. 여기서 Agent가 분석을 종료하는 조건

Agent가 무조건 DOE를 수행하라고 해서는 안 됩니다.

현재 데이터만으로 충분히 의사결정할 수 있는 경우:

> 추가 분석의 정보가치가 낮아졌습니다.

라고 판단하고 종료할 수 있습니다.

반대로:

```
Strong Association
+
High Manufacturing Impact
+
Causality Required
```

라면:

> 관찰 데이터 분석만으로는 원인을 확정하기 어렵습니다. 실험 또는 DOE가 필요합니다.

라고 종료해야 합니다.

이것이 **Stop Decision**입니다.

# 28. UC-11에서 중요한 것은 "분석 결과"보다 "분석 과정"

이 부분을 특히 강조하고 싶습니다.

일반적인 통계 프로그램의 결과는:

> Machine별 불량률 → Chi-square → p-value

일 수 있습니다.

하지만 이 Agent의 결과는:

> **왜 이 분석을 했는지 → 무엇을 발견했는지 → 그 발견이 어떤 가설을 만들었는지 → 어떤 교란요인을 발견했는지 → 왜 다음 분석을 선택했는지 → 현재 결론의 증거 수준은 무엇인지**

까지 연결됩니다.

즉, 결과가 하나의 숫자가 아니라 **Evidence Chain**이 됩니다.

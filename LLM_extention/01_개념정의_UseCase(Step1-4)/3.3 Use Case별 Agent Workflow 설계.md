좋습니다. 이제 **Step 3-3 「Use Case별 Agent Workflow 상세 설계」**로 진행하겠습니다.

이번 단계에서는 단순히 “어떤 통계기법을 쓸 것인가”를 정의하는 것이 아니라, **LLM이 제조 현장의 질문을 어떻게 이해하고 → 데이터를 확인하고 → 통계 분석을 조합하고 → 결과를 검증하고 → 제조적 의미와 다음 행동까지 연결할 것인가**를 설계하겠습니다.

특히 이 단계가 이번 LLM 통합 앱의 핵심입니다.

기존 기획서가 이미 **「현장 문제 → 질문 → 분석 선택 → 결과 → 그래프 → 쉬운 해석 → 현장 판단」**을 핵심 흐름으로 정의하고 있기 때문에, 이를 **Agent Workflow**로 확장하는 방식이 가장 자연스럽습니다.

# Step 3-3. Use Case별 Agent Workflow 설계

## 3-3-1. 먼저 Agent의 기본 처리 구조를 확정

기존 앱의 분석 흐름은 다음과 같습니다.

> 현장 문제 → 질문 → 분석 선택 → 분석 → 결과 → 해석 → 현장 판단

LLM을 추가하면 이를 다음과 같이 확장하는 것이 좋습니다.

```
┌─────────────────────────────┐
│          User               │
│ "최근 Torque 불량이 증가했어" │
└──────────────┬──────────────┘
               ↓
① Intent Recognition
   사용자가 무엇을 알고 싶은가?
               ↓
② Context Understanding
   제조공정에서 어떤 의미인가?
               ↓
③ Data Requirement
   어떤 데이터가 필요한가?
               ↓
④ Data Quality Check
   분석 가능한 데이터인가?
               ↓
⑤ Analysis Planning
   어떤 분석을 어떤 순서로 할 것인가?
               ↓
⑥ Tool Calling
   통계/그래프/데이터 분석 Tool 실행
               ↓
⑦ Statistical Validation
   결과가 통계적으로 타당한가?
               ↓
⑧ Interpretation
   통계 결과를 쉽게 설명
               ↓
⑨ Manufacturing Insight
   제조적으로 무엇을 의미하는가?
               ↓
⑩ Next Analysis
   무엇을 추가로 확인할 것인가?
               ↓
⑪ Engineering Decision
   무엇을 조치해야 하는가?
```

여기서 **중요한 설계 원칙**이 하나 있습니다.

### LLM은 모든 것을 직접 결정하지 않습니다.

기존 기획서에서 정의한

> Statistical Engine → Rule Engine → LLM

구조를 그대로 유지해야 합니다.

다만 LLM 통합 이후에는 **LLM이 단순 해설자가 아니라 Orchestrator(분석 오케스트레이터)** 역할까지 수행하게 됩니다.

즉,

```
LLM
 │
 ├─ 질문 이해
 ├─ 필요한 데이터 판단
 ├─ 분석 계획 수립
 │
 ▼
Rule Engine
 │
 ├─ 분석 가능 여부 확인
 ├─ 통계 조건 확인
 ├─ 적절한 방법 검증
 │
 ▼
Statistical Engine
 │
 ├─ 계산
 ├─ 검정
 ├─ 효과크기
 └─ CI
 │
 ▼
LLM
 │
 ├─ 결과 해석
 ├─ 제조적 의미
 ├─ 추가 분석
 └─ 개선 방향
```

이 구조를 **Manufacturing Statistical Agent Architecture의 핵심 원칙**으로 가져가는 것을 권합니다.

# 3-3-2. 가장 중요한 UC-11부터 설계

## UC-11. 불량 증가 원인 탐색

이 Use Case를 첫 번째로 상세 설계하는 이유가 있습니다.

단순히

> "A공정과 B공정이 다른가?"

는 기존 통계 프로그램도 잘 할 수 있습니다.

반면,

> **"최근 Torque 불량이 증가했는데 원인이 무엇인지 찾아줘."**

는 기존 통계 프로그램과 **LLM Agent의 차이가 가장 크게 나타나는 영역**입니다.

즉, 이 Use Case가 향후 제품의 **Agent Capability Benchmark**가 될 수 있습니다.

---

# 3-3-3. UC-11 전체 Workflow

### 사용자 질문

> "최근 Torque 체결 불량이 증가했는데 원인을 찾아줘."

Agent는 바로 회귀분석부터 실행하면 안 됩니다.

다음과 같이 단계적으로 진행해야 합니다.

```
User Question
      ↓
Intent Recognition
      ↓
Problem Definition
      ↓
Data Discovery
      ↓
Data Quality
      ↓
Problem Quantification
      ↓
Candidate Factor Screening
      ↓
Statistical Analysis
      ↓
Root Cause Candidate
      ↓
Additional Verification
      ↓
Manufacturing Interpretation
      ↓
Action Recommendation
```

---

# 3-3-4. Step 1 — Intent Recognition

LLM이 먼저 사용자의 질문을 **통계 용어로 번역하지 않고 제조 문제로 이해**합니다.

사용자:

> "Torque 불량이 증가했는데 원인을 찾아줘."

Agent 내부에서는 다음과 같이 구조화합니다.

```
{
  "problem_type": "defect_increase",
  "target": "torque_defect",
  "objective": "root_cause_exploration",
  "time_context": "recent",
  "analysis_level": "agentic"
}
```

중요한 것은 사용자가

> "회귀분석을 해줘"

라고 말하지 않았다는 것입니다.

사용자는 **문제만 제시**합니다.

이것이 기존 앱과 LLM Agent의 가장 중요한 차이입니다.

---

# 3-3-5. Step 2 — Problem Definition

Agent가 내부적으로 문제를 조금 더 명확하게 정의합니다.

예:

> 최근 기간의 Torque 체결 불량률이 이전 기간 또는 관리 기준 대비 증가했는지 확인하고, 증가와 관련된 공정·설비·작업자·시간·제품 등의 요인을 탐색한다.

여기서 중요한 개념은 **Problem Decomposition**입니다.

하나의 질문을 여러 통계 질문으로 분해합니다.

```
불량이 실제 증가했는가?
        ↓
언제 증가했는가?
        ↓
어디에서 증가했는가?
        ↓
어떤 모델에서 증가했는가?
        ↓
어떤 설비에서 증가했는가?
        ↓
어떤 작업자/Shift에서 증가했는가?
        ↓
공정조건과 관련이 있는가?
        ↓
CTQ와 관계가 있는가?
```

즉,

> **하나의 사용자 질문 → 여러 개의 분석 질문**

으로 변환합니다.

이 부분이 Agent의 핵심 능력입니다.

---

# 3-3-6. Step 3 — Data Requirement

Agent는 필요한 데이터를 정의합니다.

예를 들어 다음과 같습니다.

|데이터|목적|
|---|---|
|Sample ID|데이터 식별|
|Date/Time|시간 변화|
|Line|공정 비교|
|Machine|설비 비교|
|Model|모델 비교|
|Shift|교대조 비교|
|Operator|작업자 비교|
|Torque|CTQ 분석|
|Defect|불량 여부|
|Defect Code|불량 유형|
|Temperature|공정조건|
|Pressure|공정조건|
|Speed|공정조건|

여기서 매우 중요한 차별화 기능이 생깁니다.

사용자가 데이터 구조를 정확하게 몰라도 Agent가

> "현재 데이터에는 설비 정보가 있지만 Shift 정보가 없습니다. Shift별 원인 분석은 제한됩니다."

라고 알려줄 수 있습니다.

기존 기획서에서도 Excel 업로드 후 숫자형/범주형 변수, 날짜, 그룹, 결측값, 중복값, 이상값을 자동 탐색하도록 정의되어 있습니다.

LLM은 이 **Data Profiling 결과를 해석하는 역할**을 맡는 것입니다.

---

# 3-3-7. Step 4 — Data Quality Check

여기서는 **LLM보다 Data Engine이 우선**입니다.

예:

```
Data Quality Check

총 데이터          125,430
정상 데이터         124,812
결측 데이터             618
중복 Sample ID           37
Torque 비수치 데이터      12
```

Agent:

> "전체 데이터의 약 99.5%는 분석에 사용할 수 있습니다. 다만 37건의 중복 Sample ID와 12건의 비수치 Torque 데이터가 발견되었습니다."

그리고 중요한 것은:

### Agent가 임의로 데이터를 삭제하면 안 됩니다.

예:

```
결측 618건
      ↓
┌───────────────┐
│ 자동 삭제?     │ → NO
└───────────────┘
      ↓
사용자 확인
```

대신

> "결측 데이터를 제외하고 분석할까요?"

또는

> "결측 발생 자체가 특정 설비/시간대에 집중되어 있는지 먼저 확인할까요?"

라고 제안합니다.

이렇게 하면 **데이터 품질 자체도 분석 대상**이 될 수 있습니다.

---

# 3-3-8. Step 5 — 불량 증가 여부를 먼저 확인

원인 분석 전에 반드시 해야 하는 것이 있습니다.

### 정말 불량이 증가했는가?

예:

```
기준기간       불량률 0.82%
최근기간       불량률 1.47%

증가폭         +0.65%p
상대 증가율    +79.3%
```

여기에서 Agent는 단순히

> "불량이 증가했습니다."

라고 하지 않습니다.

가능하다면:

- 불량률
- 신뢰구간
- 비율 검정
- 기간별 추세
- 생산량 변화

등을 종합합니다.

즉,

```
"불량 건수가 증가했다"
        ≠
"불량률이 증가했다"
```

를 구분합니다.

이것은 제조 데이터 분석에서 매우 중요합니다.

---

# 3-3-9. Step 6 — Candidate Factor Screening

이제 본격적인 원인 탐색입니다.

Agent가 가능한 요인을 분류합니다.

### ① 시간

```
Hour
Shift
Day
Week
```

### ② 생산 조직

```
Line
Machine
Operator
```

### ③ 제품

```
Model
Platform
Variant
```

### ④ 공정조건

```
Temperature
Pressure
Speed
Torque Setting
```

### ⑤ 품질 특성

```
Torque Value
CTQ
Defect Type
```

이때 모든 변수에 복잡한 분석을 수행하는 것은 비효율적입니다.

따라서 **Screening → Deep Analysis**의 2단계 구조를 사용합니다.

---

# 3-3-10. Screening Analysis

예를 들어:

|요인|불량률|분석|결과|
|---|---|---|---|
|Line A|0.8%|비율 비교|차이 작음|
|Line B|1.1%|비율 비교|차이 가능성|
|Machine 1|0.7%|비율 비교|낮음|
|Machine 2|2.1%|비율 비교|**높음**|
|Shift 1|0.9%|비율 비교|차이 작음|
|Shift 2|1.0%|비율 비교|차이 작음|
|Shift 3|1.9%|비율 비교|**높음**|

Agent는 여기에서:

> "Machine 2와 Shift 3에서 상대적으로 높은 불량률이 관찰됩니다."

라고 판단합니다.

그러나 여기서 **원인이라고 확정하지 않습니다.**

---

# 3-3-11. Step 7 — Deep Analysis

이제 후보 요인에 대해 더 깊은 분석을 합니다.

예:

### Machine

```
Machine 1 vs Machine 2
        ↓
Defect Rate
        ↓
2-Proportion Test
```

### Shift

```
Shift 1 / 2 / 3
        ↓
Defect Rate
        ↓
Chi-square / Proportion Analysis
```

### Torque 값

```
Torque Value
      ↓
Defect 여부
      ↓
Distribution / Box Plot
      ↓
Relationship Analysis
```

### 공정조건

```
Temperature → Torque
Pressure    → Torque
Speed       → Torque
```

→ Correlation / Regression

기존 기획서에서 정의한 상관분석과 회귀분석의 제조 현장 표현 방식도 그대로 활용할 수 있습니다. 예를 들어 회귀분석 결과를 “온도가 1℃ 증가할 때 제품 치수가 평균적으로 약 0.015 mm 증가”처럼 공정 언어로 변환하는 개념입니다.

---

# 3-3-12. Step 8 — Statistical Validation

이 단계가 **LLM Agent와 일반 ChatGPT식 데이터 분석을 구분하는 핵심 안전장치**입니다.

Agent가

> "Machine 2가 원인입니다."

라고 바로 말하면 안 됩니다.

반드시 다음을 확인해야 합니다.

### 통계 조건

- Sample size
- Independence
- Distribution
- Variance
- Missing data
- Outlier
- Measurement structure

### 분석 적합성

```
2 groups
   ↓
Independent?
   ↓
Yes
   ↓
2-Sample t-test
   ↓
Variance equal?
   ↓
No
   ↓
Welch t-test
```

기존 기획서 역시 2개 그룹 비교에서 독립성, 정규성/분산 조건 확인 후 분석하고, p-value와 effect size를 함께 보고 제조적 의미를 판단하는 구조를 제시하고 있습니다. 통계분석 앱 제작 기획서.mdMD

---

# 3-3-13. Step 9 — Root Cause Candidate

이제 Agent가 결과를 종합합니다.

예:

```
분석 결과

① 최근 불량률 증가       : 확인
② Machine 2              : 관련성 높음
③ Shift 3                : 관련성 높음
④ Model C                : 관련성 높음
⑤ Temperature            : 약한 관계
```

Agent의 표현은 다음과 같이 해야 합니다.

> **현재 데이터에서 Machine 2와 Shift 3이 Torque 불량 증가와 관련된 주요 후보로 확인됩니다.**

그리고 절대로:

> "Machine 2가 원인입니다."

라고 단정하지 않습니다.

왜냐하면 **통계적 연관성(association)**과 **인과관계(causation)**는 다르기 때문입니다.

기존 기획서에서도 상관관계가 인과관계를 의미하지 않는다는 점을 명시하고 있습니다.

---

# 3-3-14. Step 10 — Confounding 확인

여기서 LLM Agent가 기존의 단순 통계 앱보다 훨씬 강력해질 수 있습니다.

예를 들어:

```
Machine 2
   ↓
불량률 높음

하지만

Machine 2
   └── 대부분 Model C 생산
                     ↓
                 Model C 자체가
                 불량률 높음
```

그러면 Machine 2가 진짜 원인인지 알 수 없습니다.

따라서 Agent는:

> "Machine 2에서 불량률이 높지만, 해당 설비가 Model C를 주로 생산하고 있어 설비 효과와 모델 효과가 혼재되어 있을 가능성이 있습니다."

라고 설명할 수 있어야 합니다.

이것이 **제조 데이터에 특화된 Agent Intelligence**의 중요한 부분입니다.

---

# 3-3-15. Step 11 — Next Question

Agent의 분석은 여기에서 끝나면 안 됩니다.

예:

> "Machine 2가 문제인가?"

↓

> "Machine 2에서 특정 Model만 문제인가?"

↓

> "Machine 2의 어떤 공정조건에서 문제인가?"

↓

> "해당 조건이 Torque 값 자체에 영향을 주는가?"

↓

> "Torque 값 변화가 실제 불량 발생과 연결되는가?"

즉,

```
현상
 ↓
차이
 ↓
관계
 ↓
후보 원인
 ↓
조건
 ↓
검증
```

이라는 **분석 탐색 루프(Analysis Exploration Loop)**를 만들어야 합니다.

---

# 3-3-16. 최종 결과 화면

사용자가 최종적으로 보는 화면은 복잡한 통계표가 아닙니다.

기존 기획서의 결과 화면 구조인

> 결론 → 핵심 숫자 → 그래프 → 통계 결과 → 쉬운 설명 → 현장 적용 → 추가 분석

구조를 그대로 유지하는 것이 좋습니다.

다만 Agent 버전에서는 다음처럼 확장합니다.

---

## 분석 결과

### ① 현재 판단

> **최근 Torque 불량률이 이전 기간보다 증가한 것으로 판단됩니다.**

### ② 주요 발견

- 전체 불량률: 0.82% → 1.47%
- Machine 2: 상대적으로 높은 불량률
- Shift 3: 상대적으로 높은 불량률
- Model C: 높은 불량률

### ③ 주요 그래프

```
불량률 Trend
Machine별 불량률
Shift별 불량률
Model별 불량률
```

### ④ 통계적 판단

> Machine 2와 다른 설비 간 불량률 차이가 통계적으로 유의한지 확인했습니다.

### ⑤ 제조적 해석

> Machine 2와 Shift 3에서 불량 증가가 집중되는 패턴이 관찰됩니다.

### ⑥ 주의사항

> Machine 2는 Model C 생산 비중도 높기 때문에 설비와 모델 효과가 혼재되어 있을 가능성이 있습니다.

### ⑦ 권장 다음 분석

> **Machine × Model별 불량률을 추가 분석하여 설비 효과와 모델 효과를 분리하는 것을 권장합니다.**

# 3-3-19. Agent의 분석 수준(Level)

앞서 정의한 3단계 구조도 여기에 연결합니다.

|Level|사용자 방식|Agent 동작|
|---|---|---|
|**Level 1**|Wizard|사용자가 단계 선택|
|**Level 2**|자연어 + 보조|Agent가 분석 추천|
|**Level 3**|자연어 문제 제시|Agent가 다단계 분석 수행|

기존 기획서의 **쉬운 설명 → 기술적 설명 → 통계 원문** 3단계 설명 체계도 그대로 유지할 수 있습니다.

즉, **분석 수행 수준과 설명 수준을 별도로 설정**하는 것이 좋습니다.

예:

```
Analysis Mode
① Guided
② Assisted
③ Agentic

Explanation Mode
① Field
② Engineer
③ Statistician
```

이렇게 하면 매우 유연해집니다.

# 3-3-22. 특히 UC-15가 최종 Agent Benchmark가 된다

UC-15는 향후 이 앱의 가장 높은 수준의 Agent Workflow가 될 가능성이 높습니다.

예를 들어 사용자가:

> "공정 개선을 했는데 실제로 효과가 있었는지 종합적으로 판단해줘."

라고 질문합니다.

Agent는 단일 통계 분석을 하지 않습니다.

```
개선 전/후
   │
   ├─ CTQ 평균
   ├─ CTQ 변동
   ├─ 불량률
   ├─ FPY
   ├─ Cycle Time
   ├─ Capability
   └─ 이상 발생
          ↓
     종합 평가
          ↓
     개선 효과 판단
```

즉,

> **One Question → Multiple Analyses → Integrated Decision**

구조입니다.

이것이 우리가 만들려는 앱이 단순한 **"LLM + 통계 계산기"**가 아니라 **Manufacturing Statistical Agent**가 되는 지점입니다.

# 3-3-23. 이번 단계에서 중요한 설계 원칙

이번 UC-11 설계를 통해 앞으로 앱 전체에 적용할 원칙을 7개로 확정하는 것을 제안합니다.

### 원칙 ① 질문 중심

> 사용자는 통계기법을 선택하지 않아도 된다.

**현장 질문 → 통계 분석**으로 변환한다.

### 원칙 ② LLM은 계산하지 않는다

계산은 Statistical Engine이 수행합니다.

### 원칙 ③ LLM은 분석을 조합한다

단일 분석뿐 아니라 **Analysis Plan**을 구성할 수 있어야 합니다.

### 원칙 ④ 통계적 결론과 제조적 판단을 분리한다

기존 기획서에서 강조한 핵심 원칙입니다. 통계분석 앱 제작 기획서.mdMD

```
Statistical Conclusion
        ↓
Manufacturing Interpretation
        ↓
Engineering Consideration
```

### 원칙 ⑤ 상관관계 ≠ 인과관계

Agent가 원인을 표현할 때 반드시 구분합니다.

### 원칙 ⑥ Agent는 분석을 계속할 수 있어야 한다

결과를 보고

> "그럼 다음에는 무엇을 확인해야 하지?"

라는 질문에 자동으로 이어져야 합니다.

### 원칙 ⑦ 모든 판단에는 Evidence가 있어야 한다

Agent의 문장은 다음 구조를 가져야 합니다.

```
Claim
 ↓
Evidence
 ↓
Statistical Result
 ↓
Manufacturing Meaning
 ↓
Limitation
```

예:

> **Machine 2에서 불량률이 높게 나타났습니다.**  
> → 근거: Machine 2 불량률 2.1%  
> → 통계 결과: 다른 설비 대비 유의한 차이  
> → 제조적 의미: 설비 관련 원인 가능성  
> → 제한사항: Model C 생산 비중이 높아 모델 효과가 혼재할 수 있음

이 구조를 앞으로 **Agent Response Standard**로 사용하는 것이 좋습니다.

# 다음 단계: Step 3-4

이제 상당히 중요한 단계에 도달했습니다.

**Step 3-3에서는 "Agent가 무엇을 하는가"를 정의했습니다.**

다음 **Step 3-4에서는 "Agent가 어떻게 판단하고 행동하는가"를 설계해야 합니다.**

즉, 다음 단계는:

## **Step 3-4. Manufacturing Statistical Agent의 의사결정 구조(Agent Decision Framework)**

입니다.

여기에서는 특히 다음 6가지를 설계하는 것이 좋습니다.

1. **Intent Classification**
    
    - 사용자의 질문을 8개 문제 유형 중 어디에 배치할 것인가
2. **Analysis Planning**
    
    - 단일 분석인가?
    - 복수 분석인가?
    - 분석 순서는 무엇인가?
3. **Tool Selection**
    
    - t-test / ANOVA / Correlation / Regression / SPC 등을 어떤 조건에서 호출할 것인가
4. **Statistical Guardrail**
    
    - LLM이 잘못된 통계 방법을 선택하지 못하도록 어떻게 통제할 것인가
5. **Evidence & Confidence**
    
    - Agent가 "원인 후보"라고 말할 수 있는 조건은 무엇인가
    - "추가 검증 필요"라고 판단하는 기준은 무엇인가
6. **Next Best Analysis**
    
    - 분석 결과에 따라 다음에 가장 가치가 높은 분석을 자동으로 선택하는 방법

특히 **6번의 "Next Best Analysis"**가 향후 앱을 단순한 통계 분석 도구에서 **스스로 분석을 이어가는 Agent**로 발전시키는 핵심 기능이 됩니다.

다음 단계에서는 이 구조를 **실제 Agent의 내부 의사결정 Tree + State + Tool Calling Rule + Guardrail** 수준까지 구체화하는 것이 적절합니다.

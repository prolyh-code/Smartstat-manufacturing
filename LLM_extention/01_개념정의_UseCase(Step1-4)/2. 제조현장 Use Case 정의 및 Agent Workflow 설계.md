## 왜 Use Case부터 설계해야 하는가?

기존 기획서는 이미 상당히 좋은 **통계 기능 목록**을 가지고 있습니다.

예를 들어:

> 기초통계 → Histogram → Box Plot → t-test → ANOVA → 상관분석 → 회귀분석 …

그리고 기존 앱의 핵심 방향도

> **현장 문제 → 질문 → 분석 선택 → 결과 → 해석 → 현장 판단**

으로 잘 정의되어 있습니다. 통계분석 앱 제작 기획서.mdMD

그런데 **LLM을 추가하면 제품의 중심이 바뀝니다.**

기존에는

> 사용자가 분석 방법을 선택 → 프로그램이 계산

이었다면,

LLM 통합 후에는

> **사용자가 제조 현장의 문제를 말함 → Agent가 문제를 이해 → 필요한 데이터를 확인 → 분석 방법을 결정 → 통계 Tool을 호출 → 결과를 검증 → 결과를 해석 → 다음 분석을 제안**

하는 구조가 됩니다.

따라서 먼저 실제 제조 현장에서 Agent가 **어떤 질문을 받아 어떤 행동을 해야 하는지**를 정의해야 합니다.

|구분|정의할 내용|
|---|---|
|현장 질문|사용자가 실제로 하는 질문|
|문제 유형|비교 / 관계 / 이상 / 원인 / 변화 등|
|필요한 데이터|어떤 데이터가 필요한가|
|데이터 확인|결측, 표본수, 변수형, 이상치 등|
|분석 계획|어떤 통계분석이 필요한가|
|Statistical Tool|실제 호출할 계산 기능|
|Rule Engine|분석 선택·조건 검증|
|LLM 역할|이해 / 설명 / 추론 / 대화|
|결과|그래프 + 통계 결과|
|해석|통계적 의미|
|제조 판단|공정상 의미|
|추가 분석|다음에 무엇을 볼 것인가|
|최종 Action|개선활동으로 어떻게 연결할 것인가|

이렇게 하면 나중에 **Agent Architecture → Tool 설계 → 화면 설계 → 개발**까지 그대로 연결할 수 있습니다.

# 우선 선정할 핵심 Use Case

제조 현장에서는 다음과 같이 분류하는 것이 좋습니다.

### ① 현상 파악

> "이 공정의 품질이 안정적인가?"

- 기초통계
- Histogram
- Box Plot
- 정규성
- 이상치
- 공정 분포

### ② 두 조건 비교

> "A 설비와 B 설비의 품질 차이가 있는가?"

- 2-sample t-test
- Welch t-test
- Box Plot
- Effect Size

### ③ 변경 전후 비교

> "설비 조건을 변경했는데 품질이 좋아졌는가?"

- Paired t-test
- 2-sample test
- Before/After visualization
- Effect Size

### ④ 여러 조건 비교

> "설비별 품질 차이가 있는가?"

- ANOVA
- Welch ANOVA
- Post-hoc
- Box Plot

### ⑤ 변수 간 관계

> "체결 토크와 불량 사이에 관계가 있는가?"

- Correlation
- Scatter Plot
- Regression

### ⑥ 원인 탐색

> "불량이 증가한 원인이 무엇인가?"

이것이 **LLM Agent의 중요한 차별화 영역**입니다.

단순히 하나의 통계분석을 실행하는 것이 아니라,

> 불량률 확인  
> → 시간대별 변화  
> → 설비별 비교  
> → 작업조별 비교  
> → 모델별 비교  
> → CTQ 분포 확인  
> → 관련 변수 분석  
> → 후보 원인 도출

과 같이 **Multi-step Analysis**를 수행하게 됩니다.

### ⑦ 이상 현상 탐색

> "최근 데이터에서 이상한 패턴이 있는가?"

- 이상치
- Distribution shift
- Trend
- Correlation change
- 그룹별 차이
- SPC로 확장

### ⑧ 공정능력

> "현재 공정이 규격을 만족할 능력이 있는가?"

- Cp
- Cpk
- Pp
- Ppk
- Specification analysis

### ⑨ 불량 분석

> "어떤 불량이 가장 문제가 되는가?"

- Defect rate
- Pareto
- FPY
- RTY
- Category analysis

### ⑩ 개선 효과 검증

> "개선 활동 후 실제로 좋아졌는가?"

- Before/After
- Hypothesis test
- Effect size
- Confidence interval
- Practical significance

# 특히 중요한 것은 ⑥입니다

기존 앱은 **통계분석 도구**가 중심이었습니다.

LLM 통합 앱에서는 이것을 한 단계 발전시켜야 합니다.

예를 들어 사용자가

> **"최근 체결 토크 불량이 증가했는데 원인을 찾아줘."**

라고 입력했다고 가정하겠습니다.

Agent가 바로 "상관분석을 하겠습니다"라고 하면 안 됩니다.

다음처럼 움직여야 합니다.

```
사용자 질문
   ↓
[LLM]
문제의도 파악
   ↓
"불량 증가 원인 탐색"
   ↓
[Data Engine]
사용 가능한 데이터 확인
   ↓
생산수량 / 불량 / 설비 / 시간 / 작업조 / 모델 / CTQ
   ↓
[Rule Engine]
데이터 품질 및 분석 조건 확인
   ↓
[Statistical Tools]
① 불량률 추세
② 설비별 불량률
③ 시간대별 불량률
④ 모델별 불량률
⑤ CTQ 분포
⑥ 관련 변수 분석
   ↓
[Result Validation]
통계적으로 의미 있는 차이인가?
   ↓
[LLM]
결과 종합
   ↓
"현재 데이터에서 가장 유력한 후보는 A 설비"
   ↓
추가 분석 제안
   ↓
"설비 A의 토크 분포를 B 설비와 비교하시겠습니까?"
```

이것이 우리가 만들려는 **Manufacturing Statistical Agent**의 핵심입니다.

# 따라서 다음 작업은 3개로 나누는 것이 좋습니다

### Step 3-1. Use Case Taxonomy

제조 현장의 통계적 질문을 체계적으로 분류합니다.

예:

**현상 → 비교 → 관계 → 변화 → 이상 → 원인 → 검증 → 개선**

---

### Step 3-2. 대표 Use Case 10~15개 선정

실제 제품 MVP에 사용할 대표 사례를 선정합니다.

예를 들면:

1. CTQ 분포 분석
2. 두 설비 간 품질 비교
3. 두 작업조 간 품질 비교
4. 개선 전후 비교
5. 여러 설비 간 차이 분석
6. CTQ와 공정조건 관계 분석
7. 불량률 증가 원인 탐색
8. 이상 데이터 탐색
9. 규격 대비 공정능력 분석
10. 불량 Pareto 분석
11. 공정 간 품질 차이 분석
12. 개선효과 검증
13. 품질 이상 원인 Multi-step Analysis
14. "이 데이터에서 무엇이 문제인지 찾아줘"
15. "다음에 어떤 분석을 해야 하는지 알려줘"

여기서 특히 **14, 15번이 기존 통계 프로그램과 LLM Agent를 차별화하는 핵심 Use Case**가 됩니다.

---

### Step 3-3. Agent Workflow 상세 설계

각 Use Case마다 다음을 정의합니다.

> **Input → Intent → Data → Analysis Plan → Tool Calling → Validation → Interpretation → Insight → Next Action**

이것이 완성되면 다음 단계인 **Agent Architecture**를 상당히 구체적으로 설계할 수 있습니다.

---

## 제가 권하는 진행 방식

이 프로젝트는 한 번에 전체 기획서를 만드는 것보다 **단계별로 설계하고 앞 단계의 결과를 검증하면서 다음 단계로 넘어가는 방식**이 좋습니다.

따라서 다음 답변에서는 바로 **「Step 3-1. 제조 현장 통계 질문의 Taxonomy」**부터 깊게 설계하는 것이 가장 좋습니다.

그 다음에 그 Taxonomy를 기반으로 **10~15개의 핵심 Use Case를 선정하고**, 각 Use Case의 **Agent Workflow를 하나씩 상세 설계**하면 됩니다.

이 과정을 거치면 단순한 "통계분석 앱에 ChatGPT를 붙이는 것"이 아니라, **제조 현장의 질문을 이해하고 통계분석을 수행하며 다음 판단까지 연결하는 Manufacturing Statistical Agent**의 구체적인 설계가 나오게 됩니다.

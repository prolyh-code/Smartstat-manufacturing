좋습니다. 그러면 이제 **Step 3-1 「제조 현장 통계 질문의 Taxonomy」**를 먼저 탄탄하게 설계하겠습니다.

기존 기획서에는 이미 사용자의 질문을 중심으로 한 8개 항목이 정의되어 있습니다. 즉, **공정 상태, 두 조건 비교, 여러 조건 비교, 변경 전후 비교, 변수 관계, 원인·결과 관계, 분포, 이상값**입니다.

다만 **LLM Agent로 발전시키려면 이것을 단순한 메뉴 구조가 아니라 "사용자의 질문을 Agent가 이해하는 문제 분류 체계"로 재설계할 필요가 있습니다.**

# Step 3-1. Manufacturing Statistical Question Taxonomy

## 1. 기본 방향

기존 앱의 사고방식은 다음과 같습니다.

> **현장 질문 → 통계분석 선택**

LLM 통합 버전에서는 한 단계 더 발전시킵니다.

> **자연어 질문 → 문제 유형 파악 → 필요한 데이터 파악 → 분석 목적 정의 → 분석 계획 수립 → 통계 Tool 실행 → 결과 해석 → 제조 판단**

따라서 Taxonomy는 **통계학 기준이 아니라 제조 현장에서 발생하는 의사결정 문제 기준**으로 만드는 것이 좋습니다.

---

# 2. 제조 통계 질문의 8대 Category

저는 다음과 같이 정리하는 것을 권합니다.

|Category|제조 현장의 핵심 질문|대표 분석|
|---|---|---|
|**A. 현상 파악**|현재 공정은 어떤 상태인가?|Descriptive, Histogram, Box Plot|
|**B. 기준 대비 판단**|목표/규격과 차이가 있는가?|1-Sample t-test, CI|
|**C. 그룹 비교**|A와 B가 다른가?|2-Sample t-test, Welch|
|**D. 다중 그룹 비교**|여러 조건 중 차이가 있는가?|ANOVA, Welch ANOVA, Post-hoc|
|**E. 변화 효과 분석**|개선 전후 무엇이 달라졌는가?|Paired t-test, 2-Sample|
|**F. 관계·영향 분석**|X가 변하면 Y가 변하는가?|Correlation, Regression|
|**G. 이상·원인 탐색**|왜 문제가 발생했는가?|Multi-step Analysis|
|**H. 공정 판단·개선 검증**|공정이 안정적이고 개선 효과가 있는가?|SPC, Capability, Effect Size 등|

여기서 중요한 변화가 하나 있습니다.

기존 8개 질문 중 **"이상값 확인"을 단순 분석 메뉴로 두지 않고 G의 이상·원인 탐색 영역으로 확장**하는 것입니다.

또한 기존 기획서에서 Phase 2 이후로 계획한 SPC와 Capability를 고려하면, 장기적으로 H를 별도의 중요한 영역으로 가져가는 것이 자연스럽습니다.

---

# 3. Category A — 현상 파악

### 사용자의 질문

> "이 데이터가 어떤 상태인지 먼저 봐줘."

또는

> "현재 공정의 품질 수준을 확인해줘."

### Agent가 해야 할 일

단순히 평균을 계산하는 것이 아닙니다.

```
Data
 ↓
Data Quality Check
 ↓
N / Missing / Variable Type
 ↓
Descriptive Statistics
 ↓
Histogram
 ↓
Box Plot
 ↓
Distribution Interpretation
```

### 주요 결과

- N
- Mean
- Median
- SD
- Min / Max
- Q1 / Q3
- IQR
- CV
- Skewness
- Kurtosis
- Outlier

기존 기획서에서도 이와 같은 기초통계량을 제시하고 있습니다.

### LLM의 역할

여기서 LLM은 계산하지 않습니다.

예를 들어 Statistical Engine이

```
Mean = 35.82
SD = 0.41
CV = 1.14%
Outlier = 3
```

을 반환하면 LLM이 이를 제조 언어로 바꿉니다.

> "평균은 35.82 mm이며 변동은 비교적 작습니다. 다만 일부 이상값이 확인되므로 해당 측정값이 실제 공정 이상인지 측정 오류인지 확인할 필요가 있습니다."

---

# 4. Category B — 기준 대비 판단

### 핵심 질문

> "목표값과 다른가?"

기존 기획서에서도 대표 질문으로 정의되어 있고 1-Sample t-test와 연결되어 있습니다.

예:

> "체결 토크 목표가 35 Nm인데 현재 평균이 다른가?"

Agent:

```
Target = 35
        ↓
Sample Data
        ↓
Descriptive
        ↓
1-Sample t-test
        ↓
Difference
CI
P-value
Effect Size
        ↓
Manufacturing Interpretation
```

여기서 중요한 것은

**"통계적으로 다른가?"와 "현장에서 문제가 되는가?"를 분리하는 것**입니다.

이 원칙은 기존 기획서의 핵심 설계 원칙이기도 합니다.

---

# 5. Category C — 그룹 비교

### 핵심 질문

> "A라인과 B라인의 품질이 다른가?"

> "설비 1과 설비 2의 치수가 다른가?"

기존 기획서의 대표적인 2-Sample t-test 사례입니다.

Agent는 먼저 **데이터 구조를 판단**합니다.

```
두 그룹인가?
   ↓
동일 대상인가?
 ├─ YES → Paired
 └─ NO  → Independent
             ↓
        분산 조건 확인
             ↓
        t-test / Welch
```

따라서 사용자는 반드시 "t-test"를 알고 있을 필요가 없습니다.

> "두 설비의 품질 차이를 알고 싶어요."

라고만 하면 됩니다.

---

# 6. Category D — 다중 그룹 비교

### 핵심 질문

> "설비 1, 2, 3 중 품질 차이가 있는가?"

> "A/B/C 작업조 중 어느 조의 품질이 다른가?"

> "여러 모델에서 CTQ 평균 차이가 있는가?"

### Agent Workflow

```
3개 이상 그룹
       ↓
Data validation
       ↓
Distribution / variance check
       ↓
ANOVA 또는 Welch ANOVA
       ↓
유의한 차이?
   ├─ NO → 종료
   └─ YES
       ↓
Post-hoc
       ↓
어느 그룹이 다른가?
```

이 부분은 기존 기획서의 ANOVA → Post-hoc 구조를 그대로 계승할 수 있습니다.

---

# 7. Category E — 변화 효과 분석

이 영역은 **제조 개선활동과 직접 연결**됩니다.

### 질문

> "설비 개선 후 품질이 좋아졌는가?"

> "공정조건 변경 전후 차이가 있는가?"

> "개선 활동의 효과가 실제로 있었는가?"

동일 제품/동일 대상의 Before–After라면 Paired t-test를 사용하는 구조가 기존 기획서에도 명확하게 제시되어 있습니다.

하지만 Agent는 여기서 한 단계 더 나아갈 수 있습니다.

```
Before
      ↘
        Difference → Statistical Test
      ↗
After
```

그리고 결과를

1. 평균이 변했는가?
2. 변화량은 얼마인가?
3. 통계적으로 유의한가?
4. 변화량이 제조적으로 의미 있는가?

로 분리해서 보여줍니다.

---

# 8. Category F — 관계·영향 분석

### 핵심 질문

> "온도가 올라가면 치수가 변하는가?"

> "압력이 불량률에 영향을 주는가?"

> "Torque와 체결불량 사이에 관계가 있는가?"

기존 기획서에서도 온도–치수, 압력–불량률, Torque–체결불량 등을 대표적인 Scatter Plot 사례로 제시합니다.

여기서 Agent는

```
X와 Y 관계 질문
        ↓
Scatter Plot
        ↓
Correlation
        ↓
필요시 Regression
        ↓
Residual Analysis
```

순으로 발전시킬 수 있습니다.

그리고 반드시

> **Correlation ≠ Causation**

을 관리해야 합니다. 기존 기획서도 이 원칙을 명시하고 있습니다.

---

# 9. Category G — 이상·원인 탐색

**LLM Agent로 전환하는 가장 중요한 영역**입니다.

기존 통계 프로그램에서는 사용자가 직접

> "설비별로 비교해 봐야겠다."

> "시간대별로 봐야겠다."

> "작업조별로 봐야겠다."

라고 생각해야 합니다.

Agent에서는 반대로 할 수 있습니다.

사용자:

> **"최근 불량이 증가한 원인을 찾아줘."**

Agent:

```
① 질문 의도 파악
        ↓
② 데이터 구조 확인
        ↓
③ 불량률 Trend
        ↓
④ 시간대별 비교
        ↓
⑤ 설비별 비교
        ↓
⑥ 모델별 비교
        ↓
⑦ 작업조별 비교
        ↓
⑧ 관련 CTQ 분석
        ↓
⑨ 주요 변수 Correlation
        ↓
⑩ 후보 원인 Ranking
        ↓
⑪ 추가 검증 분석 제안
```

이것이 **Multi-step Statistical Analysis**입니다.

그리고 중요한 안전장치가 있습니다.

Agent가

> "원인은 A 설비입니다."

라고 단정해서는 안 됩니다.

대신

> **"현재 데이터에서 A 설비의 불량률이 다른 설비보다 높게 나타나 원인 후보로 우선 확인할 필요가 있습니다."**

라고 해야 합니다.

즉,

**통계적 증거 → 원인 후보 → 추가 검증**

의 구조를 가져야 합니다.

---

# 10. Category H — 공정 판단·개선 검증

최종적으로 Agent가 지향해야 하는 영역입니다.

사용자의 질문은 결국 이런 형태가 됩니다.

> "그래서 이 공정에 문제가 있는가?"

> "이 개선을 계속 적용해도 되는가?"

> "어떤 부분을 먼저 개선해야 하는가?"

여기서는 단일 통계분석이 아니라 여러 분석 결과를 종합해야 합니다.

예:

```
공정 평균
+ 변동
+ 규격
+ 이상값
+ 그룹 차이
+ Trend
+ Capability
+ Defect
+ Effect Size
        ↓
Manufacturing Judgment
```

이 단계가 기존 기획서에서 말하는

> **Easy Decision**

으로 연결됩니다. 통계분석 앱 제작 기획서.mdMD

---

# 11. 중요한 것은 "분석 방법"과 "질문 유형"을 분리하는 것입니다

이 부분을 이번 설계의 **핵심 원칙**으로 제안합니다.

기존 방식:

```
t-test
ANOVA
Correlation
Regression
```

새로운 방식:

```
나는 무엇을 알고 싶은가?
        ↓
[상태]
[기준 대비]
[비교]
[변화]
[관계]
[이상]
[원인]
[개선효과]
        ↓
Agent가 적절한 통계 방법을 결정
```

즉,

> **통계분석 메뉴는 Agent 내부의 Tool이고, 사용자에게 보여주는 것은 제조 문제의 Category입니다.**

이것이 LLM 통합의 가장 중요한 UX 변화입니다.

# 12. 최종 Taxonomy 구조

전체를 계층적으로 표현하면 다음과 같습니다.

```
Manufacturing Statistical Question
│
├─ A. 현상 파악
│   ├─ 데이터 상태
│   ├─ 분포
│   └─ 변동
│
├─ B. 기준 대비 판단
│   ├─ 목표값
│   ├─ 기준값
│   └─ 규격
│
├─ C. 그룹 비교
│   ├─ 공정
│   ├─ 설비
│   ├─ 작업자
│   ├─ Shift
│   └─ 모델
│
├─ D. 다중 그룹 비교
│   ├─ 여러 설비
│   ├─ 여러 공정
│   └─ 여러 조건
│
├─ E. 변화 효과
│   ├─ Before / After
│   ├─ 개선 전 / 후
│   └─ 조건 변경 전 / 후
│
├─ F. 관계·영향
│   ├─ X ↔ Y
│   ├─ Correlation
│   └─ Regression
│
├─ G. 이상·원인 탐색
│   ├─ 이상 데이터
│   ├─ 이상 Trend
│   ├─ 불량 증가
│   ├─ 원인 후보 탐색
│   └─ Multi-step Analysis
│
└─ H. 공정 판단·개선
    ├─ 공정능력
    ├─ SPC
    ├─ 개선효과
    └─ Engineering Decision
```

# 13. 이 Taxonomy가 앞으로 어떻게 사용되는가?

이 구조는 단순한 UX 메뉴가 아닙니다.

앞으로 만들 **Agent의 핵심 분류체계**가 됩니다.

예를 들어 사용자가

> "A 설비에서 최근 치수가 이상한 것 같아."

라고 하면 LLM은 먼저 질문을 **G. 이상·원인 탐색**으로 분류합니다.

반면

> "A와 B 설비의 평균 치수가 다른지 확인해줘."

라면 **C. 그룹 비교**입니다.

그리고

> "지난주 설비 조건 변경 이후 치수가 좋아졌는지 확인해줘."

라면 **E. 변화 효과**입니다.

이렇게 **자연어 → Question Category → Analysis Plan → Statistical Tools**라는 공통 경로가 만들어집니다.

---

# 다음 단계: Step 3-2

이제 Taxonomy가 만들어졌으므로 다음에는 **각 Category에서 실제 제조 현장의 대표 질문을 선정해야 합니다.**

저는 처음부터 너무 많은 사례를 만들기보다는 **12~15개의 대표 Use Case**를 선정하는 것을 권합니다.

특히 다음 3종류를 반드시 포함해야 합니다.

### ① 단일 분석형

> "A라인과 B라인의 CTQ가 다른가?"

→ 2-Sample t-test

### ② 복합 분석형

> "설비별 CTQ 차이가 있는지 확인하고 어느 설비가 문제인지 알려줘."

→ ANOVA → Post-hoc → Effect Size → Interpretation

### ③ Agent형

> **"최근 불량이 증가했는데 가능한 원인을 데이터로 찾아줘."**

→ Data Quality → Trend → Group Analysis → Correlation → Candidate Cause → Additional Analysis

이 세 번째 유형이 **기존 SmartStat Manufacturing과 새로운 LLM-integrated Manufacturing Statistical Agent를 구분하는 핵심 검증 대상**이 될 것입니다.

따라서 **다음 단계에서는 이 Taxonomy를 기반으로 12~15개의 대표 Use Case를 선정하고, 각각에 대해 `사용자 질문 → 필요한 데이터 → Agent 판단 → Statistical Tool → 결과 → 해석 → 다음 행동`까지 구체적인 Workflow를 설계**하는 것이 가장 적절합니다.

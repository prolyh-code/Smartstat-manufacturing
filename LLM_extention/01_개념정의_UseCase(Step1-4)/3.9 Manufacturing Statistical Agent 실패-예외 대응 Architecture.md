# Step 3-9. Manufacturing Statistical Agent 실패·예외 대응 아키텍처

## 1. 왜 별도의 실패 대응 아키텍처가 필요한가

기존 통계 프로그램에서는 사용자가 잘못된 데이터를 넣거나 조건이 맞지 않으면 다음과 같이 처리할 수 있습니다.

> "분석할 수 없습니다."

하지만 LLM Agent는 이것만으로는 부족합니다.

제조 현장의 실제 질문은 대부분 데이터가 완벽하지 않고, 질문도 모호합니다.

예를 들어:

> "2번 설비에서 토크 불량이 왜 많이 발생하는지 찾아줘."

데이터를 확인해 보니,

- 2번 설비 데이터가 전체의 70%인데 특정 모델만 생산
- 일부 측정값 누락
- 불량 정의가 기간 중 변경
- 교대조별 생산량이 다름
- 동일 제품을 여러 번 측정한 데이터가 섞여 있음

등의 문제가 있을 수 있습니다.

이때 Agent가 단순히 통계분석을 수행하면 **정교하지만 잘못된 결론**을 만들어낼 수 있습니다.

따라서 이 Agent의 핵심 능력 중 하나는

> **"분석하는 능력"뿐 아니라 "분석하면 안 되는 상황을 판단하는 능력"**

이어야 합니다.

# 2. Failure & Exception의 기본 원칙

전체 원칙은 다음과 같이 정의하는 것이 좋습니다.

### 원칙 1. 무조건 분석하지 않는다

```
Question
 ↓
Data Assessment
 ↓
Can Analyze?
 ├─ YES → Analysis
 └─ NO  → Exception Handling
```

---

### 원칙 2. 오류와 분석 한계를 구분한다

예를 들어:

**데이터 오류**

> Torque 열에 숫자와 문자가 혼재되어 있습니다.

와

**통계적 한계**

> 현재 데이터만으로는 인과관계를 확인할 수 없습니다.

는 전혀 다른 문제입니다.

Agent는 이를 구분해서 설명해야 합니다.

---

### 원칙 3. 실패를 "종료"가 아니라 "다음 행동"으로 연결한다

나쁜 응답:

> 분석할 수 없습니다.

좋은 응답:

> 현재 데이터에는 설비별 생산 모델 정보가 부족하여 설비 효과와 모델 효과를 분리하기 어렵습니다.  
> 설비별 모델별 생산수량을 추가하면 교란요인을 확인할 수 있습니다.

즉,

**Exception → Reason → Impact → Required Action**

구조를 가져야 합니다.

# 3. 예외 상황 Taxonomy

제조 통계 Agent에서 발생할 수 있는 주요 예외를 10개 유형으로 정의할 수 있습니다.

|유형|대표 상황|Agent 대응|
|---|---|---|
|E01|데이터 부족|추가 데이터 요청|
|E02|데이터 품질 문제|데이터 정제/수정 안내|
|E03|변수 해석 불가|사용자 확인|
|E04|질문-데이터 불일치|분석 범위 재정의|
|E05|통계적 가정 위반|대체 분석|
|E06|표본 구조 문제|분석 중단/대체 방법|
|E07|교란요인 존재|추가 분석|
|E08|통계적 유의성 ≠ 제조적 의미|실무적 판단 별도 제시|
|E09|인과관계 판단 불가|관찰연구 한계 제시|
|E10|추가 분석의 가치 부족|Agent가 분석 종료|

이것을 Agent의 **Exception Knowledge**로 관리하는 것이 좋습니다.

# 4. E01. 데이터 부족

## 상황

예를 들어 사용자가

> "A공정과 B공정의 품질 차이를 비교해줘."

라고 했는데 A공정 데이터만 존재합니다.

### Agent의 판단

```
Required:
Group = A + B

Available:
Group = A

→ Two-group comparison impossible
```

### Agent 응답 구조

**현황**

> 현재 데이터에는 A공정 데이터만 존재합니다.

**영향**

> A와 B의 차이를 통계적으로 비교할 수 없습니다.

**필요 데이터**

> B공정의 동일 CTQ 데이터가 필요합니다.

**가능한 대안**

> 현재 A공정의 분포와 목표값 대비 상태는 분석할 수 있습니다.

여기서 중요한 것은 **할 수 없는 것과 할 수 있는 것을 동시에 알려주는 것**입니다.

---

# 5. E02. 데이터 품질 문제

제조 데이터에서는 이 부분이 매우 중요합니다.

예:

```
Torque
35.2
34.8
35.1
N/A
35.0
9999
34.9
```

Agent가 그대로 분석하면 안 됩니다.

### Data Quality Check

최소한 다음을 검사해야 합니다.

- Missing
- Duplicate
- Invalid value
- Unit mismatch
- Data type
- Range
- Specification
- Timestamp
- Group identification
- Measurement frequency
- Repeated measurement

그리고 각 문제에 **심각도**를 부여합니다.

### Severity

```
INFO
WARNING
ERROR
BLOCKER
```

예:

> Missing 1.2% → WARNING

> 측정값의 15%가 문자열 → ERROR

> Torque 단위가 N·m인지 kgf·cm인지 불명확 → BLOCKER

---

# 6. E03. 변수 해석 불가

제조 현장의 실제 데이터에서는 이런 상황이 매우 흔합니다.

예:

```
M01
M02
M03
X1
X2
Y1
TQ
```

Agent가 이것을 마음대로 해석해서는 안 됩니다.

예를 들어 `TQ`를 Torque라고 추정할 수는 있지만 **확정하면 안 됩니다.**

Agent는:

> `TQ` 변수가 토크값을 의미하는 것으로 추정됩니다. 맞습니까?

라고 확인할 수 있습니다.

단, 이미 데이터 사전이나 과거 분석 State에서 정의되어 있다면 다시 묻지 않아야 합니다.

즉,

> **Data Dictionary > Analysis State > Contextual inference > User clarification**

순으로 신뢰하도록 설계하는 것이 좋습니다.

---

# 7. E04. 질문과 데이터가 맞지 않는 경우

사용자:

> "작업자별 불량률 차이를 분석해줘."

그런데 데이터에는

```
Machine
Model
Shift
Defect
```

만 있고 `Operator`가 없습니다.

Agent는:

> 작업자별 비교를 위한 Operator 변수가 데이터에 없습니다.

라고 해야 합니다.

그리고 다음과 같이 선택지를 제시할 수 있습니다.

```
① Operator 데이터를 추가
② Machine별 불량률 분석
③ Shift별 불량률 분석
④ 현재 데이터로 가능한 원인 탐색
```

이것이 **Agentic UX의 중요한 차이**입니다.

단순 오류 메시지가 아니라 **문제를 해결할 수 있는 다음 경로를 제시**합니다.

---

# 8. E05. 통계적 가정 위반

예를 들어 두 공정의 CTQ를 비교하려고 합니다.

Agent가 먼저:

```
Normality
Variance
Independence
```

등을 평가합니다.

예를 들어:

```
Normality: questionable
Variance: unequal
```

이면 단순 Student's t-test를 무조건 수행하지 않습니다.

가능한 분석 경로:

```
Two Sample Comparison
        ↓
Variance Check
        ↓
Unequal variance
        ↓
Welch t-test
```

또는 데이터 구조에 따라

```
Non-normal
      ↓
Mann-Whitney U
```

등으로 이동합니다.

핵심은:

> **LLM이 통계적 판단을 임의로 하는 것이 아니라 Rule Engine이 분석 조건을 검증한다.**

입니다.

---

# 9. E06. 표본 구조 문제

이 부분은 제조 Agent에서 특히 중요합니다.

예를 들어 사용자가:

> "개선 전후를 비교해줘."

라고 했는데 데이터가

```
Before: 100개
After: 100개
```

입니다.

단순히 100 vs 100이라고 해서 독립표본이라고 판단해서는 안 됩니다.

실제로는:

### Case A

동일 제품을 개선 전/후 측정

→ Paired

### Case B

개선 전 생산품 100개 + 개선 후 생산품 100개

→ Independent

### Case C

동일 제품 + 여러 번 반복 측정

→ Repeated measurement

즉, **행의 개수보다 데이터 생성 구조(Data Generating Process)**가 중요합니다.

Agent가 반드시 확인해야 할 부분입니다.

---

# 10. E07. 교란요인(Confounding)

이것은 앞 단계에서 정의한 **Root Cause Agent**와 직접 연결됩니다.

예를 들어:

```
Machine 2
Defect rate = 4.8%

Other machines
Defect rate = 1.2%
```

단순 분석이라면:

> Machine 2의 불량률이 높다.

까지는 가능합니다.

그러나 데이터를 보니:

```
Machine 2
 └─ Model C 90%

Other machines
 └─ Model C 20%
```

라면 Machine 효과와 Model 효과가 섞여 있습니다.

따라서 Agent는:

> Machine 2와 높은 불량률 사이에 통계적 연관성이 관찰되지만, Machine 2가 특정 모델을 집중 생산하고 있어 Model 효과가 교란요인일 가능성이 있습니다.

라고 해야 합니다.

그리고:

> **다음 분석: Model 효과를 통제한 Machine 비교**

를 추천해야 합니다.

---

# 11. E08. 통계적 유의성과 제조적 유의성의 충돌

제조 현장에서 매우 중요한 예외입니다.

예:

```
A 평균 = 35.00
B 평균 = 35.03

p < 0.001
```

통계적으로는 매우 유의합니다.

하지만 제조적으로는:

```
Difference = 0.03
```

이고 실제 공정 허용오차가 ±5라면 의미가 없을 수 있습니다.

따라서 Agent는:

### Statistical Judgment

> 두 공정의 평균 차이는 통계적으로 유의합니다.

### Manufacturing Judgment

> 그러나 평균 차이는 0.03으로 규격 폭에 비해 매우 작아 제조 관점에서 중요한 차이라고 보기 어렵습니다.

라고 분리해야 합니다.

이 원칙은 기존 기획서의 **통계적 유의성 vs 제조적 유의성 분리**를 LLM Agent에도 그대로 유지하는 것이 적절합니다. 통계분석 앱 제작 기획서.mdMD

# 12. E09. 인과관계 판단 불가

이 Agent에서 반드시 Guardrail로 설정해야 합니다.

예:

> Machine 2에서 불량률이 높습니다.

여기서

❌ 잘못된 결론

> Machine 2가 불량의 원인입니다.

올바른 결론:

> Machine 2와 불량 발생 사이에 높은 연관성이 관찰되었습니다.

그리고:

> 현재 관찰 데이터만으로 Machine 2가 불량의 직접적인 원인이라고 확정할 수 없습니다.

### Evidence Level

앞에서 정의한 Evidence Level을 그대로 사용하면 좋습니다.

|Level|의미|
|---|---|
|E0|근거 없음|
|E1|관찰된 패턴|
|E2|통계적 차이/연관성|
|E3|반복 검증된 후보|
|E4|실험/개선 검증|

따라서 관찰 데이터 분석 결과는 대부분 **E1~E3** 수준이고, 실제 원인 확정은 DOE/실험/개선 검증을 통해 **E4**로 올라가는 구조입니다.

# 13. E10. "더 이상 분석할 필요가 없는 상황"

이것도 Agent의 중요한 능력입니다.

LLM은 대화를 계속 생성할 수 있기 때문에, 잘못 설계하면

> 분석 → 추가 분석 → 또 추가 분석 → 또 다른 분석

이라는 무한 분석이 발생할 수 있습니다.

따라서 **Stop Decision**이 필요합니다.

### Stop Condition

```
Question Answered
       OR
Information Gain Low
       OR
Data Insufficient
       OR
Experiment Required
       OR
Engineering Validation Required
```

예를 들어:

> 현재 데이터에서 Machine, Model, Shift를 분석했지만 모든 변수에서 명확한 차이가 확인되지 않았습니다. 추가적인 관찰 데이터 분석만으로는 원인을 특정하기 어렵습니다. 다음 단계는 공정조건을 통제한 실험 또는 DOE가 적절합니다.

이것이 진짜 **Agent**다운 행동입니다.

---

# 14. Exception Handling의 표준 응답 구조

모든 예외를 동일한 형식으로 설명하면 Agent의 일관성이 좋아집니다.

## Exception Response Contract

```
1. What happened?
2. Why is it a problem?
3. What analysis is affected?
4. What can still be analyzed?
5. What additional information is needed?
6. What is the recommended next action?
```

예:

> **분석 제한이 발견되었습니다.**
> 
> 현재 데이터에서 설비별 불량률 차이는 확인할 수 있지만, 설비별 모델 생산 비율이 크게 달라 설비 효과와 모델 효과를 분리하기 어렵습니다.
> 
> 따라서 현재 결과는 **설비와 불량률의 연관성**으로만 해석해야 합니다.
> 
> **권장 다음 단계:** 모델 효과를 통제한 추가 분석을 수행하거나, 동일 모델을 여러 설비에서 생산한 데이터를 확보하십시오.

# 15. Agent의 "질문하기" 기준

여기서 중요한 설계 원칙이 하나 더 나옵니다.

Agent가 너무 많이 질문하면 사용자가 피곤해집니다.

따라서 질문에는 **Question Necessity Rule**을 둡니다.

### 질문해야 하는 경우

```
Purpose ambiguity
Target ambiguity
Data structure ambiguity
Critical assumption ambiguity
Decision criterion ambiguity
```

### 질문하지 않아도 되는 경우

```
단순 계산 방법
그래프 종류
기초 통계량
명백한 데이터 형식
이미 확인된 정보
데이터에서 확실히 추론 가능한 정보
```

예를 들어:

> "토크 데이터 분석해줘."

라고 했을 때

❌

> 평균을 구할까요?

> 표준편차를 구할까요?

> 히스토그램을 그릴까요?

> Box Plot을 그릴까요?

라고 하나씩 묻는 것은 기존 Wizard와 동일한 UX입니다.

대신:

> 토크 데이터의 현재 공정 상태를 먼저 확인하겠습니다. 분포, 중심값, 변동 및 이상값을 확인한 뒤 추가 분석이 필요한지 판단하겠습니다.

가 적절합니다.

# 16. 전체 Exception Architecture

결국 Agent의 분석 Pipeline은 다음처럼 구성하는 것이 좋습니다.

```
                User Question
                      │
                      ▼
              Intent Recognition
                      │
                      ▼
               Problem Definition
                      │
                      ▼
                Data Assessment
                      │
              ┌───────┴───────┐
              │               │
           Valid           Exception
              │               │
              ▼               ▼
       Analysis Planning   Diagnose
              │               │
              ▼               ▼
        Rule / Guardrail   Explain
              │               │
              ▼               ▼
       Statistical Tool    Recovery
              │               │
              ▼               ▼
       Result Validation   Next Action
              │               │
              └───────┬───────┘
                      ▼
                 Interpretation
                      │
                      ▼
                Evidence Level
                      │
                      ▼
             Next Best Analysis?
                 │          │
                YES         NO
                 │          │
                 ▼          ▼
              Explore     Decision
                             │
                             ▼
                     Engineering Action
```

# 17. 여기서 중요한 아키텍처적 결론

지금까지의 Step 3-1 ~ 3-9를 종합하면 이 프로젝트에서 **LLM의 역할과 통계 Engine의 역할이 상당히 명확해졌습니다.**

### LLM이 담당

- 자연어 질문 이해
- 문제 정의
- 사용자 의도 파악
- 분석 계획 수립
- 결과 설명
- 제조 맥락 해석
- 추가 분석 제안
- 예외 상황 설명
- 사용자와의 대화
- 지식 검색
- 다음 행동 제안

### Statistical Engine이 담당

- 데이터 계산
- 통계 검정
- 검정통계량
- p-value
- CI
- Effect Size
- Regression
- ANOVA
- SPC 등

### Rule / Guardrail Engine이 담당

- 분석 가능 여부
- 통계적 가정
- 분석 방법 검증
- 결과 검증
- 인과관계 과장 방지
- 데이터 품질 제한
- Stop Condition

### Agent State가 담당

- 현재 문제
- 분석 목적
- 데이터 상태
- 수행한 분석
- 발견사항
- Evidence
- Hypothesis
- Confounder
- 다음 분석
- 최종 판단

즉, **LLM 하나로 통계 Agent를 만드는 구조가 아니라 4개의 역할을 결합하는 구조**가 됩니다.

> **LLM + Statistical Engine + Rule/Guardrail + Analysis State**

이것이 이번 앱 재설계에서 가장 중요한 아키텍처 원칙 중 하나라고 봅니다.

# 다음 단계: Step 4

이제부터는 상당히 중요한 단계로 넘어갑니다.

## **Step 4 — Actual Manufacturing Use Case-specific Agent Scenario Design**

여기서는 더 이상 추상적인 Agent 구조를 설계하지 않고, **실제 제조 현장에서 사용자가 이 앱을 어떻게 사용하는지**를 구체적인 시나리오로 내려갑니다.

우선 다음 5개를 **Benchmark Agent Scenario**로 선정하는 것을 권합니다.

### UC-01. 공정 상태 진단

> "이 공정의 CTQ 상태가 어떤지 분석해줘."

### UC-03. 두 공정 비교

> "A라인과 B라인의 토크 차이가 있는지 확인해줘."

### UC-05. 다중 조건 비교

> "설비별 CTQ 차이가 있는지 분석해줘."

### UC-07. 개선 전후 검증

> "개선 전과 후에 품질이 실제로 좋아졌는지 확인해줘."

### UC-11. 불량 원인 탐색

> "최근 토크 불량이 증가한 원인을 찾아줘."

특히 **UC-11을 최종 Benchmark Scenario**로 두는 것이 좋습니다. 단순 통계분석부터 복수 분석, 교란요인, 추가 분석, Evidence, Stop Decision까지 모두 검증할 수 있기 때문입니다.

그리고 Step 4에서는 각 시나리오마다 다음을 실제 Agent 대화 수준으로 설계하겠습니다.

**사용자 질문 → Agent 이해 → 필요한 데이터 → 분석 계획 → Tool Call → 결과 → 해석 → 추가 분석 → Evidence → 제조적 판단 → 다음 행동**

이 과정을 만들면 지금까지의 아키텍처가 실제 **"사용 가능한 Manufacturing Statistical Agent"**로 구체화되기 시작합니다.

좋습니다. 이제 **1단계인 「LLM의 역할과 한계(Boundary) → 전체 시스템 구성요소 → 구성요소 간 관계」**부터 구체화하겠습니다.

이번 단계에서는 아직 최종 기획서를 쓰지 않고, **향후 기획서의 기술·서비스 설계를 결정하기 위한 Concept Design**으로 접근하겠습니다. 기존 기획서의 방향을 최대한 유지하면서 LLM을 어디에 넣어야 하는지를 명확히 하겠습니다.

---

# 1. 제품의 기본 개념부터 재정의

기존 앱은 다음 구조였습니다.

> **Manufacturing Statistical Decision Support Tool**

그리고 핵심 흐름은

> **현장 질문 → 분석 선택 → 분석 → 그래프 → 해석 → 현장 판단**

이었습니다.

LLM을 추가한 새로운 버전에서는 이를 다음과 같이 확장하는 것을 제안합니다.

> **Manufacturing Statistical Analysis Agent**

핵심 흐름은:

```
사용자 질문
    ↓
LLM이 질문 이해
    ↓
분석 목적 및 데이터 상황 파악
    ↓
분석 계획(Analysis Plan) 수립
    ↓
Rule Engine 검증
    ↓
Statistical Tool 실행
    ↓
결과 검증
    ↓
LLM 해석
    ↓
Manufacturing Insight
    ↓
추가 분석 제안
    ↓
사용자와 대화하며 분석 확장
    ↓
Engineering Decision
```

즉 **기존 앱의 기능을 LLM으로 대체하는 것이 아니라, 기존 앱 위에 지능형 계층(Intelligence Layer)을 추가하는 것**입니다.

---

# 2. 가장 중요한 원칙: LLM에게 무엇을 맡길 것인가?

이번 프로젝트에서 가장 먼저 확정해야 하는 것이 이것입니다.

저는 다음과 같이 **4개 영역으로 명확하게 분리**하는 것을 권합니다.

|영역|핵심 역할|LLM|
|---|---|---|
|Data Engine|데이터 읽기·검증·변환|제한적|
|Statistical Engine|통계 계산|**X**|
|Rule Engine|통계적 조건·판정 규칙|**X**|
|LLM Agent|이해·계획·설명·대화|**O**|
|Knowledge Base|통계·제조 지식|검색 활용|
|Visualization Engine|그래프 생성|**X**|
|Report Engine|보고서 구성|LLM 활용|

여기서 중요한 것은:

> **LLM이 숫자를 계산하는 구조를 만들지 않는다.**

입니다.

기존 기획서에서도 통계 계산은 검증된 라이브러리를 사용하고, 결정론적 통계 엔진을 유지하도록 정의되어 있습니다.

이 원칙은 **LLM을 추가하더라도 그대로 유지**해야 합니다.

---

# 3. LLM의 역할을 7개로 정의

LLM은 단순한 "설명 생성기"보다 훨씬 많은 역할을 할 수 있습니다.

## ① Intent Understanding

사용자의 자연어 질문을 이해합니다.

예:

> "A라인하고 B라인 Torque가 차이가 나는지 봐줘."

LLM은 이를 구조화합니다.

```
Intent:
  Compare

Target:
  Torque

Group:
  Line

Groups:
  A
  B

Question:
  Mean difference?
```

---

# 4. ② Analysis Planning

그 다음 LLM이 분석 계획을 수립합니다.

예:

```
Analysis Plan

1. Data quality check
2. Group sample size check
3. Distribution check
4. Variance assessment
5. Two-group comparison
6. Effect size
7. Box plot
8. Manufacturing interpretation
```

여기서 중요한 것은 **LLM이 계획을 제안하지만 마음대로 실행하지 않는 것**입니다.

---

# 5. ③ Tool Selection

Agent는 필요한 통계 Tool을 선택합니다.

예:

```
compare_two_groups()
calculate_descriptive_statistics()
test_variance()
t_test()
calculate_effect_size()
generate_box_plot()
```

실제 계산은 각각의 **Deterministic Tool**이 수행합니다.

즉:

```
LLM
 ↓
Tool Calling
 ↓
Statistics Engine
 ↓
Result
```

입니다.

---

# 6. ④ Result Interpretation

이 부분은 기존 앱의 Interpretation Engine을 크게 발전시키는 영역입니다.

기존에는:

```
Statistical Result
      ↓
Decision Rule
      ↓
Template
      ↓
Manufacturing Context
      ↓
Natural Language
```

구조였습니다.

새로운 구조는:

```
Statistical Result
       ↓
Validation
       ↓
Statistical Knowledge
       ↓
Manufacturing Knowledge
       ↓
Current User Context
       ↓
LLM
       ↓
Context-aware Interpretation
```

으로 발전합니다.

---

# 7. ⑤ Follow-up Analysis

**이번 프로젝트에서 LLM을 도입하는 가장 큰 이유 중 하나**입니다.

예를 들어:

> 사용자:  
> "A라인과 B라인의 Torque 차이를 분석해줘."

Agent:

> "B라인의 평균 Torque가 A라인보다 높고 통계적으로 유의한 차이가 있습니다."

사용자:

> "왜 그런 것 같아?"

여기서 기존 앱은 막힐 가능성이 높습니다.

LLM Agent는:

> "현재 데이터에 Line 외에 Machine, Shift, Operator 정보가 있다면 이 변수별 차이를 확인해 원인 후보를 좁혀볼 수 있습니다."

사용자:

> "Machine별로 확인해줘."

그러면:

```
현재 Context
     ↓
Machine Grouping
     ↓
Box Plot
     ↓
ANOVA
     ↓
Post-hoc
     ↓
결과 해석
```

으로 연결할 수 있습니다.

---

# 8. ⑥ Insight Discovery

이것은 기존 앱에는 없었던 중요한 기능입니다.

예를 들어 사용자가

> "이 데이터에서 특이한 점이 있는지 찾아줘."

라고 하면 특정 분석 하나를 실행하는 것이 아닙니다.

Agent가 데이터를 살펴보고:

```
Mean
Variance
Distribution
Outlier
Time Trend
Group Difference
Correlation
```

등을 종합해서

> "세 가지 특징이 확인됩니다."

라고 설명할 수 있습니다.

예:

1. B라인의 평균이 A라인보다 높음
2. C설비의 변동성이 상대적으로 큼
3. 야간 Shift에서 이상값 비율이 증가

그리고:

> "이 중 어떤 부분을 먼저 확인하시겠습니까?"

라고 이어갈 수 있습니다.

이것이 **통계분석 프로그램 → 분석 Agent**의 중요한 차이입니다.

---

# 9. ⑦ Report Generation

기존 앱에서도 자동 Report가 계획되어 있었습니다.

LLM을 결합하면 보고서도 훨씬 유연해집니다.

예:

> "팀장 보고용으로 1페이지로 정리해줘."

또는

> "품질 엔지니어가 검토할 수 있도록 통계 결과를 자세히 작성해줘."

또는

> "개선활동 보고서 형식으로 작성해줘."

동일한 분석 결과를 가지고 **목적별 결과물**을 생성할 수 있습니다.

---

# 10. 반대로 LLM이 하면 안 되는 것

이것도 명확하게 정의해야 합니다.

## LLM 금지 영역

### ① 통계 계산

```
Mean
SD
t
F
P-value
CI
R²
Effect Size
```

등을 LLM이 계산하면 안 됩니다.

---

### ② 통계적 판정의 근거 변경

예를 들어 실제 결과가

> p = 0.08

인데 LLM이 문맥상

> "차이가 있는 것으로 보입니다."

라고 단정해서는 안 됩니다.

---

### ③ 데이터 임의 수정

결측값이나 이상값을 LLM이 임의로 삭제해서도 안 됩니다.

---

### ④ 인과관계 확정

기존 기획서에서도 상관관계와 인과관계를 구분하는 원칙을 명확하게 제시하고 있습니다.

LLM은 이것을 반드시 준수해야 합니다.

---

### ⑤ 근거 없는 제조적 판단

예:

> "Torque가 높으므로 체결기가 고장났습니다."

이것은 데이터가 충분하지 않으면 말하면 안 됩니다.

대신:

> "Torque 차이가 확인되었으므로 체결기 조건 또는 설비별 차이를 추가 확인하는 것이 좋습니다."

정도로 표현해야 합니다.

---

# 11. 따라서 LLM Boundary를 이렇게 정의하는 것을 제안합니다

```
┌─────────────────────────────────────┐
│              LLM 영역               │
│                                     │
│ Intent Understanding                │
│ Analysis Planning                   │
│ Tool Selection                      │
│ Natural Language                    │
│ Result Interpretation               │
│ Insight Discovery                   │
│ Follow-up Analysis                  │
│ Report Generation                   │
│                                     │
└─────────────────┬───────────────────┘
                  │
             Guardrail
                  │
┌─────────────────▼───────────────────┐
│          Deterministic 영역         │
│                                     │
│ Data Validation                     │
│ Statistical Calculation             │

│ Visualization                       │
│ Result Verification                 │
│ Reproducibility                     │
└─────────────────────────────────────┘
```

이것을 앞으로 **LLM Boundary Architecture**라고 정의해 두는 것이 좋겠습니다.

# 12. 전체 시스템 Architecture

이제 이 개념을 실제 시스템 구조로 내려보겠습니다.

제가 추천하는 구조는 **8 Layer Architecture**입니다.

```
┌────────────────────────────────────────────┐
│ ① User Experience Layer                   │
│ Chat / Dashboard / Wizard / Analysis View │
└─────────────────────┬──────────────────────┘
                      │
┌─────────────────────▼──────────────────────┐
│ ② LLM Agent Layer                         │
│ Intent / Planning / Tool Calling / Dialog │
└─────────────────────┬──────────────────────┘
                      │
┌──────────────┬──────▼──────┬──────────────┐
│              │             │              │
▼              ▼             ▼              ▼
③ Data      ④ Statistics   ⑤ Visualization ⑥ Report
Engine      Engine         Engine           Engine
│              │             │              │
└──────────────┴──────┬──────┴──────────────┘
                      │
┌─────────────────────▼──────────────────────┐
│ ⑦ Rule / Validation Layer                 │
│ Statistical Rules / Guardrails / QA        │
└─────────────────────┬──────────────────────┘
                      │
┌─────────────────────▼──────────────────────┐
│ ⑧ Knowledge Layer                          │
│ Statistical KB / Manufacturing KB / RAG    │
└────────────────────────────────────────────┘
```

다만 실제 구현에서는 **Rule/Validation을 Agent보다 아래에만 두기보다, Agent가 Tool을 호출하는 경로에 Guardrail로 배치하는 것**을 권합니다.

---

# 13. 각각의 역할을 구체화하면

|Layer|역할|
|---|---|
|UX|사용자와 앱의 상호작용|
|LLM Agent|질문 이해 및 분석 orchestration|
|Data Engine|데이터 로딩·정제·검증|
|Statistical Engine|결정론적 통계 계산|
|Visualization Engine|그래프 생성|
|Report Engine|결과물 생성|
|Rule Engine|분석 조건 및 안전성 검증|
|Knowledge Layer|통계·제조 지식 제공|

여기서 새로운 핵심은 **Agent Orchestrator**입니다.

---

# 14. Agent Orchestrator

이것이 사실상 앱의 "두뇌"입니다.

예를 들어:

> "지난달 A라인과 B라인의 Torque 데이터를 비교하고 문제가 있는지 분석해줘."

Agent가 다음과 같이 처리합니다.

```
[User]
   │
   ▼
Intent Analysis
   │
   ▼
Data Discovery
   │
   ▼
Analysis Plan
   │
   ▼
Rule Validation
   │
   ▼
Tool Execution
   │
   ├── Descriptive
   ├── Box Plot
   ├── Variance
   └── t-test
   │
   ▼
Result Validation
   │
   ▼
Interpretation
   │
   ▼
Manufacturing Insight
```

즉 사용자는 **통계 메뉴를 거의 볼 필요가 없습니다.**

---

# 15. 그런데 기존 Analysis Navigator는 어떻게 되는가?

없애면 안 됩니다.

오히려 **두 가지 인터페이스를 동일한 Agent/Engine에 연결**합니다.

```
                  Analysis System
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        Guided Navigator      AI Chat
              │                 │
              └────────┬────────┘
                       ▼
                Analysis Agent
                       │
                       ▼
              Statistical Tools
```

따라서 사용자는:

### 초보자

Wizard를 사용하고

### 숙련자

자연어로 질문하고

### 전문가

직접 분석 Tool을 선택할 수 있습니다.

이 **3-Level UX**를 추천합니다.

---

# 16. Knowledge Layer가 특히 중요합니다

여기서 기존 앱과 가장 큰 차이가 생깁니다.

기존에는 제조 사례가 주로 정적인 Case Library였습니다.

LLM 버전에서는 이것을 **Manufacturing Knowledge Base**로 발전시킬 수 있습니다.

예를 들어:

```
Manufacturing Knowledge
│
├── Quality
│   ├── CTQ
│   ├── Defect
│   ├── FPY
│   └── Inspection
│
├── Process
│   ├── Assembly
│   ├── Fastening
│   ├── Forming
│   └── Welding
│
├── Equipment
│   ├── Machine
│   ├── Parameter
│   └── Maintenance
│
└── Statistics
    ├── Hypothesis Test
    ├── SPC
    ├── Capability
    └── DOE
```

이것을 RAG와 연결하면 Agent가 단순히 통계학만 아는 것이 아니라 **제조 현장의 언어로 설명**할 수 있게 됩니다.

---

# 17. 예를 들어 CTQ 분석이라면

사용자가:

> "세탁기 Drum의 X축 Run-out이 라인별로 차이가 있는지 확인해줘."

라고 질문합니다.

Agent가:

```
CTQ = Drum X-axis Run-out
Grouping = Line
Objective = Compare
Product = Washing Machine
```

을 파악합니다.

그리고 Knowledge Base에서:

```
Run-out 정의
측정방법
단위
규격
Target
측정주기
```

등을 확인합니다.

그 후 Statistical Tool을 호출합니다.

```
Descriptive
↓
Box Plot
↓
Variance
↓
ANOVA / Welch ANOVA
↓
Post-hoc
```

그리고 결과를 제조 언어로 설명합니다.

이것은 기존 앱의 **Manufacturing Applicability**를 LLM으로 훨씬 확장하는 것입니다.

---

# 18. 이번 단계에서 중요한 설계 원칙 하나 더

**LLM에게 전체 데이터를 그대로 던지는 구조는 피하는 것이 좋습니다.**

예를 들어 100만 건의 제조 데이터를 LLM Context에 넣는 방식은 적절하지 않습니다.

대신:

```
Raw Data
   ↓
Data Engine
   ↓
Statistics / Aggregation
   ↓
Structured Result
   ↓
LLM
```

구조로 만들어야 합니다.

예:

```
{
  "group_a": {
    "n": 523,
    "mean": 35.21,
    "sd": 0.42
  },
  "group_b": {
    "n": 487,
    "mean": 35.82,
    "sd": 0.61
  },
  "test": {
    "method": "Welch t-test",
    "difference": 0.61,
    "p_value": 0.002,
    "ci": [0.42, 0.80]
  }
}
```

이런 **Structured Statistical Result**를 LLM에게 전달하는 것입니다.

이 구조가 정확성, 비용, 속도, 보안 측면에서 모두 유리합니다.

# 20. 기존 앱과 새로운 앱의 본질적 차이

이제 차이가 명확해집니다.

|기존 앱|새로운 앱|
|---|---|
|Statistical Application|Statistical Agent|
|메뉴 중심|대화 중심|
|Navigator|Agent Planner|
|Rule|Rule + LLM|
|Template|Context-aware Generation|
|단일 분석|Multi-step Analysis|
|정적 Case Library|Knowledge Base + RAG|
|고정 Report|Dynamic Report|
|분석 결과 설명|분석 과정과 결과에 대한 대화|
|사용자가 다음 분석 결정|Agent가 다음 분석 제안|
|Data → Result|Question → Investigation → Insight|

# 21. 최종적으로 제품 정의를 이렇게 바꾸는 것을 권합니다

기존 정의:

> **“제조 현장의 질문을 통계적 판단으로 바꿔주는 프로그램.”** 통계분석 앱 제작 기획서.mdMD

LLM 버전에서는 한 단계 더 나아가:

> **“제조 현장의 질문을 이해하고, 필요한 통계분석을 수행하여 데이터에서 의미를 찾아내고, 엔지니어의 판단과 개선활동을 지원하는 AI 기반 통계분석 Agent.”**

로 정의할 수 있습니다.

그리고 서비스의 핵심 Loop는:

> **Ask → Analyze → Explain → Explore → Decide → Improve**

로 잡는 것을 제안합니다.

# 22. 다음 단계에서 결정해야 할 것

여기까지가 **1차 Concept Architecture**입니다.

이제 바로 기술 스택을 정하는 것보다 다음 단계인 **「실제 제조 현장 질문 → Agent가 어떻게 분석하는가」**를 설계하는 것이 중요합니다.

제가 다음 단계에서 제안하는 작업은 **대표적인 제조 현장 시나리오 10~15개를 선정하여 각각의 Agent Workflow를 설계하는 것**입니다.

예를 들면:

1. **두 공정의 CTQ 차이 분석**
2. **개선 전/후 효과 분석**
3. **3개 이상 공정 비교**
4. **설비별 품질 차이 분석**
5. **Shift별 품질 차이 분석**
6. **공정조건과 CTQ 관계 분석**
7. **불량률 증가 원인 탐색**
8. **이상 데이터 탐색**
9. **공정능력 분석**
10. **SPC 이상상태 분석**
11. **여러 변수 중 영향요인 탐색**
12. **분석 결과를 개선보고서로 변환**

이 10~15개의 사례를 실제로 설계하면 **“LLM을 어디에 쓰면 좋은가?”라는 추상적인 논의에서 벗어나 실제 제품 기능 요구사항으로 내려갈 수 있습니다.**

그리고 그 과정에서 **어떤 것은 LLM이 처리하고, 어떤 것은 Rule Engine이 처리하고, 어떤 것은 Statistical Tool이 처리하는지**까지 하나씩 정의하겠습니다.

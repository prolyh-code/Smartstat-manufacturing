좋습니다. 이제 **Step 3-8. Agent Evaluation Framework**으로 진행하겠습니다.

이번 단계는 단순히 "LLM 답변이 자연스러운가?"를 평가하는 것이 아니라, 이 앱의 핵심 가치인 **통계적 정확성 + 제조 현장 적용성 + 분석 과정의 신뢰성**을 검증하는 체계를 만드는 것입니다.

특히 이 프로젝트에서는 **LLM 자체를 평가하는 것과 Statistical Agent 전체를 평가하는 것을 분리**해야 합니다.

# Step 3-8. Manufacturing Statistical Agent Evaluation Framework

## 1. 평가의 기본 철학

이 Agent가 좋은 Agent인지 판단하는 기준은 다음과 같이 정의하는 것이 적절합니다.

> **사용자의 제조 현장 질문을 올바르게 이해하고, 적절한 통계분석을 선택·수행하며, 결과를 과잉 해석하지 않고, 필요한 경우 추가 분석을 통해 의사결정에 유용한 근거를 제공하는가?**

따라서 단순한 LLM 평가:

```
답변이 자연스러운가?
```

는 충분하지 않습니다.

다음처럼 평가해야 합니다.

```
사용자 질문
   ↓
① 질문 이해
   ↓
② 문제 정의
   ↓
③ 분석 계획
   ↓
④ Tool 선택
   ↓
⑤ 통계 계산
   ↓
⑥ 결과 검증
   ↓
⑦ 해석
   ↓
⑧ 추가 분석
   ↓
⑨ 제조적 판단
```

---

# 2. 평가를 5개 영역으로 구분

전체 평가를 다음 5개 영역으로 나누는 것을 권장합니다.

|영역|평가 대상|핵심 질문|
|---|---|---|
|A. Intent|질문 이해|사용자의 의도를 정확히 이해했는가?|
|B. Statistics|통계 분석|적절한 분석과 계산을 했는가?|
|C. Reasoning|분석 과정|올바른 순서와 근거로 분석했는가?|
|D. Manufacturing|제조 해석|현장 관점에서 의미 있는 판단을 했는가?|
|E. Safety/Trust|신뢰성|잘못된 결론이나 과잉 해석을 방지했는가?|

여기서 **B와 C를 분리하는 것**이 중요합니다.

통계 계산은 맞았지만 분석 방법을 잘못 선택할 수 있기 때문입니다.

---

# 3. Level 1 — Intent Understanding

가장 첫 번째 평가입니다.

예를 들어 사용자 질문:

> "A라인과 B라인의 Torque가 다른지 봐줘."

Agent가 다음과 같이 이해해야 합니다.

```
Problem Type
GROUP_COMPARISON

Response
Torque

Factor
Line

Groups
A, B

Objective
Difference Detection

Data Type
Continuous

Relationship
Independent
```

### 평가 항목

- Response Variable 정확성
- Factor 정확성
- Group 정확성
- 분석 목적 정확성
- 문제 유형 분류 정확성

이를 **Intent Accuracy**로 관리합니다.

---

# 4. Level 2 — Problem Modeling Accuracy

Intent를 이해한 다음에는 통계적 문제로 변환하는 능력을 평가합니다.

예:

> "개선 전후 Torque가 좋아졌는지 확인해줘."

단순히:

> `2-sample t-test`

라고 하는 것이 아니라,

```
Response = Torque
Condition = Before / After
Relationship = Paired? / Independent?
Objective = Improvement Verification
```

를 판단해야 합니다.

특히 **paired vs independent** 판단이 중요합니다.

---

# 5. Level 3 — Analysis Selection Accuracy

이제 실제 통계 방법 선택을 평가합니다.

예:

|질문|기대 분석|
|---|---|
|기준값과 비교|1-sample t-test|
|두 독립 그룹 비교|2-sample / Welch t-test|
|전후 비교|Paired t-test|
|3개 이상 그룹|ANOVA / Welch ANOVA|
|어떤 그룹이 다른가|Post-hoc|
|두 변수 관계|Correlation|
|영향관계 모델링|Regression|
|비정규/순위 데이터|Nonparametric|
|불량률 비교|Proportion / Chi-square|
|규격 대비 공정능력|Capability|

여기서 중요한 평가 지표가:

> **Method Selection Accuracy**

입니다.

---

# 6. 단순히 "정답 Tool"만 평가하면 안 됩니다

예를 들어 3개 그룹의 평균을 비교하는 문제에서 Agent가 ANOVA를 선택했다고 합시다.

하지만 분산이 크게 다르고 표본수가 불균형하다면:

> 일반 ANOVA보다 Welch ANOVA가 적절할 수 있습니다.

따라서 평가를 두 단계로 나누는 것이 좋습니다.

```
Method Family Accuracy
        ↓
Method Variant Accuracy
```

예:

```
ANOVA 계열 선택
       ↓
일반 ANOVA / Welch ANOVA
       ↓
적절한 Post-hoc
```

---

# 7. Level 4 — Assumption Evaluation

통계 Agent에서는 이 평가가 매우 중요합니다.

Agent가 분석 방법을 선택했더라도 다음 조건을 확인해야 합니다.

### 예

- 정규성
- 등분산성
- 독립성
- 선형성
- 잔차
- 표본 크기
- 반복측정 구조
- 결측값
- 이상치

따라서:

> **Assumption Check Accuracy**

를 별도로 평가해야 합니다.

---

# 8. 중요한 평가 시나리오: "유혹적인 오답"

Agent 평가에서는 정상적인 데이터만 사용하면 안 됩니다.

의도적으로 어려운 데이터를 넣어야 합니다.

예:

```
표본수가 매우 작은 데이터
+
극단적인 이상치
+
분산 불균형
+
결측값
+
불균형 표본
```

그리고 Agent가:

> "일반적인 t-test를 적용하겠습니다."

라고 한다면 감점합니다.

즉 **어려운 데이터에서 얼마나 잘못된 분석을 피하는가**를 평가해야 합니다.

---

# 9. Level 5 — Statistical Calculation Accuracy

여기서는 LLM을 평가하는 것이 아니라 **Statistical Engine**을 평가합니다.

예:

```
Input Dataset
      ↓
Statistical Engine
      ↓
Reference Software
      ↓
Expected Result
```

비교 항목:

- Mean
- SD
- SE
- Test statistic
- DF
- p-value
- Confidence Interval
- Effect size
- R²
- Regression coefficient

등입니다.

이 부분은 LLM에게 맡기면 안 됩니다.

---

이제 중요한 개념이 나옵니다.

## Golden Dataset

**정답을 미리 알고 있는 표준 데이터 세트**를 구축합니다.

예:

```

GD-004
Paired t-test

```

각 데이터에 대해:

```
Expected Method

Expected CI
Expected Effect Size

```

를 미리 정의합니다.

---

# 11. Golden Case가 이 프로젝트의 핵심 자산이 됩니다

결국 Agent의 품질은 **Golden Case Library**에 의해 지속적으로 평가될 수 있습니다.

예:

```
GC-001
"두 라인의 Torque 차이를 확인해줘."

Expected:
Problem = Group Comparison
Method = Welch t-test
Conclusion = Difference exists
Effect = Medium
```

또:

```
GC-011
"Torque 불량 원인을 찾아줘."

Expected:
Multi-step analysis
Defect rate
Machine comparison
Model comparison
Confounding check
Candidate cause
No causal overclaim
```

이것이 나중에 **Regression Test**의 기준이 됩니다.

---

# 12. Level 6 — Interpretation Accuracy

통계적으로 올바른 결과를 얻었다고 끝이 아닙니다.

Agent가 그것을 정확하게 설명해야 합니다.

예:

```
p = 0.003
```

정답:

> 통계적으로 유의한 차이가 관찰되었습니다.

잘못된 설명:

> A라인이 B라인보다 품질이 좋다는 것이 증명되었습니다.

더 나쁜 설명:

> A라인이 품질 문제의 원인입니다.

즉 다음을 평가해야 합니다.

### Interpretation Accuracy

- p-value 해석
- CI 해석
- Effect size 해석
- 방향성
- 통계적 유의성
- 실무적 유의성
- 제한조건

---

# 13. Statistical Significance vs Practical Significance

이 프로젝트에서는 이것을 **별도의 평가 항목**으로 만드는 것이 좋습니다.

예:

```
n = 10,000

평균 차이 = 0.03 N·m
p < 0.001
```

Agent:

> 통계적으로는 유의하지만 차이 크기가 매우 작아 실제 제조상 의미가 제한적일 수 있습니다.

이렇게 말해야 합니다.

반대로:

```
n = 8

평균 차이 = 2.5 N·m
p = 0.08
```

라면:

> 현재 표본에서는 통계적 유의성을 확인하지 못했지만, 차이의 크기가 현장적으로 중요한 수준인지 추가 검토가 필요합니다.

이런 판단을 할 수 있어야 합니다.

---

# 14. Level 7 — Manufacturing Interpretation

이 앱의 차별화 포인트입니다.

일반 통계 프로그램과 달리:

> **통계 결과 → 제조 의미**

까지 평가해야 합니다.

예:

### Statistical Result

> M2 불량률 5.4%, M1 2.1%, p=0.002

### Manufacturing Interpretation

> M2에서 불량 발생 수준이 높아 공정 점검 우선순위가 높다고 판단할 수 있습니다.

하지만:

> M2 설비가 불량의 원인이다.

라고 하면 과잉 해석입니다.

---

# 15. Causal Overclaiming 평가

이것은 반드시 독립 평가항목으로 두는 것을 권장합니다.

다음 표현을 위험 신호로 관리합니다.

```
"원인이다"
"때문이다"
"영향을 준다"
"증명되었다"
"확정되었다"
```

관측 데이터만으로는 다음 수준이 적절합니다.

```
관련성이 관찰됨
차이가 관찰됨
원인 후보
연관성이 높음
추가 검증 필요
```

---

# 16. Evidence Level을 평가 기준에 넣습니다

앞서 정의했던:

```
E0 No Evidence
E1 Observed Pattern
E2 Statistical Association
E3 Repeated/Cross-validated Candidate
E4 Experimental Verification
```

을 실제 평가에 사용합니다.

예:

|Agent 주장|필요한 Evidence|
|---|---|
|"M2 불량률이 높다"|E1|
|"M2와 불량률의 연관성이 있다"|E2|
|"여러 조건에서 M2 효과가 반복된다"|E3|
|"M2 설정 변경으로 불량이 감소했다"|E4|

따라서 Agent가 **E1 데이터로 E4 수준의 주장을 하는지** 검사합니다.

---

# 17. Level 8 — Next Analysis Accuracy

Agentic UX의 핵심 평가 항목입니다.

Agent가 분석 결과를 보고:

> "다음으로 무엇을 분석해야 하는가?"

를 제대로 판단하는지 평가합니다.

예:

```
Machine 차이 발견
+
Model 분포 차이 존재
```

그렇다면:

> Model을 통제하거나 층화하여 Machine 차이를 다시 확인

하는 것이 적절합니다.

단순히:

> "Operator를 분석해보겠습니다."

라고 하는 것보다 훨씬 높은 수준의 분석 판단입니다.

---

# 18. Next Best Analysis Score

앞서 정의한 기준을 그대로 평가식으로 활용할 수 있습니다.

```
Next Analysis Score
=
Relevance
× Expected Information Gain
× Data Availability
× Statistical Validity
× Manufacturing Impact
```

각 항목을 0~1로 평가할 수 있습니다.

예:

|후보 분석|Relevance|Information|Data|Validity|Impact|
|---|---|---|---|---|---|
|Model 분석|0.95|0.90|1.0|0.95|0.90|
|Operator 분석|0.50|0.40|1.0|1.0|0.40|
|Shift 분석|0.65|0.50|1.0|1.0|0.50|

따라서 Model 분석이 우선됩니다.

이것은 향후 Agent Planner의 평가 기준이 됩니다.

---

# 19. Level 9 — Agent Stop Accuracy

의외로 매우 중요한 평가 항목입니다.

좋은 Agent는 **언제 분석을 멈춰야 하는지도 알아야 합니다.**

예:

> 사용자의 질문이 이미 충분히 해결됨.

→ 종료

또는:

> 데이터가 부족함.

→ 종료 + 데이터 요구

또는:

> 관측 데이터만으로 인과관계 확인 불가능.

→ DOE/실험 제안

반대로:

```
분석
↓
분석
↓
분석
↓
분석
↓
분석
```

처럼 의미 없는 분석을 계속한다면 Agent 품질이 낮은 것입니다.

---

# 20. Level 10 — Human Decision Utility

마지막이 가장 중요합니다.

결국 사용자가 원하는 것은:

> **통계분석 자체가 아니라 제조 의사결정입니다.**

따라서 최종적으로:

### 질문

> "이 분석 결과가 실제 현장 의사결정에 도움이 되었는가?"

를 평가해야 합니다.

예:

```
분석 결과
↓
공정 점검 우선순위 결정
↓
추가 데이터 수집
↓
조건 변경
↓
개선 검증
```

으로 연결되는지를 평가합니다.

---

# 21. 전체 평가 체계

이제 평가 Framework를 하나의 구조로 정리할 수 있습니다.

```
                 Agent Evaluation
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
   Understanding   Statistics       Reasoning
       │               │               │
    Intent         Method          Planning
    Problem        Assumption      Next Analysis
    Modeling       Calculation     Stop Condition
       │               │               │
       └───────────────┼───────────────┘
                       ↓
                 Interpretation
                       │
              ┌────────┴────────┐
              ↓                 ↓
          Statistical       Manufacturing
          Interpretation    Interpretation
              │                 │
              └────────┬────────┘
                       ↓
                   Trust/Safety
                       │
               Causal Overclaim
               Evidence Level
                       ↓
                Decision Utility
```

---

# 22. 평가 점수 체계

초기 개발 단계에서는 100점 체계가 이해하기 쉽습니다.

|평가 영역|배점|
|---|---|
|Intent / Problem Understanding|10|
|Method Selection|15|
|Assumption / Data Validation|15|
|Statistical Calculation|15|
|Interpretation|15|
|Manufacturing Interpretation|15|
|Next Analysis|10|
|Trust / Overclaim Prevention|5|
|**합계**|**100**|

단, 이것은 **초기 제안 점수**입니다.

실제 Pilot 과정에서 현장 전문가 평가 결과를 바탕으로 가중치를 재조정하는 것이 좋습니다.

---

# 23. 합격 기준도 필요합니다

단순 평균 점수만 사용하면 안 됩니다.

예를 들어:

> 평균 95점이지만 잘못된 통계 방법을 선택하는 경우

는 실무에 사용할 수 없습니다.

따라서 **Critical Error**를 별도로 정의합니다.

### Critical Error

- 잘못된 통계 방법 적용
- 계산 결과 오류
- 데이터 구조 오판
- paired/independent 오판
- 중요한 assumption 무시
- p-value 오해
- 상관관계를 인과관계로 표현
- 근거 없이 원인을 확정
- 존재하지 않는 데이터를 근거로 주장
- 실제 결과와 다른 수치 생성

이 중 하나라도 발생하면 해당 Case는 **Fail**로 처리할 수 있습니다.

---

# 24. 특히 "통계 계산 오류"와 "LLM 환각"은 분리

이것은 Architecture와 직접 연결됩니다.

```
Statistical Engine 오류
```

와

```
LLM Interpretation 오류
```

는 원인이 완전히 다릅니다.

따라서 Evaluation도:

```
Layer 1
Statistical Engine Validation

Layer 2
Agent Reasoning Validation

Layer 3
LLM Interpretation Validation
```

으로 분리해야 합니다.

---

# 25. Test Dataset도 4종류로 나누는 것을 권장

### Type A — Normal Cases

정상적인 제조 데이터

### Type B — Boundary Cases

애매한 상황

### Type C — Adversarial Cases

Agent가 잘못 판단하기 쉬운 데이터

### Type D — Real Manufacturing Cases

실제 현장 데이터

이렇게 해야 합니다.

---

# 26. 예를 들어 Torque Case를 하나 만들면

### 사용자 질문

> "Torque 불량이 증가했는데 원인을 찾아줘."

### 데이터

```
Date
Machine
Model
Shift
Operator
Torque
Spec_LSL
Spec_USL
Defect
```

### 숨겨진 정답 구조

```
불량 증가
   ↓
Model C 생산 증가
   ↓
Model C에서 Torque 불량 증가
   ↓
특정 Machine에 Model C 집중
```

Agent가 단순히:

> "Machine 2가 원인입니다."

라고 하면 **Fail**입니다.

올바른 Agent는:

> "Machine 2에서 불량률이 높게 관찰되지만 Model C 생산비중이 높은 점을 고려하면 Machine 효과와 Model 효과를 구분할 필요가 있습니다."

라고 해야 합니다.

이 하나의 Case만으로도:

- Intent
- Planning
- Tool Selection
- Confounding
- Evidence
- Causal Overclaim
- Next Analysis

를 동시에 평가할 수 있습니다.

# 27. Golden Case의 구조

각 Case는 다음처럼 관리하는 것을 권장합니다.

```
Golden Case
│
├─ User Question
├─ Dataset
├─ Data Dictionary
├─ Expected Problem Model
├─ Expected Analysis Plan
├─ Expected Tool Calls
├─ Expected Statistical Results
├─ Expected Findings
├─ Expected Evidence Level
├─ Expected Hypotheses
├─ Expected Next Analysis
├─ Expected Final Conclusion
├─ Forbidden Conclusions
└─ Evaluation Criteria
```

이 구조가 매우 중요합니다.

단순히 "정답 문장" 하나를 저장하는 것이 아닙니다.

---

# 28. 왜 정답 문장 하나만 저장하면 안 되는가?

예를 들어:

> "B라인의 평균이 높다."

가 정답이라고 해봅시다.

Agent가:

> "B라인의 평균이 A라인보다 높으며, 95% 신뢰구간에서도 차이가 확인됩니다."

라고 하면 정답입니다.

또:

> "B라인에서 더 높은 값이 관찰되지만 실제 제조상 의미는 규격과 효과크기를 함께 검토해야 합니다."

도 정답일 수 있습니다.

따라서 LLM Agent에서는 **Reference Answer**보다 **Reference Reasoning / Evidence Structure**가 더 중요합니다.

---

# 29. 평가 방식도 Hybrid로 구성

저는 다음 3단계 평가를 권장합니다.

### ① Automated Evaluation

자동 비교

- 통계량
- p-value
- CI
- Method
- Tool Call
- JSON Schema
- Evidence Level

### ② LLM-as-Judge

자연어 해석 평가

- 논리성
- 누락
- 과잉 해석
- 설명 품질

단, LLM Judge도 단독 평가 기준으로 사용하지 않습니다.

### ③ Human Expert Evaluation

제조/품질/통계 전문가 평가

- 현장 적합성
- 판단 유용성
- 실제 의사결정 가능성

          ↓          ↓          ↓
      Automated    LLM Judge   Expert

# 31. 개발 단계에서의 평가 Cycle

Agent를 한 번 평가하고 끝내면 안 됩니다.

다음 Cycle을 구축해야 합니다.

```
Golden Cases
     ↓
Agent 실행
     ↓
Evaluation
     ↓
Error Analysis
     ↓
Prompt / Rule / Tool 수정
     ↓
Regression Test
     ↓
Release
```

특히 **Regression Test**가 중요합니다.

새로운 Prompt를 넣어서 UC-11은 좋아졌는데 UC-03의 t-test 선택이 나빠질 수 있습니다.

따라서 기존 Case 전체를 다시 돌려야 합니다.

# 32. 이 프로젝트에서 가장 중요한 KPI

기존 기획서에는 핵심 KPI로:

> 데이터 업로드 후 3분 이내에 비전문가가 올바른 분석 결과와 해석을 얻는 것

이라는 방향이 잡혀 있습니다. 통계분석 앱 제작 기획서.mdMD

LLM Agent 버전에서는 이것을 다음과 같이 확장하는 것을 권장합니다.

### Core KPI

> **사용자의 제조 질문으로부터 올바른 통계적 판단과 다음 행동을 얻는 데 걸리는 시간**

그리고 세부 KPI:

```
Method Selection Accuracy
Interpretation Accuracy
Critical Error Rate
Causal Overclaim Rate
Next Analysis Accuracy
Time to Decision
User Decision Utility
```

특히 **Critical Error Rate**는 0에 가깝게 관리해야 합니다.

# 34. Step 3-8의 핵심 결론

이번 단계에서 가장 중요한 결론은 이것입니다.

> **이 앱의 Agent 품질은 LLM의 답변 품질만으로 평가해서는 안 된다.**

평가 대상은 크게:

**① 문제를 제대로 이해했는가 → ② 적절한 통계 분석을 선택했는가 → ③ 계산이 정확한가 → ④ 결과를 올바르게 해석했는가 → ⑤ 제조적으로 의미 있는 판단을 했는가 → ⑥ 과잉 해석을 하지 않았는가 → ⑦ 다음 분석을 적절하게 선택했는가**

까지 이어져야 합니다.

그리고 이 모든 것을 **Golden Dataset / Golden Case / Regression Test** 체계로 지속적으로 검증해야 합니다.

## 다음 단계: Step 3-9 — Agent Failure & Exception Architecture

이제 한 가지가 더 필요합니다.

실제 현장에서 Agent가 항상 정상적으로 작동하지는 않습니다.

예를 들어:

- 데이터에 CTQ가 없음
- Spec 정보가 없음
- 표본수가 너무 작음
- 결측이 심함
- 그룹이 하나뿐임
- 동일 데이터가 반복됨
- 변수명이 모호함
- 사용자의 질문과 데이터가 불일치
- 통계적으로는 유의하지만 제조적으로 의미 없음
- 여러 원인이 동시에 존재
- 인과관계를 통계적으로 판단할 수 없음
- 분석을 계속해도 결론이 나오지 않음

이런 상황에서 **Agent가 어떻게 실패하고, 무엇을 사용자에게 말하며, 언제 분석을 중단하고, 언제 추가 데이터를 요청하고, 언제 DOE/현장검증으로 넘길 것인가**를 설계해야 합니다.

따라서 다음 **Step 3-9에서는 "정상적인 분석"이 아니라 "Agent가 잘못되거나 막히는 상황을 어떻게 처리할 것인가"를 중심으로 Failure/Exception Architecture를 설계**하는 것이 좋겠습니다.

이 단계까지 완료하면 Step 3의 Agent 기본 구조가 상당히 견고해지고, 이후에는 **Step 4. 실제 제조 Use Case별 Agent 시나리오 설계**로 넘어갈 수 있습니다.

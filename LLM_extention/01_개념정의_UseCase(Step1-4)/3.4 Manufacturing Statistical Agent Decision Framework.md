좋습니다. 앞 단계에서 **Use Case별 Agent Workflow**를 정의했으므로, 이제 **Step 3-4. Manufacturing Statistical Agent의 의사결정 구조(Agent Decision Framework)**를 설계하겠습니다.

이번 단계의 핵심은 하나입니다.

> **LLM이 “그럴듯한 분석”을 하는 것이 아니라, 정해진 통계적·제조적 판단 규칙 안에서 스스로 다음 분석을 선택하고 실행하도록 만드는 것**입니다.

기존 기획서의 **Statistical Engine → Rule Engine → LLM** 원칙은 그대로 유지하되, LLM의 역할을 단순한 결과 설명에서 **분석 계획 수립과 분석 흐름 조정(Orchestration)**까지 확대합니다.

# 2. Intent Recognition

첫 번째 판단은 통계기법이 아니라 **사용자의 의도(Intent)**입니다.

예를 들어 다음 질문들이 있다고 하겠습니다.

|사용자 질문|Intent|
|---|---|
|"현재 Torque 상태가 어떤지 봐줘"|현상 파악|
|"목표 35Nm와 차이가 있나?"|기준 대비 판단|
|"A라인과 B라인 차이가 있나?"|그룹 비교|
|"설비 3대 중 어느 것이 다른가?"|다중 그룹 비교|
|"개선 전후가 좋아졌나?"|변화 효과|
|"온도와 Torque가 관련 있나?"|관계 분석|
|"불량이 증가한 원인을 찾아줘"|원인 탐색|
|"공정능력이 충분한지 판단해줘"|공정 판단|

앞 단계에서 정의한 8개 질문 유형을 **Agent의 최상위 Intent Taxonomy**로 사용하면 됩니다.

```
A. 현상 파악
B. 기준 대비 판단
C. 그룹 비교
D. 다중 그룹 비교
E. 변화 효과 분석
F. 관계·영향 분석
G. 이상·원인 탐색
H. 공정 판단·개선 검증
```

이 구조는 기존 기획서의 "문제 중심 분석" 철학과 일치합니다.

# 3. Intent와 Analysis Method를 분리

여기서 매우 중요한 설계 원칙이 있습니다.

### 잘못된 구조

```
사용자 질문
 ↓
LLM
 ↓
t-test
```

### 올바른 구조

```
사용자 질문
 ↓
Intent
 ↓
Problem Model
 ↓
Data Structure
 ↓
Statistical Condition
 ↓
Analysis Method
```

예를 들어:

> "A라인과 B라인의 Torque가 다른지 봐줘."

를 받았다고 해서 무조건 2-Sample t-test를 실행해서는 안 됩니다.

Agent는 먼저:

```
두 그룹인가?
   ↓ YES
독립 데이터인가?
   ↓ YES
측정값이 연속형인가?
   ↓ YES
정규성/표본구조 확인
   ↓
분산 조건 확인
   ↓
2-Sample t 또는 Welch t
```

를 거쳐야 합니다.

기존 기획서에서도 이러한 **의사결정 Tree**가 이미 핵심 UX로 정의되어 있습니다. 통계분석 앱 제작 기획서.mdMD

# 4. Problem Model

Intent를 인식한 다음에는 질문을 **Problem Model**로 변환합니다.

예를 들어:

> "A라인과 B라인의 Torque 차이가 있나?"

내부 구조:

```
Problem Type
= GROUP_COMPARISON

Response Variable
= Torque

Factor
= Line

Groups
= A, B

Objective
= Difference Detection

Data Type
= Continuous

Relationship
= Independent
```

또 다른 질문:

> "개선 전후 Torque가 좋아졌는지 봐줘."

```
Problem Type
= CHANGE_EFFECT

Response
= Torque

Factor
= Before / After

Relationship
= Paired

Objective
= Improvement Verification
```

이렇게 하면 자연어를 통계 분석 시스템이 처리할 수 있는 **Structured Problem Representation**으로 변환할 수 있습니다.

# 5. Data Assessment

Agent는 분석 전에 데이터 구조를 확인합니다.

기존 기획서에서는 데이터 업로드 후 다음을 자동 탐색하도록 되어 있습니다.

- 숫자형 변수
- 범주형 변수
- 날짜
- 그룹 변수
- 결측값
- 중복값
- 이상값

LLM Agent에서는 이것을 한 단계 발전시켜 **Data Understanding**으로 만듭니다.

예:

```
Data Profile

Rows             125,430
Numeric          18
Categorical       7
Date              1

Potential Target
 ├─ Torque
 ├─ Dimension
 └─ Cycle Time

Potential Group
 ├─ Line
 ├─ Machine
 ├─ Shift
 └─ Model
```

Agent가 이 정보를 바탕으로 분석 계획을 수립합니다.

# 6. Analysis Planner

이제 Agent의 핵심인 **Analysis Planner**입니다.

사용자가:

> "Torque 불량 원인을 찾아줘."

라고 했을 때 Agent가 하나의 분석만 선택하지 않습니다.

### Analysis Plan

```
Step 1
불량률 변화 확인

Step 2
시간별 불량 추세 확인

Step 3
Line별 비교

Step 4
Machine별 비교

Step 5
Shift별 비교

Step 6
Model별 비교

Step 7
주요 후보요인 Screening

Step 8
후보요인 Deep Analysis

Step 9
Confounding 확인

Step 10
추가 검증
```

이것을 **Analysis Plan Graph**로 관리하는 것이 좋습니다.

# 7. Analysis Plan Graph

단순한 순차적인 Workflow보다 Graph 구조가 더 적합합니다.

```
                   [불량 증가 확인]
                          │
                          ▼
                   [시간 Trend]
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
           [Line]      [Machine]    [Shift]
              │           │           │
              └───────────┼───────────┘
                          ▼
                    [후보요인 선정]
                          │
                          ▼
                   [Deep Analysis]
                          │
```

즉, 고정된 Wizard가 아니라 **Dynamic Workflow**가 됩니다.

# 8. Rule Engine의 역할

이제 가장 중요한 **Guardrail**입니다.

LLM이 아무 통계기법이나 선택하지 못하도록 합니다.

예를 들어:

```
IF
response = continuous
AND
groups = 2
AND
independent = TRUE

THEN
candidate = 2-sample t-test
```

하지만:

```
IF
variance inequality = TRUE

THEN
candidate = Welch t-test
```

그리고:

```
IF
paired = TRUE

THEN
candidate = Paired t-test
```

이 규칙들은 LLM에게 맡기지 않는 것이 좋습니다.

### LLM

> "이 데이터는 두 그룹 비교 문제로 보입니다."

### Rule Engine

> "독립성 확인 결과 independent = TRUE"

### Statistical Engine

> "Welch t-test 실행"

이렇게 역할을 분리합니다.

---

# 9. Statistical Guardrail

Guardrail은 크게 **5단계**로 구성하는 것을 권합니다.

## Guardrail 1 — Data Guard

```
데이터 형식
결측
중복
표본수
범주 수
측정 단위
```

---

## Guardrail 2 — Method Guard

```
문제 유형
변수 유형
그룹 구조
paired / independent
```

---

## Guardrail 3 — Assumption Guard

```
정규성
분산
독립성
선형성
잔차
```

---

## Guardrail 4 — Result Guard

```
p-value
CI
effect size
sample size
test statistic
```

결과 간 모순이 있는지 확인합니다.

---

## Guardrail 5 — Interpretation Guard

LLM이 과도한 결론을 내리지 못하게 합니다.

예:

### 허용

> "Machine 2에서 높은 불량률이 관찰되었으며, 설비 관련 요인일 가능성이 있습니다."

### 금지

> "Machine 2가 불량의 원인입니다."

이 차이가 매우 중요합니다.

# 10. Evidence Level

Agent가 표현할 수 있는 결론의 수준도 정의해야 합니다.

저는 다음 **4단계 Evidence Level**을 권합니다.

|Level|의미|표현|
|---|---|---|
|**E0**|근거 없음|판단 불가|
|**E1**|현상 관찰|"~한 패턴이 관찰됨"|
|**E2**|통계적 관련성|"~와 유의한 차이/관계가 있음"|
|**E3**|반복·교차 검증|"주요 영향 후보로 판단"|
|**E4**|실험/개선 검증|"개선 효과가 확인됨"|

특히 **원인(Cause)**이라는 표현은 E4 수준에서 제한적으로 사용하도록 하는 것이 안전합니다.

# 11. Statistical Significance와 Practical Significance

이 부분은 기존 기획서의 매우 중요한 차별화 요소이므로 Agent Framework에도 직접 넣어야 합니다.

기존 기획서에서는:

> Statistical Significance

와

> Practical Significance

를 분리하고 있습니다.

Agent는 다음과 같이 판단해야 합니다.

```
Statistically Significant?
          │
       YES/NO
          │
          ▼
Effect Size
          │
          ▼
Specification / Target
          │
          ▼
Manufacturing Impact
          │
          ▼
Engineering Decision
```

예를 들어:

> p = 0.001

이라고 해서

> "중요한 문제입니다."

라고 하면 안 됩니다.

평균 차이가 0.02 mm인데 제품 허용범위가 ±5 mm라면 제조적으로 중요하지 않을 수 있습니다.

반대로 p-value가 0.08이라도 규격 한계에 접근하고 있다면 현장에서는 중요한 문제일 수 있습니다.

따라서 Agent가 **p-value 중심 판단을 하지 않도록 설계**해야 합니다.

기존 기획서가 Cohen's d, η², R², 평균 차이 등을 함께 제공하도록 한 것도 이 목적입니다. 통계분석 앱 제작 기획서.mdMD

# 12. Next Best Analysis

이제 이번 단계에서 가장 중요한 부분입니다.

## "다음에 무엇을 분석해야 하는가?"

기존 프로그램에서는 사용자가 직접 선택합니다.

LLM Agent에서는 결과를 보고 Agent가 **Next Best Analysis**를 추천해야 합니다.

예를 들어:

```
현재 분석
Machine별 불량률 비교
        ↓
결과
Machine 2가 높음
        ↓
질문
"왜 Machine 2가 높은가?"
        ↓
Next Best Analysis
Machine × Model 분석
```

또 다른 경우:

```
온도 ↔ Torque
Correlation = 0.55
        ↓
Next Best Analysis
Regression
```

또:

```
ANOVA
p < 0.05
        ↓
"어느 그룹?"
        ↓
Post-hoc
```

또:

```
Before vs After
p < 0.05
        ↓
Effect Size
        ↓
규격 대비 영향 검토
```

즉, **분석 결과 자체가 다음 질문을 생성**합니다.

# 13. Next Analysis Selection Score

이 기능을 보다 체계화하려면 후보 분석마다 점수를 부여할 수 있습니다.

예:

```
Next Analysis Score
=
Relevance
×
Expected Information Gain
×
Data Availability
×
Statistical Validity
×
Manufacturing Impact
```

개념적으로:

|후보 분석|관련성|정보가치|데이터|제조 영향|우선순위|
|---|---|---|---|---|---|
|Machine × Model|높음|높음|충분|높음|**1**|
|Shift 분석|중간|중간|충분|중간|2|
|Temperature Regression|낮음|중간|부족|중간|3|

이렇게 하면 Agent가 단순히 "할 수 있는 분석"이 아니라

> **"현재 상황에서 가장 가치 있는 다음 분석"**

을 선택할 수 있습니다.

# 14. Agent가 분석을 중단해야 하는 조건

Agentic 시스템에서 이것도 매우 중요합니다.

무한히 분석하면 안 됩니다.

다음 조건에서는 분석을 종료합니다.

### Stop Condition ①

질문에 충분히 답변함

### Stop Condition ②

추가 분석의 정보가치가 낮음

### Stop Condition ③

데이터가 부족함

### Stop Condition ④

통계적 결론보다 추가 실험이 필요함

### Stop Condition ⑤

인과관계를 확인하려면 DOE 또는 현장 실험이 필요함

예:

> "현재 관측 데이터만으로는 Machine 2가 원인이라고 확정할 수 없습니다. 다음 단계에서는 Machine 2의 공정조건을 통제한 비교 또는 실험적 검증이 필요합니다."

이렇게 **Agent가 "분석할 수 없다" 또는 "통계분석을 더 하는 것보다 실험이 필요하다"고 판단할 수 있어야 합니다.**

# 15. Agent State Machine

앞의 내용을 하나로 묶으면 Agent의 상태(State)는 다음과 같이 설계할 수 있습니다.

```
IDLE
 │
 ▼
UNDERSTAND
 │
 ▼
DEFINE_PROBLEM
 │
 ▼
ASSESS_DATA
 │
 ▼
PLAN_ANALYSIS
 │
 ▼
VALIDATE_PLAN
 │
 ▼
EXECUTE_ANALYSIS
 │
 ▼
VALIDATE_RESULT
 │
 ▼
INTERPRET
 │
 ▼
ASSESS_EVIDENCE
 │
 ├───────────────┐
 ▼               ▼
NEXT_ANALYSIS    FINAL_DECISION
 │
 ▼
PLAN_ANALYSIS
```

이 구조는 향후 실제 소프트웨어를 개발할 때 매우 중요합니다.

LLM을 단순 Chat UI에 붙이는 것이 아니라 **명확한 State Machine을 가진 Agent**로 설계할 수 있기 때문입니다.

# 16. Agent와 기존 기능의 관계

여기서 기존 기획서의 기능을 버릴 필요는 없습니다.

오히려 다음처럼 역할을 재정의하는 것이 좋습니다.

|기존 기능|LLM Agent 시대 역할|
|---|---|
|Analysis Navigator|Agent Intent Router|
|Analysis Wizard|Guided Agent Mode|
|Statistical Engine|Tool Layer|
|Interpretation Engine|LLM + Rule Engine|
|Case Library|Manufacturing Knowledge Base|
|Data Quality Check|Data Validation Tool|
|Report Engine|Agent Output Tool|
|Effect Size|Decision Evidence|
|SVG Engine|Visualization Tool|
|추가 분석 추천|Next Best Analysis|
|자동 해석|Agent Explanation|
|제조 사례|RAG/Knowledge|

따라서 **기존 기획서는 폐기하는 것이 아니라 Agent Architecture에 맞게 재구성하는 것**이 바람직합니다.

# 17. 최종적으로 만들어야 할 Agent의 모습

결국 사용자는 통계 프로그램을 사용하는 것이 아니라 **제조 데이터 분석가와 대화**하는 경험을 하게 됩니다.

예:

> **사용자**  
> "최근 세탁기 조립라인의 체결 Torque 불량이 증가했는데 원인을 찾아줘."

Agent:

> **1. 현상 확인**  
> 최근 2주 불량률이 이전 4주 대비 증가했습니다.
> 
> **2. 주요 차이 탐색**  
> Line, Machine, Shift, Model별 불량률을 비교했습니다.
> 
> **3. 주요 후보**  
> Machine 2와 Shift 3에서 상대적으로 높은 불량률이 확인되었습니다.
> 
> **4. 추가 검증**  
> Machine 2가 Model C를 주로 생산하고 있어 설비와 모델 효과가 혼재되어 있을 가능성이 있습니다.
> 
> **5. 현재 판단**  
> Machine 2는 주요 원인 후보이지만 현재 데이터만으로 원인이라고 확정할 수 없습니다.
> 
> **6. 권장 분석**  
> 다음으로 **Machine × Model별 불량률 분석**을 수행하는 것이 가장 적절합니다.

그리고 사용자가:

> "그 분석 계속해."

라고 하면 Agent는 **이전 State를 유지한 채 다음 분석을 실행**합니다.

이것이 우리가 목표로 하는 **Manufacturing Statistical Analysis Agent**의 핵심 경험입니다.

# 18. Step 3-4의 최종 산출물

이번 단계까지 진행하면 Agent의 의사결정 구조는 다음과 같이 정리됩니다.

```
                    USER QUESTION
                          │
                          ▼
                  [INTENT CLASSIFIER]
                          │
                          ▼
                  [PROBLEM MODEL]
                          │
                          ▼
                   [DATA ASSESSMENT]
                          │
                          ▼
                  [ANALYSIS PLANNER]
                          │
                          ▼
                  [RULE / GUARDRAIL]
                          │
                          ▼
                   [TOOL CALLING]
                          │
                          ▼
                [STATISTICAL ENGINE]
                          │
                          ▼
                 [RESULT VALIDATOR]
                          │
                          ▼
                   [EVIDENCE LEVEL]
                          │
                          ▼
                  [LLM INTERPRETER]
                          │
                          ▼
              [MANUFACTURING INSIGHT]
                          │
                          ▼
             [NEXT BEST ANALYSIS]
                    │           │
                   YES          NO
                    │           │
                    ▼           ▼
              NEXT ANALYSIS   DECISION
```

그리고 이 구조에서 **LLM의 역할은 4가지로 압축**할 수 있습니다.

> **Understand → Plan → Explain → Explore**

반면 통계적 신뢰성을 담당하는 것은:

> **Validate → Calculate → Verify**

입니다.

이 역할 분리가 이번 프로젝트의 가장 중요한 아키텍처 원칙이 될 것입니다.

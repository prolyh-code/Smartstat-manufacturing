좋습니다. 이번에는 **화면 구성이나 UI 디자인은 완전히 제외하고**, 사용자가 이 앱을 실제로 사용하는 과정에서 **무엇을 경험하고, Agent가 언제 개입하며, 사용자가 언제 판단·승인·수정하는가**라는 관점에서 UX를 검토하겠습니다.

기존 기획서의 UX 원칙은 상당히 좋은 출발점입니다. 특히 **현장 용어 우선, 하나의 판단, 그래프 우선, 통계적 판단과 제조적 판단의 분리, 제조 사례 연결**이라는 원칙은 LLM Agent로 확장하기에도 적합합니다.

다만 **기존 Wizard UX를 그대로 LLM에 연결하면 안 됩니다.** 기존 Wizard는 사용자가 분석 방법을 선택하기 위한 절차이고, Agent UX에서는 사용자가 **문제를 해결하기 위한 대화와 분석 과정**을 경험해야 하기 때문입니다.

---

# Step 3-7. Manufacturing Statistical Agent UX Architecture

## 1. UX의 기본 개념을 먼저 바꿔야 합니다

기존 앱의 UX는:

> **사용자가 분석을 선택하고 Agent가 도와주는 방식**

에 가깝습니다.

기존 Wizard도

> 무엇을 알고 싶은가 → 어떤 데이터를 가지고 있는가 → 몇 개의 그룹인가 → 독립적인가 → 조건 확인 → 분석 → 그래프 → 해석 → 보고서

라는 순차적 구조입니다.

LLM Agent에서는 이것을 다음과 같이 바꾸는 것이 좋습니다.

> **사용자가 문제를 말하면 Agent가 분석 과정을 구성하고, 사용자는 필요한 순간에만 개입한다.**

즉:

```
기존 UX
사용자
  ↓
분석 방법 선택
  ↓
분석 실행
  ↓
결과 확인
```

에서

```
Agent UX

사용자
  ↓
현장 문제 제시
  ↓
Agent가 문제 정의
  ↓
Agent가 데이터 확인
  ↓
Agent가 분석 계획 수립
  ↓
분석 실행
  ↓
중간 결과 설명
  ↓
사용자 판단/추가 요구
  ↓
Agent가 다음 분석
  ↓
종합 판단
```

으로 전환합니다.

---

# 2. 가장 중요한 UX 원칙

제가 권장하는 새로운 UX 원칙은 **8개**입니다.

### 원칙 1. 사용자는 통계 방법을 선택하지 않아도 된다

사용자가

> "2개 그룹이니까 t-test인가?"

를 생각하게 만들면 Agent의 존재 이유가 약해집니다.

사용자는:

> "A라인과 B라인의 품질 차이가 있는지 알고 싶다."

라고만 말하면 됩니다.

---

### 원칙 2. Agent는 분석 전에 문제를 명확히 한다

사용자의 질문이 애매하면 무조건 질문을 많이 하는 것이 아니라 **최소한의 확인만 합니다.**

예:

> "A라인과 B라인의 품질 차이가 있는지 확인해줘."

Agent:

> "어떤 품질특성을 비교할까요?"

데이터에 `Torque`, `Height`, `Run-out` 등이 있다면:

> "현재 데이터에서 비교 가능한 품질특성은 Torque, Height, Run-out입니다. 어느 항목을 대상으로 할까요?"

이것이 **Clarification UX**입니다.

---

# 3. 질문을 많이 하지 않는 것이 중요합니다

여기서 기존 Wizard와 큰 차이가 발생합니다.

기존 Wizard:

```
Q1 무엇을 알고 싶은가?
Q2 어떤 데이터를 가지고 있는가?
Q3 몇 개의 그룹인가?
Q4 독립적인가?
Q5 조건은?
```

Agent가 이 질문들을 그대로 순차적으로 사용자에게 물으면 **"대화형 Wizard"에 불과합니다.**

Agent는 가능한 것은 스스로 판단해야 합니다.

예:

```
사용자:
A/B 라인의 Torque 차이를 확인해줘.

Agent:
Response = Torque
Factor = Line
Groups = A/B
Data type = Continuous
Relationship = Independent
Objective = Difference detection
```

이 정도는 데이터와 문맥에서 Agent가 자동으로 정의해야 합니다.

---

# 4. 사용자의 개입은 "필요할 때만"

Agent UX를 다음 세 단계로 구분하는 것이 좋습니다.

|단계|사용자 역할|Agent 역할|
|---|---|---|
|자동|결과 확인|분석 수행|
|승인|분석 방향 확인|다음 분석 제안|
|질문|목적/조건 결정|사용자 의도 반영|

즉, 사용자는 모든 단계에서 버튼을 누르는 사람이 아니라 **분석 책임자**입니다.

---

# 5. Agent의 행동 수준을 3단계로 정의

앞서 정의한 Guided / Assisted / Agentic을 UX 관점에서 다시 정의할 필요가 있습니다.

## Level 1 — Guided

사용자가 분석 방향을 선택합니다.

```
"두 공정을 비교"
       ↓
Agent
"비교할 품질특성은?"
       ↓
사용자
"Torque"
       ↓
Agent
분석 실행
```

초보 사용자에게 적합합니다.

---

## Level 2 — Assisted

Agent가 분석을 계획하지만 중요한 단계에서 사용자에게 확인합니다.

```
사용자:
Torque 불량 차이를 확인해줘.

Agent:
설비별 차이를 먼저 확인하는 것이 적절합니다.
이 방향으로 분석하겠습니다.
```

그리고 실행합니다.

---

## Level 3 — Agentic

사용자가 목표만 제시합니다.

```
사용자:
Torque 불량의 원인을 찾아줘.

Agent:
데이터 품질 확인
→ 불량 추이
→ 설비
→ Model
→ Shift
→ Operator
→ 관계 분석
→ Confounding 검토
```

사용자는 최종 판단이나 중요한 방향 전환에만 개입합니다.

---

# 6. 따라서 UX의 핵심은 "Analysis Loop"입니다

단순한 Chat UX가 아니라 다음 Loop를 설계해야 합니다.

```
ASK
 ↓
UNDERSTAND
 ↓
PLAN
 ↓
ANALYZE
 ↓
EXPLAIN
 ↓
CHECK
 ↓
EXPLORE
 ↓
DECIDE
```

그리고 필요하면 다시:

```
EXPLORE
 ↓
ANALYZE
 ↓
EXPLAIN
```

으로 돌아갑니다.

이것이 **Agentic UX의 핵심 Loop**입니다.

---

# 7. Step 1 — ASK

사용자는 자연어로 질문합니다.

예:

> "최근 Torque 불량이 증가했는데 원인을 찾아줘."

또는:

> "A라인과 B라인의 Drum Run-out 차이가 있는지 확인해줘."

또는:

> "온도가 제품 치수에 영향을 주는지 분석해줘."

중요한 것은 **사용자가 통계 용어를 몰라도 된다는 것**입니다.

이 부분은 기존 기획서가 지향하는 "어떤 통계를 써야 할지 몰라도 사용할 수 있는 도구"와 정확히 연결됩니다.

---

# 8. Step 2 — UNDERSTAND

Agent는 질문을 내부적으로 구조화합니다.

예:

```
사용자 질문
"Torque 불량 원인을 찾아줘."

↓

Problem Model

Problem Type:
ROOT_CAUSE_EXPLORATION

Response:
Torque

Quality Event:
Torque Defect

Objective:
Identify factors associated with defect increase
```

여기서 사용자에게 반드시 이 내부 구조를 모두 보여줄 필요는 없습니다.

중요한 것은 Agent가 **자기 자신에게 문제를 명확하게 정의한 후 분석을 시작한다는 것**입니다.

---

# 9. Step 3 — PLAN

Agent가 분석 계획을 만듭니다.

예:

```
분석 목표
Torque 불량 증가 원인 탐색

1. 데이터 품질 확인
2. 불량률 변화 확인
3. 시간적 추이 확인
4. 설비별 비교
5. Model별 비교
6. Shift별 비교
7. 주요 요인의 관계 분석
8. Confounding 확인
9. 원인 후보 평가
```

여기서 중요한 UX 원칙:

> **Agent가 모든 계획을 한꺼번에 사용자에게 강요하지 않는다.**

처음에는:

> "먼저 불량 증가가 실제로 발생했는지 확인하고, 이후 설비·Model·Shift별 차이를 비교하겠습니다."

정도로 설명할 수 있습니다.

---

# 10. Step 4 — ANALYZE

Agent가 Tool을 호출합니다.

사용자는 Tool의 내부 실행을 볼 필요가 없습니다.

예:

```
profile_data()
       ↓
check_data_quality()
       ↓
defect_rate()
       ↓
trend_analysis()
```

다만 **무엇을 분석하고 있는지는 알려주는 것이 좋습니다.**

예:

> **1단계: 불량 증가 여부 확인 중**  
> 최근 3개월 데이터를 기준으로 불량률과 추이를 확인하고 있습니다.

이것은 UX에서 매우 중요합니다.

사용자가 "Agent가 지금 무엇을 하고 있는가?"를 이해할 수 있기 때문입니다.

---

# 11. Step 5 — EXPLAIN

분석 결과가 나오면 Agent는 숫자를 그대로 나열하지 않습니다.

기존 기획서의:

> Statistical Result → Manufacturing Interpretation

구조를 그대로 유지해야 합니다.

예:

### 통계 결과

```
Machine A defect rate = 2.1%
Machine B defect rate = 5.4%
p = 0.002
```

### Agent 설명

> B설비의 불량률이 A설비보다 약 3.3%p 높으며, 통계적으로 유의한 차이가 관찰됩니다.

그리고 한 단계 더:

> 다만 이것만으로 B설비가 원인이라고 판단할 수는 없습니다. Model별 생산비중 차이가 있는지 추가 확인하겠습니다.

이 마지막 문장이 **Agent UX의 핵심**입니다.

---

# 12. Step 6 — CHECK

Agent가 자기 분석 결과를 검증합니다.

여기서 일반 ChatGPT형 UX와 크게 달라집니다.

예:

```
Finding
M2 불량률 높음

↓

Check

Model 분포?
Shift 분포?
Operator 분포?
표본수?
측정조건?
```

따라서 Agent는 스스로:

> "현재 결과만으로 결론을 내려도 되는가?"

를 확인해야 합니다.

이것은 앞서 정의한 Result Guard / Interpretation Guard와 연결됩니다.

---

# 13. Step 7 — EXPLORE

분석 결과가 새로운 질문을 만들어냅니다.

예:

> M2의 불량률이 높다.

↓

> 그런데 M2는 Model C를 주로 생산한다.

↓

> 그러면 M2 때문인가, Model C 때문인가?

↓

> Model별로 다시 비교해야 한다.

이렇게 **분석 결과 → 새로운 질문 → 새로운 분석**으로 연결됩니다.

이것이 기존 앱의 "추가 분석" 기능을 Agent 중심으로 재해석한 것입니다.

기존 기획서에서도 결과 화면의 마지막 단계로 "원인을 찾으려면 어떤 분석을 해야 하는가?"를 제시하고 있습니다.

---

# 14. 여기서 "Next Analysis" UX를 크게 강화해야 합니다

기존:

> [다음 분석]

정도의 기능이었다면 Agent에서는 훨씬 의미가 커집니다.

Agent가:

> **현재 결과로 확인된 것**

과

> **아직 확인되지 않은 것**

을 구분해야 합니다.

예:

### 확인된 것

- M2의 불량률이 높음
- 통계적으로 유의한 차이

### 아직 확인되지 않은 것

- M2 자체의 영향
- Model 영향
- Shift 영향
- Operator 영향

### 다음 분석

> Model별로 M2/A를 비교하여 설비 효과와 Model 효과를 구분하겠습니다.

이것이 **Analysis Navigation**입니다.

---

# 15. 사용자는 Agent에게 방향을 바꿀 수도 있어야 합니다

예를 들어 Agent가:

> "다음으로 Operator별 차이를 확인하겠습니다."

라고 했을 때 사용자가:

> "Operator는 중요하지 않아. 설비만 집중해서 봐."

라고 할 수 있어야 합니다.

Agent는 기존 State를 유지하면서 분석 목표를 수정합니다.

```
Original Objective
Root Cause Exploration

User Constraint
Focus = Machine

↓

Updated Analysis Plan
Machine
→ Model confounding
→ Machine × Model
→ Process condition
```

따라서 Agent UX에는 **"분석 방향 수정"이라는 개념**이 반드시 필요합니다.

---

# 16. 사용자가 직접 분석을 추가할 수도 있어야 합니다

반대 방향도 중요합니다.

Agent가:

> "Model이 주요 후보입니다."

라고 했을 때 사용자가:

> "Shift도 한번 확인해줘."

라고 하면 됩니다.

Agent는:

```
Existing Analysis State
+
User Requested Analysis
```

를 결합합니다.

즉 사용자에게:

> "메뉴에서 Shift 분석을 찾아서 다시 시작하세요."

라고 요구하지 않습니다.

---

# 17. Agent는 질문해야 할 때와 질문하면 안 될 때를 구분해야 합니다

이것이 UX 설계에서 가장 어려운 부분입니다.

## 질문해야 하는 경우

### ① 분석 목적이 여러 개일 때

> "차이가 있는지 확인하려는 것인가요, 기준을 초과했는지 확인하려는 것인가요?"

### ② 분석 대상이 명확하지 않을 때

> "Torque와 Run-out 중 어느 품질특성을 분석할까요?"

### ③ 데이터가 부족할 때

> "현재 데이터에는 개선 전/후를 구분할 수 있는 정보가 없습니다."

### ④ 제조적 기준이 필요한 경우

> "통계적으로 차이는 확인할 수 있지만, 이 차이가 현장에서 중요한지는 관리 기준이 필요합니다."

---

# 18. 반대로 질문하면 안 되는 경우

데이터에서 판단할 수 있는 것을 사용자에게 다시 묻지 않아야 합니다.

예:

```
사용자:
A라인과 B라인의 Torque 차이를 봐줘.

Agent:
몇 개 그룹인가요?
```

→ **잘못된 UX**

데이터에서 A/B 두 그룹임을 알 수 있습니다.

또:

```
독립적인 데이터인가요?
```

를 무조건 묻는 것도 좋지 않습니다.

데이터 구조에서 판단하거나 불확실하면:

> "현재 데이터 구조상 독립 표본으로 판단했습니다. 동일 제품의 전후 측정값이라면 알려주세요."

처럼 **가정(Assumption)을 명시하는 방식**이 더 좋습니다.

---

# 19. "가정"을 UX에 명시해야 합니다

Agent 분석에서는 이 기능이 상당히 중요합니다.

예:

> **분석 가정**  
> 각 측정값은 서로 독립적인 것으로 판단했습니다.

또는:

> **주의**  
> 동일 제품의 반복 측정 여부를 데이터에서 확인할 수 없어 독립성을 확정할 수 없습니다.

이것은 기존 기획서가 모든 분석에 데이터, 방법, 가설, Assumption, Test Statistic, P-value, CI, Effect Size, Software Version, Timestamp를 기록하도록 한 신뢰성 전략과 직접 연결됩니다.

---

# 20. 결과를 "한 번에 끝내지 않는 UX"

기존 UX:

```
분석
 ↓
결과
 ↓
보고서
```

Agent UX에서는:

```
분석
 ↓
결과
 ↓
해석
 ↓
추가 질문
 ↓
추가 분석
 ↓
종합 결과
```

가 되어야 합니다.

따라서 사용자가 결과를 본 뒤 가장 자연스럽게 할 수 있는 행동은:

- "왜 그런지 찾아줘"
- "다른 설비와 비교해줘"
- "Model 영향을 제외하고 봐줘"
- "개선 전후를 비교해줘"
- "이 차이가 실제로 중요한지 판단해줘"
- "보고서로 정리해줘"

등이어야 합니다.

이것이 **Statistical Conversation**입니다.

---

# 21. 매우 중요한 UX: "분석 결과"와 "분석 결론"을 분리

이 부분은 기존 기획서의 원칙을 더욱 강화할 필요가 있습니다.

예:

### 분석 결과

> B라인 평균 Torque는 A라인보다 0.82 N·m 높습니다.  
> p = 0.003.

### 통계적 판단

> 두 라인의 평균에는 통계적으로 유의한 차이가 있습니다.

### 제조적 판단

> 0.82 N·m의 차이가 제품 규격 또는 공정능력에 영향을 미치는지는 추가 검토가 필요합니다.

기존 기획서도 이처럼 Statistical Significance와 Practical Significance를 분리하고 있습니다.

Agent에서는 이것을 **모든 분석의 기본 UX 패턴**으로 만드는 것이 좋습니다.

# 22. 최종 결론은 Evidence 기반으로 작성

Agent가 최종적으로:

> "M2가 원인입니다."

라고 말하는 것은 위험합니다.

대신:

```
관찰
M2의 불량률이 높음

통계적 근거
M1 대비 유의한 차이

추가 확인
Model 분포 차이 존재

현재 판단
M2는 원인 후보이지만
M2 자체의 효과로 단정할 수 없음

다음 단계
Model을 통제한 비교 필요
```

이런 구조가 되어야 합니다.

# 23. 사용자가 원하는 깊이를 조절할 수 있어야 합니다

같은 분석이라도 사용자는 서로 다른 수준을 원합니다.

예:

> "쉽게 설명해줘."

→ 현장 작업자 수준

> "통계적으로 자세히 설명해줘."

→ 통계적 결과와 가정까지

> "보고서 수준으로 정리해줘."

→ 재현 가능한 분석 보고서

기존 기획서의 **Field User / Engineer / Statistical Expert** 3단계 설명 체계를 Agent UX에서 활용할 수 있습니다.

중요한 것은 이것을 **별도의 복잡한 설정으로 만들기보다 자연어로 전환 가능하게 하는 것**입니다.

# 24. "Teach while using" UX

기존 앱의 중요한 장점 중 하나가 분석 과정 자체가 학습이 되도록 설계되어 있다는 점입니다. 통계분석 앱 제작 기획서.mdMD

LLM Agent에서는 이것을 훨씬 발전시킬 수 있습니다.

예:

> 왜 Welch t-test를 사용했나요?

Agent:

> 두 설비의 분산이 동일하다고 보기 어려워 일반적인 Student's t-test보다 Welch t-test가 적절하다고 판단했습니다.

그리고 사용자가:

> Welch t-test가 뭐야?

라고 물으면 바로 설명합니다.

따라서 **분석 → 질문 → 학습 → 다시 분석**이 하나의 UX 안에서 이루어집니다.

# 25. Agent가 "모르겠다"고 말할 수 있어야 한다

이것도 매우 중요합니다.

예:

> "현재 데이터만으로는 원인을 특정할 수 없습니다."

또는:

> "통계적 연관성은 확인했지만 인과관계를 입증할 데이터가 없습니다."

또는:

> "현재 데이터 구조에서는 반복측정 여부를 확인할 수 없어 Paired t-test를 적용할 수 없습니다."

이것은 UX 실패가 아닙니다.

오히려 **신뢰성 높은 Agent의 정상적인 행동**입니다.

# 26. "분석 종료"도 Agent의 중요한 UX 기능

Agent는 무한히 분석해서는 안 됩니다.

다음 중 하나면 종료합니다.

### Stop Condition ①

질문이 충분히 답변됨

### Stop Condition ②

추가 분석의 정보가치가 낮음

### Stop Condition ③

데이터 부족

### Stop Condition ④

통계분석보다 현장 확인이 필요

### Stop Condition ⑤

인과관계 확인을 위해 실험/DOE 필요

예:

> "현재 데이터로는 Model C와 불량률의 연관성까지 확인했습니다. 추가적인 관측 데이터 분석만으로 인과관계를 확정하기는 어렵습니다. 공정조건을 통제한 실험 또는 DOE가 필요합니다."

이렇게 **분석을 멈출 줄 아는 Agent**가 되어야 합니다.

# 28. 기존 UX와 Agent UX의 가장 큰 차이

|기존 앱|LLM Agent|
|---|---|
|분석을 선택|문제를 말함|
|Wizard를 따라감|Agent가 계획|
|한 번의 분석|여러 분석 연결|
|결과를 확인|결과의 의미를 질문|
|추가 분석 선택|Agent가 Next Analysis 제안|
|사용자가 분석 순서 결정|Agent가 분석 순서 계획|
|결과 중심|Evidence 중심|
|분석 완료|의사결정 완료|
|통계 Tool 사용|문제 해결 과정 자체가 UX|

따라서 **기존 Wizard를 없애는 것이 아니라 역할을 바꾸는 것**이 좋습니다.

> Wizard = **초보자를 위한 Guided Agent**

> Chat = **자연어 기반 Assisted/Agentic Agent**

> Statistical Engine = **신뢰성 있는 계산 인프라**

이렇게 통합합니다.

# 29. 제가 보는 핵심 UX 개선점

기존 기획서의 UX는 이미 상당히 잘 잡혀 있습니다. 특히 "그래프를 보고 → 결과를 이해하고 → 공정을 판단한다"는 방향은 유지할 가치가 큽니다.

다만 LLM 통합을 전제로 하면 **다음 6가지는 반드시 강화**하는 것을 권장합니다.

### ① Wizard → Agent Conversation

단순 절차 진행이 아니라 **문제 해결 대화**로 변경

### ② Additional Analysis → Next Best Analysis

단순히 "다음 분석"이 아니라 **왜 다음 분석이 필요한지 설명**

### ③ Result → Evidence

숫자를 보여주는 것을 넘어 **주장을 뒷받침하는 근거를 축적**

### ④ Interpretation → Reasoning

결과를 설명하는 것뿐 아니라 **왜 이 분석을 했는지 설명**

### ⑤ User Input → User Intervention

사용자가 매 단계 입력하는 구조에서 **Agent가 대부분 수행하고 사용자는 방향을 수정**

### ⑥ Analysis Complete → Decision Ready

통계분석이 끝났다는 것이 아니라:

> **"현재 데이터로 무엇을 말할 수 있고, 무엇을 아직 말할 수 없는가?"**

까지 도달해야 분석이 완료된 것으로 봅니다.

# 30. UX 관점에서 새롭게 정의하는 제품의 핵심 경험

기존 제품의 핵심 경험은:

> **현장 문제 → 질문 → 분석 → 시각화 → 해석 → 판단**

이었습니다. 통계분석 앱 제작 기획서.mdMD

LLM Agent에서는 이를 한 단계 발전시켜 다음과 같이 정의하는 것을 권장합니다.

> **현장 문제 → 질문 → 문제 정의 → 분석 계획 → 분석 → 근거 발견 → 추가 탐색 → 통계적 판단 → 제조적 판단 → 개선 행동**

즉, 제품의 최종 목적은 **"통계 결과를 보여주는 것"이 아니라 "사용자가 더 나은 제조 판단을 하도록 만드는 것"**입니다.

## 다음 단계: Step 3-8 — Agent Evaluation Framework

여기까지 오면 중요한 문제가 하나 남습니다.

**"이 Agent가 정말 좋은 Agent인지 어떻게 평가할 것인가?"**

특히 이 앱에서는 일반적인 LLM 평가만으로는 부족합니다.

예를 들어 답변이 자연스럽다고 해서 좋은 Agent가 아닙니다.

다음 항목을 별도로 평가해야 합니다.

```
① 질문 이해 정확성
② 적절한 분석 선택률
③ 통계 계산 정확성
④ Assumption 판단 정확성
⑤ 잘못된 분석 방지율
⑥ 결과 해석 정확성
⑦ 제조적 해석의 적절성
⑧ 인과관계 과잉해석 방지
⑨ Next Analysis 적절성
⑩ 최종 의사결정 유용성
```

그리고 특히 이 프로젝트에서는 **Golden Dataset + Golden Analysis + Golden Interpretation**을 만들어 Agent를 지속적으로 검증하는 체계가 필요합니다.

다음 **Step 3-8에서는 이 평가 체계를 실제 개발에 사용할 수 있는 수준까지 설계**하는 것이 좋겠습니다.

# Step 3-5. Manufacturing Statistical Agent — Tool Architecture

이번 단계의 목표는 단순히 `t_test()` 같은 함수를 나열하는 것이 아니라,

> **LLM이 어떤 상황에서 어떤 Tool을 선택하고, Tool의 결과를 어떻게 다음 분석으로 연결하며, 최종적으로 제조 현장의 판단까지 어떻게 전달할 것인가**

를 설계하는 것입니다.

기존 기획서에서 정의한 통계 기능은 그대로 활용하되, LLM이 직접 통계를 계산하는 것이 아니라 **LLM → Tool → 검증 → LLM** 구조로 재구성하는 것이 핵심입니다. 통계분석 앱 제작 기획서.mdMD

---

# 1. Tool Architecture의 기본 원칙

전체 구조를 먼저 한 장으로 표현하면 다음과 같습니다.

```
                    User Question
                         │
                         ▼
                ┌─────────────────┐
                │   LLM Agent     │
                │ Understand/Plan │
                └────────┬────────┘
                         │
                  Analysis Plan
                         │
                         ▼
                ┌─────────────────┐
                │  Rule / Guard   │
                │    Engine       │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ Statistical     │
                │ Tool Layer      │
                └────────┬────────┘
                         │
                  Statistical Result
                         │
                         ▼
                ┌─────────────────┐
                │ Result Validator│
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │   LLM Agent     │
                │ Explain/Explore │
                └────────┬────────┘
                         │
                         ▼
                Manufacturing Insight
                         │
                  ┌──────┴──────┐
                  ▼             ▼
             Next Analysis    Final Decision
```

여기서 가장 중요한 원칙은 **LLM이 Tool의 역할을 대체하지 않는 것**입니다.

### LLM이 하는 일

- 사용자의 질문 이해
- 문제 유형 분류
- 분석 목적 정의
- 필요한 데이터 판단
- 분석 계획 수립
- 다음 분석 결정
- 결과 해석
- 제조 관점으로 설명
- 추가 분석 제안

### Statistical Tool이 하는 일

- 데이터 계산
- 통계 검정
- 그래프 생성
- 신뢰구간 계산
- 효과크기 계산
- 회귀계수 계산
- 이상치 탐색
- SPC 계산

즉,

> **LLM = Reasoning / Orchestration**  
> **Tool = Calculation / Evidence**

로 역할을 명확히 분리합니다.

# 2. Tool의 전체 분류

Tool은 크게 **7개 계층**으로 구성하는 것이 좋습니다.

|Layer|Tool 영역|주요 역할|
|---|---|---|
|T1|Data Tools|데이터 이해·검증|
|T2|Exploration Tools|현상 파악|
|T3|Statistical Test Tools|가설검정|
|T4|Modeling Tools|관계·영향 분석|
|T5|Quality/SPC Tools|제조 공정 판단|
|T6|Visualization Tools|그래프 생성|
|T7|Reporting Tools|결과 저장·보고|

그리고 별도로 **Knowledge Tools**와 **Agent Control Tools**를 두는 구조를 권장합니다.

# 3. T1 — Data Tools

Agent가 통계분석을 시작하기 전에 가장 먼저 사용하는 Tool입니다.

## 3-1. `profile_data()`

### 목적

데이터가 무엇인지 파악합니다.

### Input

```
{
  "dataset_id": "DS001"
}
```

### Output

```
{
  "rows": 12500,
  "columns": 12,
  "variables": [
    {
      "name": "Torque",
      "type": "numeric",
      "unit": "N·m"
    },
    {
      "name": "Machine",
      "type": "categorical",
      "levels": ["M1", "M2", "M3"]
    },
    {
      "name": "Model",
      "type": "categorical",
      "levels": ["A", "B", "C"]
    }
  ]
}
```

Agent는 이것을 보고

> Torque는 연속형 Response이고 Machine은 범주형 Factor이다.

라고 판단합니다.

---

# 4. `check_data_quality()`

통계분석 전에 반드시 호출합니다.

검사 항목은 기존 기획서의 데이터 품질 원칙과 연결합니다.

- completeness
- uniqueness
- validity
- consistency
- accuracy/reliability

### Output 예

```
{
  "missing_rate": 0.8,
  "duplicate_rows": 12,
  "invalid_values": 3,
  "outlier_candidates": 47,
  "unit_consistency": true,
  "quality_status": "WARNING"
}
```

중요한 점은 **Outlier = 삭제 대상**으로 판단하지 않는 것입니다.

Tool은

> “이상치 후보가 존재한다.”

까지만 말하고, 실제 처리 여부는 Agent가 제조 맥락과 함께 판단하도록 합니다.

---

Std
Variance

이 Tool은 사실상 모든 분석의 출발점입니다.

여기부터는 **현상 파악 → 패턴 발견**을 담당합니다.

기존 앱의 핵심 그래프였던 Histogram, Box Plot, Scatter Plot을 그대로 Tool화합니다.

---

# 7. `group_summary()`

제조 현장에서 상당히 중요한 Tool입니다.

예를 들어 사용자가

> "설비별 Torque 차이가 있는지 봐줘."

라고 했다고 합시다.

Agent가 바로 t-test를 실행하지 않고 먼저:

```
group_summary(
    response = Torque,
    factor = Machine
)
```

을 실행합니다.

결과:

|Machine|N|Mean|Std|Median|
|---|---|---|---|---|
|M1|3,100|34.8|2.1|34.7|
|M2|3,050|37.1|3.4|36.8|
|M3|3,200|35.0|2.0|35.1|

그러면 Agent는

> M2의 평균 Torque가 상대적으로 높고 산포도 큰 것으로 관찰된다.

라고 판단하고 다음 Tool을 선택합니다.

# 9. 중요한 변화: Tool은 단순 계산기가 아니다

예를 들어 `two_sample_t_test()`의 Input을 단순하게 만들면:

```
data + group
```

정도로 끝납니다.

그러나 Agent Architecture에서는 이것보다 훨씬 엄격하게 정의해야 합니다.

### Input

```
{
  "dataset_id": "DS001",
  "response": "Torque",
  "factor": "Machine",
  "groups": ["M1", "M2"],
  "alternative": "two-sided",
  "confidence_level": 0.95
}
```

그리고 Tool 내부에서:

1. 독립성 확인
2. 표본 수 확인
3. 분산 조건 확인
4. 적절한 검정 수행
5. 효과크기 계산
6. CI 계산
7. 결과 구조화

를 수행합니다.

즉,

> **Tool 자체가 Statistical Contract를 준수해야 합니다.**

# 10. Statistical Result 표준 구조

이 부분이 **Step 3-5에서 가장 중요한 설계 요소 중 하나**입니다.

모든 통계 Tool의 결과를 서로 다른 형식으로 반환하면 Agent가 복잡해집니다.

따라서 모든 Tool이 공통적으로 다음 구조를 반환하도록 설계합니다.

```
Statistical Result
│
├─ Analysis Metadata
├─ Data Information
├─ Method
├─ Assumption Check
├─ Test Statistic
├─ P-value
├─ Confidence Interval
├─ Effect Size
├─ Practical Significance
├─ Visualization Reference
└─ Validation Status
```

예:

```
{
  "analysis_id": "AN001",
  "method": "Welch Two Sample t-test",

  "data": {
    "response": "Torque",
    "factor": "Machine",
    "groups": ["M1", "M2"],
    "n": {
      "M1": 3100,
      "M2": 3050
    }
  },

  "result": {
    "mean_difference": 2.3,
    "t": -12.4,
    "df": 5120,
    "p_value": "<0.001",
    "ci95": [1.95, 2.65]
  },

  "effect_size": {
    "cohens_d": 0.82
  },

  "assumption": {
    "variance_homogeneity": false,
    "independence": "assumed"
  },

  "validation": {
    "status": "VALID"
  }
}
```

이렇게 하면 LLM은 숫자를 다시 계산할 필요가 없습니다.

# 14. T6 — Visualization Tools

그래프는 단순히 결과를 꾸미는 기능이 아니라 **Agent의 분석 증거(Evidence)** 역할을 해야 합니다.

```

# 16. Knowledge Tools

LLM 기반으로 전환하면서 새롭게 중요해지는 부분입니다.

통계 Tool만 가지고는 다음 질문에 답하기 어렵습니다.

> "Torque가 35±5 N·m인데 평균은 규격 안에 있는데 왜 불량이 발생하지?"

이것은 통계 문제가 아니라 **제조 지식 + 품질 지식 + 공정 맥락**의 문제입니다.

따라서 Knowledge Layer를 별도로 둡니다.

```
Knowledge Tools
│
├─ Statistical Knowledge
│
├─ Manufacturing Knowledge
│
├─ Quality Knowledge
│
├─ Process Knowledge
│
└─ Company Knowledge
```

향후 RAG로 구현할 수 있습니다.

# 17. Tool 호출 조건

이제 중요한 질문입니다.

> **LLM은 언제 어떤 Tool을 호출하는가?**

이것을 Prompt에 전부 맡기면 안 됩니다.

다음과 같은 **Tool Selection Rule**을 둡니다.

|상황|1차 Tool|다음 Tool|
|---|---|---|
|데이터가 무엇인지 모름|`profile_data`|`check_data_quality`|
|현재 상태 파악|`summarize_variable`|Histogram|
|두 그룹 비교|`group_summary`|t-test/Welch|
|3개 이상 그룹|`group_summary`|ANOVA/Welch|
|전후 비교|`paired_summary`|Paired t-test|
|관계 확인|`scatter_plot`|correlation|
|영향 분석|correlation|regression|
|불량 증가|defect_rate|trend/Pareto|
|불량 원인 탐색|defect_rate|group comparison|
|공정능력|capability|distribution check|
|공정 이상|control chart|anomaly analysis|

즉,

> **LLM은 자유롭게 Tool을 선택하는 것이 아니라 Rule Engine이 허용한 범위에서 선택한다.**

# 19. Tool Chain의 핵심은 "분석 결과가 다음 질문을 만든다"는 것

예를 들어:

```
Machine M2의 불량률이 높다.
```

에서 분석이 끝나면 안 됩니다.

Agent는 다음 질문을 생성합니다.

```
왜 M2가 높은가?
```

그리고:

```
M2의 특정 Model 생산 비중이 높은가?
```

라는 Confounding Check를 합니다.

그 결과:

```
M2 → Model C 생산비중 82%
Model C → 불량률 높음
```

이라면,

> "M2 자체의 영향인지 Model C 생산 비중에 따른 차이인지 추가 확인이 필요하다."

라는 결론을 내립니다.

이것이 **통계 분석 Agent와 단순 통계 계산기의 가장 큰 차이**입니다.

# 20. Evidence Object

Agent가 분석 결과를 장기적으로 기억하고 다음 분석에 사용하려면 `Evidence`라는 개념을 두는 것이 좋습니다.

예:

```
{
  "evidence_id": "E005",
  "type": "STATISTICAL_ASSOCIATION",

  "claim": "Machine M2 has a higher defect rate.",

  "support": [
    "AN015",
    "AN018"
  ],

  "strength": "E2",

  "limitations": [
    "Model distribution differs by machine"
  ]
}
```

앞서 정의한 Evidence Level과 연결합니다.

```
E0  No Evidence
E1  Observed Pattern
E2  Statistical Association
E3  Repeated / Cross-validated
E4  Experimental Verification
```

따라서 Agent가

> "M2가 원인입니다."

라고 쉽게 단정하는 것을 방지할 수 있습니다.

대신:

> **"M2는 불량률 증가와 통계적으로 관련된 주요 후보입니다. 다만 Model별 생산비중 차이가 존재하므로 M2 자체의 인과효과는 추가 검증이 필요합니다."**

처럼 표현하게 됩니다.

# 21. 전체 Data Contract

Step 3-5의 최종 핵심 구조를 하나로 정리하면 다음과 같습니다.

```
┌─────────────────────────────┐
│       User Question         │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│       Problem Model         │
│ What / Target / Factor      │
│ Response / Objective        │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│        Data Profile         │
│ Variables / Types / N       │
│ Missing / Quality            │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐

# 22. 기존 앱과 LLM Agent의 대응 관계

기존 기획서를 버리는 것이 아니라 **기존 기능을 Agent Architecture 안으로 재배치**하는 것이 핵심입니다.

|기존 기능|LLM Agent Architecture|
|---|---|
|Analysis Navigator|Intent Router|
|Wizard|Guided Agent|
|Data Quality|Data Validation Tool|
|Statistical Engine|Statistical Tool Layer|
|Interpretation Engine|LLM + Rule Engine|
|Case Library|Manufacturing Knowledge|
|Effect Size|Evidence|
|SVG Engine|Visualization Tool|
|Additional Analysis|Next Best Analysis|
|Report Engine|Output/Report Tool|

따라서 지금까지 작성한 기획서는 상당 부분 **폐기할 필요가 없습니다.**

오히려 기존 기획서가 정의한 통계 Engine과 해석 체계를 **Agent가 사용할 Tool과 Knowledge로 승격**시키는 방향이 적절합니다. 통계분석 앱 제작 기획서.mdMD

# 23. 여기서 중요한 설계 결론

이번 Step 3-5를 통해 앱의 본질이 상당히 명확해집니다.

기존:

> **Statistical Analysis App**

에서

새로운:

> **Manufacturing Statistical Analysis Agent**

로 발전합니다.

그리고 핵심 경쟁력은 통계분석 함수의 개수가 아닙니다.

### ① 질문을 이해하는 능력

```
"설비 2번에서 왜 불량이 많이 나와?"
```

→ 단순 t-test가 아니라 **원인 탐색 문제**로 해석

### ② 분석을 연결하는 능력

```
현상 → 비교 → 관계 → 영향 → 검증
```

### ③ 통계적 과잉해석을 막는 능력

```
Correlation ≠ Causation
Statistical Significance ≠ Practical Significance
```

### ④ 제조 관점으로 번역하는 능력

```
p = 0.003
```

을 보여주는 것이 아니라

> "설비 간 평균 차이는 통계적으로 유의하며, 차이의 크기도 현장 관리 기준에서 무시하기 어려운 수준이다."

라고 설명

### ⑤ 다음 행동을 제안하는 능력

> "현재 결과만으로 설비 자체가 원인이라고 판단하기 어렵습니다. Model별 생산비중을 통제한 추가 분석이 필요합니다."

이 다섯 가지가 핵심입니다.

# 24. 다음 단계 — Step 3-6

이제 자연스럽게 다음 단계로 넘어갈 수 있습니다.

## **Step 3-6. Agent Memory & Analysis State Architecture**

여기서는 다음을 설계하는 것이 좋습니다.

1. **Agent가 분석 과정에서 무엇을 기억해야 하는가**
2. 사용자 질문과 분석 결과를 어떻게 State로 관리할 것인가
3. 이전 분석 결과를 다음 분석에 어떻게 전달할 것인가
4. `Analysis Plan Graph`를 어떻게 저장할 것인가
5. `Evidence`를 어떻게 축적할 것인가
6. 사용자가 중간에 질문을 바꾸면 어떻게 처리할 것인가
7. 여러 데이터셋을 사용한 분석을 어떻게 관리할 것인가
8. "이 분석은 이미 수행했다"를 어떻게 기억할 것인가
9. 최종 보고서에 분석 과정과 근거를 어떻게 재구성할 것인가

특히 **Agent State**가 제대로 설계되어야 나중에 단순한 "통계 챗봇"이 아니라 **실제로 여러 단계의 제조 분석을 수행하는 Agent**가 됩니다.

다음 단계에서는 이를 **실제 JSON Schema 수준의 데이터 구조까지 내려가서** 설계하는 것이 가장 좋겠습니다.

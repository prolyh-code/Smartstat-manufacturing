좋습니다. 이어서 **Step 3-6. Agent Memory & Analysis State Architecture**를 진행하겠습니다.

이번 단계에서는 특히 중요한 원칙을 하나 두겠습니다.

> **LLM의 대화 기억과 통계 분석의 상태(State)는 분리한다.**

LLM이 이전 대화를 “기억하는 것”만으로 분석 이력을 관리하면 재현성과 신뢰성이 떨어집니다. 따라서 **분석 상태는 애플리케이션이 구조화된 데이터로 관리하고, LLM은 그 State를 읽고 갱신하는 역할**을 하도록 설계하는 것이 적절합니다.

---

# Step 3-6. Agent Memory & Analysis State Architecture

## 1. 왜 Agent State가 필요한가?

기존 통계 앱은 일반적으로 다음과 같습니다.

```
데이터 입력
   ↓
분석 선택
   ↓
분석 실행
   ↓
결과 표시
```

각 분석은 독립적입니다.

하지만 Agent는 다음과 같이 동작해야 합니다.

```
사용자 질문
   ↓
"Torque 불량 원인을 찾아줘"
   ↓
분석 ① 불량률
   ↓
분석 ② 시간 추이
   ↓
분석 ③ 설비 비교
   ↓
분석 ④ Model 비교
   ↓
분석 ⑤ 설비 × Model 관계
   ↓
분석 ⑥ 회귀/관계 분석
   ↓
원인 후보
   ↓
추가 검증
```

여기서 Agent는 최소한 다음을 알고 있어야 합니다.

- 처음 사용자가 무엇을 물었는가?
- 분석 대상은 무엇인가?
- 어떤 데이터가 사용됐는가?
- 이미 어떤 분석을 했는가?
- 각 분석에서 무엇이 발견됐는가?
- 어떤 가설이 생겼는가?
- 어떤 가설이 기각됐는가?
- 아직 확인하지 않은 것은 무엇인가?
- 다음에 어떤 분석을 해야 하는가?

따라서 **Analysis State가 Agent의 작업 메모리(Working Memory)** 역할을 합니다.

---

# 2. Memory를 4종류로 분리

제조 통계 Agent에서는 Memory를 하나로 만들지 않는 것을 권장합니다.

```
Agent Memory
│
├─ ① Conversation Memory
│
├─ ② Analysis State
│
├─ ③ Evidence Memory
│
└─ ④ Knowledge Memory
```

### ① Conversation Memory

사용자와의 대화 맥락입니다.

> "아까 설비 2번이라고 했잖아."

같은 대화에서 자연스럽게 이어가기 위한 것입니다.

---

### ② Analysis State

현재 진행 중인 분석의 구조적 상태입니다.

> 현재 무엇을 분석하고 있고 어디까지 진행했는가?

---

### ③ Evidence Memory

분석을 통해 발견한 통계적 근거입니다.

> 어떤 주장을 어떤 분석이 뒷받침하는가?

---

### ④ Knowledge Memory

제조 및 통계에 관한 일반적인 지식입니다.

> Torque 체결, CTQ, SPC, 공정능력, 검사방법 등

이것은 향후 RAG/Knowledge Base와 연결합니다.

---

# 3. Analysis State의 최상위 구조

가장 중요한 객체를 다음과 같이 설계할 수 있습니다.

```
AnalysisSession
│
├─ Session Metadata
│
├─ User Question
│
├─ Problem Model
│
├─ Dataset Context
│
├─ Analysis Plan
│
├─ Analysis History
│
├─ Findings
│
├─ Evidence
│
├─ Hypotheses
│
├─ Confounders
│
├─ Next Actions
│
└─ Final Decision
```

이 구조를 향후 실제 소프트웨어의 핵심 Domain Model로 사용할 수 있습니다.

---

# 4. AnalysisSession

하나의 사용자 분석 요청을 하나의 `AnalysisSession`으로 관리합니다.

예:

```
{
  "session_id": "AS202609120001",
  "status": "ANALYZING",

  "user_question": {
    "original": "Torque 불량의 원인을 찾아줘",
    "normalized": "Identify factors associated with increased Torque defects"
  },

  "problem_model": {},

  "datasets": [],

  "analysis_plan": {},

  "analysis_history": [],

  "findings": [],

  "evidence": [],

  "hypotheses": [],

  "next_actions": [],

  "decision": null
}
```

이 객체 하나만 보면 Agent가 **현재 분석 상황을 복원할 수 있어야 합니다.**

---

# 5. Problem Model

사용자의 자연어 질문을 통계적 문제 구조로 변환한 결과입니다.

예:

```
{
  "problem_type": "ROOT_CAUSE_EXPLORATION",

  "response_variable": {
    "name": "Torque",
    "type": "continuous",
    "unit": "N·m"
  },

  "quality_event": {
    "name": "Torque defect",
    "type": "binary"
  },

  "objective": "Identify factors associated with defect increase",

  "candidate_factors": [
    "Machine",
    "Model",
    "Shift",
    "Operator"
  ]
}
```

이 부분은 Step 3-4에서 정의한 **Problem Model**을 그대로 State에 저장하는 것입니다.

---

# 6. Dataset Context

분석에 사용된 데이터의 상태도 저장해야 합니다.

```
{
  "dataset_id": "DS001",
  "version": "v3",

  "rows": 12500,

  "variables": {
    "Torque": "numeric",
    "Machine": "categorical",
    "Model": "categorical",
    "Shift": "categorical",
    "Operator": "categorical"
  },

  "quality_status": "WARNING",

  "missing_rate": 0.8,

  "analysis_scope": {
    "start": "2026-08-01",
    "end": "2026-08-31"
  }
}
```

여기서 **Dataset Version**이 매우 중요합니다.

같은 Excel 파일을 사용자가 수정하면 분석 결과가 달라질 수 있기 때문입니다.

따라서 향후에는:

```
Dataset ID
+
Dataset Version
+
Analysis ID
```

를 함께 관리해야 합니다.

---

# 7. Analysis Plan

Agent가 앞으로 수행할 분석 계획입니다.

단순한 리스트보다 **Graph 구조**가 좋습니다.

```
AP001 Data Quality
       ↓
AP002 Defect Rate
       ↓
AP003 Trend
       ↓
   ┌───┼────┐
   ↓   ↓    ↓
Machine Model Shift
   ↓
AP007 Machine × Model
       ↓
AP008 Regression
       ↓
Candidate Cause
```

JSON으로 표현하면:

```
{
  "plan_id": "PLAN001",

  "nodes": [
    {
      "id": "A01",
      "type": "DATA_QUALITY",
      "tool": "check_data_quality"
    },
    {
      "id": "A02",
      "type": "DEFECT_RATE",
      "tool": "defect_rate"
    },
    {
      "id": "A03",
      "type": "MACHINE_COMPARISON",
      "tool": "two_proportion_test"
    }
  ],

  "edges": [
    {
      "from": "A01",
      "to": "A02"
    },
    {
      "from": "A02",
      "to": "A03"
    }
  ]
}
```

이 구조의 장점은 **Agent가 분석 순서를 변경할 수 있다는 것**입니다.

---

# 8. Analysis History

실행한 Tool의 이력을 보관합니다.

예:

```
{
  "analysis_id": "AN003",

  "tool": "two_proportion_test",

  "input": {
    "response": "Defect",
    "factor": "Machine",
    "groups": ["M1", "M2"]
  },

  "result": {
    "p_value": 0.002,
    "difference": 0.031,
    "ci95": [0.012, 0.050]
  },

  "status": "VALID",

  "timestamp": "2026-09-12T09:21:10"
}
```

이 정보는 단순 로그가 아닙니다.

Agent가 다음과 같이 판단할 수 있게 해줍니다.

> "Machine별 불량률 비교는 이미 수행했으므로 동일한 분석을 반복할 필요가 없다."

즉 **중복 분석 방지**에도 사용됩니다.

---

# 9. Finding

Analysis Result와 Finding은 분리하는 것이 좋습니다.

### Statistical Result

```
p = 0.002
Difference = 3.1%
95% CI = 1.2~5.0%
```

### Finding

```
Machine M2에서 불량률이 높게 관찰됨.
```

즉,

> **Result = 계산 결과**  
> **Finding = 결과에서 추출한 의미**

입니다.

---

# 10. Evidence

Finding보다 한 단계 더 중요한 것이 Evidence입니다.

예:

```
{
  "evidence_id": "EV003",

  "claim": "Machine M2 has a higher defect rate.",

  "supporting_analysis": [
    "AN003"
  ],

  "evidence_level": "E2",

  "strength": "MODERATE",

  "limitations": [
    "Model distribution differs between machines"
  ]
}
```

이렇게 하면 Agent가 최종 답변을 생성할 때 **근거가 없는 주장을 하지 않도록** 할 수 있습니다.

---

# 11. Hypothesis

원인 분석에서는 `Finding`과 `Hypothesis`를 반드시 구분하는 것이 좋습니다.

예:

### Finding

> M2의 불량률이 높다.

### Hypothesis

> M2에서 특정 체결조건이 적용되기 때문에 불량률이 높을 가능성이 있다.

즉:

```
Finding
   ↓
Hypothesis
   ↓
Test
   ↓
Evidence
   ↓
Accept / Reject / Unresolved
```

이 구조가 제조 현장의 **가설검증형 문제해결**과 잘 맞습니다.

---

# 12. Hypothesis Schema

```
{
  "hypothesis_id": "H002",

  "statement":
    "Machine M2's higher defect rate may be associated with Model C production.",

  "status": "UNRESOLVED",

  "supporting_evidence": [
    "EV003"
  ],

  "required_analysis": [
    "machine_model_cross_tab",
    "stratified_comparison"
  ]
}
```

상태는 최소한:

```
OPEN
SUPPORTED
WEAKLY_SUPPORTED
REJECTED
UNRESOLVED
VERIFIED
```

정도로 관리할 수 있습니다.

---

# 13. Confounder Memory

이 Agent에서 상당히 중요한 구조입니다.

예를 들어:

```
Machine M2
   ↓
불량률 높음
```

만 보면 M2가 원인처럼 보입니다.

그런데:

```
Machine M2 → Model C 생산비중 82%
Model C → 불량률 높음
```

이라면 **Model이 Confounder 또는 설명변수일 가능성**을 검토해야 합니다.

따라서 State에:

```
{
  "confounders": [
    {
      "variable": "Model",
      "related_factors": [
        "Machine"
      ],
      "status": "REQUIRES_CHECK"
    }
  ]
}
```

와 같이 저장합니다.

이것은 제조 Agent의 신뢰성을 크게 높일 수 있는 부분입니다.

---

# 14. Next Action

Agent는 항상 "다음에 무엇을 할 것인가"를 State에 가지고 있어야 합니다.

```
{
  "next_actions": [
    {
      "action": "stratified_machine_comparison",
      "reason":
        "Machine and Model distributions are confounded",
      "priority": 0.91
    },
    {
      "action": "operator_comparison",
      "reason":
        "Operator information is available",
      "priority": 0.62
    }
  ]
}
```

앞 단계에서 정의했던:

> **Relevance × Expected Information Gain × Data Availability × Statistical Validity × Manufacturing Impact**

개념을 여기서 실제 Agent Planning에 적용할 수 있습니다.

전체적으로 보면:

```
             USER
              │
              ▼
       User Question
              │
              ▼
        Problem Model
              │
              ▼
        Dataset Context
              │
              ▼
        Analysis Plan
              │
              ▼
        Tool Execution
              │
              ▼
     Statistical Result
              │
              ▼
          Finding
              │

              │
```

이것이 Agent의 **분석 기억 구조**입니다.

---

# 16. Agent가 중간에 질문을 바꾸는 경우

실제 사용에서는 매우 중요합니다.

사용자가 처음에는:

> "Torque 불량 원인을 찾아줘."

라고 했다가 분석 중간에:

> "설비별 차이만 먼저 확인해줘."

라고 할 수 있습니다.

이때 기존 분석을 모두 버리는 것은 비효율적입니다.

State에서는:

```
Original Objective
      ↓
Root Cause Exploration
      │
      ├── Existing Evidence
      ├── Existing Analysis
      └── Existing Data Profile
              
Current Objective
      ↓
Machine Comparison
```

처럼 **Objective만 변경**할 수 있습니다.

즉, 기존 분석 결과를 재사용합니다.

---

# 17. 분석을 중단했다가 다시 시작하는 경우

Agent State를 저장하면 가능합니다.

예:

```
09:00
불량 원인 분석 시작

09:05
Machine 분석 완료

09:07
Model 분석 완료

09:10
Confounding 발견

09:11
사용자 종료
```

다음날:

> "어제 Torque 불량 분석 이어서 해줘."

하면:

```
AnalysisSession
     ↓
Last State
     ↓
Unresolved Hypothesis
     ↓
Next Action
```

으로 바로 복구할 수 있습니다.

이것은 일반적인 Chatbot보다 훨씬 중요한 Agent 기능입니다.

---

# 18. "대화 기억"과 "분석 기억"의 차이

이 부분은 개발 단계에서 명확히 구분해야 합니다.

### Conversation Memory

```
사용자:
"아까 설비 2번 얘기했잖아."
```

LLM이 대화 맥락을 이해하기 위한 것.

### Analysis State

```
Machine M2
defect rate = 8.2%
p = 0.002
Evidence = E2
Model confounding = suspected
```

통계 분석의 **사실(Fact)**을 저장하는 것.

따라서:

> **분석의 Fact는 LLM Memory에 저장하지 않고 Application State에 저장한다.**

이 원칙을 강하게 권장합니다.

---

# 19. Agent State와 LLM Context

LLM에게 매번 전체 데이터를 보내는 것도 적절하지 않습니다.

예를 들어 12,500행의 데이터를 그대로 전달하는 대신:

```
LLM Context

User Question
+
Problem Model
+
Data Profile
+
Current Analysis Plan
+
Relevant Statistical Results
+
Evidence
+
Open Hypotheses
+
Next Action Candidates
```

만 전달합니다.

즉:

```
Raw Data
   ↓
Data Engine
   ↓
Statistical Engine
   ↓
Structured Result
   ↓
Agent State
   ↓
LLM
```

입니다.

이 구조는 비용, 속도, 보안, 재현성 측면에서도 훨씬 유리합니다.

# 21. 이 구조가 만들어내는 중요한 변화

이제 Agent는 단순히:

> **질문 → 답변**

하는 시스템이 아닙니다.

다음과 같은 **분석 상태 머신**이 됩니다.

```
질문
 ↓
문제 정의
 ↓
데이터 확인
 ↓
분석 계획
 ↓
분석 실행
 ↓
결과 검증
 ↓
Finding 생성
 ↓
Evidence 축적
 ↓
Hypothesis 생성
 ↓
추가 검증
 ↓
Evidence 강화
 ↓
Decision
```

그리고 이 과정에서 State가 계속 업데이트됩니다.

---

# 22. 여기까지를 기준으로 한 전체 Agent Architecture

지금까지 Step 3-1 ~ 3-6을 합치면 상당히 명확한 구조가 됩니다.

```
┌──────────────────────────────────────────────┐
│                  USER                        │
│       "Torque 불량 원인을 찾아줘"             │
└─────────────────────┬────────────────────────┘
                      ↓
┌──────────────────────────────────────────────┐
│              LLM AGENT                       │
│                                              │
│ Understand → Plan → Explain → Explore        │
└─────────────────────┬────────────────────────┘
                      ↓
┌──────────────────────────────────────────────┐
│             AGENT STATE                      │
│                                              │
│ Problem / Dataset / Plan / History           │
│ Finding / Evidence / Hypothesis / Next       │
└─────────────────────┬────────────────────────┘
                      ↓
┌──────────────────────────────────────────────┐
│          RULE / GUARD ENGINE                  │
│                                              │
│ Data / Method / Assumption / Result          │
└─────────────────────┬────────────────────────┘
                      ↓
┌──────────────────────────────────────────────┐
│             TOOL LAYER                       │
│                                              │
│ Data / Exploration / Test / Model / SPC      │
│ Visualization / Report                       │
└─────────────────────┬────────────────────────┘
                      ↓
┌──────────────────────────────────────────────┐
│             KNOWLEDGE LAYER                  │
│                                              │
│ Statistics / Manufacturing / Quality /       │
│ Process / Company Knowledge                  │
└──────────────────────────────────────────────┘
```

이제 이 구조를 갖추면 **"LLM을 통계 앱에 붙인다"**는 수준을 넘어섭니다.

정확히는:

> **기존 통계분석 Engine을 중심으로, LLM이 문제를 정의하고 분석을 계획하며 여러 통계 Tool을 순차적으로 호출하고, 그 결과를 Evidence와 Hypothesis로 축적하면서 제조 현장의 의사결정까지 지원하는 Agent Architecture**

가 됩니다.

# 23. 다음 단계는 꽤 중요합니다

이제 **Step 3-7. Agent Conversation UX**로 넘어가는 것이 좋습니다.

여기서는 실제 사용자가 앱을 열었을 때의 경험을 설계합니다.

예를 들어 사용자가:

> **"세탁기 Drum Run-out이 기준보다 큰 것 같은데 분석해줘."**

라고 입력했을 때,

Agent가 단순히 질문 하나를 더 던지는 것이 아니라:

```
[Agent]

확인했습니다.

분석 목적:
Drum Run-out의 기준 초과 여부와
공정 상태를 확인하겠습니다.

현재 데이터에서 확인되는 항목:
✓ Run-out 측정값
✓ Model
✓ Line
✓ Machine

먼저 다음 3가지를 확인하겠습니다.

① 기준 대비 평균 차이
② 분포 및 이상치
③ Model/Line별 차이

[분석 시작]
```

그리고 분석이 진행되면서:

```
① 기준 대비 평균
→ 유의한 차이 없음

② 분포
→ 일부 이상치 존재

③ Line 비교
→ Line B에서 높은 수준

④ Model 분포 확인
→ Line B에 Model C가 집중

⑤ Model C 제외 후 재분석
→ Line 차이 감소

[현재 판단]

Line B 자체가 원인이라고 판단하기는 어렵습니다.
Model C의 생산비중 차이가 주요 설명요인일 가능성이 있습니다.

다음으로 Model별 공정조건을 확인하는 것이 좋습니다.
```

처럼 **분석 과정 자체가 사용자에게 보이는 UX**를 설계해야 합니다.

따라서 다음 단계에서는 **Chat UI + Guided UI + Analysis Progress + Evidence 표시 + 사용자의 개입 시점 + Agent가 질문해야 하는 상황**까지 설계하는 것이 좋겠습니다.

이 단계가 완성되면 그 다음 **Step 3-8. Agent Evaluation Framework**에서 "이 Agent가 통계적으로 얼마나 정확하고 제조 현장에서 얼마나 유용한가?"를 객관적으로 평가할 수 있는 기준을 만들 수 있습니다.

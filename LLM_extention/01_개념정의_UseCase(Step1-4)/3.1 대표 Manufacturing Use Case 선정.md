# Step 3-2. 대표 Manufacturing Use Case 선정

## 1. Use Case 선정 원칙

이번 단계에서는 단순히 "통계분석 15개"를 선정하지 않습니다.

**Agent가 제조 현장의 문제를 얼마나 잘 해결할 수 있는지를 검증할 수 있는 사례**를 선정해야 합니다.

따라서 다음 5가지 기준을 적용하겠습니다.

|기준|의미|
|---|---|
|제조 현장성|실제 생산·품질·설비 업무에서 자주 발생하는가|
|통계성|통계적 분석이 실질적으로 필요한가|
|Agent성|자연어 이해와 분석계획 수립이 필요한가|
|확장성|다른 제조 문제로 확장할 수 있는가|
|MVP 적합성|초기 개발에서 구현 가능한가|

특히 기존 앱의 핵심 KPI가 **비전문가가 데이터를 올린 뒤 3분 이내에 올바른 분석 결과와 해석을 얻는 것**으로 설정되어 있으므로, 단순히 복잡한 분석보다 **현장에서 자주 쓰이고 결과를 이해하기 쉬운 사례**를 우선해야 합니다.

# 3. UC-01 — 공정 상태 진단

### 사용자

> "이 공정 데이터가 어떤 상태인지 확인해줘."

Agent가 가장 먼저 해야 하는 기본적인 분석입니다.

### Workflow

```
Data Upload
    ↓
Data Quality Check
    ↓
Variable Identification
    ↓
Descriptive Statistics
    ↓
Histogram
    ↓
Box Plot
    ↓
Distribution / Variation Interpretation
    ↓
Potential Issue Identification
```

### Agent가 반환해야 하는 것

단순히

> Mean = 35.82  
> SD = 0.41

이 아니라,

> 평균은 35.82이며 표준편차는 0.41입니다. 데이터의 중심과 변동을 확인한 결과, 전체적으로 변동 폭은 작습니다. 다만 일부 이상값이 확인되므로 해당 데이터의 원인을 추가 확인하는 것이 좋습니다.

처럼 설명해야 합니다.

기존 기획서에서도 기초통계량을 단순 숫자가 아니라 제조 현장 언어로 해석하도록 설계되어 있습니다.

---

# 4. UC-02 — 목표값 비교

### 사용자

> "목표가 35인데 현재 평균이 다른지 확인해줘."

### Agent Workflow

```
목표값 확인
 ↓
측정 데이터 확인
 ↓
Descriptive Statistics
 ↓
1-Sample t-test
 ↓
Difference + CI + P-value
 ↓
Effect Size
 ↓
Statistical Conclusion
 ↓
Manufacturing Interpretation
```

여기서 **P-value만으로 결론을 내리지 않는 것**이 중요합니다.

예를 들어:

> 통계적으로 평균은 목표값과 유의한 차이가 있습니다.

와

> 평균 차이는 0.12 mm로 실제 제조 영향은 작을 가능성이 있습니다.

를 분리합니다.

이것은 기존 기획서가 강조한 **Statistical Significance와 Manufacturing Significance의 분리**를 Agent에도 그대로 계승하는 것입니다.

---

# 5. UC-03 — 두 공정 비교

### 사용자

> "A공정과 B공정의 치수가 다른지 확인해줘."

Agent가 먼저 판단해야 합니다.

```
2 Groups
   ↓
Independent?
   ├─ YES → 2-Sample / Welch
   └─ NO  → Paired
```

이것이 기존 Analysis Navigator의 핵심 논리입니다.

### Agent의 중요한 역할

사용자는

> "Welch t-test를 사용해."

라고 말할 필요가 없습니다.

Agent가 데이터 구조와 조건을 보고 적절한 방법을 선택해야 합니다.

---

# 6. UC-04 — 설비 비교

UC-03과 통계적으로 유사하지만 **제조 의미가 다릅니다.**

### 질문

> "설비 1과 설비 2의 품질 차이가 있는지 알려줘."

여기서 Agent는 단순히 평균 차이를 보는 데 그치지 않고:

```
Equipment
 ↓
Mean
 ↓
Variation
 ↓
Distribution
 ↓
Statistical Difference
 ↓
Effect Size
 ↓
Specification Position
```

까지 연결해야 합니다.

즉,

> **"차이가 있는가?"**

뿐 아니라

> **"그 차이가 제조적으로 중요한가?"**

를 판단하도록 합니다.

---

# 7. UC-05 — 여러 조건 비교

### 질문

> "설비 1, 2, 3 중 어느 설비의 품질이 다른가?"

Agent:

```
3+ Groups
 ↓
Data validation
 ↓
ANOVA / Welch ANOVA
 ↓
Significant?
 ├─ NO → 종료
 └─ YES
      ↓
    Post-hoc
      ↓
   Group Ranking
```

---

# 8. UC-06 — 차이 발생 조건 탐색

이것은 UC-05의 후속 질문입니다.

사용자:

> "그래서 어느 설비가 다른데?"

Agent:

> "전체 설비 간 평균 차이는 통계적으로 유의합니다."

에서 끝나면 안 됩니다.

Post-hoc 결과를 이용해

> "설비 1과 3 사이에 유의한 차이가 있으며, 설비 2와 3 사이에도 차이가 있습니다. 설비 1과 2의 차이는 통계적으로 유의하지 않습니다."

라고 설명해야 합니다.

기존 기획서에서도 Post-hoc의 목적을 **"어느 조건에서 차이가 발생했는가?"**로 정의하고 있습니다.

---

# 9. UC-07 — 개선 전후 검증

### 질문

> "공정 개선 후 품질이 좋아졌는지 확인해줘."

이것은 제조 개선활동과 직접 연결됩니다.

### Agent의 첫 번째 판단

**Before/After 데이터가 동일 대상의 Pair인지 확인**

```
Before / After
       ↓
Same subject?
   ├─ YES → Paired t-test
   └─ NO  → Independent comparison
```

그 다음:

```
Mean Difference
 ↓
Confidence Interval
 ↓
P-value
 ↓
Effect Size
 ↓
Manufacturing Significance
```

기존 기획서도 개선 전후 분석에서 동일 대상의 변화량(Difference)을 분석하는 구조를 명시합니다.

---

# 10. UC-08 — 변수 관계 분석

### 질문

> "온도와 치수 사이에 관계가 있는지 확인해줘."

Agent:

```
X = Temperature
Y = Dimension
       ↓
Scatter Plot
       ↓
Data Pattern
       ↓
Correlation
       ↓
Confidence Interval
       ↓
Interpretation
```

여기서 중요한 Guardrail:

> **상관관계가 있다고 해서 인과관계가 증명되는 것은 아닙니다.**

이 원칙은 기존 기획서에도 명시되어 있습니다.

---

# 11. UC-09 — 영향도 분석

### 질문

> "온도가 치수에 얼마나 영향을 주는지 알려줘."

여기서는 Correlation보다 Regression이 적절합니다.

예:

> 온도가 1℃ 증가할 때 제품 치수가 평균적으로 약 0.015 mm 증가하는 것으로 추정됩니다.

기존 기획서에서도 Regression 결과를 이러한 **공정 언어**로 변환하는 것을 목표로 하고 있습니다.

---

# 12. UC-10 — 이상 데이터 탐색

### 질문

> "이 데이터에서 이상한 값이나 이상한 패턴을 찾아줘."

이 경우 Agent는 특정 분석 하나를 바로 선택하면 안 됩니다.

```
Data Quality
 ↓
Distribution
 ↓
Box Plot
 ↓
Outlier Detection
 ↓
Group Comparison
 ↓
Time / Sequence Pattern
 ↓
Potential Anomaly
```

즉 **"이상값"과 "공정 이상"을 구분**해야 합니다.

통계적 Outlier가 발견됐다는 사실과 실제 설비 이상이라는 판단은 동일하지 않기 때문입니다.

---

# 13. UC-11 — 불량 원인 탐색

이제 본격적인 Agent Use Case입니다.

### 사용자

> **"최근 불량이 증가했는데 원인을 찾아줘."**

Agent는 단일 Tool을 호출하지 않습니다.

### Step 1 — 불량 현상 확인

```
Production Qty
Defect Qty
Defect Rate
```

### Step 2 — 시간적 변화

```
Daily / Hourly Trend
```

### Step 3 — 그룹별 분석

```
Equipment
Model
Shift
Operator
Process
```

### Step 4 — 품질 특성 분석

```
CTQ
Dimension
Torque
Temperature
Pressure
Speed
...
```

### Step 5 — 관계 분석

```
Correlation
Regression
Group Difference
```

### Step 6 — 후보 원인 Ranking

```
Evidence
Effect Size
Statistical Significance
Manufacturing Relevance
```

### Step 7 — 추가 검증

> "A설비의 불량률이 다른 설비보다 높게 나타났습니다. A설비의 특정 조건이 원인인지 확인하기 위해 해당 조건에 대한 추가 분석을 권장합니다."

이것이 **LLM Agent의 핵심 차별화 Use Case**입니다.

# 14. UC-12 — 공정조건 영향 탐색

### 질문

> "어떤 공정조건이 CTQ에 영향을 주는지 찾아줘."

예:

```
Temperature
Pressure
Speed
Torque
Cycle Time
       ↓
      CTQ
```

Agent는

- 변수별 분포
- 상관관계
- Scatter Plot
- Regression
- Group Difference

등을 조합합니다.

향후에는 여기에 **Multiple Regression → PCA → DOE**가 연결될 수 있습니다.

따라서 이 Use Case는 향후 확장성이 매우 큽니다.

---

# 15. UC-13 — 규격 대비 공정 판단

### 질문

> "현재 공정이 규격을 안정적으로 만족하는지 확인해줘."

이것은 단순 평균 비교와 다릅니다.

```
Specification
      +
Process Distribution
      ↓
Cp / Cpk
Pp / Ppk
      ↓
Specification Position
      ↓
Capability Interpretation
```

향후 SPC와 Capability를 확장하는 기존 로드맵과도 자연스럽게 연결됩니다.

# 16. UC-14 — 불량 현상 분석

### 질문

> "어떤 불량이 가장 많이 발생하는지 분석해줘."

Agent:

```
Defect Classification
 ↓
Frequency
 ↓
Defect Rate
 ↓
Pareto
 ↓
Top Contributors
 ↓
Trend
```

그리고 단순 Pareto에서 끝나지 않고

> "상위 3개 불량이 전체 불량의 78%를 차지합니다."

처럼 **개선 우선순위**로 연결합니다.

# 17. UC-15 — 개선 효과 종합 판단

마지막 Use Case가 가장 중요합니다.

### 질문

> **"이번 개선활동이 실제로 효과가 있었는지 종합적으로 판단해줘."**

Agent는 여러 분석을 종합합니다.

```
Before
After
   ↓
Mean
Variation
Defect Rate
CTQ
Capability
SPC
   ↓
Statistical Evidence
   ↓
Practical Effect
   ↓
Manufacturing Impact
   ↓
Overall Judgment
```

결과는 예를 들어:

> **종합 판단: 개선 후 CTQ 평균과 변동성이 개선되었으며, 불량률도 감소했습니다. 평균 차이는 통계적으로 유의하고 제조적으로도 의미 있는 수준으로 판단됩니다. 다만 개선 효과가 특정 설비에 국한되는지 추가 확인이 필요합니다.**

와 같은 형태가 됩니다.

이것이 기존 기획서의 **Statistical Result → Manufacturing Interpretation → Engineering Consideration** 구조를 Agent 수준으로 확장한 것입니다. 통계분석 앱 제작 기획서.mdMD

# 18. 15개 Use Case를 다시 보면

전체 구조가 상당히 명확해집니다.

```
                 Manufacturing Question
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
     현상 파악          비교             관계
        │                │                │
      UC-01          UC-03~06          UC-08~09
        │                │                │
        └────────────┬───┴────────────────┘
                     ↓
                  변화/이상
                 UC-07, UC-10
                     ↓

                     ↓
                 공정 판단

```

이 구조가 중요한 이유는 **Agent의 자율성이 단계적으로 증가하기 때문**입니다.

# 19. Agent 난이도에 따른 3단계 구조

저는 이것을 제품 개발에서도 그대로 사용하기를 권합니다.

## Level 1 — Guided Analysis

UC-01 ~ UC-04

사용자가 질문하면 Agent가 분석 방법을 안내합니다.

> "두 공정의 평균 차이를 비교하시겠습니까?"

→ Tool 실행

---

## Level 2 — Assisted Analysis

UC-05 ~ UC-10

Agent가 여러 통계 Tool을 선택하고 연결합니다.

> "3개 설비의 차이를 분석하고 어느 설비가 다른지도 알려줘."

Agent:

> ANOVA → Post-hoc → Effect Size → Interpretation

---

## Level 3 — Agentic Analysis

UC-11 ~ UC-15

사용자가 **목표만 제시**합니다.

> "불량 원인을 찾아줘."

> "개선 효과를 종합적으로 판단해줘."

Agent가 분석계획을 수립하고 여러 Tool을 순차적으로 호출합니다.

---

# 20. 이것이 앞으로의 핵심 구조입니다

따라서 앞으로 만들 앱의 사용자 경험은 다음처럼 발전시키는 것이 좋습니다.

### 기존 앱

> **질문 → 분석방법 선택 → 실행**

### LLM 통합 앱

# 21. 이번 단계에서 중요한 결론

이번 Step 3-2를 통해 **15개의 대표 Use Case를 확정하는 것을 제안**합니다.

### MVP 핵심 Benchmark

저라면 우선 다음 **5개를 Agent 성능 검증용 핵심 사례**로 선정하겠습니다.

|우선순위|Use Case|이유|
|---|---|---|
|1|**UC-03 두 공정 비교**|가장 기본적인 통계 의사결정|
|2|**UC-05 다중 조건 비교**|Analysis Planning 검증|
|3|**UC-07 개선 전후 검증**|제조 개선과 직접 연결|

그리고 **UC-11과 UC-15가 제대로 작동하면 이 프로젝트가 단순한 "LLM이 붙은 통계 앱"을 넘어섰다고 판단할 수 있습니다.**

## 다음 단계

이제 아주 중요한 단계로 들어갑니다.

**Step 3-3 「Use Case별 Agent Workflow 상세 설계」**입니다.

여기서는 각 Use Case를 단순 설명하는 것이 아니라 실제 개발에 사용할 수준으로 다음을 정의하겠습니다.

> **User Input → Intent Recognition → Data Requirement → Data Validation → Analysis Planning → Tool Calling → Statistical Validation → Interpretation → Manufacturing Insight → Next Question**

특히 **UC-11 「불량 증가 원인 탐색」**을 첫 번째 대표 사례로 잡아, **LLM이 어디까지 판단하고, Rule Engine이 어디에서 통제하며, Statistical Engine이 어떤 Tool을 제공해야 하는지**를 아주 구체적으로 설계하는 것이 좋습니다.

이 설계가 완성되면 이후의 **Agent Architecture와 Tool Specification이 사실상 자연스럽게 도출**됩니다.
